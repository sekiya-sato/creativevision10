# SQL方言変換 実DB検証結果（2026-11-04）

SQLite（正典）の書き方を基準に、MariaDB / PostgreSQL の方言変換が正しく動くかを、経路の洗い出し・静的検査・実DBでの再実行で確認した。

- 調査対象HEAD: `f85d660b`（本検証の修正はこの上のコミット）
- 基準DB: 開発DB（`server-user52.db`）の複製。MariaDB / PostgreSQL は DB切替処理で同じ複製から移行した cv00（全71表、件数・全行の Id/Vdc/Vdu 一致を確認済み）
- 対応下限: MariaDB 11系（cv00）/ PostgreSQL 16 以降

## 1. SQL変換を通る経路

| 種別 | 経路 | 変換 |
|---|---|---|
| クライアントSQL | `HandlerClass.TranslateClientSql`（QueryOne / QueryList / QueryListSql、QueryKey 上書き） | あり |
| サーバSQL | `ExDatabase.ExecuteDialect` / `FetchDialect` / `FirstOrDefaultDialect`（今回追加） / `TranslateDialect` | あり |
| 印刷 | `PrintPre`（マクロ展開 → `RawExecCmd`） | **なし → 修正** |
| NPoco 生成SQL | Insert / Update / Delete / `where Id=@0` 等 | 不要（標準SQL） |
| DDL・メタデータ | プロバイダー別 override | 不要 |
| DBバージョン更新 | `UpdateDb`（SQLite のDDL） | 方言別SQLを持てる構造にした（`InnerVersion.DialectSql`、未定義の方言では実行せず未適用として記録） |

変換を通らずに SQLite 固有構文を実行していたサーバ側の箇所（静的検査 `SqlRouteInventoryTests` で候補40件を抽出し、個別に確認）:
集計の期首日・税率（`sqlite_master`）、原価更新（`IFNULL`・`json_each`）、完了判定、名称再構築、旧DB変換（`changes()` 等）、上代の原価割れチェック。いずれも変換経路へ寄せた。

## 2. 静的検査

全SQLリテラル235本を両方言へ変換し、未対応構文が残るのは3本（`sqlite_master` 2本はプロバイダー override 済み・AI照会は SQLite 専用経路、残り1本は C# 補間穴のテンプレート）。

収集SQLを `Doc/spec/tools/sqlreplay` で SQLite / MariaDB / PostgreSQL に再実行し、更新系はロールバック、SELECT は結果を照合した。

## 4. 見つかった不具合と修正

| # | 対象 | 内容 | 修正 |
|---|---|---|---|
| 1 | MariaDB | NPoco がトランザクション終了時に接続をプールへ戻し、再利用時にセッションの sql_mode（PIPES_AS_CONCAT / NO_BACKSLASH_ESCAPES）が消える。`||` が論理和になり、`'\'` が壊れる | 接続が開くたびにセッション設定を当て直す（`StateChange`） |
| 2 | PostgreSQL | クライアントの引数はすべて文字列のため、整数列との比較が `integer = text` の型エラー | 文字列引数を型未指定(unknown)で送る（NPoco 経由・`RawExecCmd` とも） |
| 3 | 両方言 | SQLite の二重引用符識別子 `"Offset"` を変換していない | 予約語列の二重引用符も各DBの引用へ |
| 4 | 両方言 | 引数2個以上の `max` / `min`（スカラー） | `GREATEST` / `LEAST`（ルール A06） |
| 5 | 完了判定・発注残/受注残 | MariaDB は派生表から外側を参照できない、PostgreSQL はカンマより JOIN が先に結び付く、伝票×SKUごとの相関副問合せで JSON を展開し直すため遅い | 残と実績を対象伝票だけ1回ずつ集計して突き合わせる形へ（SQLite の結果は同じ） |
| 6 | 印刷 | 印刷SQLを変換していない | `TranslateClientSql` を通す |
| 7 | サーバSQL | 1章の変換なし経路 | 変換経路へ |

あわせて、UATで条件指定ダイアログ（`RangeParamView` 等）に応答できず一覧SQLが実行されていなかったため、`DialogTestRoute` を追加した（UatVm README 5.1.1）。

## 5. 未確認・残課題

- 画面からの保存操作の実SQLは収集していない。月次集計・原価・棚卸は 5.1 で別に検証した。
- `RebuildDb` の Jcolsiz 更新は `RawExecCmd` のためエラーを返さない（従来どおり）。
- `UpdateDb` の方言別SQLは未定義（現行の移行済みDBは最新版のため実行対象なし）。
- PostgreSQL の `GREATEST` / `LEAST` は NULL を無視する（SQLite・MariaDB は NULL）。現在の使用箇所は NULL を潰した値のみ。

## 5.1 月次集計・原価・棚卸の実DB検証（2026-11-05、batchverify）

`Doc/spec/tools/batchverify` で、在庫・売掛・買掛の再集計（202202〜202203）、請求残（締5/9/10/15/20/末）、支払残（締20/末）、原価の確認5種、消化仕入更新を3DBでそれぞれ2回実行し、集計表の指紋（年月ごとの件数・数値合計・文字列長合計）を照合した。

| 観点 | SQLite | MariaDB | PostgreSQL |
|---|---|---|---|
| 冪等性（1回目と2回目） | 一致 | 一致 | 一致 |
| 売掛・買掛・請求残・支払残（SQLiteとの比較） | 基準 | 一致 | 一致 |
| 在庫（SummaryStock / SummaryRealStock） | 基準 | 比較不可 | 比較不可 |
| 消化仕入更新（支払計算済み範囲） | 業務チェックで中断し排他を解放、2回目も同じ中断 | 同左 | 同左 |

在庫は、過去の棚卸確定の試行で作られた在庫調整伝票（Tran61Chosei 202203: 8 / 49 / 4 件）が3DBで異なり、入力が揃っていないため比較できない。原価確認の差も、同じ理由で確認時点の元件数（`Confirmed.SourceCount`）が違うことだけによる。

見つかった不具合と修正:

| # | 対象 | 内容 | 修正 |
|---|---|---|---|
| 8 | MariaDB | `WITH … INSERT`（共通表式を更新文の前に置く形）が構文エラー（在庫・売掛・買掛・請求残・支払残の全集計） | `INSERT INTO t (列…) WITH … SELECT` へ（3DBで同じ意味を実DBで確認） |
| 9 | MariaDB | 派生表に別名が無い（支払残、仕入先元帳・得意先元帳・半期報告の画面SQL） | `) AS src` を付ける |
| 10 | MariaDB | `UPDATE … SET (a, b, c) = (SELECT …)` が無い（在庫再集計の非Tran列復元） | 列ごとのスカラー副問合せへ |
| 11 | 両方言 | 請求・支払の予定日で `date()` の修飾子を `printf('+%d months', n)` で作っていて変換できない／請求番号の `printf('%d-%s-%02d')` | 修飾子は連結形 `'+' \|\| n \|\| ' months'`、printf は `%d` / `%s` を B06 で変換 |
| 12 | 両方言 | 消費税の端数処理 `ABS(x) / 100` が SQLite では整数除算、MariaDB / PostgreSQL では小数除算になり1円ずれる | `(a - a % 100) / 100`（割り切れる除算）で3DB同じ整数に |
| 13 | PostgreSQL | `ON CONFLICT … DO UPDATE SET Su = Su + excluded.Su` の `Su` が曖昧 | `SummaryStock.Su` と表名で修飾 |
| 14 | MariaDB | `length` がバイト数（全角1文字の帳票補正 `Pad1` が効かない） | `CHAR_LENGTH` へ変換（A06） |
| 15 | 両方言 | 一時表 `CREATE TEMP TABLE`・TEXT主キー、`json_type`、JSON値と整数の比較、排他の手順名が列幅超過 | `TEMPORARY`・varchar、B09 追加、`cast(… as integer)`、手順名を列幅で切る |

回帰テスト（`SqlRouteInventoryTests`）: 変換経路外での実行、`INSERT OR …`、`WITH … 更新文`、派生表の別名なし、行値の一括代入を静的に検出する。

あわせて、業務チェックによる中断（支払計算済み、確認後の変更、計算エラー等）では排他行を解放し結果コード2で記録、想定外の例外では従来どおり行を残すよう区別した（設計判断記録 8.6）。

未確認・残課題:

- 棚卸（開始・確定）の MariaDB / PostgreSQL での実行と、在庫の3DB比較。3DBの入力（在庫調整伝票）を同じ状態へ揃え直してから行う必要がある。
- SQLite でも棚卸確定が約17分（202203、約183万行）かかる。速度の調査は未着手。
- `UpdateDb` の移行SQL（`update … set (vdc,vdu)=(select …)` を含む）は方言別に未対応（既定の方針どおり）。
- 内部Id（`Id_*`）の JSON 取り出しは `cast(… as integer)`（PostgreSQL では int4）。Id が 2^31 を超える運用では bigint への見直しが要る。

## 6. 再実行手順

1. 認証を外す: `./Doc/spec/tools/change4uat_run.ps1`、CvServer・UatVm・sqlreplay を build
2. 収集: `CV_SQL_CAPTURE=<jsonl>` を設定して `UatVm menulayout --search --manage-server --url <専用URL> --sqlite <複製DB>`
3. 照合: `sqlreplay <jsonl> <複製DB> <出力フォルダ>`（MariaDB/PostgreSQL は appsettings.Development.json の MariaDb / Postgres）
4. 認証を戻す: `./Doc/spec/tools/change4uat_run.ps1 enable_auth`、CvServer を再 build
5. 月次集計等（5.1）: `batchverify <複製DB> <出力フォルダ> --from 202202 --month 202203 [--skip-stocktake]`（認証の切替は不要。MariaDB / PostgreSQL は検証専用DBを指定し、対象DBを更新する）
