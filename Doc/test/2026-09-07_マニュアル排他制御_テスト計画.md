### 6.1 Step T8: 強制クリア履歴への端末情報の追加（2026-09-07 決定）

Step T3 で「JWTのclaimが無い場合は実行社員0で記録され、例外にはならない」ことが判明した
（`Tests/TestServer/ManualLockHandlerTests.cs` の `Msg062_JWTのclaimが無い場合は実行社員0で記録される`）。
「誰が解放したか分からない履歴」が残り得るため、端末情報を併せて記録する。

**新規のDB列は不要である。** 必要な情報は既に `SysHistJwt`（`CvBase/BaseDb0Login.cs:79`）が
`Id_Login` ごとに保持している。JWTの `ClaimTypes.SerialNumber` は `SysLogin.Id` = `SysHistJwt.Id_Login`
であり、既存の `HandlerClass.ResolveLoginShainId` と同じ経路で辿れる。

| 情報 | 取得元 | 出所の性質 |
|---|---|---|
| IPアドレス | 強制クリア時の `HttpContext.Connection.RemoteIpAddress`（`SysHistJwt.Ip` も同じ値をログイン時に記録） | **サーバー由来**。最も確実 |
| マシン名 | `SysHistJwt.Jsub.Machine` | クライアント申告（`CvWpfclient/ViewModels/00System/LoginViewModel.cs:88`） |
| ログオンユーザー名 | `SysHistJwt.Jsub.User` | クライアント申告（同:89） |
| OSバージョン・MACアドレス | `SysHistJwt.Jsub.OsVer` / `Jsub.MacAddress` | クライアント申告 |

**実行社員が判明している場合も常に記録する。** 実行社員が0のときだけにしてはならない。理由は次の3点。

1. 実行社員は「誰が」を示すが「どの端末から」を示さない。同一社員が複数の端末からログインできる。
2. 強制クリアは排他制御そのものを無効化する操作であり、後の原因追跡では
   「どの端末で何が動いていたか」が要になる。
3. 0のときだけ記録する設計では、「社員が判ったから省いた」のか
   「端末情報も取得できなかった」のかを履歴から区別できない。

**注意点2点。**

- `Machine` / `User` / `OsVer` / `MacAddress` は**ログイン時のクライアント申告値**である。
  サーバー由来はIPだけである。詳細設計§2.5.3 が定めた「申告値を監査値にしない」原則に照らし、
  履歴上でも申告値であることを明示する。IPは強制クリア時点の `RemoteIpAddress` を
  直接取るほうが新鮮で確実である。
- `SysHistAutoexec.Memo` の列幅は**列幅拡張で対応した（2026-09-07 ユーザー判断、実施済み）**。
  削除行の内容（`TableName`/`ColumnName`/`SeqNo`/`Vdc`/`Vdu`/`Memo`）に端末情報を加えると
  従来の上限に収まらないため、`[ColumnSizeDml(2000)]` を明示した。
  **実装時の判明事項**: 本属性は起票時点で「`[ColumnSizeDml(300)]`」と記していたが、実際は
  **属性が未指定で既定（255）が使われており**、一方でアプリ側は300文字まで書こうとしていた。
  SQLiteはTEXT型のため実害は無かったが、方言によっては溢れうる状態だった。
  なお`ManualLockDb`の`MemoMaxLength`(300)は`SysSequence.Memo`専用であり、混同しやすいため
  `SysHistAutoexec.Memo`用に`HistoryMemoMaxLength`(2000)を分けた。
- **他方言の既存列の拡張は別途必要（未実装）**。`CvBase/UpdateDb.cs` は生SQLの`ALTER TABLE`を
  列挙する方式で属性変更に自動追随しない。PostgreSQL（`ExDatabasePostgre`）は`ColumnSizeDml`から
  `varchar(n)`を生成するため、既存DBには`ALTER TABLE SysHistAutoexec ALTER COLUMN Memo TYPE varchar(2000)`
  相当の追加が要る。Oracle（`ExDatabaseOracle`）は`ColumnSizeDml`を無視するため影響しない。

### 6.2 Step T9: 孤立した2bへの補完記録の追加（2026-09-07 決定）

Step T6のE-13で、**監視ログの2b→2f/2eの対が CvServer再起動を跨ぐと成立しない**ことが実測で判明した。
監視タスクの前回状態は `CvServer/Services/SchedulerService.cs` の `_manualLockMonitorState`
（DIシングルトンのインスタンスフィールド）にしか無く、プロセス終了で失われる。
排他行はDBに残るため、再起動後の最初のtickは「前回状態なし＋行あり」となり2bを再び記録する。
実運用の履歴と試験を通じて**計5例**観測している。詳細は詳細設計§3.7の追記を参照。

**実装方針（決定済み）。**

- 監視タスクの各tickで、**直近の監視ログが2bのまま閾値を超えていた場合に、対を閉じる補完記録を1行書く**。
- マーカーは既存の2e/2fを流用せず**新しいマーカーを起こす**。
  「実際に解放した2e」と「後から対を閉じただけの記録」を履歴上で区別する必要があるためである。
- **冪等性は追加の仕掛けなしに成立する。** 補完記録を書いた瞬間に直近の監視ログが2bでなくなるため、
  次のtickでは条件を満たさない。
- **やらないこと**: 前回状態の永続化、DBスキーマの追加、`Memo`文字列の解析。
  マニュアル排他制御の目的は「時間のかかる処理の実行中に他の割り込みを入れないこと」だけであり、
  実装を複雑にしない方針である。
