## 2. スイッチ一覧

| ID | 環境変数 | 既定 | 効果 | 実装位置 |
|---|---|---|---|---|
| S1 | `CV10_LOCK_SLEEP_BEGIN_MS` | 0（未設定・何もしない） | 指定ミリ秒だけ`Thread.Sleep`する。**Vduを前進させずに**占有し、停止した処理を模擬する | `ManualLockTestKnobs.SleepAtBegin()`（`ManualLockDb.TryBegin`から勝者確定直後に呼ばれる） |
| S2 | `CV10_LOCK_SLEEP_STEP_MS` | 0（未設定・何もしない） | 指定ミリ秒だけ`Thread.Sleep`する。**Vduを前進させながら**長時間占有し、生きている長時間処理を模擬する | `ManualLockTestKnobs.SleepAtProgress()`（`ManualLockDb.Progress`からUPDATE直前に呼ばれる） |
| S3 | `CV10_LOCK_MIN_THRESHOLD_MIN` | 15（未設定・1以上のみ有効） | 異常判定の閾値の下限（分）を短縮する | `ManualLockTestKnobs.MinThresholdMinutes`（`ManualLockMonitor.ComputeThresholdTicks`が参照） |
| S5 | `CV10_LOCK_EXPECTED_SEC` | 未設定（元の値をそのまま使用） | 一連処理のExpectedDuration（秒）を一時的に縮小する | `ManualLockTestKnobs.OverrideExpectedDuration()`（`ManualLockDb.TryBegin`の本体先頭で呼ばれる） |
| S4 | （環境変数ではない） | cron `*/5 * * * *`、実行フラグ`1`（有効） | 監視タスクの観測間隔・実行有無をDB上で変更する | `MasterConfig`テーブル（4章参照） |

環境変数（S1・S2・S3・S5）は**プロセス単位で静的初期化時に1度だけ**読み込まれる。
値を変えたい場合はプロセスを再起動すること（再読み込みはしない）。

## 3. 設定例（PowerShell）

計画書§4.1のE-01〜E-03の組み合わせをそのまま示す。いずれもCvServerを起動する
**前**に設定し、設定後にCvServerを起動（または再起動）すること。

### E-01: 排他制御の正常実行

```powershell
Remove-Item Env:\CV10_LOCK_SLEEP_BEGIN_MS -ErrorAction SilentlyContinue   # S1=0(未設定)
$env:CV10_LOCK_SLEEP_STEP_MS = "30000"                                    # S2=30秒/ステップ
$env:CV10_LOCK_MIN_THRESHOLD_MIN = "1"                                    # S3=1分
# S4: cronを1分間隔へ（4章のSQLを実行し、CvServerを再起動）
#
# 補足: E-01はS5を設定しないため閾値は ExpectedDuration×2（数十分）が勝ち、S3=1分は効かない。
# E-01で確認したいのは2b→2fの対であって閾値ではないため支障はない。
# S2=30秒ごとにVduが前進するので、仮にS3が効いた場合でも誤解放されない（2cのまま）。
```

### E-02: 排他制御で他タスクの実行中エラー

### E-03: 管理メニューからの解除処理

## 4. S4: 監視タスクcronと実行フラグのDB更新

対象DB: `CvServer/server-user163.db`（SQLite）。

まず現在値を確認する。

```sql
SELECT Category, Name, Val FROM MasterConfig WHERE Category='自動実行管理';
```

行が存在しない場合がある（未登録なら既定値 `AutoExecCronManualLockMonitor`＝`*/5 * * * *`、
`AutoExecEnabledManualLockMonitor`＝有効、が使われる）。

### cronを1分間隔へ（E-01用）

```sql
UPDATE MasterConfig SET Val='*/1 * * * *'
WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecCronb8c9d0e1';
```

既定へ戻す:

```sql
UPDATE MasterConfig SET Val='*/5 * * * *'
WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecCronb8c9d0e1';
```

### 監視タスクを停止（E-02/E-03用）

```sql
UPDATE MasterConfig SET Val='0'
WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecb8c9d0e1';
```

再開:

```sql
UPDATE MasterConfig SET Val='1'
WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecb8c9d0e1';
```

### 反映タイミングの非対称性

- **cronの反映はサーバ再起動時**である（`RegisterSystemJob`、`CvServer/Services/SchedulerService.cs:764`）。
  cronを変更したらCvServerを再起動しないと反映されない。
- 一方、**実行フラグは実行の都度DBを見る**ため、CvServerを再起動しなくても次回tick以降に即時反映される。

### 名前の由来

`GenericSQLRegAutoExecCron`＋TaskId先頭8桁（TaskIdは
`CvBase/BaseDb1Master.cs:1177`の`AutoExecTaskIdManualLockMonitor`＝`b8c9d0e1-f2a3-...`）。

## 7. 2プロセス同時実行（E-04・E-02の実プロセス版）

計画書§4.2 E-04（真の同時TryBegin）とE-02（実行中エラー）を、**同一CvServerへ別プロセスの
クライアントから同時に要求を投げる**ことで検証する手順。単体の`manuallock`シナリオ（1章〜6章、
1プロセス内で順に検証）とは別に、`Doc/test/UatVm/Scenarios/ManualLockRaceScenario.cs`
（シナリオ名`manuallockrace`）と`Doc/test/UatVm/Run-ManualLockRace.ps1`を用意した。

### 7.1 前提

- **CvServerは1本のみ**動かす（`Doc/test/UatVm/README.md`「並列実行はできない（単一の開発DBを
  共有するため）」）。2サーバは起動しない。排他は`SysSequence`の行1本で効くため、
  同一サーバへ2つの独立したクライアントプロセスから同時要求を投げれば「真の同時TryBegin」の
  条件を満たす。
- **S1（`CV10_LOCK_SLEEP_BEGIN_MS`）をCvServerの環境へ渡しておくこと**が必須。S1が無いと、
  勝者確定後の占有時間が実質0秒になり、後発が確実に弾かれるE-02の状況を再現できない。
  `Run-ManualLockRace.ps1`は既定で`-ManageServer $true`（自分でCvServerを起動）のとき、
  この環境変数を自動で設定してからCvServerを起動する（2章のS1と同じ変数）。
- 発火の同期は共通の壁時計時刻（`--fire-at HH:mm:ss`）で行う。WPFとgRPCの起動時間には
  プロセスごとにばらつきがあるため、「起動してすぐ撃つ」では真に同時にならない。
  スクリプトは現在時刻+`LeadSeconds`秒（既定40秒）を計算し、両プロセスへ同じ値を渡す。
  各プロセスはその時刻まで`Task.Delay`→最後の約100msはスピンウェイトで待ち、
  プロセス間のズレを数十ms程度に収める。

### 7.2 実行コマンド例

事前に以下が済んでいること。

```powershell
dotnet build Doc\test\UatVm\UatVm.csproj
dotnet build CvServer\CvServer.csproj
```

CvServerの起動・終了までスクリプトに任せる場合（推奨）。

```powershell
powershell -NoProfile -File Doc\test\UatVm\Run-ManualLockRace.ps1
```

既に動作中のCvServer（S1設定済みで起動していること）へ接続する場合。

```powershell
powershell -NoProfile -File Doc\test\UatVm\Run-ManualLockRace.ps1 -ManageServer:$false -Url http://127.0.0.1:5002
```

主なパラメータ:

| パラメータ | 既定 | 意味 |
|---|---|---|
| `-Url` | `http://127.0.0.1:5002` | 接続先CvServer |
| `-LeadSeconds` | `40` | 発火時刻までの猶予秒数（WPF起動を考慮） |
| `-ManageServer` | `$true` | CvServerの起動・終了(Ctrl+C相当)をスクリプトが行うか |
| `-SleepBeginMs` | `60000` | S1（`CV10_LOCK_SLEEP_BEGIN_MS`）としてCvServerへ渡すミリ秒数 |

### 7.3 内部で起きること

1. （`-ManageServer`のとき）`CV10_LOCK_SLEEP_BEGIN_MS`等をスクリプト自身の環境変数へ設定し、
   `dotnet CvServer.dll`を起動して待ち受け開始を確認する。
2. 発火時刻を1つ計算し、`UatVm.exe manuallockrace --url <Url> --fire-at <時刻> --race-label A --hide-views`
   と同じ発火時刻・`--race-label B`のものを、**2つの独立したプロセス**として起動する
   （`--manage-server`は付けない。CvServerは1本のみ）。
   - `--race-label A`＝請求計算役（得意先`000002`、既存`manuallock`のE-01と同じ対象）
   - `--race-label B`＝支払計算役（仕入先1件目、既存`manuallock`のE-02の後発と同じ対象）
   - 2つの異なる画面を割り当てるのは、勝者・敗者どちらになっても、エラー本文中の
     先行`TableName`から「相手に先を越された」ことを一意に確認できるようにするため。
3. 両プロセスの終了を待ち、`Doc/test/UatVm/out/manuallockrace-A-*.jsonl` /
   `manuallockrace-B-*.jsonl`（race-labelとミリ秒・PIDを含めた名前にしており、
   同一秒に2プロセスが起動しても衝突しない）から`race:結果`（`VmSession.Note`）を読み取る。
4. （`-ManageServer`のとき）`Stop-CvServer.ps1`と同じ作法（Ctrl+C相当）でCvServerを正規終了させる。

### 7.4 判定基準

- **各プロセス単体**: 勝ち（排他を取得できた）でも負け（先行がいるためエラーで中断された）でも
  PASS扱いである（どちらになるかは競争の結果であり、片方が負けるのが正しい挙動）。
  「勝ったのに自分の排他行が一度も観測できない」「負けたのに自分の行が残っている」等の
  **矛盾だけがFAIL**になる（`ManualLockRaceScenario`内の`session.Check`）。
- **スクリプト全体（`VERDICT`）**:
  1. 2プロセスの結果が**1勝1敗**になっていること（両方勝ち・両方負け・判定不能はFAIL）。
  2. 収束後、`SysSeqType=1`の行が最終的に**0行または1行**であること
     （各プロセスが記録した`afterRows`から判定。2行以上はFAIL）。
  3. 各プロセスの終了コードが`0`（全PASSの意味。1は矛盾チェック等のFAILを含む）であること。
  - 上記いずれかを満たさない場合、スクリプトは`VERDICT: FAIL`と理由を出力し、終了コード`1`で終わる。
    全て満たせば`VERDICT: PASS`・終了コード`0`。

### 7.5 証跡の場所

- サーバー起動・停止と全体の判定ログ: コンソール出力（`Run-ManualLockRace.ps1`自身の`Write-Output`）。
- 各プロセスの詳細な証跡: `Doc/test/UatVm/out/manuallockrace-A-<yyyyMMdd-HHmmssfff>-pid<PID>.jsonl`、
  同様に`-B-`。`kind=note, name=race:結果`に勝敗（`outcome`＝`win`/`lose`/`ambiguous`）・
  直後の排他行数（`afterRows`）・エラー本文（負けた場合の`body`）等が入っている。
  その他`check`/`fail`等は既存`manuallock`と同じ形式（README.md §3参照）。
