## 0. 目的と範囲

旧CV（CVnet、Oracle）から CreativeVision10（SQLite）へデータを移行した後に、全メニューが移行データで正しく使えることを確認する。

- **旧DB**: Oracle `192.168.9.243/cvnet` のスキーマ `CV52`。参照には MCP `cv-oracle`（読み取り専用）を使う。
- **新DB**: `CvServer/appsettings.Development.json` の `ConnectionStrings:sqlite`（2026-10-21 時点は `server-user52.db`）。CV52 から変換したDBで、参照には MCP `cv-sqlite`（読み取り専用）を使う。
- **対象メニュー**: `MenuData.CreateDefault()` の全項目（末端208件、重複掲載を除くと約180画面）。
- **省略の原則**: SQLだけ、またはViewModelだけで検証が済むものは画面UATを省略する。
- **必須の確認**: **売掛・買掛・請求・支払・在庫の5区分**は、旧CVとの残高一致（SQL）を確認したうえで、CV10の画面・帳票でも**最低1回**残高を目視確認する（Step 6）。

### 0.1 検証レベル

| レベル | 方法 | 画面UAT |
|---|---|---|
| **S** | `cv-oracle` と `cv-sqlite` で同じ集計を取って突合する | 省略 |
| **V** | UatVm（実View/ViewModel→CvServer）で実行する。`menulayout` による全画面の描画確認もここに含める | 省略（JSONL・JPGで判定） |

### 0.2 移行の仕組み（設計の前提）

- 移行は `ConvertDb`（`CvDomainLogic/ConvertDb.cs`、`ConvertDbTran.cs`）が旧Oracleを直接読む方式。メニューは「旧DBからの変換処理」「旧DBからの選択変換処理」。
- 伝票の対応: 旧 `HC$TRAN_TORI0/1` の `伝票処理区分` 0→Tran00Uriage、1→Tran01Tenuri、2→Tran02Material、3→Tran03Shiire、5→Tran05Ido、6→Tran06Nyukin、7→Tran07Shiharai、10→Tran10IdoOut、11→Tran11IdoIn、12→Tran12Jyuchu、13→Tran13Hachu、18→Tran61Chosei。棚卸は `HC$TRAN_TANA0/1` → Tran60Tana。
- 伝票の主要列: 旧 `SEQ_NO`→`OldSeqNo`、`在庫計上日`→`DenDay`、`掛計上日`→`KakeDay`、`取引区分`→`Kubun`、`数量合計`→`SuTotal`、`明細金額合計`→`KingakuTotal`。
- **旧の残高テーブル（`HC$MANAGE_*`）は移行しない。** CV10の残高は、移行した伝票を「在庫・掛再更新」で再集計し、必要に応じて「残高登録処理」で期首残高CSVを取り込んで作る。そのため、**旧の残高テーブルとCV10の再集計結果を突き合わせること自体が、移行の主要な受入判定になる**。
- 色は `MasterMeisho`（Kubun=`COL`）、サイズは `MasterMeisho`（Kubun=商品の `SizeKu`）、倉庫は `MasterTokui` の Id に変換される。在庫照合では Id をコードへ戻して比較する。

### 0.3 照合に使う旧・新テーブル

| 区分 | 旧CV（CV52） | 旧のキーと値の列 | CV10 | CV10のキーと値の列 |
|---|---|---|---|---|
| 売掛 | `HC$MANAGE_KAKEURI` | 得意先CD, 年月, 当月残高 | `SummaryUriKake` | Id_Tokui, DenMonth, `TotalSales-TotalIn` |
| 請求 | `HC$MANAGE_KAKESKY` | 得意先CD, 請求日, 当月残高 | `SummaryUriSei` | Id_Tokui, DenDay(=締日), DayFrom, DayTo |

| 支払 | `HC$MANAGE_KAKESIH`（※1） | 仕入先CD, 支払日, 当月支払額, 現金支払…その他支払 | `SummaryKaiShi` | Id_Shiire, DenDay, `TotalShiire-TotalOut` |

### 3-2. 伝票（区分×年月の件数・数量・金額）

```sql
-- cv-oracle: 売上（区分0）。他の区分は :p0 を変えて実行する。
select substr(在庫計上日,1,6) ym, count(*) cnt, sum(数量合計) su, sum(明細金額合計) kin, sum(SEQ_NO) seqsum
from HC$TRAN_TORI0 where 伝票処理区分 = :p0
group by substr(在庫計上日,1,6) order by 1
```
```sql
-- cv-sqlite: 対応する表（例 Tran00Uriage）
SELECT substr(DenDay,1,6) ym, count(*) cnt, sum(SuTotal) su, sum(KingakuTotal) kin, sum(OldSeqNo) seqsum
FROM Tran00Uriage GROUP BY 1 ORDER BY 1;
```

- 区分 0,1,2,3,5,6,7,10,11,12,13,18 と棚卸（`HC$TRAN_TANA0` ↔ `Tran60Tana`）のすべてで実行する。入金・支払など `SuTotal` を持たない表は、件数・金額・`seqsum` だけを比べる。
- **判定**: すべての年月で `cnt` と `seqsum`（旧 SEQ_NO の合計＝伝票の取りこぼし検出）が一致すること。`kin` / `su` は、変換で符号や値引の扱いを変えている区分（返品・値引・在庫調整）があるので、差があれば年月→伝票（`OldSeqNo`）の順に絞り込んで、仕様差か不具合かを記録する。
- 明細の件数は、`HC$TRAN_TORI1` の件数と、CV10の `Jmeisai` の JSON 配列長の合計（`sum(json_array_length(Jmeisai))`）で比べる。

**完了条件**: 区分ごとの照合表を `$run/step3-counts.md` に保存し、差分の理由をすべて記録した。

## Step 4. 期首残高の取込（必要な場合だけ）

旧CVの伝票が期首より前の分を持っていない（削除・パージ済み）場合、伝票の再集計だけでは旧の残高に一致しない。その場合だけ実施する。

1. **S**: 旧の期首前月時点の残高を `HC$MANAGE_KAKEURI`/`KAKEKAI`（年月 < 期首年月の合計）と `KAKESKY`/`KAKESIH`（期首直前の締日）から抽出し、残高登録用のCSVを作る。列は `CvBase/OpeningBalanceCsv.cs` の `GetColumns` に合わせる。

3. **S**: 取り込んだ行のキーが、売掛・買掛は期首年月の前月、請求・支払は期首直前の締日になっていること。

**判断が必要になる点**: 期首日（`MasterSysman.FiscalStartDate`）と、どの時点の旧残高を期首残とするかは業務判断になる。実施前に決める。

## Step 6. 残高の照合【必須】（S＋U）

各区分で、**6-x-1 の旧↔新のSQL照合**と、**6-x-2 の画面・帳票での1回以上の目視**を必ず行う。照合基準年月 `X`（例: 移行直前の締め月）と照合基準締日 `D` を Step 1 で決め、`$run/README.md` に記録する。

SQLの結果は1000行で打ち切られるので、**総計 → 年月別 → 取引先別（コード範囲で分割）** の順に絞り込む。

### 6-1. 売掛

**6-1-1（S）**: 得意先別の、X時点の累計残高。

```sql
-- cv-oracle
select 得意先CD, sum(当月残高) zan from HC$MANAGE_KAKEURI
where 年月 <= :p0 group by 得意先CD having sum(当月残高) <> 0 order by 得意先CD
```
```sql
-- cv-sqlite（@p0 = 'YYYYMM'）
SELECT t.Code, sum(k.TotalSales - k.TotalIn) zan
FROM SummaryUriKake k JOIN MasterTokui t ON t.Id = k.Id_Tokui
WHERE k.DenMonth <= @p0 GROUP BY t.Code HAVING zan <> 0 ORDER BY t.Code;
```

まず両方で `sum(zan)` と `count(*)` だけを取る（総計）。一致しなければ年月別、次に得意先別へ絞る。

**6-1-2（U）**: 「掛管理/売掛・請求 → 売掛金管理表」を年月Xで出力し、残高が上位3社と、6-1-1 で差のあった得意先（あれば）について、PDFの前月残・当月残が `cv-sqlite` の値と一致することを目視する。「得意先元帳」で同じ1社の期末残高も確認する（元帳は伝票から直接計算するため、Summary と独立した照合になる）。

### 6-2. 請求

**6-2-1（S）**: 締日Dの請求残。

```sql
-- cv-oracle
select 得意先CD, sum(当月残高) zan from HC$MANAGE_KAKESKY
where 請求日 <= :p0 group by 得意先CD having sum(当月残高) <> 0 order by 得意先CD
```
```sql
-- cv-sqlite（@p0 = 'YYYYMMDD'）
SELECT t.Code, sum(u.TotalSales - u.TotalIn) zan
FROM SummaryUriSei u JOIN MasterTokui t ON t.Id = u.Id_Tokui
WHERE u.DayTo <= @p0 GROUP BY t.Code HAVING zan <> 0 ORDER BY t.Code;
```

あわせて、締日Dの1回分の請求額（今回売上・入金・消費税）を、得意先別に比較する。

```sql
-- cv-sqlite
SELECT t.Code, u.DayFrom, u.DayTo, u.Uriage, u.Henpin, u.Nebiki, u.Tax1+u.Tax2+u.Tax3 tax, u.TotalIn
FROM SummaryUriSei u JOIN MasterTokui t ON t.Id = u.Id_Tokui
WHERE u.DenDay = @p0 ORDER BY t.Code;
```

**6-2-2（U）**: 「請求一覧表」と「請求書印刷」を締日Dで出力し、代表3社の前回請求残・今回入金・今回売上・今回請求残が 6-2-1 と一致することを目視する。請求書は印刷確定（採番）をせず、プレビューだけにする。

### 6-4. 支払

**6-4-1（S）**: Step 1 で確定した支払残の表を使う。旧の残高列が無く `当月支払額` と支払内訳しか無い場合は、仕入側（`明細金額合計` 系）と支払側（現金支払＋振込手数料＋手形支払＋相殺支払＋その他支払）を別々に比べる。

```sql
-- cv-oracle（KAKESIH に当月残高がある場合）
select 仕入先CD, sum(当月残高) zan from HC$MANAGE_KAKESIH
where 支払日 <= :p0 group by 仕入先CD having sum(当月残高) <> 0 order by 仕入先CD
```
```sql
-- cv-oracle（支払の内訳だけを比べる場合）
select 仕入先CD, sum(現金支払+振込手数料+手形支払+相殺支払+その他支払) shi
from HC$MANAGE_KAKESIH where 支払日 = :p0 group by 仕入先CD order by 仕入先CD
```
```sql
-- cv-sqlite
SELECT s.Code, sum(k.TotalShiire - k.TotalOut) zan, sum(CASE WHEN k.DenDay = @p0 THEN k.TotalOut END) shi
FROM SummaryKaiShi k JOIN MasterShiire s ON s.Id = k.Id_Shiire
WHERE k.DayTo <= @p0 GROUP BY s.Code ORDER BY s.Code;
```

**6-4-2（U）**: 「支払一覧表」と「支払残高明細書」を締日Dで出力し、代表3社を目視する。

### 6-6. 判定と差の扱い

- **一致**: 総計・年月別・取引先（倉庫）別がすべて一致すれば PASS。
- **差がある場合**: 該当の取引先・SKU を伝票まで絞り込み、原因を次のどれかに分類して記録する。
  - (a) 旧の残高テーブル側の不整合（旧の再集計漏れ）
  - (b) 仕様差（自社締日の暦月集計、返品の符号、消費税の端数処理、その他売上 Kubun 99 など）
  - (c) 移行・集計の不具合
- (c) があれば FAIL とし、移行をやり直すか修正するかを判断してもらう。(a)(b) は、件数・金額と理由を一覧にして承認を得る。
