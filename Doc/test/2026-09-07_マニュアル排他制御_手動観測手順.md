### 2.4 監視ログの読み方

| 項目 | 意味 |
|---|---|
| `SysHistType=0` | 監視タスク自身の自動実行ログ |
| `SysHistType=1` | 処理側の正常終了ログ、または強制クリアの操作ログ（`TaskName`で区別） |
| `Memo` 先頭 `[2b:検知]` | 監視が排他行を新規検知した（設計§3.2） |
| `Memo` 先頭 `[2e:タイムアウト解放]` | 閾値超過で監視が行を削除した（設計§3.5）。`ReturnCode=9` |
| `Memo` 先頭 `[2f:正常終了]` | 監視が「行が消えた」ことを検知した（設計§3.6）。`ReturnCode=0` |
| ログの対応関係 | 監視ログは必ず `2b→2f`（正常終了）か `2b→2e`（異常解放）の対になる（設計§3.7、L-11）。`2a`（行なし）・`2c`（Vdu前進中）ではログを出さない |

`Memo` には検知時点の `TableName` / `ColumnName` / `SeqNo` / `Vdc` / `Vdu` /
`ExpectedDuration` が文字列として埋め込まれる（`ManualLockDb` の監視ログ組み立て処理）。
したがって `SeqNo` の値も `Memo` の文字列としてそのまま読み取れる（§8で利用）。

## 3. E-05 プロセス強制終了→監視による自動解放

### 3.1 目的と対応するテスト観点

設計§5 **L-07**「処理が例外で落ちたとき行が残り、監視タスクが閾値超過で削除する」の
実サーバ版。`CvDomainLogic/ManualLockDb.cs:81` の `Dispose` が意図的に行を残す設計を、
単体テストの模擬ではなく実プロセスの強制終了で実証する。付随して **L-11**
（ログが2b→2eの対になること）も同時に確認する。

§2.2の既存残骸行（消化仕入更新）の解放も、本ケースの一部として観測する。

### 3.2 前提とスイッチ設定

| ID | 設定値 | 再起動要否 |
|---|---|---|
| S1 | `CV10_LOCK_SLEEP_BEGIN_MS=180000`（3分占有） | 要（環境変数はプロセス起動時1回読み） |
| S3 | `CV10_LOCK_MIN_THRESHOLD_MIN=1` | 要 |
| S5 | `CV10_LOCK_EXPECTED_SEC=10` | 要 |
| S4 cron | `*/1 * * * *` | 要（cronはサーバ再起動時にしか反映されない） |
| S4 実行フラグ | 手順の中で `1`→`0`→`1` と切り替える（下記） | 不要（発火の都度DBを読むため即時反映。`CvServer/Services/SchedulerService.cs:878`） |

閾値は `max(10×2, 1分)=1分` になる。kill後1〜2tick（最大約2分）で `[2e:タイムアウト解放]`
が出る見込みである。

占有させる処理は**請求計算**を選ぶ。単一得意先（`000002`）に絞れば実処理が軽く、
既存UatVmシナリオの対象と揃う。

**S1と監視は干渉するため、実行フラグの切り替えが必須である**（計画書§3の注意点
「S1とS3/S4は干渉する」）。S1で占有している間 `Vdu` は前進しない一方、S3=1・S5=10により
閾値は1分に縮まる。監視を有効にしたまま占有すると、**killする前に監視が2eで解放してしまい、
「killしたから行が残った」という本ケースの主眼が観測できない**。
したがって占有〜killの間だけ実行フラグを`0`にし、kill後に`1`へ戻す。
実行フラグは発火の都度DBから読まれるため、この切り替えにCvServerの再起動は不要である。

本ケースは次の3段構成になる。

| 段 | 内容 | 実行フラグ |
|---|---|---|
| 第1段 | §2.2の既存残骸行（消化仕入更新）が監視に自動解放されるのを観測する | `1` |
| 第2段 | 請求計算で占有させ、その最中にCvServerを強制終了して行を残す | `0` |
| 第3段 | 残った行が監視に自動解放されるのを観測する | `1` |

### 3.3 手順

**第1段: 既存残骸行の自動解放を観測する**

1. §2.3の3SQLで現状を確認する（§2.2の残骸行が残っていること、実行フラグが`1`であることを再確認）。
2. PowerShellで環境変数を設定する。

   ```powershell
   $env:CV10_LOCK_SLEEP_BEGIN_MS = "180000"
   $env:CV10_LOCK_MIN_THRESHOLD_MIN = "1"
   $env:CV10_LOCK_EXPECTED_SEC = "10"
   $env:DOTNET_ENVIRONMENT = "Development"
   $env:ASPNETCORE_ENVIRONMENT = "Development"
   $env:Kestrel__Endpoints__Http__Url = "http://127.0.0.1:5002"
   ```

3. MasterConfigのcronを`*/1 * * * *`へ更新する（テストスイッチ手順書§4）。

   ```sql
   UPDATE MasterConfig SET Val='*/1 * * * *'
   WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecCronb8c9d0e1';
   ```

4. CvServerを起動する（専用のPowerShellウィンドウで前景実行し、そのまま起動ログを見る）。

   ```powershell
   Set-Location C:\gitroot\new2022\cv10\CvServer
   dotnet .\bin\Debug\net10.0\CvServer.dll
   ```

5. 待ち受け開始（`http://127.0.0.1:5002` で応答すること）まで数秒〜数十秒待つ。
6. 2tick（約2分）待ち、§2.3(2)のSQLで`TableName=消化仕入更新`に対する
   `[2b:検知]`→`[2e:タイムアウト解放]`の対が出て、§2.3(1)のSQLで当該行が消えていることを
   確認する。この行には`ExpectedDuration=600`が既に書かれており閾値は`max(1200秒,1分)=20分`
   だが、`Vdu`が18.7時間前のため**検知（2b）の次のtickで即座に2eになる**（S3・S5は
   この行の判定には効かない。`ExpectedDuration`は行に保存済みの値が使われるため）。

**第2段: 占有させ、その最中に強制終了して行を残す**

7. 監視の実行フラグを`0`（無効）にする。**これを忘れると第2段が成立しない**（§3.2の干渉）。

   ```sql
   UPDATE MasterConfig SET Val='0'
   WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecb8c9d0e1';
   ```

8. WPFクライアント（または相当のクライアント）から「請求計算」画面
   （`BillingCalculationView`、Msg056）を開き、得意先`000002`のみを対象に実行を開始する。
   S1により、勝者確定直後の3分間は`Vdu`が前進しないまま占有される。
9. §2.3(1)のSQLで`TableName=請求計算`の行が1件できていることを確認する。
   **このとき`ExpectedDuration`が`10`になっていること**（=S5がCvServerに効いていること）も
   併せて確認する。`1800`のままならS5が起動前に設定されていない。
10. 別のPowerShellウィンドウでCvServerプロセスを特定する。

    ```powershell
    Get-CimInstance Win32_Process -Filter "Name='dotnet.exe'" |
      Where-Object { $_.CommandLine -like '*CvServer.dll*' } |
      Select-Object ProcessId, CommandLine
    ```

11. 該当PIDを**強制終了**する（3分の占有ウィンドウの中で行う）。

    ```powershell
    Stop-Process -Id <上で取得したProcessId> -Force
    ```

12. §2.3(1)のSQLで`TableName=請求計算`の行が残っていることを確認する
    （正規終了ではないため`Dispose`が走らず、かつ監視も無効なため残る）。

**第3段: 残った行の自動解放を観測する**

13. 監視の実行フラグを`1`（有効）へ戻す（即時反映。再起動は不要）。

    ```sql
    UPDATE MasterConfig SET Val='1'
    WHERE Category='自動実行管理' AND Name='GenericSQLRegAutoExecb8c9d0e1';
    ```

14. CvServerを同じ環境変数のまま再起動する（手順4と同じコマンド）。
15. 1〜2tick（最大約2分）待ち、§2.3(2)のSQLで`TableName=請求計算`に対する
    `[2b:検知]`→`[2e:タイムアウト解放]`の対が出て、§2.3(1)のSQLで行が消えたことを確認する
    （この行は`ExpectedDuration=10`のため閾値は1分である）。

### 3.4 期待結果

- 既存残骸行（消化仕入更新）・強制終了させた行（請求計算）の**両方**について、
  `SysHistAutoexec` に `[2b:検知]`→`[2e:タイムアウト解放]` の対が記録される。
- `[2b:検知]` の `ReturnCode=0`、`[2e:タイムアウト解放]` の `ReturnCode=9`
  （`ManualLockDb.MonitorTimeoutReturnCode`）。
- **第2段（実行フラグ=0）の間は、閾値を超えていても行が解放されない。**
  これが第3段との対比により「解放しているのは監視タスクである」ことの裏付けになる。
- 最終的に `SysSequence` の `SysSeqType=1` 行が0行になる。
- `SysHistType=0`（監視の自動実行ログ）としてのみ記録され、`SysHistType=1`
  （処理側の正常終了ログ）は請求計算側からは記録されない
  （`Complete` まで到達していないため）。

### 3.5 後始末

本ケースの環境変数・cronはこの後の§8（E-15）でもそのまま使うため、
ここでは**環境変数・MasterConfigを戻さない**。全ケース終了後（§9末尾）でまとめて戻す。
ただし**実行フラグが`1`に戻っている状態で本ケースを終えること**（手順13）。

テスト用に作った行は手順の中で監視により削除済みのため、削除SQLは不要。

## 4. E-11 `SysSeqType=0` の連番行が排他・監視に無影響

### 4.1 目的と対応するテスト観点

設計§5 **L-12**「`SysSeqType=0`（テーブル連番）の行が排他判定にも監視にも影響しない」の
実サーバ版。付随して **L-17**（強制クリアが`SysSeqType=1`の行だけを消し、`SysSeqType=0`の
行を消さない）も本ケースの中で確認する。

`SysSeqType=0` の行を運用操作で作る経路は現行CV10に存在しない。`SysSequence` を採番に
使っている実装が無く、単体テストが直接INSERTして擬似的に作っているだけである。
したがって本ケースもSQLite直接INSERTで作る。

### 4.2 前提とスイッチ設定

| ID | 設定値 | 再起動要否 |
|---|---|---|
| S1/S2/S3/S5 | 不要 | — |
| S4 cron | `*/1 * * * *`（観測を速くするだけで必須ではない。§3から継続していれば変更不要） | 変更する場合は要 |
| S4 実行フラグ | `1`（有効。監視が動いている状態で「無視される」ことを見るのが目的） | 不要 |

§3（E-05）に続けて同一CvServerセッションで実施できる。

### 4.3 手順

1. `SysSequence` の列構成を確認する。

   ```sql
   PRAGMA table_info(SysSequence);
   ```

2. `SysSeqType=1` の行が0件であること（§3で解放済みのはず）を§2.3(1)のSQLで確認する。
3. 現在時刻のUTC Ticksを求める（PowerShell）。

## 8. E-15 `SeqNo=99` が残った状態からの自動解放

### 8.1 目的と対応するテスト観点

設計§2.3「`SeqNo=99`を先に書くのは、履歴書き込み中にプロセスが落ちた場合に
『終了処理まで到達していた』ことを監視タスクとログから読み取れるようにするため」の
意図を実証する。関連する観点は設計§5 **L-07**（監視タスクによる解放）。

**この方法は代替であり、実際のクラッシュを再現したものではない。** 既存のテスト用
スイッチ4種（S1〜S5）は`ManualLockDb.Complete`の内部（`SeqNo=99`書き込み→履歴INSERT→

自動でも手動再現でも作れない。よって本ケースでは**「①〜③の途中で落ちた結果の状態」を
SQLiteで直接作り**、その状態から監視が解放できるか、履歴から終了処理到達を読み取れるかを
確認する。検証しているのは「`SeqNo=99`の行が残っていたとき監視と履歴から終了処理到達を
読み取れるか」であって、`Complete`の途中で落ちる事象そのものではない。

### 8.2 前提とスイッチ設定

| ID | 設定値 | 再起動要否 |
|---|---|---|
| S1 | 不要 | — |
| S3 | `CV10_LOCK_MIN_THRESHOLD_MIN=1` | 要 |
| S5 | `CV10_LOCK_EXPECTED_SEC=10` | 要 |
| S4 cron | `*/1 * * * *` | 要 |
| S4 実行フラグ | `1`（有効） | 不要 |

§3（E-05）と同一の環境変数構成のため、**§3の直後であれば再起動不要でそのまま続けられる**。
§6（E-13）の後に本ケースを行う場合は、E-13で解除した環境変数を再設定した上での再起動が
必要になる。

### 8.3 手順

1. 排他行を直接INSERTする。`SeqNo`をあらかじめ`99`にし、`Vdu`を2分以上前にしておく
   （`ExpectedDuration=10`のときの閾値は`max(10×2,1分)=1分`のため、2分前にしておけば
   即座に閾値超過となる）。

   ```powershell
   $ticks = [DateTime]::UtcNow.AddMinutes(-2).Ticks
   ```

   ```sql
   INSERT INTO SysSequence
     (SysSeqType, TableName, ColumnName, SeqNo, Memo, ExpectedDuration, Vdc, Vdu)
   VALUES
     (1, 'MANUAL-E15', '終了処理中', 99, '', 10, <ticks>, <ticks>);
   ```

2. 1〜2tick（最大約2分）待つ。
3. §2.3(2)のSQLで`MANUAL-E15`に対する`[2b:検知]`→`[2e:タイムアウト解放]`の対が
   出ていることを確認する。`ReturnCode`は`[2e]`側が`9`。
4. `[2e:タイムアウト解放]`の`Memo`本文に`SeqNo=99`という文字列が含まれていることを
   確認する（監視ログの組み立てが検知時点の`SeqNo`列の値をそのまま埋め込むため、
   `SysSequence.SeqNo=99`にしておけばログにもその値が literal に残る）。
5. §2.3(1)のSQLで`MANUAL-E15`行が消えたことを確認する。

### 8.4 期待結果

- `[2b:検知]`→`[2e:タイムアウト解放]`の対が記録され、`[2e]`の`Memo`から
  `SeqNo=99`であったことが読み取れる。
- この状態は「終了処理（`SysHistAutoexec`へのINSERTと行のDELETE）まで到達していた
  可能性がある」ことの代替観測であり、実際に`Complete`の途中で落ちた事象を
  再現したものではないことを結果レポートにも明記する。

### 8.5 後始末

環境変数・MasterConfigは§9末尾でまとめて戻す（本ケース単独では戻さない）。
行はすでに監視により削除済みのため、削除SQLは不要。

### 8.6 想定される失敗と切り分け

| 症状 | 疑う箇所 |
|---|---|
| `[2e]`が出ない | S3・S5の環境変数がCvServer起動前に設定されていたか確認（プロセス起動時1回読みのため、後から設定しても効かない） |
| `ReturnCode`が9でない | `ManualLockDb.MonitorTimeoutReturnCode`の値が変更されていないか確認 |
| `Memo`に`SeqNo=99`の文字列が見当たらない | `Memo`は300文字で古い内容から切り捨てられる仕様のため、`TableName`等が長い場合に末尾側の`ExpectedDuration`部分まで切り捨てられている可能性がある。`TableName`を短く（`MANUAL-E15`程度）保てば通常は収まる |

## 9. 実施順序の推奨

6ケースを効率よく回すため、**CvServerを2セッション（環境変数構成2種）に分けて**
実施することを推奨する。理由は、E-13だけが「S3/S5を使わず閾値15分以上を維持する」
必要があり、他の5ケース（E-05・E-15はS1/S3/S5あり、E-11・E-12・E-14はS1/S3/S5不要だが
残っていても支障なし）と環境変数構成が両立しないためである。

| 順序 | ケース | セッション | 備考 |
|---|---|---|---|
| 1 | E-05 | セッション1（S1=180000, S3=1, S5=10, cron=`*/1`） | 実行フラグを`1`→`0`→`1`と切り替える3段構成（§3.2）。第1段で§2.2の既存残骸行の解放も観測する。終了時は実行フラグ`1` |
| 2 | E-11 | セッション1継続 | 監視が有効なまま`SysSeqType=0`行が無視されることを見るため、実行フラグ=1を維持したまま行う |
| 3 | E-12 | セッション1継続。実行フラグのみ`0`へ | 環境変数の再起動は不要（実行フラグはDB即時反映）。終了後は実行フラグを`1`へ戻す |
| 4 | E-14 | セッション1継続。実行フラグ`0`のまま（E-12から続けてよい） | 終了後は実行フラグを`1`へ戻す |
| 5 | E-15 | セッション1継続。実行フラグ`1`（E-14の後始末で戻した状態） | E-05と同じ環境変数構成のため再起動不要 |
| 6 | E-13 | セッション2（環境変数を全解除、cron=`*/1`、実行フラグ=1） | 環境変数を戻すため**CvServer再起動が必要**。本ケース自体もう1回の再起動（正規終了→再起動）を内部で行う |

**再起動が必要になる境目**は次の2箇所である。

- セッション1の開始時（環境変数を新規に設定してCvServerを起動する）。
- セッション1からセッション2へ移る境目（E-15終了後、E-13のために環境変数を全解除して
  再起動する）。加えてE-13の手順自体の中でもう1回、正規終了と再起動を行う。

セッション1の内部でE-05の手順11〜14（強制終了→再起動）が発生するが、これは
S1/S3/S5/cronの値を変えない同一構成での再起動であり、上記の「境目」には含めない。

全ケース終了後、Step T6でUatVmシナリオ（`manuallock`/`manuallockrace`）を回す前に、
MasterConfigのcronを既定（`*/5 * * * *`）へ戻し、CvServerを一度正規終了・再起動して
反映させる。実行フラグは最終的に`1`（既定）であることを確認する。環境変数は全て解除し、
`SysSequence`にテスト用の行（`MANUAL-E*`）が残っていないことを§2.3(1)のSQLで確認する。

強制終了で残った`server-user163.db-wal`について: **WALが残るのは想定内であり、
次回CvServerの正規終了、または毎日2時のWALチェックポイント自動実行タスク
（`CvServer/Program.cs:207`、cron`0 2 * * *`）のいずれかで`PRAGMA wal_checkpoint(TRUNCATE)`
が走り解消される。慌てて手で消してはならない。**
