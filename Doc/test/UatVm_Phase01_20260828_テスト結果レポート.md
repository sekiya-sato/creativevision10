## 2. 判定

**Phase 0（ハーネス基盤）・Phase 1（C-01〜C-10）とも完了、全ケースPASS。** ただし実施過程で以下の重要事項が生じており、いずれもユーザーへ報告し対応方針を確定済みである。

1. **インシデント**：C-04実行時、実行前チェックの不備により実運用相当データ48,691件（差額合計 約144億円）を書き換えた。ユーザー判断により「変更を受け入れる」（ロールバックしない）で確定。詳細は計画書6.1。
2. **仕様上の発見**：C-10検証により、集計系Rebuild（在庫・売掛・買掛等）はキャンセルしてもサーバー側処理が中断されないことを実証した。クラッシュ・DB破損は起きないが、「キャンセル＝処理停止」という利用者の期待とは乖離する。D-07で扱うべき事項として計画書6.3に記録。
3. **テストデータ不備の自己発見・修正**：UAT専用シード（`ShimeBoundarySeeder`）が明細（`Jmeisai`）を設定し忘れており、対象期間での在庫Rebuildが失敗する不具合を作り込んでいた。修正済み。既存ツール`summaryreconcile`にも同種の不備が残っており、UAT-07着手時の要注意事項として記録した（計画書6.2）。

WPFクライアントの実View生成・ViewModelコマンド駆動によって、チェックリストが要求する「画面からサーバー、DB、帳票まで完遂する」ことをすべてのケースで確認した。画面操作を人が行わずに完走したのは、完成度チェックリストP0「WPF Mini-UAT」の到達目標に相当する。

## 6. 検出事項

### 6.1 インシデント：C-04実行による実運用相当データの大規模更新

「伝票税額再更新」（`TranTaxRebuildDb.RebuildAll`）を実行前チェック不足のまま実行し、以下を更新した。

```
Tran00Uriage   走査    50,323件 / 更新     1件 / ヘッダTax変化     1件 差額         1,400円（UAT分）
Tran01Tenuri   走査 3,432,479件 / 更新 33,395件 / ヘッダTax変化     0件 差額             0円
Tran03Shiire   走査     8,608件 / 更新  8,602件 / ヘッダTax変化 8,598件 差額 -8,631,689,207円
Tran12Jyuchu   走査         1件 / 更新     0件 / ヘッダTax変化     0件 差額             0円
Tran13Hachu    走査     6,693件 / 更新  6,693件 / ヘッダTax変化 6,690件 差額 -5,810,119,012円

更新合計 48,691件　ヘッダTax変化 15,289件　差額合計 -14,441,806,819円
```

原因：実行前チェックを`Tran00Uriage`のみで行い、`Tran03Shiire`・`Tran13Hachu`に対象データ（明細別消費税未対応の既存伝票）が大量に残っていたことを見落とした。`TranTaxRebuildDb`自体は設計文書（2026-08-25）で承認済みの正規機能であり、動作は仕様通り。

対応：ユーザー報告のうえ「変更を受け入れる」で確定（ロールバックしない、2026-08-28）。教訓を計画書6.1に記録。

### 6.2 発見：UAT系シードデータの明細欠落と在庫Rebuild失敗

C-10検証中、対象範囲に202607を含めると在庫Rebuildが`SQLite Error 19: NOT NULL constraint failed: SummaryStock.InQty`で失敗する事象を発見した。原因は`ShimeBoundarySeeder`（本ハーネス）が投入した売上に明細（`Jmeisai`）が無く、`json_extract(明細,'$.Su')`のSUMがNULLになるため。同種の不備が既存ツール`summaryreconcile`のシードにも残っている（未修正）。

対応：`ShimeBoundarySeeder`を修正（明細追加）。C-10の対象範囲を202607を含まない2020年へ変更。`summaryreconcile`側の修正はUAT-07着手前の課題として計画書6.2に記録。

### 6.3 発見：集計系Rebuildのキャンセルはサーバー処理を中断しない

C-10検証中、画面の「キャンセルしました」表示とサーバー側の実際の処理結果が食い違うことを、サーバー側への一時的なsleep注入（検証後に完全復元）で実証した。原因は`SummaryAllAsyncStream`が1ステップのみで構成され、その本体`CalcSummaryStockRange`が`CancellationToken`を一切受け取らない同期メソッドであるため。クラッシュ・DB破損は起きないが、「キャンセル＝処理停止」という利用者の期待とは乖離する。

対応：D-07（月次処理の順序とロック）で扱うべき仕様決定事項として計画書6.3・A-5に記録。
