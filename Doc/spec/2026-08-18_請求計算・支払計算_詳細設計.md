# 請求計算・支払計算 詳細設計（2026-08-18）

対象HEAD: `074d6c0`（Doc/spec 整理）
対象: `SummaryUriSei`（請求残）/ `SummaryKaiShi`（支払残）の生成、請求計算 `BillingCalculation` / 支払計算 `PaymentCalculation` 画面
根拠: 判断材料 7章（決定済 E1〜E9・E8a〜g）、2026-08-18 ユーザー決定（E10 / E11 / E7 / E8-g）、
チェックリスト 4章（`SummaryUriSei` / `SummaryKaiShi` は「スキーマのみ・生成処理皆無」）。

## 1. 目的とスコープ

`SummaryUriSei` / `SummaryKaiShi` を生成する**請求計算・支払計算**を実装し、請求一覧表・支払一覧表・
月別入金/支払予定表・請求書印刷の元データを作る。**第1段階＝1得意先1締日**（`Shime1` のみ、
移行実データ全件 `Shime1=99`＝末日／仕入先 `PayMonth=0`・`PayDay=0`＝当月末）を対象にする。

本設計の実装スコープ:
- スキーマ追加（請求書番号・入金/支払予定日）。
- 請求計算・支払計算ロジック（`SummaryDb`）と gRPC ストリーミング接続（既存の掛再更新と同型）。
- 請求計算 `BillingCalculation` / 支払計算 `PaymentCalculation` の実行画面（31Monthly、現状 L0）。

**スコープ外（別課題）**: 請求書印刷（帳票 qfm）、請求一覧表・支払一覧表の帳票実データ突合、最大3締日（第2段階）、
締日更新（J1＝1.0対象外）、親子請求の合算出力（親のみ／子含む）。

## 2. 前提（既存資産）

- 掛月次集計 `SummaryDb.CalcSummaryUriKake(fromYYYYMM, toYYYYMM)` / `CalcSummaryKaiKake` が実装済みで、
  内訳（`Uriage`/`Henpin`/`Nebiki`/`Cash`/`Fee`/`Densai`/`Offset`/`Other`）と繰越 `Balance`・当月残を計算する。
  ストリーミングは `Msg052_SummaryUriKake` / `Msg053_SummaryKaiKake`（`StockKakeUpdate` 画面が呼ぶ）。
- スキーマ（`CvBase/BaseDbKake.cs`）:
  - `SummaryUriKake`（売掛月次）: `Id_Tokui`・`DenMonth`(yyyyMM)＋内訳＋`Balance`/`TotalIn`/`TotalSales`。
  - `SummaryUriSei`（請求残）: `Id_Tokui`・`DenDay`(請求日)・`DayFrom`・`DayTo`（請求期間）＋**掛と同じ内訳列**。
  - 買掛側 `SummaryKaiKake` / `SummaryKaiShi` は `Id_Shiire`・`TotalOut`/`TotalShiire` で同型。
- 締日: `MasterTokui.Shime1`（`EnumShime`、99=末日）。支払: `MasterShiire.PayMonth`（0=当月）・`PayDay`（0/99=末日）。
- 決定 E8-f により「正式な税額は請求書側（`SummaryUriSei.Tax`）」。`SummaryUriKake.Tax` は目安。

## 4. 請求計算ロジック（`SummaryDb.CalcSummaryUriSei`）

旧CV.netの「締日ごとに回す月末処理」（判断材料 7.1）に倣う。パラメータは**締日・請求月・得意先範囲**。

### 4.1 対象と期間（E2/E3、決定済）

- 対象得意先 = `MasterTokui.Shime1 = 指定締日` かつ 得意先CD範囲内。
- 請求期間 `DayFrom`〜`DayTo`:
  - `DayTo`（請求終了日）＝請求月の締日（`Shime1=99` なら月末日）。
  - `DayFrom` ＝前回締日の翌日（前月締日＋1日）。
  - `DenDay`（請求日）＝`DayTo`（**請求日＝請求終了日＝締日**、決定 E3）。

### 4.2 再計算の単位（E5、決定済）

締日＋請求月＋得意先範囲で**対象期間を DELETE → 再作成**（掛集計と同じ）。冪等で「通常更新値＝Rebuild値」を保つ。

### 4.3 内訳の集計（E1/7.1.1）

請求期間内（`Tran00Uriage.KakeDay` が `DayFrom`〜`DayTo`）の売上を得意先単位に集計する。
- `Uriage`＝区分10/11（売上）※**区分99は除く**、`Henpin`＝返品、`Nebiki`＝値引（`CalcFlag` 符号付き保持、帳票で符号反転）。
- **`Other`（その他売上）＝区分99**（E11 決定：請求一覧用に分離。掛側で `Uriage` に畳んでいたものを請求では切り出す）。
- 入金内訳（`Cash`/`Fee`/`Densai`/`Offset`/`Other` の入金側）は消込ではなく `Tran06Nyukin` の `Jmeisai` を `Id_Kin` 区分で集計（掛集計と同じ規則を流用）。
- `Balance`（前月残）＝前回請求（同得意先の直前 `SummaryUriSei`）の当月残。無ければ 0（期首残は移行の残高登録で投入、別課題）。
- `TotalSales`（売上合計）＝`Uriage − Henpin − Nebiki ＋ Other ＋ Tax`（7.1.1）。`TotalIn`（入金計）＝現金＋手数料＋手形＋相殺＋その他入金。
- 当月残＝`Balance ＋ TotalSales − TotalIn`（繰越金額の考え方は 7.1.1 に合わせる）。

### 4.4 消費税（E8a〜g、決定済＋2026-08-18）

- **得意先×年月**で、課税標準＝`Kingaku`（金額）月次集計に対して**四捨五入・外税**で計算（E8a/b/c/e）。
- **E8-g（2026-08-18 訂正決定）**: 締日が月末以外のとき「月」と「請求期間」がずれる。第1段階は `Shime1=99`（末日）で一致するため
  正値になるが、締日を月末以外にした場合は**請求データ（締日ベース）を取引先との正**とし、月末一括計算の消費税との差は
  **手動の相殺データ（`Tran06Nyukin`/`Tran07Shiharai` の `Kubun=相殺`）で金額調整**する（自動の税再計算はしない、E8-f'）。
  実装上は締日=月末のときのみ月次税額をそのまま採用し、月末以外のときは**仮計算フラグ**として扱えるよう `SummaryUriSei` に
  記録するか、または「請求期間の月次税額を按分せず当月分を採用」する（第1段階は末日固定のため単純採用でよい）。

### 4.5 請求書番号（E10、2026-08-18 決定）

- `Renban` 既定1、`SeikyuNo = {Id_Tokui}-{DayTo:yyyyMMdd}-{Renban:00}`。得意先Id＋請求日＋連番2桁でユニーク。
- 再計算（再発行・差し替え）で同一得意先・同一請求日の行を作り直すときは `Renban` を＋1して新採番し、差し替えを識別できるようにする。

### 4.6 入金予定日（7.0）

`NyukinYoteiDay`＝`MasterTokui.PayMonth`/`PayDay` から算出（`PayMonth=0`＝当月、`PayDay=0/99`＝末日。E2'）。月別入金予定表の基準。

## 5. 支払計算ロジック（`SummaryDb.CalcSummaryKaiShi`）

請求計算の仕入先版。集計元は `Tran03Shiire`（仕入）/`Tran07Shiharai`（支払）。締日は `PayMonth`/`PayDay`（E2'：
`PayMonth=0`＝当月、`PayDay=0`＝末日扱い）。`ShiharaiYoteiDay` を算出。請求書番号は持たない（支払側は不要）。

## 6. E7 親子締日チェック（2026-08-18 決定）

請求計算の実行前に、対象得意先の `Shime1` と請求先（親、`Id_Paysaki`）の `Shime1` が食い違う得意先を検出する。
- 現状 `Id_Paysaki` 全件0のため検出0件。**不一致があれば警告**し、「マスタ変更および請求再計算が必要」である旨をメッセージ表示する（**ブロックはしない**）。

## 7. サーバ接続（新規 Msg、ストリーミング）

掛再更新（`Msg052/053`）・棚卸（`Msg054/055`）と同型。`CvFlag` に `Msg056_SummaryUriSei` / `Msg057_SummaryKaiShi` を追加し、
`QueryMsgStreamService` へ結線。パラメータは請求月・締日・得意先(仕入先)範囲を持つ新 `BillingParameter`。
`CalcSummaryUriSei` / `CalcSummaryKaiShi` を Serializable トランザクションでストリーミング実行する。

## 8. 画面（31Monthly）

- `BillingCalculation`（請求計算）: 締日（`MasterTokui.Shime1` の実データから動的リスト、判断材料 7.1）・請求月・得意先CD範囲・実行/キャンセル・進捗・
  親子締日チェックの警告表示。`BaseStocktakeViewModel` と同型のストリーミング実行（`Msg056`）。
- `PaymentCalculation`（支払計算）: 仕入先版（`Msg057`）。締日は `PayDay` の実データから。

## 9. Rebuild 対象への追加（E6）

在庫・掛再更新（`StockKakeUpdate`）に請求残・支払残の再作成も乗せられるよう、`CalcSummaryUriSei`/`CalcSummaryKaiShi` を
Rebuild 経路からも呼べるようにする（当面は請求計算画面から明示実行で足りる。段階実装）。

## 10. 受入確認（Given/When/Then）

- G/W/T-1: 締日=末日・請求月・得意先範囲で請求計算 → 対象得意先ごとに `SummaryUriSei` が1行でき、`DenDay=DayTo=月末`、
  内訳・消費税（外税四捨五入）・繰越・`SeikyuNo`（`{Id_Tokui}-{yyyyMMdd}-01`）が入る。
- G/W/T-2: 同条件で再実行 → 対象期間 DELETE→再作成で冪等。再発行時は `Renban` が＋1。
- G/W/T-3: 区分99の売上は `Other`（その他売上）へ分離され、`Uriage` には含まれない（E11）。
- G/W/T-4: 得意先と親の締日が異なる → 警告が出る（ブロックしない、E7）。
- G/W/T-5: 支払計算で `SummaryKaiShi` が仕入先ごとにでき、`PayMonth=0/PayDay=0` は当月末で `ShiharaiYoteiDay` が入る（E2'）。
- G/W/T-6: 掲題外の月末以外締日は第1段階では発生しない（`Shime1=99`）。発生時は仮計算＋相殺で調整（E8-g）。
