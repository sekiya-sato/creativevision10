# 請求計算・支払計算 詳細設計（2026-08-18）

対象HEAD: `85cb27a`（Rebuild 経路追加済み、月次掛集計ルール修正前）
対象: `SummaryUriSei`（請求残）/ `SummaryKaiShi`（支払残）の生成、請求計算 `BillingCalculation` / 支払計算 `PaymentCalculation` 画面
根拠: 判断材料 7章（決定済 E1〜E9・E8a〜g）、2026-08-18 ユーザー決定（E10 / E11 / E7 / E8-g）、
チェックリスト 4章の初版時点の課題（`SummaryUriSei` / `SummaryKaiShi` は「スキーマのみ・生成処理皆無」）。

## 1. 目的とスコープ

`SummaryUriSei` / `SummaryKaiShi` を生成する**請求計算・支払計算**を実装し、請求一覧表・支払一覧表・
月別入金/支払予定表・請求書印刷の元データを作る。**第1段階＝1得意先1締日**（`Shime1` のみ、
移行実データ全件 `Shime1=99`＝末日）を対象にする。入金・支払予定日は `PayMonth`/`PayDay` で決定する。

本設計の実装スコープ:
- スキーマ追加（請求書番号・入金/支払予定日）。
- 請求計算・支払計算ロジック（`SummaryDb`）と gRPC ストリーミング接続（既存の掛再更新と同型）。
- 請求計算 `BillingCalculation` / 支払計算 `PaymentCalculation` の実行画面（31Monthly、現状 L0）。

**スコープ外（別課題）**: 請求書印刷（帳票 qfm）、請求一覧表・支払一覧表の帳票実データ突合、月別入金/支払予定表、最大3締日（第2段階）、
締日マスタを変更する機能（J1＝1.0対象外）、親子請求の合算出力（親のみ／子含む）。ただし、Rebuild 実行時に締日マスタが変更済みであることを検出してブロックする安全策は本設計の対象とする。

## 2. 前提（既存資産）

- 掛月次集計 `SummaryDb.CalcSummaryUriKake(fromYYYYMM, toYYYYMM)` / `CalcSummaryKaiKake` が実装済みで、
  内訳（`Uriage`/`Henpin`/`Nebiki`/`Cash`/`Fee`/`Densai`/`Offset`/`Other`）と繰越 `Balance`・当月残を計算する。
  ストリーミングは `Msg052_SummaryUriKake` / `Msg053_SummaryKaiKake`（`StockKakeUpdate` 画面が呼ぶ）。
- スキーマ（`CvBase/BaseDbKake.cs`）:
  - `SummaryUriKake`（売掛月次）: `Id_Tokui`・`DenMonth`(yyyyMM)＋内訳＋`Balance`/`TotalIn`/`TotalSales`。
  - `SummaryUriSei`（請求残）: `Id_Tokui`・`DenDay`(請求日)・`DayFrom`・`DayTo`（請求期間）＋**掛と同じ内訳列**。
  - 買掛側 `SummaryKaiKake` / `SummaryKaiShi` は `Id_Shiire`・`TotalOut`/`TotalShiire` で同型。
- 締日: 得意先は `MasterTokui.Shime1`、仕入先は `MasterShiire.Shime1`（`EnumShime`、99=末日）を使用する。
  `PayMonth`/`PayDay` は締日ではなく、入金・支払予定日の算出にのみ使用する（`PayMonth=0`＝当月、`PayDay=0/99`＝末日）。
- 税率は 1.0 では `MasterSysMan` の `No=1` の `Tax` を使用する。丸めは四捨五入で統一する。1.1以降は `MasterShohin` の税率区分を使用する。

### 2.1 掛月次集計の確定ルール（次段階の修正対象）

`SummaryUriKake` / `SummaryKaiKake` は自社の締日を基準とする月次残高である。各行の内訳・合計列は対象年月分だけを保持し、`Balance` は対象年月以前からの累計残とする。請求残 `SummaryUriSei` / 支払残 `SummaryKaiShi` と同じ残高符号、すなわち売掛は `TotalIn − TotalSales`、買掛は `TotalOut − TotalShiire` を加算する。

#### 2.1.1 売上・仕入のSQL集計

- 金額の正値源は `Tran00Uriage.Total` / `Tran03Shiire.Total` とする。`KingakuTotal` は月次掛集計の金額集計に使用しない。
- `Uriage` / `Shiire` は `Kubun` 10〜19、40〜89の `Total` 正値合計、`Henpin` は20〜29の `Total` 正値合計、`Nebiki` は30〜39の `Total` 正値合計とする。3内訳には `CalcFlag` を使用しない。`Kubun=99` は3内訳のいずれにも含めない。
- `Tax` は、`Kubun` 20〜29だけ `Tax * CalcFlag`、その他区分は `Tax` をそのまま合計する。よって返品税だけが負値となる。
- SQLは取引側CTEで上記5列を `CASE WHEN` により集計し、月次CTEで `TotalSales = Uriage - Henpin - Nebiki + Tax`、`TotalShiire = Shiire - Henpin - Nebiki + Tax` を式で算出する。伝票の別総額列を同じ正値源として併用しない。

#### 2.1.2 入金・支払のSQL集計

- `Tran06Nyukin` / `Tran07Shiharai` は `Jmeisai` を `json_valid()` で防御して `json_each` 展開し、有効JSONの明細金額だけを集計する。ヘッダ `KingakuTotal` を `TotalIn` / `TotalOut` の別枝で集計しない。
- KINコード01 / 02 / 03 / 04 / 05を順に `Cash` / `Fee` / `Densai` / `Offset` / `Other` とする。05は正規のOtherである。
- **有効JSON内の明細**で `Id_Kin=0`、KINマスタ未登録、KINコード空、または01〜05以外のコードはOtherへフォールバックする。明細金額を欠落させず、常に `TotalIn = Cash + Fee + Densai + Offset + Other`、`TotalOut = Cash + Fee + Densai + Offset + Other` を保つためである。
- 不正JSONは `json_valid()` 防御で空配列として扱うため明細金額を復元できない。その伝票の `TotalIn` / `TotalOut` は0とし、Otherへ振り替えない。例外にせず処理を継続する一方、不正JSONの検知・補正は別途データ品質課題として扱う。

#### 2.1.3 残高・安全策

- `Balance` は売掛が前残＋対象月までの累計 `(TotalIn - TotalSales)`、買掛が前残＋対象月までの累計 `(TotalOut - TotalShiire)` とする。売上・仕入が入金・支払を上回る代表ケースでは負方向へ動く。
- `IsPay=1` の売上・仕入だけを対象にし、入金・支払の日付基準は `KakeDay` とする。過去月の再計算では、繰越整合のため既存の後続月延長規則を維持する。
- DELETE→再作成は `Serializable` トランザクションで行う。JSON不正値は空配列として扱い、SQLite例外を発生させない。

#### 2.1.4 現行実装との差と実装方針

現行 `CalcSummaryUriKake` / `CalcSummaryKaiKake` は `KingakuTotal` と `CalcFlag` を内訳に使用し、ヘッダ `KingakuTotal` を `TotalIn` / `TotalOut` の別集計としているため、本節の確定ルールを未反映である。次段階で両メソッドを対称に置換し、請求残・支払残と同じ残高符号へ統一する。金額結果を広範囲に変えるため、`handoff.md` 区分Cの高リスク作業とし、実装後に実装担当とは別の独立確認を必須とする。

## 4. 請求計算ロジック（`SummaryDb.CalcSummaryUriSei`）

旧CV.netの「締日ごとに回す月末処理」（判断材料 7.1）に倣う。パラメータは**締日・請求月・得意先範囲**。

### 4.1 対象と期間（E2/E3、決定済）

- 対象得意先 = `MasterTokui.Shime1 = 指定締日` かつ 得意先CD範囲内。
- 請求期間 `DayFrom`〜`DayTo`:
  - `DayTo`（請求終了日）＝請求月の締日（`Shime1=99` なら月末日）。
  - `DayFrom` ＝前回締日の翌日（前月締日＋1日）。
  - `DenDay`（請求日）＝`DayTo`（**請求日＝請求終了日＝締日**、決定 E3）。

### 4.2 再計算の単位（E5、決定済）

締日＋請求月＋得意先範囲で**対象期間を DELETE → 再作成**（掛集計と同じ）。冪等で「通常更新値＝Rebuild値」を保つ。

### 4.3 内訳・残高の集計

請求期間内（`Tran00Uriage.KakeDay` が `DayFrom`〜`DayTo`）の売上と、`Tran06Nyukin` の入金を得意先単位に集計する。金額列は税抜の `Total` を用い、`Uriage`/`Henpin`/`Nebiki` は `CalcFlag` を使用しない。

| 列 | 集計規則 |
|---|---|
| `Uriage` | `Tran00Uriage.Kubun` が 10〜19、40〜89 の `Total` 合計 |
| `Henpin` | `Tran00Uriage.Kubun` が 20〜29 の `Total` 合計 |
| `Nebiki` | `Tran00Uriage.Kubun` が 30〜39 の `Total` 合計 |
| `Tax` | `Tran00Uriage.Tax` の合計。区分20〜29は `CalcFlag` によりマイナスとして集計 |
| `Cash` / `Fee` / `Densai` / `Offset` / `Other` | 有効JSONの `Tran06Nyukin.JDetail.Code_Kin` が順に 01 / 02 / 03 / 04 / 05 の明細金額合計。`Id_Kin=0`、未知・未登録・空コードはOtherへフォールバック。不正JSONは空明細・0 |

- `TotalSales = Uriage − Henpin − Nebiki + Tax`。
- `TotalIn = Cash + Fee + Densai + Offset + Other`。
- `Balance` は対象期間以前の同得意先 `SummaryUriSei` の `(TotalIn − TotalSales)` 合計に、対象期間の `(TotalIn − TotalSales)` を加えた累計残とする。1レコードの内訳・合計値は対象期間分のみ保持する。

### 4.4 消費税

- `Tax` は対象取引の `Tax` を集計する。返品（区分20〜29）は `CalcFlag` を用いて負値とする。
- 1.0で新たに税額を算出する必要がある場合は、`MasterSysMan` の `No=1` の `Tax` を税率に用い、外税・四捨五入で統一する。1.1以降は `MasterShohin` の税率区分を使用する。

### 4.5 請求書番号（E10、2026-08-18 決定）

- `Renban` 既定1、`SeikyuNo = {Id_Tokui}-{DayTo:yyyyMMdd}-{Renban:00}`。得意先Id＋請求日＋連番2桁でユニーク。
- 通常の再計算と Rebuild は既存の `Renban` / `SeikyuNo` を維持して DELETE→再作成し、冪等にする。明示的な再発行・差し替え時のみ `Renban` を＋1して新採番する。

### 4.6 入金予定日（7.0）

`NyukinYoteiDay`＝`MasterTokui.PayMonth`/`PayDay` から算出（`PayMonth=0`＝当月、`PayDay=0/99`＝末日。E2'）。月別入金予定表の基準。

## 5. 支払計算ロジック（`SummaryDb.CalcSummaryKaiShi`）

請求計算の仕入先版。集計元は `Tran03Shiire`（仕入）/`Tran07Shiharai`（支払）、締日は `MasterShiire.Shime1` を使用する。`PayMonth`/`PayDay` から `ShiharaiYoteiDay` を算出する。請求書番号は持たない（支払側は不要）。

支払期間内の `Tran03Shiire` / `Tran07Shiharai` を仕入先単位に集計する。`Shiire` は `Kubun` 10〜19・40〜89、`Henpin` は20〜29、`Nebiki` は30〜39の各 `Total` 合計（いずれも `CalcFlag` は使用しない）とする。`Tax` は取引の `Tax` を集計し、20〜29は `CalcFlag` により負値とする。`Cash` / `Fee` / `Densai` / `Offset` / `Other` は有効JSONの `Tran07Shiharai.JDetail.Code_Kin` の01 / 02 / 03 / 04 / 05を順に明細金額で集計し、`Id_Kin=0`、未知・未登録・空コードはOtherへフォールバックする。不正JSONは空明細として `TotalOut=0` とする。

- `TotalShiire = Shiire − Henpin − Nebiki + Tax`。
- `TotalOut = Cash + Fee + Densai + Offset + Other`。
- `Balance` は対象期間以前の同仕入先 `SummaryKaiShi` の `(TotalOut − TotalShiire)` 合計に、対象期間の `(TotalOut − TotalShiire)` を加えた累計残とする。1レコードの内訳・合計値は対象期間分のみ保持する。

## 9. Rebuild 対象への追加・締日変更ブロック（E6）

在庫・掛再更新（`StockKakeUpdate`）は、対象が「全て」「売掛のみ」「買掛のみ」のとき、該当側の掛再集計後に `CalcSummaryUriSei` / `CalcSummaryKaiShi` をRebuild経路から呼ぶ。請求残・支払残は対象年月×マスタに実在する有効締日（1〜31、99=末日）で `BillingParameter(IsReissue=false)` を順次実行し、得意先／仕入先範囲は空（全件）とする。

### 9.1 締日変更の事前検出

- `ExecuteAsync` は利用者の確認後、**要求列を作成する前**に検査する。「全て」は売掛・買掛両方、「売掛のみ」は売掛だけ、「買掛のみ」は買掛だけを対象にする。「在庫のみ」は検査・請求残/支払残Rebuildの対象外である。
- 売掛は `SummaryUriSei` と `MasterTokui`、買掛は `SummaryKaiShi` と `MasterShiire` を `Id_Tokui` / `Id_Shiire` で結合し、**請求日／支払日である `DenDay`** の年月が選択範囲内の既存残高行を照会する。通常生成では `DenDay=DayTo=締日` であり、選択月の識別に `DenDay` を使うことで、空・不正な `DayTo` も検査から脱落させない。照会SQLは固定テーブル名・固定列名だけを組み立て、開始年月・終了年月は `QueryListSqlParam` のパラメータ配列で `Msg101_Op_Query` に渡す。ユーザー入力をSQL文字列へ直結しない。
- 照会結果は取引先コード、保存済み `DayTo`、現在の `Shime1` を返す。ViewModel側で `DayTo` の年月と現在締日から期待締日を算出する。`DayTo` がNULL・空・8桁以外・不正年月の場合も不一致とする。1〜31は当月日数で丸め、99は当月末日とし、期待締日と保存済み `DayTo` が異なる行を不一致とする。
- 取引先ごとに保存行が複数ある場合はすべて判定し、不一致が1件でもあれば当該実行をブロックする。ブロック時は在庫・売掛・買掛を含むバッチの `Msg051`〜`Msg057` を一件も送信しない。
- 警告は売掛/買掛、取引先コード、保存締日、現在締日（`01日`〜`31日`または`末日`）を最大5件と残件数で示し、次の案内を必ず含める。`マスタ締日が変更されています。請求計算／支払計算画面で対象を手動再計算し、旧締日の残データを確認してから再実行してください`
- 選択期間に既存 `SummaryUriSei` / `SummaryKaiShi` 行が無い場合は、締日変更履歴を証明できないためブロックしない。この検出限界を画面説明・テスト記録に残す。

### 9.2 Rebuildの実行順と不変条件

- 締日変更検査を通過後に要求列を作り、在庫（対象時）、売掛、買掛、請求残、支払残の順に既存ストリーミングを直列実行する。売掛のみ／買掛のみでは該当側だけを実行する。
- 要求列は共有Plannerが `CvFlag`、対象年月範囲、対象月、締日まで展開済みの順序付き記述子として作る。WPFは各記述子を表示名・`CvMsg`・パラメータへ一対一に変換するだけとし、対象別の分岐または回数展開を独自に持たない。マスタに有効締日が0件でも、売掛・買掛の記述子は残し、該当する請求残・支払残の記述子だけを0件とする。
- 締日照会、不一致判定、記述子生成、要求変換、ストリーム送信は共通の非同期送信境界でこの順に実行する。送信は同境界のコールバックだけから行い、不一致、照会例外、照会取消ではコールバックを0回とする。正常時はPlanner記述子と同じ順序・件数で送信する。
- Rebuildは常に `IsReissue=false` とし、既存の `SeikyuNo` / `Renban` を変更しない。請求残・支払残のDELETEは既存の締日・年月・全件範囲に限定し、選択範囲外を破壊しない。
