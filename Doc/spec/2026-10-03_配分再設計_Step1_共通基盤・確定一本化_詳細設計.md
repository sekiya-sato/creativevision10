## 1. 目的と範囲

## 2. 状態と不変条件（Step 1 以降）

| 状態 | 条件 | 引当 |
|---|---|---|
| 未確定 | `EndFlag = 0` | `Kubun <> 0` の行の数量を引当に含める（現行と同じ） |
| 完了 | `EndFlag = 1` | 含めない |

**不変条件**

1. 完了した行は `Su = JitsuSu + ShortSu` を満たし、`KakuteiDay` に確定日が入っている。
2. `JitsuSu > 0` の行は、`RelateNo2` に生成伝票の Id が入っている。全量欠品の行（`JitsuSu = 0`）は `RelateNo2 = 0`。
3. 修正（洗い替えでの削除）ができるのは `SendFlg = 0 AND EndFlag = 0 AND ifnull(KakuteiDay,'') = ''` の行だけ。この条件はサーバ側で判定する。
4. 確定は全件成功か全件失敗のどちらか。在庫割れ・競合・状態不一致が 1 件でもあれば、何も書き込まない。
5. 引当数は、キー単位の引き直し（`CalcHaibun2Reserve`）と全件の作り直し（`CalcReserveQtyAll`）で一致する（現行と同じ）。

**移行時の扱い**

- 旧状態「確定済み・未出荷」（`KakuteiDay <> '' AND EndFlag = 0`）の行は、未確定と同じく確定画面に表示し、確定できるようにする。確定時に `KakuteiDay` は上書きする。DB の移行処理は行わない。
- この行は不変条件 3 により洗い替えでは削除できない。消したい場合は確定数 0 で完了させる。

### 3.1 `TranHaibun` への定数追加（CvBase、`BaseDbHaibun.cs`）

クライアント（層 1 しか参照できない）とサーバが同じ条件を使うため、SQL 片の定数は CvBase に置く。

```csharp
/// <summary>修正（洗い替え削除）できる行の条件。エイリアスなしの列名で書く</summary>
public const string EditableWhereSql = "SendFlg = 0 AND EndFlag = 0 AND ifnull(KakuteiDay,'') = ''";
```

### 3.2 `AllocationRules`（CvDomainLogic、新規 `AllocationRules.cs`）

DB に依存しない static クラス。単体テストの主な対象。

| メンバ | 内容 |
|---|---|
| `bool IsEditable(TranHaibun row)` | 3.1 の条件を C# で判定する |
| `bool IsCreatableKubun(int kubun)` | 新規作成できる区分は 0 / 1 / 2 / 6。3 / 4 / 5 / 7 は作成できない（D2） |
| `bool IsCommittableKubun(int kubun)` | Step 1 で確定できる区分は 0 / 1 / 2。6 は Step 5 で追加する |
| `string? ValidateNewRow(TranHaibun row)` | 新しい行の検査。`Su > 0`、`Id_Soko` / `Id_Tenpo` / `Id_Shohin > 0`、区分が作成可能、の 3 点。違反があればメッセージを返す |
| `void NormalizeNewRow(TranHaibun row)` | 状態列を初期値にそろえる：`Id=0, KakuteiDay='', EndFlag=0, JitsuSu=0, ShortSu=0, RelateNo2=0, SendFlg=0` |
| `int ClampCommitSu(int requested, int su)` | 確定数を 0〜`Su` に収める |
| `IReadOnlyList<ShippingConfirmError> FindShortages(IEnumerable<CommitStockInput> inputs)` | 確定時の在庫検査（3.3） |

`CommitStockInput` は倉庫＋SKU 単位に集計した入力で、次の値を持つ。

| 値 | 意味 |
|---|---|
| `RealSu` | 実在庫（`SummaryRealStock.Su`。行がなければ 0） |
| `ReserveQty` | 引当数（`SummaryRealStock.ReserveQty`。行がなければ 0） |
| `OwnReserved` | 確定対象の行がすでに引当に含めている数量 |
| `CommitSu` | 今回の確定数の合計 |

### 3.3 確定時の在庫検査式

```
確定対象以外の引当 = ReserveQty − OwnReserved
有効在庫(確定前)   = RealSu − 確定対象以外の引当
割れ               = CommitSu > 0 かつ 有効在庫(確定前) − CommitSu < 0
```

- `OwnReserved` は、確定対象のうち `Kubun <> 0` の行の「未確定なら `Su`、確定済み（旧状態）なら `JitsuSu`」の合計。引当数に積んでいる数量（`SummaryDb.ReserveQtyExpr`）と同じ式にする。
- 現行の式（`RealSu − ReserveQty < 0`）との違いは 2 つ。
  - **区分 0（仕入配分）**: 引当に含まれていないので、現行では自分の数量が検査から漏れていた（P6）。新しい式では `CommitSu` として必ず差し引く。
  - **確定数 < 指示数**: 欠品になる数量は在庫を使わないので、検査から外す。
- 全量欠品（`CommitSu = 0`）の SKU は検査しない。在庫がなくても欠品完了にはできる。
- エラーで返す `ShippingConfirmError` の値は、`Shiji = CommitSu`、`Yuko = 有効在庫(確定前)`。

## 4. API

### 4.1 パラメータ（CvBase、`Parameters.cs`）

```csharp
/// 配分の洗い替え保存。ReplaceRows を削除して NewRows を登録し、引当を引き直すまでを1トランザクションで行う。
public sealed record HaibunSaveParam(DeleteBulkRow[] ReplaceRows, TranHaibun[] NewRows);
public sealed record HaibunSaveResult(int DeletedCount, int InsertedCount);

/// 配分確定。確定数を反映し、出荷売上／移動伝票を作成して完了にする（D8）。
public sealed record HaibunCommitParam(HaibunCommitRow[] Rows, string DenDay, long IdShain);
/// 確定数は 0〜Su にサーバ側で収める。0 は全量欠品（伝票なしで完了）。
public sealed record HaibunCommitRow(long Id, long ExpectedVdu, int KakuteiSu);
public sealed record HaibunCommitResult(long[] CreatedSlipIds, int CommittedCount, int ShortageRowCount);
```

- 削除するもの: `ShippingConfirmParam` / `ShippingCancelParam` / `ShippingCreateParam` / `ShippingCreateRow` / `ShippingConfirmResult` / `ShippingCancelResult` / `ShippingCreateResult`
- 残すもの: `ShippingShortageDto`、`CvMsgErrorCode.ShippingUnavailable`（コメントを「配分確定で…」に直す）

### 4.2 保存 `HandleHaibunSave`（CvServer、`HandlerClass.cs`）

既存の `HandleBulkDelete` / `HandleBulkInsert` と同じ部品（`Effects.Before` / `After`、`FlushReserve`、`SetCreatedAuditValues`）を使い、1 つのトランザクションにまとめる。

1. `NewRows` の各行に `AllocationRules.ValidateNewRow` を実行する。
   - 違反があれば `InvalidParameter` を返す（トランザクションを始める前に判定する）。
2. `BeginTransaction(Serializable)` を開始する。
3. `ReplaceRows` の全行を先に検証する。
   - 行がない、または `Vdu` が一致しない → `ConcurrentUpdate`。
   - `AllocationRules.IsEditable` が false → `InvalidParameter`（「確定済みまたは送信済みの配分は変更できません」）。
   - どちらの場合もロールバックし、何も書き込まない。
4. `ReplaceRows` を削除する（`Effects.After(Delete…, reserveKeys)`）。
5. `NewRows` に `NormalizeNewRow` と `SetCreatedAuditValues` を適用して登録する（`Effects.After(Insert…, reserveKeys)`）。
6. `FlushReserve(reserveKeys)` で引当を引き直してから、コミットする。
7. `HaibunSaveResult` を返す。

### 4.3 確定 `HandleHaibunCommit` と `ShippingDb.Commit`

`HandlerClass` は現行の `HandleShippingCreate` と同じ形にする。

- `Serializable` トランザクションを使う。
- 競合なら `ConcurrentUpdate`、在庫割れなら `ShippingUnavailable` と `ShippingShortageDto[]`、区分・入力の違反なら `InvalidParameter` を返す。どの場合もロールバックする。

`ShippingDb.Commit(rows, denDay, idShain, out CommitOutcome outcome)` の手順:

1. `Id > 0` の行を `Id` で重複除去する。0 件なら何もしない。`denDay` が空なら `InvalidParameter`。
2. `EndFlag = 0` の対象行を `Id IN (...)` で取得する（`KakuteiDay` の値は問わない。移行時の扱いのため）。
3. **全行を先に検証する**。
   - 行がない、または `Vdu` が一致しない → 競合。
   - `IsCommittableKubun` が false → `InvalidParameter`。
   - 1 件でも該当すれば何も書き込まずに返す。
4. 確定数を `ClampCommitSu` で収め、倉庫＋SKU 単位に `CommitStockInput` を作る。
   - `SummaryRealStock` は対象キーだけを読む。
   - `FindShortages` で割れがあれば、何も書き込まずに返す。
5. 各行を更新する：`KakuteiDay = denDay, JitsuSu = 確定数, ShortSu = Su − 確定数, Vdu = now`。
6. 既存の `CreateShippingSlips(ids, denDay, idShain)` を呼ぶ。
   - 伝票の作成、在庫の計上、`EndFlag = 1`、`RelateNo2` の設定、引当の引き直しは、現行のロジックをそのまま使う。
7. `HaibunCommitResult` を返す。
   - `CreatedSlipIds`: 作成した伝票の Id
   - `CommittedCount`: 対象の行数
   - `ShortageRowCount`: `ShortSu > 0` の行数

削除するメソッド: `ConfirmShipping` / `CancelConfirm` / `ProcessShipping`。`CreateShippingSlips` は `private` にしない。既存のテストが直接呼んでいるため。

**確定日**: 確定日と伝票日は同じ日付 `DenDay` にする（画面の入力は 1 つ。既定は本日）。

**伝票の訂正（D9）**: 確定取消は設けない。訂正は、作成した `Tran00Uriage` / `Tran10IdoOut` を通常の伝票画面で直す。配分は完了のまま残す。

### 4.4 クライアント共通（`CoreServiceClient.cs`）

```csharp
internal static Task<HaibunSaveResult> SaveHaibunAsync(IEnumerable<TranHaibun> replaceRows, IEnumerable<TranHaibun> newRows, string label, CancellationToken ct)
```

- `DeleteBulkAsync` と同じく、失敗は例外にして呼び出し元に再取得させる。
- `InvalidParameter` のときは、サーバのメッセージをそのまま例外メッセージにする。

### 5.2 配分確定（旧：出荷指示確定(商品) / (得意先)）（S5）

対象は `BaseShippingConfirmViewModel`、`ShippingConfirmShohinView` / `ShippingConfirmTokuiView`。クラス名は Step 6 の統合時に変える。

- **抽出条件**
  - `h.EndFlag = 0 AND h.Kubun <> 6`。取置は自分の画面で扱う。
  - 表示切替（「未確定のみ / 確定済みも表示」）は削除する。旧状態の行も未確定と同じに表示する。
- **一覧の行（`ShippingConfirmRow`）**
  - `KakuteiSu` を追加する。入力でき、既定は `Su`、0〜`Su` に収める。
  - `ShortSu = Su − KakuteiSu` を追加する（表示のみ）。
  - `IsConfirmed` / `StatusDisplay` は削除する。
- **確定コマンド**
  - チェックした行を `HaibunCommitParam(Id, Vdu, KakuteiSu)` で送る。
  - 確認メッセージには、件数、伝票を作る行数、欠品になる行数を出す。
  - `ShippingUnavailable` が返ったら、現行どおり割れた SKU の一覧を出す。
  - `ConcurrentUpdate` が返ったら「再検索してください」と出す。
- 取消コマンドと取消ボタンは削除する。
- 日付の入力欄の見出しを「確定日（伝票日）」にする。
- **一括操作**: 「確定数を指示数に戻す」と「確定数を 0 にする」を追加する（チェックした行が対象）。
- **メニュー表示（2 か所）**: 「配分確定(商品)」「配分確定(得意先)」。addInfo は「確定数を入力し出荷売上/移動伝票を作成(引当解除)。有効在庫割れはエラー」。
