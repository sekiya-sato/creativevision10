# 請求台帳（発行控え）帳票 詳細設計

作成日: 2026-08-19
対象HEAD: `7f6ab56`
関連: [完成度チェックリスト §4.1 段階7 / §3.11](2026-08-18_CV10機能完成度チェックリスト.md)、[PrintStream qfm フォーマット仕様](PrintStream_qfmフォーマット仕様.md)、`author-printstream-qfm` skill

## 1. 目的と背景

### 1.1 選定理由（qfm スキル検証タスクとして）

完成度チェックリスト §4.1 段階7・§3.11 の P0 Release Gate は「請求計算が生成した `SummaryUriSei` を帳票と数値突合する」ことである。

調査の結果、請求・支払の主要 6 帳票（請求一覧表・請求書印刷・売掛金管理表・月別入金予定表ほか）は qfm・SQL・画面・メニューが**すべて実装済み**だった。しかし請求計算が `SummaryUriSei` に保存する次の確定値を**どの帳票も出力していない**（`CvWpfclient` 全体で参照ゼロ）:

- `SeikyuNo`（請求書番号 = 得意先Id-請求日-連番）
- `Renban`（再発行・差し替え世代）
- `NyukinYoteiDay`（締め時点で確定した入金予定日。列に保存済み）

既存「請求一覧表」(`SeikyuListReport.qfm`) は金額中心で、上記の発行情報を持たない。現行「月別入金予定表」は `MasterTokui` の回収条件から予定日をライブ再計算しており、保存済み `NyukinYoteiDay` とは別物である。

したがって「請求計算の確定結果（請求書番号・再発行世代・保存済み入金予定日）を突合・確認する帳票」が欠落している。これを埋める新帳票 **請求台帳（発行控え）** を作る。

- データ源（`SummaryUriSei`）は実装済み。
- D-04（親子請求出力）・D-05（適格請求書要件）に**ブロックされない**。本帳票は顧客提出用の請求書ではなく、社内の発行確認・突合用の管理一覧のため。
- qfm を新規作成し、実 PDF まで通すことで `author-printstream-qfm` スキルと qfm フォーマット仕様を実地検証する。

### 1.2 既存帳票との棲み分け

| 帳票 | 用途 | 発行情報(SeikyuNo/Renban/予定日) |
|---|---|---|
| 請求一覧表 (既存) | 請求日単位の金額一覧 | 出力しない |
| 請求書印刷 (既存) | 得意先1件ごとの請求書（顧客提出、単票） | D-04/D-05 待ち |
| **請求台帳（発行控え）(新設)** | 請求計算の確定結果の突合・発行控え（一覧） | **出力する** |

## 2. 仕様

### 2.1 データ源

`SummaryUriSei u` JOIN `MasterTokui t ON t.Id = u.Id_Tokui`（既存 `SeikyuListReport` と同一の結合）。

### 2.2 出力列（qfm item1..item10、SELECT 列順と一致）

| # | item | 見出し | ソース | 型/整形 |
|---:|---|---|---|---|
| 1 | item1 | 請求書番号 | `u.SeikyuNo` | 文字列 |
| 2 | item2 | 請求日 | `DateLabel(u.DenDay)` | yyyy/MM/dd |
| 3 | item3 | 得意先CD | `t.Code` | 文字列 |
| 4 | item4 | 得意先名 | `t.Name` | 文字列 |
| 5 | item5 | 対象期間 | `DateLabel(u.DayFrom)‖'～'‖DateLabel(u.DayTo)` | 文字列 |
| 6 | item6 | 売上額 | `u.TotalSales` | 整数（右詰） |
| 7 | item7 | 消費税 | `u.Tax` | 整数（右詰） |
| 8 | item8 | 残高 | `u.Balance` | 整数（右詰） |
| 9 | item9 | 入金予定日 | `DateLabel(u.NyukinYoteiDay)` | yyyy/MM/dd（空欄可） |
| 10 | item10 | 再発行 | `u.Renban` | 整数（右詰） |

金額列の `decode` は既存 `SeikyuListReport.qfm` と同じく `datatype="string"`（SQL は生の整数を返す）を踏襲する。突合用途では DB 値そのままの方が比較しやすく、姉妹帳票との一貫性も保てるため、カンマ整形は入れない（qfm フォーマット仕様 §5.2 のカンマ書式は将来の改善余地として残す）。

### 2.3 入力パラメータ（画面）

`SeikyuListReport` と同一の UI:

- 請求日 From / To（`yyyy/MM/dd`、既定 = 当月1日〜今日）
- 得意先 From / To（コード範囲、検索ダイアログ付き、空欄可）
- 出力対象: 「請求額･残高があるのみ」(既定) / 「全て」

検証:
- 日付書式不正 → 警告して中止（`TryParseDate`）。
- From > To → 「請求日の範囲が逆転しています。」警告して中止。

### 2.4 SQL（列順 = item 順）

```sql
SELECT
    u.SeikyuNo AS seikyuNo,
    {DateLabel("u.DenDay")}   AS seikyuDayLabel,
    t.Code AS tokuiCode,
    t.Name AS tokuiName,
    {DateLabel("u.DayFrom")} || '～' || {DateLabel("u.DayTo")} AS termLabel,
    u.TotalSales AS totalSales,
    u.Tax        AS tax,
    u.Balance    AS balance,
    {DateLabel("u.NyukinYoteiDay")} AS nyukinYoteiLabel,
    u.Renban     AS renban
FROM SummaryUriSei u
JOIN MasterTokui t ON t.Id = u.Id_Tokui
WHERE u.DenDay >= @from AND u.DenDay <= @to
  {activeOnly}{tokuiWhere}
ORDER BY u.DenDay, t.Code, u.SeikyuNo
```

- `@from` / `@to` = 請求日範囲（`yyyyMMdd`）。`AddSqlParameter` で採番。
- `activeOnly` = `IsActiveOnly` のとき `AND (u.TotalSales != 0 OR u.Balance != 0)`。
- `tokuiWhere` = `BuildCodeRangeWhere(params, "t.Code", from, to)`。

## 5. 受入条件

- G/W/T-1: 請求日範囲・得意先範囲・出力対象を指定 → `SummaryUriSei` の対象行が請求書番号・請求日・得意先・対象期間・売上・消費税・残高・入金予定日・再発行世代の順で印字される。
- G/W/T-2: `NyukinYoteiDay` が空の行 → 入金予定日欄は空欄で他列は正常。
- G/W/T-3: 請求計算未実行の期間 → 0 行（空帳票）。
- G/W/T-4: From > To → 警告して印刷しない。
- G/W/T-5: 実 PDF が例外なく生成され、10 列が桁溢れせず収まる。

## 6. 非対象・リスク

- 顧客提出用の請求書様式（親子・適格要件）は D-04/D-05 決定後の「請求書印刷」で扱う。本帳票は社内突合・発行控え。
- 実 DB での数値突合・Mini-UAT は P1（本設計では合成データでの描画確認まで）。
- 金額のカンマ整形は将来改善（qfm 仕様 §5.2）。
