## 1. 目的

`CvServer.Services.PointOfSaleService` が作成する店舗売上伝票（`Tran01Tenuri`）へ、
既存の共通消費税計算を適用する。

現行の `CreateSale` は明細金額合計をそのまま `Total` に設定しており、次の税関連項目を設定していない。

- 明細: `Id_Tax` / `TaxRate` / `Tax`
- ヘッダ: `TaxRounding` / `TaxableAmount1/2/3` / `Tax1/2/3`

そのため、POS経由の売上は内税運用ではなく、消費税計算が未実装の状態である。
本設計では、WPF店舗売上入力（`ShopUriageInputViewModel`）と同じく
`TaxCalculator.Apply` を使用し、POS確定時点で税額と税込総合計を確定する。

前提となる税計算仕様は
`Doc/spec/2026-09-01_消費税計算単位・端数処理_全体設計.md` の3.1〜3.7を正とする。
本書は同設計9章の残課題R4を解消するための詳細設計であり、共通税計算仕様そのものは変更しない。

## 4. 現状分析

### 4.1 POS売上確定

現行 `CreateSale` は、サーバで商品と適用上代を引き直して明細を作成する一方、税計算を行っていない。

```text
明細作成
  Kingaku = Quantity * 適用上代
  Id_Tax / TaxRate / Tax = 未設定（0）

ヘッダ作成
  KingakuTotal = 明細Kingaku合計
  TaxableAmount1/2/3 = 0
  Tax1/2/3 = 0
  Total = KingakuTotal
```

決済検証も `KingakuTotal` 相当の `total` と受領金額を比較しているため、
修正前は消費税分が不足していても売上を確定できる。

### 4.2 POS取消

`CancelSaleAsync` は元売上から明細・金額・決済内訳を複写するが、
`TaxRounding` / `TaxableAmount1/2/3` / `Tax1/2/3` を複写していない。
元売上に正しい税額があっても、取消伝票の税内訳は0になる。

取消は元売上の完全な反対伝票であるため、取消時点の税マスタで再計算してはならない。
元売上確定時の明細税区分・適用税率・税額とヘッダ税内訳をそのまま継承する必要がある。

### 4.3 冪等応答

`CheckoutAsync` は `PosClientSaleId` が既存の場合、保存済み伝票を返す。
この経路は保存済みの `Total` と `JposPayment.ChangeAmount` を返す現在の動作を維持する。
旧版で作られた税未設定伝票を重複要求時に再計算すると、初回応答と金額が変わって冪等性を壊すため、
重複要求を契機とした補正は行わない。

## 5. POS売上・返品の処理設計

### 5.1 処理順序

`CreateSale` の処理順序を次のようにする。

1. 店舗、倉庫、担当者をサーバで取得する
2. サーバ日付から `DenDay`（`yyyyMMdd`）を1回だけ確定する
3. 各商品を取得し、店舗・日付に対応する適用上代で明細を作る
4. 各明細の `Id_Tax` に `MasterShohin.Id_Tax` を設定する
5. `MasterSysman` を取得し、`TaxRateResolver.CreateRateResolver(sysman, denDay)` を作る
6. 店舗の `TaxRounding` と伝票単位を指定して `TaxCalculator.Apply` を実行する
7. 明細税率・明細税額、ヘッダ課税対象額・ヘッダ税額・税込総合計を伝票へ設定する
8. 受領金額と税込総合計を比較する
9. 決済内訳の釣銭を `受領金額 - 税込総合計` で保存する

### 5.2 明細作成

`CreateLine` で取得済みの `MasterShohin` から、次を追加設定する。

| 項目 | 設定値 |
|------|--------|
| `Id_Tax` | `product.Id_Tax` |
| `TaxRate` | `TaxCalculator.Apply` が伝票日と税区分から設定 |
| `Tax` | `TaxCalculator.Apply` が税区分別税額を明細へ按分して設定 |

商品は `FindRequired<MasterShohin>` で取得必須であるため、商品が引けない場合の税区分フォールバックは不要である。
`MasterShohin.Id_Tax = 0` は非課税として維持する。

### 5.3 ヘッダ計算

```csharp
var rounding = (EnumRounding)store.TaxRounding;
var rateOf = TaxRateResolver.CreateRateResolver(sysman, denDay);
var totals = TaxCalculator.Apply(lines, rateOf, EnumTaxCalcUnit.Slip, rounding);
```

計算結果を次のように設定する。

| ヘッダ項目 | 設定値 |
|------------|--------|
| `TaxRounding` | `store.TaxRounding` |
| `TaxableAmount1/2/3` | `totals.TaxableAmount1/2/3` |
| `Tax1/2/3` | `totals.Tax1/2/3` |
| `KingakuTotal` | 明細 `Kingaku` 合計 |
| `Total` | `Math.Abs(KingakuTotal) + totals.TaxTotal` |

`Tran01Tenuri` は `TaxCalcUnit` 列を持たず、常に伝票単位である。
税区分ごとに1回だけ端数処理し、その税額を同じ税区分の明細へ按分する既存仕様を変更しない。

### 5.4 税率・端数処理の取得失敗

- `MasterSysman` が存在しない場合は、他の税計算経路と同様に空の `MasterSysman` を使用し、
  `TaxRateResolver` の既定税率解決へ委ねる
- 店舗は `FindRequired<MasterTokui>` で必須取得済みであるため、端数処理は店舗の `TaxRounding` を使う
- `TaxRounding` の値域は既存マスタ保守と `EnumRounding` の前提を維持し、POS固有の補正は追加しない

### 5.5 決済照合

受領金額は次の既存式を維持する。

```text
paid = CashAmount + CardAmount + OtherAmount
```

比較対象だけを税抜合計から税込総合計へ変更する。

```text
paid < Total（税込） なら確定を拒否
ChangeAmount = paid - Total（税込）
```

売上・返品とも、現在のAPIは金種を0以上の正値で受け取る契約である。
返品時の金種を「返金方法・返金額」として正値で送る既存方式は変更せず、
R4では比較対象へ税額を含めることだけを行う。

完全一致を必須にせず `paid >= Total` を維持する。現金売上では預り金と釣銭があるためである。

### 5.6 応答

`PosCheckoutResponse` の項目追加は行わない。

| 応答項目 | 修正後の意味 |
|----------|--------------|
| `TotalAmount` | 税込総合計（`Tran01Tenuri.Total`） |
| `ChangeAmount` | 受領金額から税込総合計を引いた釣銭・差額 |

この意味は初回確定と同一 `ClientSaleId` の冪等応答で一致する。

## 6. POS取消の処理設計

`CancelSaleAsync` が作成する `cancelSale` へ、元売上から次を追加複写する。

- `TaxRounding`
- `TaxableAmount1/2/3`
- `Tax1/2/3`

`Jmeisai` は元売上の保存済みJSONに含まれる `Id_Tax` / `TaxRate` / `Tax` を継承する。
取消時に商品マスタ・税率マスタ・店舗端数処理を引き直さない。

取消伝票の `TaxableAmount1/2/3` と `Tax1/2/3` は元伝票と同じ正値、
`Total` も元伝票と同額とする。返品方向の符号は `Kubun = 20` により、
在庫・売上集計側の `CalcFlag` が反転させる既存規約に従う。

元売上が旧版で作成され税関連項目が0の場合、取消だけを現在マスタで再計算しない。
元売上と取消の対称性を優先し、必要なら元売上を含めて「伝票税額再更新」の対象とする。

## 7. データ・公開APIへの影響

### 7.1 DBスキーマ

変更なし。必要な列は `Tran01Tenuri` と `Tran99Meisai` に既に存在する。

### 7.2 gRPC契約

変更なし。`CodeShare/IPointOfSaleService.cs` の `DataMember(Order)` に変更はない。

ただし既存POSクライアントには、次の意味変更を周知する。

- `Payment` の合計は税抜商品合計ではなく税込総合計以上であること
- `PosCheckoutResponse.TotalAmount` は税込総合計になること
- `ChangeAmount` は税込総合計を基準に計算されること

これはDTO形状の互換性は維持するが、金額の業務意味が変わるため、POSクライアント側では
税込金額を前提に対応する必要がある。実POS端末との結合テストはPOS側プロジェクトの責務とし、
cv10のR4完了条件には含めない。

### 7.3 既存データ

自動更新しない。
既存POS伝票の税項目を補正する必要がある環境では、導入手順として次を実施する。

1. 対象件数と差額を事前確認する
2. 「システム > その他処理 > 伝票税額再更新」を実行する
3. `Tran01Tenuri` の更新件数、税額差額、課税対象額設定件数を確認する

「伝票税額再更新」は期首日以降の6伝票種別を対象とする大規模更新であるため、
POSだけを補正する目的で無確認実行しない。
