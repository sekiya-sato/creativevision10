## 4. 発注・受注残の完了（Phase 2〜3 / Decision 7-8）

### 4.1 旧CV.netの業務機能

`業務フロー/02_受注・発注`、`帳票集PDF〔０３〕発注`、`〔０５〕受注` より。

- 受注・発注とも完了状態で残を管理し、**完納・全量配分した時点で自動的に「未完了→完了」へ切り替わる**。
  発注入力の説明に「完納されると未完了から完了に切り替わります」、受注に「受注分、全てを受注配分した時点で『完了』となります」。
- **受注残完了設定 / 発注残完了設定**は、その自動判定に対する**手動の一括上書き**である。
- 完了の効果は2つ。①受注残管理表の「残のみ」出力に現れない ②受注配分入力で検索されない。
- 旧は完了を**伝票明細の行単位**で管理していた（受注データの明細ごとの残管理の完了FLG）。
- 発注残・受注残の各帳票に **表示区分「残のみ / 全て」** がある。

#### 4.1.1 帳票が定義する残の算式（一次根拠）

**発注残管理表**（〔０３〕発注）

| 項目 | 定義 |
| --- | --- |
| 発注数 | 発注データの数量 |
| 納品数 | **仕入データの数量**。※ **発注伝票NOとの紐付けが必要** |
| 残数 | 発注数 − 納品数 |
| 残金額 | 発注金額 − 納品金額 |
| 納期予定 | **発注データの納品日** |

**受注残管理表**（〔０５〕受注）

| 項目 | 定義 |
| --- | --- |
| 受注数 | 商品色サイズごとの受注数 |
| 納品数 | 指定条件の受注データと紐づいた**出荷売上数量**。※ 出荷売上データの**受注Noに受注伝票Noが登録されていないものは対象外**。※ 出荷売上データは**出荷日の指定範囲内の数量のみ**を対象 |
| 残数 | 受注数 − 納品数 |
| 残金額 | 受注金額 − 納品金額 |
| 納期予定 | **受注データの納品日** |

別途「商品ごとに受注数・納品済数・受注残数を集計する簡易的な受注残管理表」もあり、そちらも `受注残数 = 受注数 − 納品済数` である。

#### 4.2.1 G0（伝票単位化）に伴う派生論点（決定済 2026-08-17）

| # | 派生論点 | 決定 |
| --- | --- | --- |
| **G0-a** | 「残のみ」の定義 | **完了を除外したうえで、明細残を出す。** 除外判定は伝票単位、残数の算出は明細単位で行う |
| **G0-b** | 部分完了伝票の扱い | **伝票ごと完了にしたものは、SKUに残があっても完了とみなす。** 旧は明細単位で残ありSKUが残ったが、CV10 では消える |
| **G0-c** | 自動完了の判定式 | **明細単位で全SKUが充足されたものを自動完了とする。** 伝票合計数量での比較は採らない |

G0-c により、1SKUでも未充足なら伝票は「一部処理」に留まる。
G0-b は運用上、残を残したまま締めたいときの手段（G0' の手動完了）として機能する。

### 4.3 状態遷移（決定済 2026-08-17）

第1回 3.2（Architect）の要求に対応する。

**発注**

| 状態 | 条件 | 遷移 |
| --- | --- | --- |
| 未処理 | `EndFlag=0`、仕入 0 | 発注伝票の登録 |
| 一部処理 | `EndFlag=0`、仕入 一部 | 関連伝票NO1で紐付いた仕入伝票の登録 |
| 完了（自動） | `EndFlag=0` の状態で、**仕入が全て発注数量を超えた → `EndFlag=1` へ変更** | 仕入伝票の登録・修正 |
| 完了（強制） | 発注残完了設定画面で `EndFlag` を更新 | 手動 |

**受注**

| 状態 | 条件 | 遷移 |
| --- | --- | --- |
| 未処理 | `EndFlag=0`、出荷 0 | 受注伝票の登録 |
| 一部処理 | `EndFlag=0`、出荷 一部 | 受注伝票Idで紐付いた出荷（`Tran00Uriage`、`TenType=1` or `3`）の登録 |
| 完了（自動） | `EndFlag=0` の状態で、**出荷が全て受注数量を超えた → `EndFlag=1` へ変更** | 出荷伝票の登録・修正 |
| 完了（強制） | 受注残完了設定画面で `EndFlag` を更新 | 手動 |

**この `EndFlag` は `Tran13Hachu` / `Tran12Jyuchu` へ新設する列である**（4.4）。
発注残・受注残の完了判定は、必ずこの新設 `EndFlag` を参照する。

「未処理／一部処理」は `EndFlag=0` の内部区分であり、独立した永続値を持たない。
帳票上は残数の有無で区別される。自動完了の判定は G0-c により**明細単位で全SKU充足**を条件とする。

#### 4.3.1 完了後に関連伝票が減ったときの扱い（決定済 2026-08-17）

**いったん `EndFlag=1` になったものは、仕入・出荷の削除や数量減があっても自動では 0 に戻さない。**
戻すのは手動操作（発注残完了設定 / 受注残完了設定）に限る。

ただし気付けないまま残るのを防ぐため、**編集完了時に対象伝票が `EndFlag=1` であればワーニングを出す**。
「関連する発注（受注）は完了済みです」の旨を表示し、必要なら残完了設定から解除してもらう。

自動で戻さない理由は、数量減・削除のたびに完了が揺れ戻ると残管理表の内容が不安定になり、
強制完了（G0-b で「SKUに残があっても完了とみなす」と決めた運用）と区別できなくなるためである。
Phase 3 の「解除・取消時の復元」はこの方針で閉じる。

なお出荷指示確定の「出荷区分」プルダウンは **0:在庫配分 / 1:初回配分 / 2:店舗出荷依頼 / 3:受注配分（卸）** の4種で、

2. **出荷指示確定**（商品別／得意先別の2画面） — ここで確定したものが倉庫への指示になる。
3. **出荷指示明細書印刷** — ピッキングリスト。**配分伝票NO単位で「1出庫元 ⇒ 1出荷先」**にまとまる。
   なお帳票仕様に「配分データの**完了FLG及び確定FLGは参照しておりません**」と明記がある。
4. **伝票作成** — ハンディ読取→取込、**または「出荷処理入力」メニュー**から。ここで初めて在庫が動く伝票が生成される。
   生成先は出荷先の店種区分で分岐し、**卸先 → 出荷売上伝票 / 倉庫・売仕店・直営店 → 移動伝票**。

#### 5.1.1 配分データが持つ数量と完了判定（帳票集PDF〔０７〕）

**出荷指示一覧印刷**の出力項目定義より。

| 数量 | 定義 |
| --- | --- |
| 予定数量 | 配分入力での配分数 |
| 確定数量 | 配分数に対して**出荷した数量** |
| 欠品数量 | 配分数に対しての**欠品数** |

同帳票の検索条件「出荷依頼倉庫完了」が、完了の判定式をそのまま示している。

> **0未完了 ： 指示数 > 出荷数 + 欠品数**
> **1完了済 ： 指示数 <= 出荷数 + 欠品数**

つまり旧では、配分は**出荷されるか欠品として確定するかのどちらかで解消**され、その両方が指示数に届いて初めて完了になる。
検索条件にはこのほか「CV出荷確定登録（0未確定 / 1確定済み）」があり、**確定と完了は独立した2軸**である。

#### 5.1.2 CV10における配分の数量と状態（決定済 2026-08-17）

旧の3数量に対応させ、`TranHaibun` へ **`ShortSu`（欠品数）を新設**する（4.4）。

| CV10 列 | 対応 | 設定者 |
| --- | --- | --- |
| `Su` | 予定数量（指示数） | **ユーザーが配分入力で設定** |
| `JitsuSu` | 確定数量（出荷した数量） | **倉庫から戻されるデータで設定** |
| `ShortSu` | 欠品数量 | **倉庫から戻されるデータで設定**（新設） |
| `KakuteiDay` | 確定日 | 確定処理 |
| `EndFlag` | 完了 | 完了処理（既存列） |

**状態の定義**

1. ユーザーが `Su` を入力する。
2. そのデータが倉庫へ送信される。
3. 倉庫側から戻されるデータにより `JitsuSu` と `ShortSu` が設定される。**`Su = JitsuSu + ShortSu`** が成立する。
4. その状態であり、かつ **`KakuteiDay` に有効な日付が設定された**データを**確定**とみなす。
5. **完了は `EndFlag = 1`。**

旧の完了判定「指示数 ≤ 出荷数 + 欠品数」は、CV10 では `Su = JitsuSu + ShortSu` の成立として表現される。
これにより、出荷できなかった分は欠品として解消でき、`EndFlag` の手動更新だけに頼る必要がなくなる。

### 5.2 引当対象（決定済 2026-08-17）— 重要な仕様変更

#### 5.2.1 旧CV.netの定義

旧資料は4スライドで同一の定義を繰り返している。

> 有効在庫数 … 実在庫から、指示した分を差し引いた数。「実在庫 − 配分入力（**初回配分は除く**）」

さらに受注配分入力・店舗配分入力の注意書きに、

> 区分「初回配分」「在庫配分」で分けることができます。注意：発注入力を元に配分入力ができます。
> **初回配分は引き当てがかからない（有効在庫数が減らない）ので、在庫のある商品は必ず在庫配分を選択してください。**

補強材料として、第1回会議7章で cvnet-developer は
**「入荷前の初回配分」**を、汎用ERPでは追加設計が必要になるアパレル固有業務の代表例として列挙している。

#### 5.2.2 決定内容（決定済 2026-08-17）

**引当対象は `EnumHaibun = 0`（初回配分）**以外**のすべてとする。**
すなわち引当判定は **`Kubun != 0`** の一点で行い、`0:初回配分` のみが引当対象外となる。

区分の意味づけは **KEEP**（旧の「初回配分は引き当てがかからない」を維持）、
引当判定のロジックは **CHANGE**（2026-08-15 実装の「全区分を引当対象」から変更）である。
`TranHaibun` は実データ0件のため、移行コストは発生しない。

#### 5.2.2b マニュアル13が示す有効在庫の正確な定義【要確認】

業務フロー資料の「実在庫 − 配分入力（初回配分は除く）」は要約であり、
マニュアル13-配分は4つの配分入力画面すべてで**より厳密な定義**を与えている。

> **有効在庫数 = 倉庫在庫数 −（①出荷指示確定済みのデータ数量 ＋ ②指定日範囲外の数量 ＋ ③受注済みで出荷が完了していない数量）**

初回配分だけは別ロジックで制御される。

> 有効在庫は**参照用**として表示するのみ。「マイナス値であっても入荷予定数があれば配分可能」
> 「入荷予定数が入っていないと、配分できません」
> **配分残数 = 基準倉庫在庫数 + 入荷予定数 − 各店舗へ配分済みの数量**
> 入荷予定数は手入力、または入荷予定ボタンで発注データの発注数を呼び出す。

また店舗出荷依頼の画面は倉庫在庫を **在庫数 / 引当数 / 自店数 / 有効在庫数** の4つで表示し、
引当数を「**受注などにより**出荷予定な数」と説明している。

旧との差分2点は本日いずれも決定した。

| # | 旧の定義 | 決定（2026-08-17） |
| --- | --- | --- |
| **I1-x** | 引当になるのは「出荷指示確定済み」の配分のみ | **CHANGE。出荷指示直後（未確定）と確定後の両方を引当対象とする。** ただし**確定後は引当数の見方を変える**（下記 5.2.2c） |
| **I1-y** | ③受注済みで出荷が完了していない数量も有効在庫を減らす | **CHANGE。受注残は有効在庫から引かない。** 引当の源泉は `TranHaibun` のみとする |

②「指定日範囲外の数量」は、配分入力画面の日付範囲指定に対する除外条件であり、画面仕様の一部と読める。

#### 5.2.2c 引当数の算定（決定済 2026-08-17）

引当の対象行は **`EndFlag = 0` かつ `Kubun != 0`** で変わらない。
変わるのは**行ごとにどの数量を引当数として積むか**である。

| 行の状態 | 引当数に積む値 | 理由 |
| --- | --- | --- |
| **未確定**（`KakuteiDay` が空） | **`Su`**（予定数量） | まだ倉庫から実績が返っていないため、指示数をそのまま押さえる |
| **確定済み**（`KakuteiDay` に有効日付） | **`JitsuSu`**（確定数） | 倉庫から `JitsuSu` / `ShortSu` が返って `Su = JitsuSu + ShortSu` が成立しており、欠品分は出荷されないため押さえる必要が無い |

すなわち引当数は次式になる。

```
ReserveQty = Σ ( KakuteiDay が空 ? Su : JitsuSu )
             WHERE EndFlag = 0 AND Kubun != 0
             GROUP BY 倉庫 + SKU
```

欠品（`ShortSu`）分は確定と同時に自動的に引当から外れる。
これにより「出荷できない分をいつまでも押さえ続ける」状態が構造的に発生しない。

**実装への影響**: `CvDomainLogic/SummaryDb.cs` の `CalcHaibun2Reserve()` / `CalcReserveQtyAll()` は
現在 `h.EndFlag = 0` だけで絞り `Su` を合計している。`Kubun != 0` の条件と、
`KakuteiDay` による `Su` / `JitsuSu` の切替を追加する必要がある。

#### 5.2.3 区分ごとの扱い

現行 `EnumHaibun`（`CvBase/BaseDbHaibun.cs`）の8区分に対する判定は次のとおり確定する。

| 値 | 名称 | 引当 |
| --- | --- | --- |
| 0 | 初回配分 | **対象外**（入荷前の振り分けであり現物を押さえない） |
| 1 | 在庫配分 | 対象 |
| 2 | 受注配分 | 対象 |
| 3 | 得意先別配分 | 対象 |
| 4 | 店舗出荷依頼 | 対象 |
| 5 | 在庫品配分 | 対象 |
| 6 | 取置 | 対象 |
| 7 | 移動指示 | 対象 |

区分値を2つへ集約する必要はなく、**8区分を維持したまま判定式を `Kubun != 0` にすればよい**。
これにより「どの画面から登録された配分か」も区分から判別でき続ける。

コード上で `EnumHaibun` の値を参照しているのは `HachuHaibunInputViewModel`（`Hatsukai`）と
`ShopHaibunInputViewModel`（`Hatsukai` / `Zaiko`）の2ファイルのみで、いずれも 0 と 1 しか使っていない。
変更が必要なのは `SummaryDb.CalcHaibun2Reserve()` / `CalcReserveQtyAll()` の集計条件である
（現行は `EndFlag=0` のみで絞っており、`Kubun != 0` の条件が無い）。

なお旧の店舗出荷依頼は「本部で出荷確定をするまでは倉庫の有効在庫数は減りません」とされていた。
本決定では `4:店舗出荷依頼` も引当対象とするため、この点は旧に対する **CHANGE** となる。

### 5.2.4 出荷指示確定と出荷処理入力の仕様（マニュアル13-配分）

I2・I3・I7 の一次根拠。旧の2段階はそれぞれ独立した画面である。

**5「出荷指示確定」** — 配分入力した内容を確認して確定する。

- 検索条件は 出荷区分 / **確定基準（店舗基準・伝票基準）** / 指示日・納品日の切替 / **倉庫CD（必須）** / 店舗 From-To / ブランド or 伝票No。
- 一覧の「確定」欄が **未 / 確** の2値。全チェック有・無で一括切替し、**確定ボタンで確定処理**を行う。
- **確定後は再検索しても表示されない**（「出荷確定待ちでなくなるため」）。
- 一覧には **確指示（確定指示がかかっている数）** と **予指示（予定指示がかかっている数）** の2つの数量が並ぶ。
- **割り当てられた配分数が有効在庫を下回っている場合はエラー**になる。エラー一覧→エラー修正タブで予指示を修正し、
  **「有効在庫数 − 入力した予指示が正の場合のみ『確』にできる」**。

**6「出荷処理入力」** — 確定済みのものから伝票を起こす。CV10 の `ShippingInput` に相当する。

- 「出荷指示確定を行った商品に対し、正しければ**移動伝票または出荷売伝票を起こす**」。
- **出荷処理待ちのデータのみ表示。一度伝票作成されたものは再検索で表示されない。**
- 検索条件は 倉庫CD / 店種区分 From-To。明細タブで内容を確認できる。
- **掛計上日の一括展開**機能を持つ。プルダウンの締日と得意先の締日が等しい行に展開フラグが立ち、
  日付を入力して一括展開すると**掛計上日が伝票単位で更新**される。
- 全チェック有・無で出荷フラグを 未 / 確 に切り替え、**伝票作成ボタンで「確」の行の伝票を作成**する。

**引当完了フラグが立つ契機**は、配分問合わせ・引当問合わせ・有効在庫問合わせの3画面に同じ注記がある。

> ※日付範囲を検索に使用するチェックは、**出荷処理入力を行い、引当完了フラグが立てる運用でなく、
> 移動入力のみを行う際、必要になります。**

すなわち旧では **出荷処理入力の伝票作成をもって引当完了フラグが立つ**。
配分を経由せず移動入力だけで出荷する運用では完了フラグが立たないため、日付範囲で古い引当を除外する必要があった。

**7・8「配分データメンテ（追加／修正）」** — 管理者による直接編集。

- ヘッダの修正可能項目: 配分指示日、納品日、区分、**確定FLG**、倉庫、区分2、**送信FLG**、出荷先、備考
- 明細の修正可能項目: 商品、原価フラグ、色、サイズ、金額、**予定数量**、**確定日**、**欠品日**、**完了FLG**

#### 7.1.1 請求一覧表の算式（帳票集PDF〔０６〕売上 — 一次根拠）

| 項目 | 定義 |
| --- | --- |
| 日付 | 請求データの請求日または入金予定日 |
| 締日 | 得意先マスタの締日 |
| 前月残 / 現金 / 振込手数料 / 手形 / 相殺 / その他 | 請求データの各合計 |
| **繰越金額** | **前月残 −（現金 + 振込手数料 + 手形 + 相殺 + その他）** |
| 売上 / 返品 / 値引 | 請求データの各合計 |
| **売上合計** | **売上 − 返品 − 値引 +（その他売上の合計）+ 消費税** |
| **純売上** | **売上合計 − 消費税** |
| 当月残 | 繰越金額 + 売上合計（サンプル値で検算済み） |

出力基準は **請求集計月**（請求日基準）と **入金予定月**（支払予定日基準）の2種、
出力区分は **親のみ**（請求先のみ）と **子含む**（請求先および同一請求先の得意先）の2種。

注意点として、旧は**返品・値引を正値で保持して減算**している。
CV10 のドラフトD2は `CalcFlag` を掛けた符号付きで保持し `Henpin` / `Nebiki` を負値で入れる方式を採り、実装済みである。
合計は一致するため機能等価だが、帳票の表示時に符号を反転する必要がある。

また算式に **「その他売上」** が含まれる。CV10 には該当列が無く、ドラフトD2 は区分 `99`（その他）を `Uriage` に含めている。
合計は一致するが、**請求一覧表の「売上」列の値が旧と変わる**点は CHANGE として認識しておく必要がある。

## 8. 棚卸・在庫調整・締日（Phase 5 / Decision 7-6）

### 8.1 旧CV.netの棚卸業務機能

`業務フロー/01`、`マニュアル/11-月次更新` 3〜4章、`帳票集PDF〔０８〕在庫管理` より。棚卸は**7段階**である。

1. **棚卸準備** — 棚卸日設定／棚卸日一括メンテナンスで倉庫ごとの対象日を設定。
2. **棚卸入力** — ハンディ読取→取込（実地棚卸数）。
3. **帳票印刷** — 棚卸明細表／棚卸差異表／棚卸チェックリスト。
   差異表は **帳簿在庫・実在庫・差異の3ブロック**をそれぞれ数量・上代合計・原価合計で出力し、**差異が無い場合は出力しない**。
4. **棚卸開始処理** — 「①で設定した日付時点の在庫を保存」。棚卸中に帳簿在庫が動かないようスナップショットを取り、
   棚卸明細表の「帳簿在庫数」欄へ反映する。得意先ごとに「する／しない」を選べる一覧形式。**自動実行に組み込める**。
5. **差異調査・伝票修正**。
6. **棚卸開始処理を再実行** — 修正後の在庫を再保存。
7. **棚卸確定処理（棚卸更新）** — 「①設定日付時点在庫を棚卸数にする」。**帳簿在庫を実地棚卸数で置き換える**。
   「棚卸確定処理後に過去の伝票を訂正した場合は、在庫が変動しますので、この画面に再度確定の表示がでます。再確定をして下さい」
   とあり、**再確定が正常な運用手順**として想定されている。

在庫強制調整は旧も独立した伝票入力メニューとして存在し、倉庫・売仕店・直営店を対象に商品マスタと紐づく。

### 8.2 旧CV.netの締日制御

`業務フロー/05` スライド20〜22。旧は伝票の遡及修正を**2層**で制御していた。

- **締日更新** — 設定日を含めそれ以前の**すべての伝票**の修正・削除・追加を禁止。請求計算・支払計算も対象。
  何度でも変更でき、前回締日・最終更新日・最終更新者を表示する。ただし**外部連携経由の登録は締日以前でも通る**。
- **システム管理設定** — 「修正有効日数」（過去何日前まで登録可）と「先付有効日数」（未来何日先まで登録可）。
  **締日更新の設定が優先**される。

ハンディ側にも対応するエラー（締日以前）があり、締日制御が全入力経路に効いていた。

### 8.3 参考: 総平均原価の算式（帳票集PDF〔１２〕月次更新）

Phase 5 の原価更新に直接使える一次根拠が取れたため記録する。

> **総平均原価 =（前月在庫 × 原価 + 当月仕入金額 + TQ）÷（前月在庫 + 当月仕入数）**

更新前に「総平均原価計算チェックリスト」で更新後の値を確認でき、
**更新結果確認（更新できる商品のみ）／エラー確認（エラーで更新できない商品のみ）／更新** の3操作に分かれている。
`TQ` の意味は帳票上で定義されておらず**判断材料不足**（諸掛の可能性がある。`業務フロー/06_諸掛・総平均原価更新` の精読が必要）。

#### 8.4.1 F0 に伴う在庫恒等式の変更

`SummaryStock` は `Su`（在庫数）のほか `InQty`（入庫数）/ `OutQty`（出庫数）/ `AdjustQty`（調整数）/
`ActualQty`（棚卸数）/ `StocktakeDdate`（棚卸日）/ `CumulativeSu`（当月までの累計数量）を持つ。

F0 の決定により、棚卸確定時に `AdjustQty = 当月棚卸数 − 確定前の Su` を設定し、
在庫数は `Su = InQty + OutQty + AdjustQty` を満たす構成へ変更する。

これは修正第1回 一致点5「通常更新値 = Rebuild値」の検証対象式が置き換わることを意味する。
実装時には、①`AdjustQty` を Rebuild 側でも同じ手順で再現できること
②前月繰越（`CumulativeSu`）との関係を明示すること の2点を仕様として固定する必要がある。
`AdjustQty` はこれまで書き手が存在せず読み手（受払表3帳票）だけだったため、既存帳票の値が変わる点にも注意する。
