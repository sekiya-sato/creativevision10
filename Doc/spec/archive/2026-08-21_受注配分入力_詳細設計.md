## 1. 目的とスコープ

得意先からの**受注残**を、出庫元倉庫の**有効在庫**を参照しながら割り当て、
`TranHaibun`（区分 `2:受注配分`）を作成・修正する。

- サーバ側の変更・スキーマ変更・新規Msgは**なし**。既存の `Msg101_Op_Query` / `Msg201_Op_Execute`
  （`QueryListParam` / `QueryListSqlParam` / `InsertBulkParam` / `DeleteByIdParam`）だけで完結する。
- 引当数（`SummaryRealStock.ReserveQty`）は `TranHaibun` の書き込み時にサーバが自動で引き直す
  （`WriteEffectRunner` → `SummaryDb.CalcHaibun2Reserve`）。クライアントからの再計算指示は不要。
- 出荷指示確定・出荷処理は既存画面（`ShippingConfirmShohin` / `ShippingConfirmTokui` / `ShippingInput`）が担当する。本画面は配分の作成までを担う。

### 1.1 入力単位の決定（2026-08-21 ユーザー確定）

**受注伝票1件＝配分1件**を単位とする。

旧CV.netは「倉庫＋商品を選び、SKU行 × 得意先列のクロス表へ入力する」商品単位の画面だったが、
CV10 は**受注伝票を選んでその明細を配分する**方式に変更する。

| 観点 | 旧（商品単位クロス表） | CV10（受注伝票単位） |
|---|---|---|
| 選択するもの | 倉庫 + 商品 | 受注伝票（受注No） |
| 配分先 | 画面で選んだ複数得意先（列） | 受注ヘッダの得意先1件で固定 |
| 出庫元倉庫 | 画面で選択 | 受注ヘッダの `Id_Soko` |
| `RelateNo1`（元伝票） | セルの数量を得意先の受注残へFIFOで割り当てて決める | 選択した受注Idで一意に決まる |
| 入力グリッド | SKU × 得意先の動的クロス表 | 商品×SKU の明細1本（配分数を入力） |

発注配分入力（`HachuHaibunInputViewModel`、2026-08-13 に「発注伝票まるごとを1配分として扱う」で確定）と
同じ構造になり、`RelateNo1 = 元伝票Id` の規約が素直に成立する。
また出荷処理が `(DenDay, NouhinDay, Id_Soko, Id_Tenpo, Kubun, RelateNo1)` 単位で出荷売上を作るため
（`ShippingDb.CreateShippingSlips`）、受注Idが一意に決まることで受注の自動完了判定
（`CompletionDb.CalcJuchuEndFlag`）が確実に働く。

在庫が限られる中で複数得意先へ配分を割り振る用途は「得意先別配分入力」（`TokuiHaibunInput`）で扱う。

## 2. 業務ルールの確定事項

### 2.1 配分先と区分

| 項目 | 確定内容 |
|---|---|
| 配分区分 | `EnumHaibun.Juchu`(2)。**引当対象**（`Kubun != 0`）である |
| 出庫元倉庫 | `TranHaibun.Id_Soko` = 受注ヘッダの `Tran12Jyuchu.Id_Soko` |
| 配分先 | `TranHaibun.Id_Tenpo` = 受注ヘッダの `Tran12Jyuchu.Id_Tokui`（得意先） |
| 元伝票 | `TranHaibun.RelateNo1` = 受注Id（`Tran12Jyuchu.Id`） |

配分先が卸先(1)・売仕店(3)であれば、出荷処理で `Tran00Uriage.RelateNo1 = 配分.RelateNo1`（＝受注Id）の
出荷売上が作られ、受注残が消化される（決定 I4、`ShippingDb.CreateShippingSlips`）。
倉庫(0)・直営店(6)への受注は移動伝票になり受注残を消化しないため、一覧取得時に警告する。

> 注: `TranHaibun.Id_Tenpo` の `[ForeignKey]` の `additionalInfo` は `TenType in (0,3,6)` のままで
> 卸先(1)を含んでいない。この注記はメタデータ（生成ドキュメント用）で検証には使われないため
> 本作業では変更しない。受注配分・得意先別配分・取置の実装が揃った時点でまとめて見直す。

### 2.2 対象となる受注

`Tran12Jyuchu` のうち `CalcFlag <> 0`（計算除外でない）かつ `EndFlag = 0`（未完了）を対象とする。
完了済みの受注は本画面に出てこない（旧の「完了の効果 ②受注配分入力で検索されない」を維持）。

### 2.3 受注残の算式

一覧（タブ1）と明細（タブ2）で見せる残は用途が違うため、名前を分けて両方定義する。

**タブ1「未配分残」** — まだ配分していない数量。配分状況の判定に使う。

```
未配分残(受注) = Σ_SKU MAX( 受注数 − 出荷済数 − 配分数 , 0 )
```

**タブ2「受注残」** — この画面で今から配分できる数量。

```
受注残(SKU) = MAX( 受注数 − 出荷済数 − 確定済配分数 , 0 )
```

| 項目 | 定義 |
|---|---|
| 受注数 | 受注明細（`Jmeisai`）を SKU 単位に合算した `Su * CalcFlag` |
| 出荷済数 | `Tran00Uriage`（`RelateNo1` = 受注Id、出荷先 `TenType IN (1,3)`）の明細 `Su * CalcFlag` の SKU 単位合計 |
| 配分数 | `TranHaibun`（`Kubun=2`、`RelateNo1` = 受注Id、`EndFlag=0`）の `Su` の SKU 単位合計 |
| 確定済配分数 | 上記のうち**本画面の編集対象ではない**もの（＝確定済み or 送信中） |
| 編集対象 | `Kubun=2` かつ `RelateNo1` = 受注Id かつ `SendFlg=0` かつ `KakuteiDay=''` かつ `EndFlag=0` |

- 出荷済配分は `EndFlag=1` になり出荷売上が立つので、出荷済数と配分数で二重に引かれることはない。
- タブ2で編集対象を差し引かないのは、その分を洗い替えで作り直すためである（旧CV.netも
  「未完了・未確定・指示日範囲内」の配分を残から除外していた）。

### 2.4 有効在庫（配分可能数）

```
配分可能数(SKU) = 在庫数 − 引当数 + 編集対象配分数
```

- 在庫数 = `SummaryRealStock.Su`（受注ヘッダの倉庫）
- 引当数 = `SummaryRealStock.ReserveQty`（同）。定義は決定 5.2.2c により
  `EndFlag=0 AND Kubun<>0` の行で「未確定=`Su` / 確定済み=`JitsuSu`」を積んだもの（materialize済み）。
- 編集対象配分は引当に含まれているので、洗い替えで消える分を足し戻す
  （`ShopHaibunInputViewModel` の `OtherShijiSu` と同じ考え方）。

旧の「②指定日範囲外の数量」「③受注済みで出荷が完了していない数量」は決定 I1-x / I1-y で
CV10 の有効在庫から外しているため、本画面でも引かない。
配分可能数は**参照表示**で、入力を止めない（2.5）。

### 2.5 超過の扱い（2026-08-21 ユーザー確定）

| 超過 | 扱い |
|---|---|
| 配分数 > 配分可能数（有効在庫割れ） | **警告のみで登録できる**。出荷指示確定でエラーになる（既存仕様）ため、配分段階では止めない。`HachuHaibunInput` の発注数超過と同じ方針 |
| 配分数 > 受注残 | **警告のみで登録できる**。受注残までは `RelateNo1` = 受注Id、超過分は `RelateNo1 = 0` の別行で登録する |

`RelateNo1 = 0` の行は出荷時に受注Noの無い出荷売上になり、受注残を消化しない。
受注数を超えて出荷した分が受注の完了判定へ混ざらないようにするためである。

### 2.6 単価

`TranHaibun` の `Tanka` / `Jodai` / `Gedai` は**受注明細の値をそのまま引き継ぐ**（伝票時点の価格）。
`Kingaku` = `Su × Tanka`。`RelateNo1 = 0` の超過行も同じ単価を使う。
同一SKUの明細が複数行あるときは数量を合算し、単価は最小値を採る。

## 3. 画面構成

旧画面の2タブ構成（検索画面 / 修正・登録画面）を `TabControl` で再現する。
`HachuHaibunInputView` と同じ「タブヘッダを隠して VM の `SelectedTabIndex` で切り替える」方式にする。

### 3.1 タブ1: 検索画面

条件（画面内に直接配置。`HachuHaibunInputView` と同じ並び）

| 条件 | 内容 |
|---|---|
| 受注No From〜To | 受注Id の範囲 |
| 受注日 From〜To | 既定は当月1日〜未指定 |
| 指示日 From〜To / 納品日 From〜To | 配分側の日付で絞る |
| 得意先 / 入力者 | 任意。入力者は配分側の `Id_Shain` |
| 商品CD From〜To | 受注明細（JSON）を展開して判定 |
| 取引区分 | `EnumJuchu`（10受注 / 20返品 / 30値引 / 99その他） |
| 配分状況 | 全て / 未配分のみ / 配分ありのみ |
| 最大件数 | 既定 `AppGlobal.Limit` |

一覧（受注伝票1件＝1行）

`受注No / 受注日 / 指示日 / 納品日 / 得意先 / 出庫元倉庫 / 取引区分 / 配分状況 / 受注数 / 出荷済 / 配分数 / 未配分残 / メモ`

- 配分状況 = 配分数0 → 未配分 / 未配分残0 → 配分済 / それ以外 → 一部配分
- 行のダブルクリック、または［配分入力へ］(F6) でタブ2へ
- ［削除］(F7) で選択受注の編集対象配分をまとめて削除

### 3.2 タブ2: 修正・登録画面

ヘッダ（配分情報カード）

`受注No（選び直し可）/ 受注日 / 得意先 / 出庫元倉庫 / 取引区分 / 指示日 / 納品日 / 入力者 / 受注数 / 受注残計 / 総配分数 / 備考`

配分明細（`商品 × SKU` の1行1明細）

`商品CD / 商品名 / 色 / サイズ / 上代 / 受注数 / 出荷済 / 確定済配分 / 受注残 / 在庫 / 配分可 / 配分数(入力) / 残`

- 残 = 受注残 − 配分数（マイナスは受注残超過）
- 在庫・配分可 は参照表示。配分可がマイナスなら有効在庫割れ
- 配分数は 0 を空欄で表示する（`SuText`）

操作

| 操作 | キー | 内容 |
|---|---|---|
| 一覧へ | Shift+F1 | タブ1へ戻る |
| 受注No選択 | — | 汎用伝票選択ダイアログ（`SelectTranWinView`）で受注を選び直す |
| 受注残読込 | — | 全明細の配分数をその受注残で上書きする（確認ダイアログあり）。旧の［受注残読込］ |
| 同数展開 | — | 数値を入れて［全SKU］で全明細へ同じ数を入れる。旧の［同数展開］［全SKU］ |
| 全クリア | Shift+F6 | 入力した配分数をすべて0にする |
| 登録 | F2 | 編集対象配分を削除してから、配分数>0の明細を一括Insert（洗い替え）。旧の［確定］ |

### 3.3 登録処理（洗い替え）

1. 指示日の未入力をチェックする。
2. 有効在庫割れ・受注残超過があれば件数を出して続行確認する。
3. 編集対象配分（`SendFlg=0` かつ `KakuteiDay=''` かつ `EndFlag=0`）を `DeleteByIdParam` で
   `Vdu` 付きで1件ずつ削除する（他端末更新は失敗させて再取得を促す）。
4. 配分数>0の明細を `TranHaibun` へ展開する。受注残を超える分は `RelateNo1 = 0` の行に分ける。
   `InsertBulkParam` で一括Insertする。
5. 再読込して画面を最新化する。

配分数が全て0のときは削除だけを行う（`ShopHaibunInput` / `HachuHaibunInput` と同じ）。

## 4. データアクセス

すべて `QueryListSqlParam`（生SQL）または `QueryListParam`（where/order）で読む。
生SQLの受け皿は既存の `CvBase` 型へ射影する（サーバが型を解決できる必要があるため、
クライアント専用のDTOは使わない）。

| 用途 | データ源 | 受け皿 | 射影 |
|---|---|---|---|
| 受注一覧 | `Tran12Jyuchu`（配分側の条件は `EXISTS` / `NOT EXISTS`） | `Tran12Jyuchu` | — |
| 受注Id別の配分サマリ | `TranHaibun` | `TranHaibun` | `RelateNo1`=受注Id / `Su`=配分数 / `DenDay`・`NouhinDay`・`Id_Shain`=最小値 |
| 受注Id別の出荷済・未配分残 | 受注展開 + 出荷済 + 配分 の3段 | `TranHaibun` | `RelateNo1`=受注Id / `JitsuSu`=出荷済 / `Su`=未配分残 |
| 選択受注のSKU別 出荷済・確定済配分 | 出荷済 + 確定済配分 | `TranHaibun` | `Id_Col`・`Id_Siz`=SKU / `JitsuSu`=出荷済 / `Su`=確定済配分 |
| SKU別 在庫・引当 | `SummaryRealStock` | `SummaryRealStock` | `Su`=在庫 / `ReserveQty`=引当 |
| 編集対象配分 | `TranHaibun` | `TranHaibun` | — |
| 商品マスタ | `MasterShohin` | `MasterShohin` | — |

JSON明細は AGENTS.md の規約どおり `CASE WHEN json_valid(...) THEN ... ELSE '[]' END` で防御する。
上代は受注明細の `Jodai` を使うため `DerivedJodai` の解決は行わない（伝票時点の価格を優先する）。
