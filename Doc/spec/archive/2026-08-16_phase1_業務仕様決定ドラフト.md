## 3. 本日の決定事項

### 3.1 A1 請求先・支払先の解釈（前版 2.1.2-1 / B1）

**`Id_Paysaki = 0` は「親を持たない」を意味し、その取引先自身に対して請求（支払）を行うものとみなす。**

- 消込画面の絞り込み条件を `Id_Paysaki = X OR (Id = X AND Id_Paysaki IN (0, X))` で確定する（2026-08-14 実装済みの条件をそのまま採用）。
- 事実として現在の移行データは全件 `Id_Paysaki = 0` であり、「請求先＝得意先自身」としてのみ動作する。複数得意先を1請求先へ束ねる運用は `Id_Paysaki` を整備した時点で有効になる。条件式の変更は不要である。
- 旧 `Code_Kin = 85` を `02` 振込手数料へ寄せたことにより、振込手数料の金額が78件で31.4億円（平均4,034万円）と実態にそぐわない値になっている。
  **本件は一旦、仕様どおり `02` 振込手数料とみなす。** 実運用で問題になった時点で再マッピングする。`03` 手形入金は入金側の割当が0件である。

### 3.2 A2 入金・支払の日付列を `KakeDay` へ改名（前版 2.1.2-2 の変更）

前版は「`Tran06Nyukin` / `Tran07Shiharai` の `DenDay` を支払日として流用し、専用列を追加しない」としていた。**これを変更する。**

**`TranKinHeader.DenDay` を `KakeDay` へ列名変更し、掛計上日とみなす。**

- 意味づけ: 入金・支払も売上・仕入と同じ「掛計上日」の軸で扱う。`Tran00Uriage` / `Tran03Shiire` の `KakeDay` と同じ意味の列になる。
- 列は追加しない。既存列の改名であり、値の移行は不要である。
- DB移行は `CvBase/UpdateDb.cs` の `versions` へ1行追加し、`ALTER TABLE ... RENAME COLUMN DenDay TO KakeDay` を両テーブルへ適用する。インデックス `nk1` は SQLite が自動追随する。
- `SummaryUriSei` / `SummaryKaiShi` の `DenDay`（請求日・支払日）は**改名対象外**である。意味が異なる。

この改名により、前版 2.6-5 が挙げていた「売上は `KakeDay`、入金は `DenDay`」という基準日の非対称が消える。
売掛・買掛の集計、得意先元帳・仕入先元帳、消込画面のいずれも `KakeDay` 一本になる（3.5 D5）。

### 3.3 A3 / A4 / A5 消込仕様の承認（前版 2.1.2-4 / -5 / -7）

前版の推奨案どおりで承認・確定する。2026-08-14 実装済みの挙動を変更しない。

### 3.4 C1 元帳の消込マーク（前版 2.1.2-6）

**`*` は伝票の `EndFlag = 1` を条件に表示する。帳票定義（`printform/TokuiLedger.qfm` / `ShiireLedger.qfm`）は変更しない。**

- `*` 専用の列は設けない。**メモを印字している欄の先頭へ `*` を出す。**
- メモが空でなければ `*` とメモの間に半角空白を1つ入れる。メモが空なら `*` だけを出す。
- `EndFlag = 0` の伝票はメモをそのまま出す。
- 入金・支払の行と繰越行には `EndFlag` が無いため `*` を出さない。

| 伝票の状態 | メモ欄の印字 |
| --- | --- |
| `EndFlag = 1`、メモあり | `* メモ本文` |
| `EndFlag = 1`、メモなし | `*` |
| `EndFlag = 0`、メモあり | `メモ本文` |
| `EndFlag = 0`、メモなし | （空） |

列を増やさないため qfm の座標調整が不要になり、既存の帳票レイアウトを維持できる。

### 3.5 D 掛集計（`SummaryUriKake` / `SummaryKaiKake`）（前版 2.6-1〜6）

前版の推奨案をすべて採用する。

#### D1 集計キーの粒度 — 得意先・仕入先単位を維持する

`SummaryUriKake` は `Id_Tokui + DenMonth`、`SummaryKaiKake` は `Id_Shiire + DenMonth` のまま変更しない。
請求先での合算は照会側で行う。現在の移行データは `Id_Paysaki` が全件 `0` であり、請求先単位へ変えると全件が単一キーへ集約されて破綻する。

#### D2 区分別内訳を埋める

前版まで `Henpin` / `Nebiki` / `Cash` / `Fee` / `Densai` / `Offset` / `Other` は `0` 固定だった。これを実値で埋める。

売上側は `EnumUri00`、仕入側は `EnumShiire` の `Kubun` で振り分ける。

| 列 | 対象 `Kubun` |
| --- | --- |
| `Uriage` / `Shiire` | `10`(P売上 / 仕入) `11`(S売上、売上のみ) `99`(その他) |
| `Henpin` | `20`(P返品 / 仕入返品) `21`(S返品、売上のみ) |
| `Nebiki` | `30`(値引) |

`EnumShiire` は `10` / `20` / `30` / `99` のみで `11` / `21` を持たないが、振り分け条件は売上側と共通の式で書く。

- 内訳は `CalcFlag` を掛けた**符号付き**で保持する。`Kubun` が 20〜39 のとき `CalcFlag = -1` になるため、`Henpin` と `Nebiki` は負値で入る。
- この定義により `Uriage + Henpin + Nebiki` が改名前の `Uriage`（全区分の符号付き合計）と一致する。テストで検証できる不変条件として扱う。
- 売上側に「その他」の内訳列が無いため、区分 `99` は `Uriage` / `Shiire` に含める。

入金・支払側は明細 `Jmeisai` の `Id_Kin` で振り分ける。

| 列 | 対象 `KIN` 区分 |
| --- | --- |
| `Cash` | `01` 現金入金 / 現金支払 |
| `Fee` | `02` 振込手数料 |
| `Densai` | `03` 手形入金 / 手形支払 |
| `Offset` | `04` 相殺入金 / 相殺支払 |
| `Other` | `05` その他入金 / その他支払、および上記以外（`Id_Kin = 0` を含む） |

- 展開方法は **SQLite の `json_each` をバッチSQL内で使う**。前版 2.1.2-3 は「JSON関数への依存を増やさない」意図でクライアント側C#展開を採ったが、
  それは画面照会が `QueryListSqlParam` の既存経路に載るという理由によるものだった。夜間バッチにはクライアントが存在せず、
  `BaseDbDerived` / `BaseDbJodai` / `TranMeisaiSql` が既に `json_each` を使っているため、依存を新規に増やすことにはならない。
- `Cash + Fee + Densai + Offset + Other` は `TotalIn` / `TotalOut` と一致する。移行データ2,302件すべてで明細合計＝ヘッダ合計であることを確認済み。

#### D3 `IsPay` による絞り込みを行う

`Tran00Uriage` / `Tran03Shiire` の集計条件へ `IsPay = 1` を追加し、掛計上しない伝票を売掛・買掛から除く。
移行データは全件 `1` へ修正済みのため、この条件を入れても既存の残高は変わらない。

#### D4 対象期間より後の月も再計算する

現行は指定範囲だけを `DELETE` → 再作成するため、過去月を単独で再集計すると以降の月の繰越（`Balance`）が古いまま残る。

**実効の終了月を、指定の `DateToYyyymm` と「その月より後に既存行または伝票が存在する最大の月」の大きいほうまで自動的に伸ばす。**

- 伸びた場合はログへ残す。
- 夜間ジョブは前月・当月を順に回すため、通常運用では実効終了月は当月のままで挙動が変わらない。
- `StockKakeUpdate` 画面から過去月を指定したときだけ、以降の月が併せて再作成される。

#### D5 基準日を `KakeDay` に統一する

A2 の改名により、売上・仕入・入金・支払のすべてが `KakeDay` を持つ。掛集計は4テーブルとも `substr(KakeDay, 1, 6)` を基準にする。
併せて、得意先元帳・仕入先元帳も `DenDay` 基準から `KakeDay` 基準へ変更し、掛集計と一致させる。

前版 2.6-5 は「入金には掛計上日の概念が無いため非対称を仕様として明記する」としていたが、A2 でこの前提自体が変わったため
**非対称を解消する方向で確定する**。移行データは `KakeDay = DenDay` が全件一致するため、既存の残高・元帳の出力は変わらない。

#### D6 締日単位の税計算は 1.0 の対象外

`TaxRecalculation` 画面は未着手であり、`SummaryUriKake.Tax` / `SummaryKaiKake.Tax` は伝票ヘッダの `Tax` の単純合算のままとする。
税の再計算を導入する際に、掛集計を再計算対象へ含めるかを改めて決める。

### 6.1 列名変更の影響監査

`CvBase` / `CvDomainLogic` / `CvServer` / `CvWpfclient` の全SQLを対象に、両方向で確認した。

- 据え置きが正しい `DenDay` は次のとおり。`TranAllHeader` 系（売上・仕入・移動・棚卸・受注・発注・店舗売上）、`TranHaibun`（引当集計の軸）、
  `SummaryUriSei` / `SummaryKaiShi`（請求日・支払日）、`CvServer/PointOfSaleService`（`Tran01Tenuri` / `Tran02PosSeisan`）。
