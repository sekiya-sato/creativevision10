## 3. 計算仕様

### 3.1 共通の丸め

```
Tax = Rounding( Σ(課税対象額 × 税率) / 100 )
```
丸めは `TranCalcBase.RoundTax(taxableAmount, taxRate, EnumRounding)` に集約済み。
**税額は常に正値**で保持し、返品等の符号はヘッダ `Kubun` から決まる `CalcFlag` が集計側で担う（既存方針を踏襲）。

### 3.2 明細（全ケース共通・保存時）

伝票種別によらず、明細には次を保存する。丸め方針が変わっても明細の内訳は必要になるため。

| 列 | 値 |
|----|-----|
| `Id_Tax` | `MasterShohin.Id_Tax` / `MasterMaterial.Id_Tax`（引けなければ 1） |
| `TaxRate` | 伝票日付時点の税率（`TaxRateResolver.ResolveTaxRatePercent`） |
| `Tax` | 伝票単位のときのみ按分値、請求単位のときは **0** |

明細 `Tax` は「伝票内で税区分ごとに丸めた額」を明細へ按分した参考値であり、
ヘッダ `Tax1/2/3` が正となる（合計は必ず一致させる）。

### 3.3 伝票単位（`TaxCalcUnit = 1`）

伝票入力・保存時に確定する。

```
TaxableAmountN = Σ |明細.Kingaku|   (明細.Id_Tax = N)
TaxN           = RoundTax(TaxableAmountN, 税率N, ヘッダ.TaxRounding)
Total          = |KingakuTotal| + Tax1 + Tax2 + Tax3
```

同一税区分内で税率が混在することは無い（税率は伝票日付から一意に決まる）ため、
`TaxableAmountN` に対して1回丸めれば足りる。

### 3.4 請求単位（`TaxCalcUnit = 0`）

伝票入力・保存時:

```
TaxableAmountN = Σ |明細.Kingaku|   (明細.Id_Tax = N)
TaxN           = 0
Total          = |KingakuTotal|
```

請求計算（`CalcSummaryUriSei`）／支払計算（`CalcSummaryKaiShi`）時:

```
Summary.TaxableAmountN = Σ(伝票.TaxableAmountN × 符号)      -- 締請求期間の全伝票
Summary.TaxN           = RoundTax(Σ(期間内の課税対象額 × その伝票日の税率), 取引先.TaxRounding)
```

**期中の税率改定**: `MasterSysTax` は税区分ごとに `TaxRate`（現行）と
`DateFrom` 以降の `TaxNewRate`（新）の2値しか持たない。締請求期間が `DateFrom` をまたぐ場合は、
SQL 側で `DenDay >= DateFrom` の有無で課税対象額を2分し、それぞれに税率を掛けてから合算し、
**期間全体で1回だけ**丸める。これで税率改定跨ぎでも誤差が出ない。

売掛月次（`CalcSummaryUriKake`）／買掛月次（`CalcSummaryKaiKake`）も
`KakeDay` を締日で月へ畳み込んでおり請求と同じ期間境界になるため、同一の計算式を使う。

> **注意：売掛月次と請求残で税額が一致しないことがある（決定 2026-09-01：許容する）**
> `CalcSummaryUriKake` は **自社締日** `MasterSysman.ShimeBi` で `KakeDay` を月へ畳み込むのに対し、
> `CalcSummaryUriSei` は **得意先締日** `MasterTokui.Shime1` で締請求期間を決める（`SummaryDb.cs:32-43` / `857`）。
> 締日が異なれば集計期間の区切りが変わるため、請求単位（期間で1回丸め）の得意先では
> `SummaryUriKake.Tax1/2/3` と `SummaryUriSei.Tax1/2/3` が一致しないことがある。
> **これは仕様として許容する。** 売掛月次は自社の月次管理値、請求残は得意先へ提示する確定値であり、
> 目的が異なるため一致させる必要はない。
> 現行データは `ShimeBi = 99` かつ得意先全件 `Shime1 = 99` のため結果的に一致している。
> 締日が多様化（第2段階の最大3締日対応を含む）すると差が出るが、**不具合ではない**。
> 突合資料を作る場合は、どちらの期間で切ったものかを明示すること。

### 3.5 伝票単位と請求単位の混在

`TaxCalcUnit` は**伝票ヘッダのスナップショット値**で判定する。
1つの締請求期間に両方の伝票が混ざり得る（期中に取引先設定を変えた場合）ため、請求計算は

```
Summary.TaxN = Σ(伝票単位の伝票の TaxN)                                  -- 既に丸め済み
             + RoundTax(Σ(請求単位の伝票の TaxableAmountN × 税率), 端数)   -- 期間で1回丸め
```

とする。伝票単位ぶんは伝票の値をそのまま信用し、二重丸めを避ける。

**制度上の根拠（決定 2026-09-01）**: 「伝票単位」設定の取引先では、
**個々の伝票（納品書）を適格請求書として交付する**運用を採る。
適格請求書の「税率ごとに1回の端数処理」は納品書1枚ごとに満たされるため、
月次請求書は伝票の `Tax1/2/3` を単純合算すればよく、請求書側で丸め直してはならない。
「請求単位」設定の取引先では月次請求書そのものが適格請求書となるため、
締請求期間で1回だけ丸める。

### 3.6 税区分と税率の対応制約

丸めのグルーピングキーは税区分（`Id_Tax` = `MasterSysTax.Id` 1-3）とする。
制度が求めるのは「**税率**ごとに1回の端数処理」なので、
**同一適用日において同一税率となる `Id_Tax` を複数定義してはならない**。

現状の確認結果:

| 出所 | Id=1 | Id=2 | Id=3 | 実際に解決される税率 |
|------|------|------|------|----------------------|
| 旧CVnet 実データ (`HC$master_systax`) | `TaxRate=8` / `DateFrom=20191001` / `TaxNewRate=10` | `8` / `20191001` / `8` | `15` / `19010101` / `0` | Id=1: 8%→10%、Id=2: 8%、**Id=3: 常に15%** |
| 初期シード (`DefineDataTable.cs:193`、修正前) | 10% | 8% | 10% | **Id=1 と Id=3 が同率で重複** |

- 初期シードの Id=3 は Id=1 と同率で制度違反を作り込むため、未使用枠の 0% へ修正した（commit `0b86e47`）。
- 旧実データは 2019/10/01 より前で Id=1 と Id=2 がともに 8% だが、
  期首日以前は期首残高として凍結し再計算しないため実害はない。

> **旧データ Id=3 の注意（2026-09-01 判明）**
> `CvAsset.Common.CompareYmd(ymd1, ymd2)` は `ymd2` が初期値 `19010101` 以下なら
> **必ず -1 を返す**（`CvAsset/CommonClass.cs:109`）。`DateFrom` を「未設定」とみなす仕様である。
> そのため旧実データの Id=3（`DateFrom=19010101`）は `TaxNewRate=0` が一切効かず、
> **常に現行税率 15% として解決される**。15% は実在しない税率であり、明らかな不正データ。
> Id=3 を割り当てた商品があると 15% で課税されるので、移行後に Id=3 を使うなら税率定義を修正すること。

#### 3.6.1 税率重複チェックの詳細設計

`MasterSysman` 保守画面の保存時に、税率が重複する `Id_Tax` の組を検出して利用者へ知らせる。

**判定対象**
`MasterSysman.Jsub`（`List<MasterSysTax>`、`Id` 1-3）の各要素が持つ
`TaxRate`（現行税率）/ `DateFrom`（新税率の適用開始日 yyyyMMdd）/ `TaxNewRate`（新税率）。

**適用期間の考え方**
`TaxRateResolver.ResolveTaxRatePercent` と同じ判定にする。すなわち各 `Id_Tax` は
`DateFrom` を境に「`DateFrom` より前 = `TaxRate`」「`DateFrom` 以降 = `TaxNewRate`」の2区間を持つ。
`DateFrom` が未設定・8桁でない場合、および初期値 `19010101` 以下の場合は
切替が無いものとして全期間 `TaxRate` を使う。切替判定は `TaxRateResolver` の
`ResolveRateOf`（private）に1箇所だけ置き、`ResolveTaxRatePercent` と重複チェックの双方がこれを使う。

**判定手順**
1. 全 `Id_Tax` の `DateFrom`（妥当な8桁のみ）を集めて昇順に並べ、区間の境界とする。
   境界が n 個なら比較すべき区間は n+1 個（最初の区間は「最も早い `DateFrom` より前」）。
2. 各区間について、`Id_Tax` 1-3 の適用税率を求める。
3. 同一区間で**税率が一致する `Id_Tax` の組**があれば重複とする。
4. **税率 0 どうしの重複は警告しない。** 0 は非課税・未使用枠を意味し、
   複数の枠が未使用であるのは正常な運用だから。
5. 同じ組み合わせが複数区間で重複しても、報告は 1 組につき 1 件にまとめる
   （どの期間で重複したかは併記する）。

**利用者への提示**
- **保存を禁止しない。** 移行途中や一時的な設定変更で重複が生じ得るため、
  確認ダイアログで続行するかを尋ねる（`MessageEx.ShowQuestionDialog`）。
- メッセージにはどの `Id_Tax` どうしが何%で、いつから重複しているかを具体的に示す。

**実装場所**
判定ロジックは ViewModel から切り離した純粋な `static` メソッドとし、
`CvWpfclient` を参照できない `Tests/TestServer` から単体テストできるよう `CvBase` 側へ置く。

**テスト観点**
1. 重複あり（同一区間で 2 つの `Id_Tax` が同率）→ 検出される
2. 重複なし（10% / 8% / 0%）→ 検出されない
3. 税率 0 の重複（複数の未使用枠）→ 検出されない
4. `DateFrom` の前後で判定が変わる（切替前は重複、切替後は解消／その逆）
5. `DateFrom` が未設定・不正な8桁でない → 全期間 `TaxRate` として判定される

### 3.7 `TaxRounding` の解決順

1. 伝票ヘッダの `TaxRounding`（入力時に取引先から転記済み）
2. 伝票に無い場合（旧データ）は取引先マスタの `TaxRounding`
3. 取引先も引けない場合は `MasterSysman.TaxRounding`

`Tran01Tenuri`（店舗売上）は `Id_Tenpo` の `MasterTokui` を 2. に使う。

### 3.8 掛残・請求残の金額は税抜で積む

**2026-09-01 発覚・同日修正。** `SummaryDb` の4メソッド
（`CalcSummaryUriKake` / `CalcSummaryUriSei` / `CalcSummaryKaiShi` / `CalcSummaryKaiKake`）は、
売上・仕入の内訳（`Uriage` / `Henpin` / `Nebiki` / `Sonota` / `Shiire`）を
伝票の `Total` 列（`|KingakuTotal| + Tax1 + Tax2 + Tax3`、**税込**）で `SUM` していた。
そのうえで各テーブルの合計式は

```
TotalSales = Uriage - Henpin - Nebiki + Sonota + (Tax1+Tax2+Tax3)
TotalShiire = Shiire - Henpin - Nebiki + (Tax1+Tax2+Tax3)
```

としており、`Uriage` 等に含まれる消費税ぶんへさらに `Tax1+Tax2+Tax3` を加算していたため、
**消費税が二重に計上されていた**。実データで確認したところ `Tran00Uriage` 50,322件中
50,311件が税込（`Total ≠ KingakuTotal` かつ `Total = |KingakuTotal| + Tax1+Tax2+Tax3` の関係）であり、
伝票単位・請求単位のいずれの取引先でもこの二重計上が発生していた。

修正は、内訳の集計元を `t.Total`（税込）から `ABS(t.KingakuTotal)`（税抜、常に正値）へ置き換えることで行った。
`Tran02Material` の区分99（その他、仕入ではなく消費税へ全額を積む特殊処理、A-6）も同様に
`ABS(t.KingakuTotal)` へ揃えている。結果、

```
TotalSales = 税抜売上(KingakuTotal合計) - 返品 - 値引 + その他 + 消費税(Tax1+Tax2+Tax3)
TotalShiire = 税抜仕入(KingakuTotal合計) - 返品 - 値引 + 消費税(Tax1+Tax2+Tax3)
```

となり、二重計上が解消される。当時は `Balance` は `TotalSales` / `TotalIn`（買掛側は `TotalShiire` /
`TotalOut`）から導出されるため、この修正だけで連動して正しくなるとしていたが、その後の
`Doc/spec/archive/2026-09-02_Summary残高_期間集計化とPreviousBalance_詳細設計.md` により、
**`Balance` 自体の式・符号規約が変更された**（繰越の積み上げをやめ、`Balance = TotalSales - TotalIn`
〔債務側は `TotalShiire - TotalOut`〕の当期間ネット・正＝未回収／未払へ統一）。
前残が必要な場面は `PreviousBalance`（表示専用・SQLで都度算出）を使う。詳細は同設計書を参照。

**影響（重要）**: この修正により、既存の売掛残・請求残・買掛残・支払残の金額（`Uriage` / `TotalSales` /
`Shiire` / `TotalShiire` / `Balance` 等）はバージョンアップの前後で変わる。
**バージョンアップ後は、影響を受ける全期間について4メソッドの再計算（全体再計算）が必要**である。
再計算しないまま新バージョンの画面・帳票を旧集計行に対して使うと、旧数値（二重計上ぶんを含む）が残ったままになる。

**期首残高CSVとの整合（フェーズ5で確認済み、commit `b5f583b`）**:
期首残高CSV（`OpeningBalanceCsv`）の内訳列（売上／仕入・返品・値引・消費税1-3・課税対象額1-3）は
Summary 各テーブルと同じく**税抜**が前提であり、消費税は元々 `Tax` 列として売上等とは別に保持していたため、
本修正で不整合は生じない。`OpeningBalanceCsv` のクラスコメントに税抜前提と移行元換算の注意書きを追記した。
なお期首以前は凍結され再計算しないため、期首残高そのものは本修正の影響を受けない。

### 10.2 最初に押さえるべき勘所

1. **`CvBase/TaxCalculator.cs` が税計算の唯一の入口。** 入力ViewModel・HHT・配分出荷・
   一括再計算はすべてここを通る。新しく伝票を作る処理を書くときも必ずこれを使うこと。
   `CvWpfclient` は `CvDomainLogic` を参照しないため、共通ロジックは `CvBase` に置く。
2. **請求単位（`TaxCalcUnit=0`）が実運用の全件。** 伝票の `Tax1/2/3` は 0 で、
   税額は `SummaryDb.CalcSummaryUriSei` / `CalcSummaryKaiShi` が締請求期間で1回だけ丸めて確定する。
   「伝票を見たら消費税が 0 だ」は正常。
3. **`TaxableAmount1/2/3` が請求計算の入力。** ここが 0 の伝票は請求計算で税額 0 になる。
   移行直後や `TranTaxRebuildDb` 未実行だとこの状態になる（8章 手順4）。
4. **`Tran*.Total` は税込、`Summary*.Uriage/Shiire` は税抜。** 3.8 の修正でこの区別が入った。
   集計SQLを書くときに `t.Total` を足すと消費税が二重計上になる。`ABS(t.KingakuTotal)` を使うこと。
5. **税額は常に正値。** 返品等の符号はヘッダ `Kubun` から決まる `CalcFlag` が集計側で担う。
   明細やヘッダで符号を付けると二重反転になる。
6. **`Tran99Meisai.Tax`（明細JSON）はリネームしていない。** `json_extract(m.value,'$.Tax')` は正常。
   リネームしたのは伝票ヘッダと Summary の `Tax` 列だけ。

### 10.3 踏み抜きやすい落とし穴

- **SQL文字列はコンパイラが検出しない。** 今回この理由で約85箇所が壊れていた。
  列名を変えたら `Doc/test/**` と `Doc/spec/tools/**`（メインsolution外・ビルドで検出されない）まで走査すること。
- **`dotnet test` はこの環境で 0 件になる。** `TestServer.exe` を直接実行する。
- **`CvAsset.Common.CompareYmd(ymd1, ymd2)` は `ymd2` が `19010101` 以下なら必ず -1。**
  「未設定」を表す仕様。旧データの `MasterSysTax` Id=3 がこれに該当し、常に 15% として解決される（3.6の注記）。
- **`TaxRateResolver.DefaultTaxRatePercent`(10%) は「定義が引けないとき」専用**（D9）。
  税率 0% を 10% へ読み替えてはいけない。未使用枠の売上に課税してしまう。
- **`TaxCalcUnit`/`TaxRounding` は伝票作成時点のスナップショット（監査値）。**
  既存伝票の読込時に上書きしないこと。マスタを変えても過去伝票の税額が再現できる必要がある。
  一方、請求計算の丸めに使うのは**取引先マスタの現在値**であって伝票のスナップショットではない（3.5）。
- **`WriteEffectRunner.PartialUpdateDeniedColumns`** に税関連の列を足し忘れると、
  部分更新APIで直接書き換えられて集計と整合しなくなる。例外にならないので気付きにくい。
