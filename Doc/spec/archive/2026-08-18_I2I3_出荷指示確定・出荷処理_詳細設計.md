## 1. 目的とスコープ

旧CV.netの「出荷指示確定」「出荷処理」に相当する2段階フローを画面から実行できるようにする。
サーバ側ロジック `ShippingDb`（`ConfirmShipping` / `CancelConfirm` / `CreateShippingSlips`）は
実装済み・テスト済みだが、**gRPCハンドラに未接続**（Msg・param型が無い）。本作業で接続し、3画面を作る。

- 出荷指示確定(商品) / (得意先): 未確定の配分を選んで `KakuteiDay` を立てる。有効在庫割れは全件エラー。誤確定の取消も可能。
- 出荷処理入力: 確定済みの配分に実数量(`JitsuSu`)を入れ、出荷売上／移動伝票を作成し `EndFlag=1`（引当解除）。

**`ShippingDb` は変更しない**（テスト済みのドメインロジックを保つ）。サーバは薄いハンドラでトランザクションを張って呼ぶだけ。

## 2. 業務モデルと状態遷移

配分行(`TranHaibun`)の状態は3列で表す（判断材料 5.1.2）。

| 状態 | `KakuteiDay` | `JitsuSu`/`ShortSu` | `EndFlag` | 引当(`ReserveQty`) |
|---|---|---|---|---|
| 未確定 | 空 | 0 | 0 | `Su` を積む |
| 確定済み(未処理) | 有効日付 | 出荷処理で設定 | 0 | `JitsuSu` を積む（下記注） |
| 出荷処理済み(完了) | 有効日付 | 設定済み | 1 | 積まない（解除） |

状態遷移:

```
未確定 ──[出荷指示確定 ConfirmShipping]──▶ 確定済み ──[出荷処理 CreateShippingSlips]──▶ 完了(伝票生成+引当解除)
  ▲                                          │
  └──────────[確定取消 CancelConfirm]─────────┘  （伝票未作成 RelateNo2=0 のときだけ）
```

- **確定は伝票を作らない。** `KakuteiDay` を立て、倉庫へのピッキング指示を確定するだけ。有効在庫（`Su - ReserveQty`）が
  1SKUでも負になる場合は**1件も確定しない**（`ShippingDb.ConfirmShipping` が検証）。
- **引当のタイミング注記（既存設計の性質、本作業では変えない）**: `ReserveQtySumExpr` は
  「未確定=`Su` / 確定済み=`JitsuSu`」で積む。確定直後は `JitsuSu=0` だが、`ConfirmShipping` は引当を再計算しない
  ため、materialize済みの `ReserveQty` は確定前の値（`Su` ぶん）のまま保たれる。実数量は続く出荷処理入力で設定し、
  そこで `CalcHaibun2Reserve` が走って正しい引当へ更新される。確定と出荷処理の間に**全件Rebuildを挟むと**
  一時的に引当が0扱いになる既知の隙間があるが、通常運用（確定→即出荷処理）では表面化しない。台帳の残課題とする。

## 3. サーバ設計（CvBase / CodeShare / CvServer）

### 3.1 パラメータ・結果型（`CvBase/Parameters.cs` に追加）

```csharp
// 出荷指示確定。KakuteiDayを立てる。有効在庫割れは全件エラーで1件も確定しない。
public sealed record ShippingConfirmParam(long[] HaibunIds, string KakuteiDay);
// 確定取消。伝票未作成(RelateNo2=0)の確定済み行のKakuteiDayを空へ戻す。
public sealed record ShippingCancelParam(long[] HaibunIds);
// 出荷処理。実数量を確定し、出荷売上/移動伝票を作成、EndFlag=1で引当解除。
public sealed record ShippingCreateParam(ShippingCreateRow[] Rows, string DenDay, long IdShain);
public sealed record ShippingCreateRow(long Id, long ExpectedVdu, int JitsuSu);

public sealed record ShippingConfirmResult(int ConfirmedCount);
public sealed record ShippingCancelResult(int CanceledCount);
public sealed record ShippingCreateResult(long[] CreatedSlipIds, int ReleasedCount);
// 有効在庫割れ1件（画面へ返す）
public sealed record ShippingShortageDto(long Id_Soko, long Id_Shohin, long Id_Col, long Id_Siz, int Shiji, int Yuko);
```

`ShippingConfirmError`（`ShippingDb` 内の record struct）はサーバ専用なので、ワイヤ用の
`ShippingShortageDto` を CvBase に置き、ハンドラで詰め替える（クライアントは CvDomainLogic を参照しない）。

### 3.2 エラーコード（`CodeShare/ICoreService.cs` の `CvMsgErrorCode` に追加）

```csharp
public const int ShippingUnavailable = -9903;  // 有効在庫割れ。DataTypeに ShippingShortageDto[] を載せて返す
```

### 3.3 ハンドラ（`CvServer/Services/HandlerClass.cs` の `HandleOpExecute` に分岐追加）

```csharp
ShippingConfirmParam confirm => HandleShippingConfirm(request.Flag, confirm),
ShippingCancelParam  cancel  => HandleShippingCancel(request.Flag, cancel),
ShippingCreateParam  create  => HandleShippingCreate(request.Flag, create),
```

- **HandleShippingConfirm**: `BeginTransaction(Serializable)` →
  `new ShippingDb(_db).ConfirmShipping(ids, kakuteiDay, out errors)` →
  errors有 → `AbortTransaction`、`CvMsgErrorCode.ShippingUnavailable` と `ShippingShortageDto[]` を返す。
  errors無 → `CompleteTransaction`、`ShippingConfirmResult(count)` を返す。
- **HandleShippingCancel**: `Begin` → `CancelConfirm(ids)` → `Complete`、`ShippingCancelResult(count)`。
- **HandleShippingCreate**: `Begin` → `ShippingDb.ProcessShipping(rows, denDay, idShain, out conflict)` →
  conflict → `Abort`＋`ConcurrentUpdate`／正常 → `Complete`、`ShippingCreateResult(createdIds, releasedCount)`。

**`ShippingDb` への追加メソッド `ProcessShipping`**（既存メソッドは変更しない）:
実数量の設定と伝票作成をまとめる薄いメソッドを1本足す。テスト容易性のため
`CoreService` のDIを介さず CvDomainLogic 単体でテストできるようにする。
1. 対象行（`EndFlag=0` かつ `KakuteiDay<>''`）の現在の `Vdu` と指示数 `Su` を取得。
2. **全行の存在と `Vdu` 一致を先に検証**し、1件でも不一致なら**何も書かずに** `concurrencyConflict=true` で返す（fail-fast）。
3. 各行に `JitsuSu = clamp(入力, 0, Su)`、`ShortSu = Su - JitsuSu`、`Vdu` を設定。
4. 既存の `CreateShippingSlips(ids, denDay, idShain)` を呼んで伝票作成＋`EndFlag=1`＋引当解除。
`releasedCount` は完了にした配分行数（＝入力行数）、`CreatedSlipIds` は作成した伝票Id。

いずれも `Msg201_Op_Execute`（既存の書き込みMsg）で送る。**新規Msgフラグは追加しない**
（StocktakeはストリーミングのためMsgを足したが、確定・出荷処理は即時応答なので既存の実行Msgに相乗り）。

### 3.4 検証（TestServer に追加）

## 4. クライアント設計（CvWpfclient）

### 4.1 出荷指示確定（商品／得意先）— 共通基底＋2サブクラス

`BaseZanCompletionViewModel`（残完了設定）と同型の「一覧取得 → 実行」2段構成。

- 一覧行 `ShippingConfirmRow`: `Id`, `Vdu`, 指示日, 納品日, 倉庫, 出荷先(得意先＋TenType→出荷/移動), 商品, 色サイズ,

### 4.2 出荷処理入力

新規 `ViewModels/07Haibun/ShippingInputViewModel.cs`（`BaseQueryViewModel` を継承）。

- 検索条件: 確定日(`KakuteiDay`) from-to、倉庫CD、出荷先CD、最大件数。

  成功で「n件の伝票を作成し、m件を引当解除しました」を表示し一覧を取り直す。

## 6. 受入確認（Given/When/Then）

- G/W/T-1（確定・正常）: 未確定配分を選び確定実行 → `KakuteiDay` が立ち、一覧の状態が「確定済み」になる。
- G/W/T-2（確定・割れ）: 有効在庫を超える指示を確定 → 1件も確定せず、割れたSKU一覧がダイアログに出る。
- G/W/T-3（取消）: 確定済み(伝票未作成)を取消 → `KakuteiDay` が空へ戻る。伝票作成済みは対象外。
- G/W/T-4（出荷処理・全量）: 確定済みを既定(実数量=指示数)で処理 → 出荷先TenTypeに応じ `Tran00Uriage`/`Tran10IdoOut` が
  1仮想ヘッダ=1伝票で作られ、`RelateNo2` と `EndFlag=1` が立ち、引当が解除される。
- G/W/T-5（出荷処理・欠品）: 実数量を指示数未満で処理 → `ShortSu` が入り、出荷は実数量ぶん。全量欠品(実数量0)は伝票を作らず完了だけ立てる。
- G/W/T-6（楽観排他）: 他端末が更新した行を出荷処理 → `ConcurrentUpdate` で全件rollback、一覧再取得を促す。
