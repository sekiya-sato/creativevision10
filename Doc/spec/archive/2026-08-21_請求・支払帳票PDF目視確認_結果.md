## 1. 目的と位置づけ

チェックリスト §8.1-2 の残作業「帳票PDFの目視確認」を実施した。SQL層の数値突合は `tools/summaryreconcile` で成立済みであり、
本書は **qfm による PDF 実出力が、保存済み `SummaryUriSei` / `SummaryKaiShi` の値をレイアウトどおり印字するか** を確認した記録である。

WPFクライアント経由の操作（画面→gRPC→サーバPDF生成）ではなく、サーバ `PrintPdfService` と同じ経路
（SQL → CSV(`data.txt`, Shift_JIS) → `PrintAdapter`/`FormWriter.PDF`）をローカルで再現して確認した。
このため **画面操作・ダイアログ・PDFビューアの確認は含まない**（Mini-UAT D-09 の範囲）。

## 2. 実施手順（再現手順）

1. 開発DBを退避: `refer/back/P0PDF_20260821_pre-seed_server-user163.db`（9.6GB、`CvServer/server-user163.db` のコピー）。
2. テストデータ投入と請求・支払計算: `dotnet run --project tools/summaryreconcile -- seed <dbPath>`。
   テスト月 202607（得意先 000002 / 000014、仕入先 001 / 002）。
3. 各帳票 ViewModel の `BuildPrintSqlParamAsync` と同一のSQL（パラメータをリテラル展開）を開発DBへ実行し、
   `WriteDynamicCsv` と同じ体裁（ヘッダ無し・必要時のみ二重引用符）のCSVを **Shift_JIS(cp932)・CRLF** で `data.txt` として生成。
4. `qfmprint.exe <printform/*.qfm> <workdir>` で実PDFを描画（`CheckLicense` の3プロダクトとも `status=True`）。
5. PDFのテキスト層を座標付きで抽出し、行ごとに突合（poppler の `pdftotext` は Adobe-Japan1 の CMap を持たず抽出不可のため、
   コンテンツストリームを inflate して `Tm`/`Td` 座標と `Tj` 文字列を UTF-16BE として復号する方法で確認した）。

### 手順上の注意（今回の教訓）

`sqlite3 -csv` の出力を Windows の標準出力リダイレクトで受けると改行が `\r\r\n` になる。
この `data.txt` を PrintStream へ渡すと **全レコードが2行に重複印字**され（2行目は先頭列が欠落）、
qfm 側の不具合と誤認する。実サーバは `StreamWriter`＋`WriteLine` で `\r\n` 単独のため発生しない。
検証データは必ず `\r\n` 単独にすること。

## 4. 指摘事項

| ID | 内容 | 状態 |
|---|---|---|
| R-01 | 金額列がカンマ区切りされず `92300` と印字されていた | **2026-08-23 対応済み**。6帳票の金額26項目を `<decode datatype="number" format="MI999,999,990"/>` へ変更（旧cvnet請求帳票・`DeliveryScheduleTable.qfm` と同書式）。再描画で `92,300` / `-41,860` を確認。値・列順・右寄せ(`halign="right"`)は不変 |
| R-02 | 残高・予定額が負値（`-41,860`）で印字される | **仕様として確定**。マイナス表示のままとする（`MI` 書式が負数に `-` を付ける） |
| R-03 | ローカル描画はフォント埋め込みが実サーバと異なり、CJKグリフのラスタ差異が出る | qfmprint harness の既知の制約。最終確認は実サーバ出力で行う |

カンマ区切り対象は金額列のみとし、件数（`再発行` 世代・`締回数`）とコード・日付は文字列のまま据え置いた。
