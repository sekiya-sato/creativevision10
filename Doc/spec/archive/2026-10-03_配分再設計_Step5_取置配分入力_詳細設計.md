## 1. 決定済みの前提

| ID | 決定 |
|---|---|
| D5 | 取置は「店舗売上へ変換」するか、「取消・期限切れで自動取消」で終わる |
| D6 | 取置の相手は、店舗の一般顧客（`MasterEndCustomer`） |
| D10 | 店舗売上は、当面 CV10 の取置画面の「売上変換」で `Tran01Tenuri` を作る。POS の会計で取置を消化する連携は 1.1 以降。**同じ商品を POS でも会計すると二重計上になる**（運用で防ぐ） |

区分は `EnumHaibun.Reservation`(6)。区分 6 は Step 1 から確定 API（`HaibunCommitParam`）の対象外で、配分確定画面・滞留一覧にも出ない。

## 3. データ

### 3.1 列の追加（migration `UpdateDb`）

| 列 | 型 | 既定 | 意味 |
|---|---|---|---|
| `Id_Customer` | NUMBER | 0 | 取置の顧客（`MasterEndCustomer.Id`）。区分 6 だけが使う |
| `LimitDay` | TEXT | '' | 取置の期限日 yyyyMMdd。区分 6 だけが使う |
| `EndReason` | NUMBER | 0 | 完了の理由。0 = 通常（確定・欠品）、1 = 売上変換、2 = 取消、3 = 期限切れ。区分 6 だけが 1〜3 を使う |

```sql
ALTER TABLE TranHaibun ADD COLUMN Id_Customer NUMBER not null default 0;
ALTER TABLE TranHaibun ADD COLUMN LimitDay TEXT not null default '';
ALTER TABLE TranHaibun ADD COLUMN EndReason NUMBER not null default 0;
```

- 既存データの区分 6 は 0 件の想定（取置画面がなかったため）。
- 顧客名は、ほかの `TranHaibun` の列と同じく Id だけを持ち、表示時にマスタから引く。

### 3.2 取置 1 件の値

| 列 | 値 |
|---|---|
| `Kubun` | 6 |
| `Id_Tenpo` | 取置した店舗（`TenType = 6`、直営店） |
| `Id_Soko` | 在庫を押さえる拠点。店舗自身（`Id_Tenpo` と同じ値） |
| `Id_Customer` | 顧客 |
| `DenDay` | 取置日 |
| `LimitDay` | 期限日（初期値は取置日 + 7 日） |
| `Su` | 取置数 |
| `Tanka` / `Jodai` | 取置日時点の店舗の上代。売上変換ではこの単価を使う（判断 3） |
| `RelateNo1` | 0 |
| `RelateNo2` | 売上変換で作った `Tran01Tenuri.Id` |

引当は Step 4 の算式のまま（区分 6 は未完了の間 `Su` を引当に積む）。

## 4. 処理

### 4.1 登録・変更（既存の `HaibunSaveParam`）

- 画面で 1 件ずつ登録する。
- 数量・期限日の変更は、洗い替え（置換対象 1 件と新しい行 1 件）で行う。
- サーバ（`AllocationRules.ValidateNewRow`）が、区分 6 について次を検査する。
  - `Id_Customer > 0`
  - `LimitDay` が 8 桁で、`DenDay` 以降
  - `Id_Soko = Id_Tenpo`
- **在庫検査（判断 2：警告だけ）**
  - サーバは在庫で保存を止めない（ほかの区分と同じ）。店舗在庫の精度が分からないため（7 章 2 の事実）。
  - 画面は、登録・数量変更の前に、その店舗×SKU の有効在庫（実在庫 − 引当。数量変更では自分の行の分を戻す）が取置数より少なければ、確認ダイアログで警告し、［はい］なら登録する。

### 4.2 売上変換（`ReservationConvertParam` → `ReservationDb.Convert`）

1. 対象行を取得する。次のいずれかに当たれば競合として、何も書かない。
   - 区分 6 でない
   - 完了している（`EndFlag = 0` でない）
   - `Vdu` が画面取得時と一致しない
2. 店舗×顧客ごとに 1 伝票の `Tran01Tenuri` を作る。
   - `Kubun = 10`（売上）
   - `Id_Tenpo` / `Id_Soko` / `Id_Customer`。V* 列は伝票時点の名称として埋める
   - `DenDay` = 画面の売上日
   - `Memo = "取置売上"`
3. 明細の作り方
   - 単価は取置行の `Tanka`。
   - 消費税区分は商品マスタの `Id_Tax`。
   - 税計算は POS と同じ `TaxCalculator.Apply`（伝票単位、店舗の端数処理）。
4. 在庫を計上する（`CalcTran2SummaryStock(Tran01Tenuri, Id_Soko)`）。
5. 取置行を更新する。
   - `EndFlag = 1`、`JitsuSu = Su`、`ShortSu = 0`
   - `KakuteiDay` = 売上日、`RelateNo2` = 伝票Id、`EndReason = 1`
6. 引当を引き直す。

### 4.3 取消（`ReservationCancelParam` → `ReservationDb.Cancel`）

- 競合の検査は 4.2 と同じ。
- 取置行を `EndFlag = 1`、`JitsuSu = 0`、`ShortSu = Su`、`KakuteiDay` = 当日、`EndReason = 2` にする。伝票は作らない。
- 引当を引き直す。

### 4.4 期限切れの自動取消（`ReservationDb.ExpireOverdue(today)`）

- 対象: 区分 6 で未完了のうち、`LimitDay < today` の行。
- 4.3 と同じ更新をする。ただし `EndReason = 3`、`KakuteiDay` は期限日の翌日にする。
- スケジューラの日次タスク「取置期限切れ自動取消」から呼ぶ。
  - cron の既定は `50 0 * * *`（毎日 0:50）、既定は有効。
  - `MasterConfig` の `AutoExecJobDefault` 一覧に追加し、`SchedulerService` にジョブを登録する（既存の上代パージと同じ作り）。
- 期限日当日は有効、翌日に取消になる。

### 5.2.1 実装時の補足

- 顧客の［選択］は、その店舗の顧客（`MasterEndCustomer.Id_Tenpo` = 店舗）だけを出す。ほかの店舗の顧客はコードを直接入力する（選択画面の並び順を店舗優先に変える仕組みがないため）。
- 商品コードを打ち替えたまま［取置登録］を押した場合は、色サイズを読み直して登録を止める（前の商品の色サイズで登録しないため）。
- 店舗を選び直したら、［検索］を押すまで一覧・登録・変更を操作できない（前の店舗に登録しないため）。期限日を今日より前にする登録・期限変更は確認を出す。
- 売上変換で作る店舗売上は決済内訳（`JposPayment`）を持たないので、売上金種Viewerの金種別には出ない（手入力の店舗売上と同じ）。店頭で受け取った代金はレジ精算との差として扱う運用になる（D10 の POS 連携までの制約）。
- サーバは売上日・取消日が yyyyMMdd の実在日か、取置の出庫元が店舗と同じかを検査し、外れれば何も書かない（独立レビュー指摘）。
- 取消ボタンのコマンド名は `CancelReservationCommand`。`BaseWindow` は閉じるときに名前が「CancelCommand」で終わるコマンドを中断用とみなして実行するため、`DoCancelCommand` にすると画面を閉じるだけで取消が走る。

### 5.3 POS との二重計上の注意（D10）

- 画面上部に常に「取置の売上は、この画面の［売上変換］で計上します。POS で同じ商品を会計しないでください。」と出す。
- ［売上変換］の確認ダイアログでも同じ注意を出す。

## 7. 承認時の判断（2026-10-03 決定）

- 1・3〜6 は推奨どおり。2 は「警告だけ」の案に決定（以下は承認依頼時の記載）。

1. **列の追加**: `Id_Customer` / `LimitDay` / `EndReason` の 3 列を `TranHaibun` に追加する方式でよいか（フラット構造を維持する D3 の範囲内）。
2. **取置時の在庫検査**: 取置は、保存時に店舗の有効在庫を厳密に検査し、不足ならエラーにしてよいか（ほかの区分は警告だけ）。
   - 取置は確定の段階がなく、売上変換まで在庫検査の機会がないため。
   - **注意（開発DBで確認した事実）**: 直営店（`TenType=6`）の現在庫（`SummaryRealStock`）は 126 店の合計で −2,051,264 点と大きくマイナスになっている（店舗売上は 3,432,479 件すべて `Id_Soko = Id_Tenpo`）。店舗在庫が実態と合っていない場合、厳密に検査すると取置がほとんど登録できない。
   - 代わりの案: 在庫不足は**警告だけ**にして登録はできるようにする（ほかの区分と同じ扱い）。店舗在庫の精度が分からない間は、こちらのほうが安全。
3. **売上変換の単価**: 取置した日の店舗上代（取置行に保存した単価）でよいか。
   - もう一つの案は、変換した日の上代を引き直す方式。
4. **期限切れの扱い**: 期限日の翌日 0:50 の日次タスクで自動取消し、既定を有効にしてよいか。
5. **在庫の拠点**: 取置の在庫拠点（`Id_Soko`）は店舗自身でよいか。開発DBで、店舗売上はすべて `Id_Soko = Id_Tenpo`、直営店の在庫も店舗の Id で管理されていることを確認済み。
6. **履歴の見せ方**: 取置の取消・期限切れの履歴は取置画面（状態＝完了を含む）で見ることにし、滞留・欠品例外の欠品実績からは区分 6 を除いてよいか。
