## 2. サーバは変更しない（既存経路の再利用）

I2/I3 で実装済みの `Msg201_Op_Execute` 経路をそのまま使う。**新規Msg・param・スキーマ変更はなし**。

- **確定取消** … `ShippingCancelParam(long[] HaibunIds)` → `ShippingDb.CancelConfirm`（伝票未作成の確定を `KakuteiDay=''` へ戻す）。
- **強制完了（全量欠品）** … `ShippingCreateParam(rows[(Id,Vdu,JitsuSu=0)], DenDay=今日, IdShain=0)` → `ShippingDb.ProcessShipping`。
  実数量0なので `CreateShippingSlips` は伝票を作らず（`JitsuSu>0` の明細が無い）、対象行に `EndFlag=1`＋引当解除だけを行う
  （既存の「全量欠品の行は伝票を作らずに完了だけ立てて引当から外す」挙動、テスト済み `CreateShippingSlips_AllShortage`）。

## 3. 画面設計（`ShippingConfirmList`）

`BaseQueryViewModel` 派生の照会＋一括操作画面（残完了設定・出荷指示確定と同型）。一覧は既存DBマップ型 `TranHaibun` を取得しクライアントで合成する。

### 3.1 表示区分（2モード）

- **滞留（既定）**: `EndFlag=0 AND ifnull(KakuteiDay,'')<>''`（確定済み・未処理）。
  経過日数＝今日 − `KakuteiDay`、`NouhinDay` 超過を併記。**滞留日数閾値以上**または**予定日超過**の行を出す（A）。
  ここでのみ例外操作（確定取消／強制完了）を行う。
- **欠品実績**: `EndFlag=1 AND ShortSu>0`（完了かつ欠品）。read-only の履歴照会。指示数・実数量・欠品数を出す。

### 3.2 検索条件

- 確定日 from-to（滞留）/ 完了日相当（欠品実績は `KakuteiDay` で代用）
- 倉庫CD、出荷先CD
- 滞留日数（≥N日、既定3）
- 「予定日超過のみ」トグル（滞留モード）
- 取得件数上限

### 3.3 一覧行 `ShippingStagnationRow`

`Id`, `Vdu`, 確定日, 納品予定日, **経過日数**, 予定日超過(bool), 倉庫, 出荷先, 種別(出荷売上/移動), 商品, 色/サイズ,
指示数(`Su`)。欠品実績モードでは 実数量(`JitsuSu`)・欠品数(`ShortSu`) も出す。選択CheckBox（滞留モード）。

倉庫・出荷先・商品・色サイズは `MasterTokui`/`MasterShohin`/`DerivedShohinColSiz` を引いて合成
（出荷指示確定画面 `BaseShippingConfirmViewModel` と同じ方式）。

### 3.4 操作（滞留モードのみ、複数選択→一括）

- **確定取消**: チェック行 → `ShippingCancelParam`。成功後に一覧再取得。
- **強制完了**: チェック行 → `ShippingCreateParam`（実数量0）。確認ダイアログで「出荷せず完了（全量欠品）にし引当を解除します」と明示。成功後に一覧再取得。
- 楽観排他競合（`ConcurrentUpdate`）は一覧破棄→再取得を促す。

### 3.5 メニュー

`MenuData.cs` の「出荷指示一覧印刷」を **「滞留・欠品例外（出荷指示一覧）」** に改名し、addInfo を interactive な滞留検出＋例外操作に更新する。純・帳票印刷版は follow-up。
