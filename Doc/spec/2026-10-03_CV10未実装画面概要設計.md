## 2. CV10全体の共通仕様案

以下は本概要設計の**提案**。既存承認事項以外は、承認後に各画面の詳細設計で型・API・SQL・DDLを確定する。

### 2.1 画面・通信・責務

- 既存 `BaseWindow`、CommunityToolkit MVVM、`App.xaml` と共有リソースを使用する。初期化は `InitCommand`、長時間処理は取消・進捗・結果表示を持つ既存方式に合わせる。
- マスタ系は近傍の `BaseMenteViewModel`、帳票は `BaseReportViewModel`／`PrintPdfHelper` を優先する。カルテ・実行画面は必要な範囲だけ個別ViewModelとする。
- 通信は既存 `ICoreService` のQuery／Streamとハンドラを使用し、計算・更新は `CvDomainLogic` に置く。新しい汎用エンジンや独自通信基盤は作らない。
- メニュー既存導線を使用し、機能完成後に当該「準備中」表示だけを更新する。配分メニューの改変は本書の対象外。
- 倉庫・店舗・商品・顧客は既存選択部品を使用。無制限の顧客全件ロードを避け、検索条件・取得上限・ページ単位取得を設ける。
- 通貨額とポイントは別量として扱う。件数・金額の合計は64bit／既存金額型を使い、現行int列へ保存する場合は範囲検査する。

### 2.2 更新・再実行・監査

| 処理 | 不変条件・方式案 |
|---|---|
| 単一マスタ更新 | 検索→編集→入力検査→保存。`Vdu`等の既存競合検査を使い、競合時は再読込して再編集 |
| 実行系 | 条件入力→プレビュー→対象選択→確認→サーバ再検査→実行→結果。プレビュー後に対象が変われば再取得を要求 |
| 一括更新 | 各画面で業務上の単位を定め、その単位で全件成功またはロールバック。長時間処理の取消は完了単位と未処理単位を区別 |
| 再送・再取込 | 実行ID・外部メッセージID・元伝票IDを使い、同じ業務結果を重複作成しない。通信タイムアウトを未実行と断定しない |
| 集計再実行 | 同じ条件・同じ元データなら同じ結果。集計は残高を置換し、付与取引を追加しない |
| 訂正 | 確定後の数量・残高の無根拠な直接更新を避ける。元取引を参照する訂正・取消の履歴を残す |
| 監査 | 実行者、条件、対象、日時、成功／失敗、元／生成伝票、変更理由を保存。外部連携の原文は別管理し、通常ログに顧客情報・秘密を出さない |

伝票の `V*` は伝票時点の値を維持する。マスタの現行名表示と混同しない。SKUは商品×色×サイズ、在庫はさらに拠点を含めて識別する。
SQLはSQLiteを正典とし、パラメータ化・既存JSON防御・方言実行経路を維持する。MariaDB／PostgreSQLの実DB検証は採用時の受入条件とし、今回互換を確認済みとは扱わない。

### 2.3 日付・締め・在庫

- 日付保存は既存の `yyyyMMdd`、画面表示は既存形式。サーバ基準の業務日を使用し、クライアント時刻だけで締め可否・期限を判定しない。
- 自社締日による月帰属、取引先別請求／支払締日、更新禁止境界日は別項目とする。
- 在庫は伝票・既存計上処理を源泉とし、画面から `SummaryStock`／`SummaryRealStock` を直接ゼロ化しない。
- HHT・物流・補充の生成伝票も締め制御・在庫計上・重複防止を共通経路で満たす。配分の入荷割当・引当算式は既存仕様を参照する。

### 2.4 権限・出力・運用

想定操作者は各節に示すが、現状の画面名「管理者用」はアクセス制限の実装を意味しない。[Role・Scope設計](2026-09-12_担当者Role・Scope・権限判定_詳細設計.md) の採用時期を変更する場合は別承認とする。
締め解除・積送解消・ポイント利用等を運用公開する前に、既存の運用制限で足りるか、サーバ制御を追加するかを判断する。ここで権限基盤全体を新設しない。
帳票は条件・基準日・対象件数・数量合計を表示し、0件は「対象なし」とする。QFMはcp932／LF、SQL別名と `itemN` の対応を確認する。
顧客カルテ・RFMの出力は個人情報を含むため、初版は画面照会を中心とし、CSV／顧客別帳票の採用は判断事項とする。

## 3. 月次・更新処理の画面概要

### M01 締日更新

- **目的・操作者**: 経理／システム管理者が締済み期間を確定し、過去伝票の更新を制御する。`MasterSysman.ShimeBi` の設定画面とは分ける。
- **入力・画面**: 締対象業務（在庫・売上／売掛・仕入／買掛）、対象年月、現在の境界日、更新後の境界日、実行理由。現行境界→新境界、未処理件数、事前確認結果を一覧表示。
- **処理・保存案**: 業務別の締管理記録（仮称 `SysPeriodClose`）に締済み境界日・履歴を保存。新規・修正・削除・CSV・HHT・物流・POS・自動実行の実書込入口でサーバ検査する。日付変更は変更前・変更後双方を検査し、締済みデータの修正・移動を防ぐ。期首登録・保護データの扱いも詳細設計で列挙する。
- **出力**: 対象期間、事前確認の警告／阻害理由、更新履歴、適用された制御。請求／支払計算結果と締めロックは別管理。
- **受入条件**: 境界日以前／翌日の登録、締済み伝票の修正・削除、締済みから未締への日付変更、HHT／CSV／物流経由、競合で同じ判定となる。締日99・月末・閏月で期間境界が一致し、処理途中の失敗で境界だけ進まない。
- **判断 J01**: 推奨は「初版は確認・警告方式で導入し、対象入口の洗出し完了後に更新禁止を有効化」。全面禁止／対象業務限定、締解除の可否、未処理の阻害条件は利用者決定。現行メニューの1.1以降という採用時期も維持・変更を判断する。
- **参照**: `CvBase/BaseDb0System.cs`、`CvDomainLogic/SummaryDb.cs`、`CvBase/ClosingMonthCalculator.cs`、`31Monthly/BaseBillingCalculationViewModel.cs`。期間ロックの実装は高リスク。

### M02 積送中クリア

- **目的・操作者**: 在庫管理者が長期未受の移動を理由付きで解消する。「クリア」の業務意味を選ばず一括ゼロ化しない。
- **入力・画面**: 出庫日上限、出庫元／移動先、出庫伝票、SKU、処理日、解消理由。出庫数・既受入数・未受残・経過日数を表示し、選択行の残数のみ処理候補にする。
- **処理・保存案**: 推奨初版は「実物受入済み・登録漏れ」に限定し、`Tran11IdoIn` を未受残で作成して `RelateNo1` に出庫Idを保持する。移動先在庫が増えることを確認画面に明示。紛失／廃棄／誤出庫は別の訂正・調整仕様を承認するまで選択不可。
- **出力**: 処理候補、処理前後の未受残・両拠点在庫、生成受入伝票Id、理由・実行結果。
- **受入条件**: 全未受／一部受入／受入済み／取消済み／過受入を区別。最新の出庫・受入・残数を実行時に再検査し、受入済みへの再実行は生成0件。失敗時は伝票・積送・移動先在庫が一括で戻る。
- **判断 J02**: 登録漏れ受入だけでよいか、紛失等も必要か。後者では損失負担拠点・在庫評価・調整伝票・計上月を先に決定する。古い出庫を現在月で受けるかも承認対象。
- **参照**: `CvBase/BaseDb2Trans.cs`、`08Zaiko/IdoInputUkeViewModel.cs`、`08Zaiko/IdoUnreceivedListViewModel.cs`、`CvDomainLogic/SummaryDb.cs`。未受リストの「受入力未実装」コメントは古く、受入力の実コードを優先する。

### M03 自動発注・補充の実行

- **目的・操作者**: 商品／在庫管理担当が、配分側で承認・実装された設定と計算処理に基づく候補を確認して実行する。
- **入力・画面**: 基準日、対象拠点・商品範囲、実行種別、設定版。候補の必要数・除外理由・生成予定データ、前回実行結果を表示。
- **処理・保存案**: 既存／別途承認された補充処理へ委譲し、画面はプレビュー・選択・実行・履歴に限定。プレビューIDに条件・元データ版を対応させ、実行直前に再検査する。自動発注／配分指示の生成先は配分仕様の確定値を使用し、`TranHoju` の存在だけで生成先と断定しない。
- **出力**: 採用／除外候補、処理件数、生成伝票・指示Id、警告、再実行時の既処理表示。
- **受入条件**: 設定不足は書込前に停止。プレビューだけではDB更新なし。同一実行IDの再試行で二重生成なし。実行中の在庫・設定変更と手動処理競合を検出する。
- **判断 J03**: 本画面を今回に含めるか、手動だけかSchedulerも含めるか。推奨は設定・計算・生成先が完成後に手動実行から導入。これらが未確定の間は、実行画面の実装を保留する。
- **参照**: `CvBase/BaseDbHaibun.cs` の `TranHoju`、既存配分基本設計。補充計算・設定仕様は本書では作成しない。

## 4. HHT専用帳票の画面概要

共通案: 「指示」と「実績」を帳票名・状態表示で区別する。変換済み実績は `TranVulcanHht.TargetTableName/TargetId` で実伝票に関連付け、原データのJAN・数量を未解決のまま実績合計に混ぜない。HHTによる配分確定機能は新設しない。

### H01 出荷指示明細書印刷

- **目的・操作者**: 倉庫／HHT担当が出荷指示を帳票で確認する。既存配分側帳票と同一業務なら共通処理へ接続する。
- **入力・画面**: 指示日・納品日範囲、倉庫、出荷先、区分、未完了のみ。候補ヘッダとSKU明細、指示数、入荷済み数、状態を表示。
- **処理・出力案**: 指示の正典は `TranHaibun`、既存 `HaibunHeaderKey` と既存出荷指示QFMを再利用する。HHT受信実績は別表示し、指示数を書き換えない。取置はこの出荷指示対象から除く。
- **受入条件**: 同条件の配分側帳票と指示数・ヘッダ単位が一致。複数倉庫・部分入荷・同商品別色サイズ・0件で正しい出力。印刷が引当・SendFlg・完了状態を変えない。
- **判断 J04**: 推奨は同名2画面の処理を共通化し、メニュー導線は残す。独自HHT帳票が必要なら端末に渡す番号・バーコード・並びを実物帳票で確定する。既存の「配分の確定にハンディを使わない」決定は維持する。
- **参照**: `07Haibun/ShippingConfirmDetailPrintViewModel.cs`、`printform/ShippingInstructionDetail_header.qfm`／`_detail.qfm`。

### H02 移動明細書印刷

- **目的・操作者**: 倉庫／HHT担当が、HHTで登録された積送移動の実績と未受残を確認する。
- **入力・画面**: 伝票日、出庫元・移動先、HHT取込ファイル・担当者、出庫／受入、変換済み／エラー／未変換。変換済み実伝票一覧から明細を表示。
- **処理・出力案**: `Tran10IdoOut`／`Tran11IdoIn` とHHT対象Idを関連付け、実伝票を重複排除して印刷する。未受残は出庫Id×SKUで集計。未変換・エラーの原データは別一覧とし、実績帳票へ含めない。
- **受入条件**: 同じ伝票に複数HHT行があっても二重出力なし。出庫・一部受入・全受入で数量と未受リストが一致。修正後の実伝票を表示し、原データとの差を確認できる。
- **判断 J05**: 推奨は変換後実伝票の明細書を初版対象とする。未変換原データの検収帳票、出庫／受入別の様式、JANバーコードの要否を決める。
- **参照**: `CvDomainLogic/HhtProcessUpdate.cs`／`HhtProcessUpdateMap.cs`、`08Zaiko/IdoInputOutViewModel.cs`／`IdoInputUkeViewModel.cs`、`printform/IdoInputOut_*`／`IdoInputUke_*`。

### H03 即時移動明細書

- **目的・操作者**: 倉庫／HHT担当が、HHT由来の即時移動を出庫元・移動先単位で確認する。
- **入力・画面**: 伝票日、両拠点、担当者、取込ファイル、伝票番号。対象・SKU明細・数量合計を表示。
- **処理・出力案**: HHT対象Idから `Tran05Ido` に到達し、既存即時移動QFMを再利用する。積送出庫／受入とは混在させない。

## 5. 物流連携の共通仕様と画面概要

### 5.1 外部契約・状態・保存案

- **前提 J06**: 連携先・サンプル送受信データ・ファイル／API仕様・認証・送達確認方式が未提示。文字コード、列順、時刻、番号桁、通信方式を本書で既定契約として断定しない。推奨初版は手動ファイル連携だが、相手仕様に従って決める。
- 論理的な必須項目はメッセージID／版、出荷指示行ID、倉庫・出荷先、商品・色・サイズ、指示数または確定数・欠品数、出荷日。外部コードはマスタ対応表で解決し、品番だけでSKUを特定しない。
- 送信バッチ・対象行・送信時の内容／`Vdu`・送達結果、受信バッチ・原文・行別検査結果・適用結果を保存する（仮称 `LogisticsBatch`／`LogisticsDetail`）。送信側と受信側で使う履歴基盤は共有する。
- 状態案は「作成→送信中→送達確認済み」、失敗は「送達なし確認済み」か「送達不明」を分ける。DBと外部通信を1トランザクションで完了したとみなさず、再送は同一メッセージIDを使う。
- `SendFlg=1` で対象を確保し、送達確認後に2へ進める。失敗時に0へ戻すのは、外部で受領されていないと確認できた場合だけ。相手に取消／差替仕様がなければ送信済み指示を編集しない。
- 受信は「取込→検査→承認待ち→適用済み／エラー」。原文取込と在庫・伝票更新を分離し、実績適用は既存確定のトランザクションを使用する。
- **前提 J07**: 推奨は外部の最終実績を受信し、CV10画面で確認して確定する方式。同じ指示に複数回出荷する契約は現行の一回確定・残り欠品完了と一致しないため、別設計承認が必要。
- 手動確定との競合は同じ指示行で検出する。送信済み対象を手動確定してよいかは決定事項とし、少なくとも既完了行へ外部実績を再適用しない。

### L01 マスタデータ作成

- **目的・操作者**: 物流担当が連携先に必要な商品SKU・倉庫・店舗・取引先マスタを出力する。
- **入力・画面**: 連携先、対象マスタ・範囲、全件／差分、基準日時、出力先。件数・外部コード・JAN不足／重複をプレビュー。
- **処理・出力案**: 指定時点の整合したマスタ集合を作成し、ファイル／APIデータとバッチID・版・件数・検査結果を出力。初版は全件を推奨。差分は削除・無効化・名称変更の伝達方式が決まった後に対応する。
- **受入条件**: 同一基準の全件出力で再現可能。JANや外部コードの重複・文字化け・欠番を検出し、不完全なマスタを正常終了扱いしない。出力途中失敗では完成品扱いのファイルを残さない。
- **判断 J06**: 必須マスタ、SKUキー、JAN優先順位、文字コード、全件／差分、廃番の通知、連携先への渡し方。
- **参照**: `CvBase/BaseDb1Master.cs`、`DerivedShohinColSiz`、`30HHT/HhtMasterDataCreateViewModel.cs`（出力操作の参考。HHT形式を物流形式とみなさない）。

### L02 連携データ手動送信

- **目的・操作者**: 物流担当が未送信の出荷指示を確認して倉庫へ渡す。
- **入力・画面**: 連携先・倉庫、指示日／納品日、配分区分、対象選択。数量・SKU・出荷先・送信状態・前回結果を一覧化。
- **処理・出力案**: 未完了・未送信・未確定で通常出荷対象の行を検査し、送信履歴と内容を保存してから外部送信する。仕入配分の指示数／入荷済み数のどちらを渡すかは既存配分仕様・相手契約と照合する。取置は送信対象外。
- **受入条件**: 二重操作・同時送信・送信中の指示修正・応答喪失・再起動を確認。送達不明でも別IDで同じ指示を送り直さない。送信だけでは伝票を作らず引当を解除しない。
- **判断 J06/J07**: 送達確認の条件、送信単位、再送・取消・差替、送信済み指示の手動確定可否、指示数量の契約。
- **参照**: `CvBase/BaseDbHaibun.cs`、`CvDomainLogic/AllocationRules.cs`、`CvServer/Services/HandlerClass.cs`。

### L03 連携データ手動受信

- **目的・操作者**: 物流担当が倉庫の実績を取り込み、指示との照合後に確定する。
- **入力・画面**: 連携先、受信元、ファイル／メッセージ、適用日・担当者。指示数、確定数、欠品数、在庫／入荷制約、相違理由、適用状態を表示。
- **処理・保存案**: メッセージIDで重複排除し、送信時行IDと現行指示を照合する。`0≦確定数≦指示数`、最終実績なら `指示数=確定数+欠品数` を検査。未知SKU・改変済み指示・既完了・取置は拒否。確認後に `ShippingDb.Commit` を使い、伝票作成・完了・引当解除と適用履歴を同一トランザクションで保存する。
- **出力**: 取込件数、検査エラー、適用件数、生成伝票Id、全量欠品完了、重複受信表示。
- **受入条件**: 同一受信の再試行、同一指示の別ID再受信、手動確定との競合、入荷／在庫不足、全量欠品で二重伝票なし。推奨は仮想ヘッダ単位で成功／失敗を分け、その中は全件ロールバック。確定応答喪失後も履歴から既適用を返す。
- **判断 J07**: 検査後の手動確定か自動確定か、部分出荷を受けるか、処理単位、実出荷日と締済み期間の衝突時の運用。
- **参照**: `CvDomainLogic/ShippingDb.cs`、`CvBase/Parameters.cs` の配分確定契約。配分確定仕様自体は変更しない。

### L04 連携エラーデータ照会

- **目的・操作者**: 物流担当／保守担当がマスタ・送信・受信の失敗原因を追跡する。
- **入力・画面**: 連携先、日時、バッチ、種別、エラー区分、未解決のみ。原文行番号・対象指示・外部コード・原因・処理履歴を表示。
- **処理・出力案**: 履歴の照会、詳細、原文確認、送達状況再照会、L01～L03への再処理導線を提供する。確定数量や在庫をこの画面から直接修正しない。原文は保持し、訂正版を新しい履歴として関連付ける。
- **受入条件**: 正常／エラー／送達不明／既適用を区別。原因解消後の再処理で二重生成なし。保存原文の文字コードを維持し、通常ログへの秘密・個人情報流出を避ける。
- **判断 J08**: 原文保管期間、閲覧可能な担当範囲、再処理権限、ファイル再作成と原文訂正の扱い。推奨は原文不変・訂正版履歴追加。
- **参照**: 新規物流履歴、`30HHT/HhtErrorDataInputViewModel.cs`（一覧・エラー操作の参考。HHT保存先を物流に流用しない）。

## 6. 顧客・ポイントの共通仕様案

### 6.1 正典と業務フロー

1. 顧客は `MasterEndCustomer`、会員状態／ポイントランクは `MasterEndCustomerAccount` を参照する。ランク文字列と `MasterPointRank.Kubun` の対応は明示し、名称だけで曖昧に照合しない。
2. 購入の源泉は顧客Id付き `Tran01Tenuri`。顧客なし売上を氏名や同一日の購入から推定配賦しない。店舗売上入力・HHT・取置売上のポイント対象経路は承認時に決定する。**POS 10.0は顧客入力を可能とするが、ポイント計算対象の顧客は運用で除外する（利用者決定）。** 顧客を指定しただけではポイント付与・利用を行わない。
3. ポイントの正典は取引別の追記台帳（仮称 `TranPointEvent`）とする提案。取引キー、顧客、店舗、業務日、元売上／明細、付与・利用・失効・取消・調整、数量、適用ルール版、元イベント、理由を保持する。
4. `TranPointRireki` は顧客×日付の既存日別履歴として扱い、取引別台帳の代用にしない。`SummaryPoint` は台帳から再生成する残高・購入実績。会員情報の `Point` 等は互換上必要なら同期する派生値とし、画面別に異なる残高を使わない。
5. 既存残高は承認した移行基準日時点の期首イベントとして取り込む。移行済み残高と過去取引の再付与を重複させない。履歴が不完全なら推測で過去キャンペーンを再計算しない。
6. ポイント利用は残高検査・売上保存・利用イベント保存を一括処理し、同時会計の二重使用を防ぐ。取消／返品は元の付与・利用イベントを参照する反対イベントを作る。
7. POS 10.0では顧客入力からサーバの `Tran01Tenuri.Id_Customer` への接続を確認する。現行 `PosCheckoutRequest` に顧客項目がないため、必要な追加契約は既存番号を維持した後方互換拡張として別途詳細設計する。顧客なしの既存端末は現行動作を保つ。**ポイント計算対象顧客の除外は運用判断であり、10.0の自動拒否機能を追加する決定ではない。** 顧客入力UI・検索条件・端末側の実装は今回静的確認していない。
8. POSのポイント計算・利用・取消／返品連携は将来対応。POS 10.0の売上を後日一括でポイント付与しない。ポイント運用を開始する際は、対応対象の売上経路・店舗・開始日を承認し、POSの既存取引を自動対象にしない。端末側改修・連携試験は将来対応の別見積りとし、18画面の照会・設定の実装開始条件にしない。

### 6.2 計算ルールの推奨案（未承認）

| 項目 | 推奨案 | 判断 |

## 7. 顧客管理の画面概要

### C01 顧客カルテ

- **目的・操作者**: 店舗／顧客管理担当が顧客の基本情報と購入・ポイント履歴を一画面で確認する。

- **処理・出力案**: 顧客マスタ・会員情報・顧客付き店舗売上・台帳／残高を参照。購入は売上と返品／取消を区別し、元伝票明細へ遷移。マスタ編集は既存顧客マスタへ渡す。初版はポイント残高の直接修正・顧客への送信機能を持たない。
- **受入条件**: 同姓同名、顧客なし売上、購入0件、退会、返品／取消、複数店舗でも別顧客と混ざらない。ポイントの源泉未移行時は未確定と表示し、0残高と誤認させない。
- **判断 J12**: 全店舗の購入を見せるか担当店舗だけか、住所等の表示範囲、CSV／帳票、メモ入力の要否。推奨は照会から導入し、接客メモ履歴を新設する場合は別途項目・保存規約を決める。
- **参照**: `CvBase/BaseDb1Master.cs`、`BaseDbKokyaku.cs`、`01Master/MasterEndCustomerMenteViewModel.cs`、`CvDomainLogic/ConvertDb.cs`。既存顧客マスタ印刷SQLには削除済み集計列の参照があり、カルテSQLへ流用しない（今回は既存画面を修正しない）。

### C02 ポイントマスタ（ベース）（管理者用）

- **目的・操作者**: 顧客制度管理者がランク別の基本付与条件を設定する。
- **入力・画面**: ランク区分・名称、付与単価、プロパー／セール付与数、有効期間・有効状態。ランク一覧と編集領域、購入額に対する計算例を表示。
- **処理・保存案**: `MasterPointRank` を核に、適用期間・版を補う。単価は正、付与数は0以上、ランク区分は一意。同期間同ランクの重複は拒否。会員情報のランク対応を検証し、未設定会員の既定条件を明示する。
- **受入条件**: 単価0／負数、付与0、端数、期間境界、未登録ランク、競合を検査。変更前売上の結果は不変。計算例とサーバ計算結果が一致する。
- **判断 J09**: 税基準、控除額、丸め単位、ランク対応、未設定会員の既定ランク、付与開始日。
- **参照**: `CvBase/BaseDbKokyaku.cs`。保存した設定が実付与へ反映される共通計算処理を伴う。

### C03 ポイントマスタ（キャンペーン）

- **目的・操作者**: 顧客制度／販促担当が期間限定の倍付け等を設定する。
- **入力・画面**: コード・名称、開始／終了日、倍率または追加付与数、対象ランク・商品条件、優先度、有効状態。期間一覧・重複警告・計算例を表示。
- **処理・保存案**: 新規キャンペーンマスタに保存。店舗適用はC05で管理。同条件・同順位の期間重複は拒否し、使用済み版は保持。無効化で過去イベントを削除しない。
- **受入条件**: 開始日／終了日、対象外店舗・商品・ランク、重複、プロパー／セールで適用条件が一致。確定後の条件変更で過去ポイント不変。
- **判断 J10**: 倍率／固定加算の採用、複数キャンペーンの併用、対象条件、優先度。
- **参照**: 新規データ定義は承認後に確定。既存上代販促データをポイント条件として無条件流用しない。

### C04 ポイントマスタ（ボーナス）

- **目的・操作者**: 顧客制度担当が誕生日・初回購入等の追加付与を設定する。
- **入力・画面**: コード・名称、付与契機、対象期間、対象ランク、固定ポイント、最低購入額、回数上限、有効状態。適用例と上限の説明を表示。
- **処理・保存案**: 新規ボーナスマスタに保存。初版は購入確定時の付与を推奨し、購入なしの日次一括付与は含めない。実適用は台帳の一意な付与単位で回数制限する。
- **受入条件**: 同日複数購入・会計再送・別店舗購入でも回数上限を守る。誕生日不明・2月29日・初回売上取消時の扱いは決定値どおり。
- **判断 J10/J11**: 採用契機、年度／期間の範囲、再付与条件、購入なし付与、誕生日補正。
- **参照**: `MasterEndCustomer.Birthday/BirthNoyear`、新規ボーナスマスタ・イベント台帳。

### C05 店舗別キャンペーン設定

- **目的・操作者**: 販促担当が登録済みキャンペーンを店舗へ適用する。
- **入力・画面**: キャンペーン、店舗一覧、適用／除外、有効期間。全店一括選択・個別除外・店舗別一覧を提供。
- **処理・保存案**: 店舗×キャンペーン×期間の適用関連を保存。親キャンペーン期間内に限定し、同一組合せの重複を拒否。全店指定は将来の新店舗にも自動適用するかを明文化する。
- **受入条件**: 未設定店舗・廃止店舗・キャンペーン無効・期間外に付与しない。適用解除は将来売上だけに影響し、台帳不変。複数担当同時編集を検出。
- **判断 J10**: 全店指定の意味、店舗種別、対象開始日、店舗独自条件の可否。
- **参照**: `MasterTokui`、C03のキャンペーン定義。店舗コードを自由文字列で持たない。

### C06 商品店舗別ポイント設定

- **目的・操作者**: 顧客制度／商品担当が特定商品・店舗の付与条件を設定する。
- **入力・画面**: 商品（必要ならSKU）、店舗／全店、期間、付与単価・プロパー／セール付与数、付与対象外。商品一覧・店舗別条件・最終適用例を表示。
- **処理・保存案**: 商品×店舗×期間の個別条件を保存し、6.2節の優先順で1つの基本条件を選ぶ。同順位期間重複は拒否。対象外指定は倍率キャンペーンでもベース0とし、ボーナス対象まで除外するかは別判断。
- **受入条件**: 個別店舗／全店／ランクの優先度、未設定フォールバック、対象外、期間境界で適用条件が一意。SKU採用時は色だけ一致して別サイズに適用しない。
- **判断 J10**: 品番／SKU単位、全店条件の有無、付与対象外の範囲、ランク条件との関係。
- **参照**: `MasterShohin`／`DerivedShohinColSiz`、C02～C05、共通ポイント計算処理。

### C07 ポイント集計

- **目的・操作者**: 顧客制度管理者が残高・購入実績を再集計し、会員情報との差を確認する。
- **入力・画面**: 基準日、顧客／店舗範囲、差異のみ、照合／再集計。現残高・台帳計算残高・差異・購入回数・純購入額・期首情報を表示。
- **処理・保存案**: 承認済み期首＋台帳イベントから `SummaryPoint` を再生成し、必要な会員派生値を同期。購入実績は顧客付き売上から別計算する。確定売上に新たな付与を追加する機能とは分ける。ポイント付与／利用と集計の排他・基準時点を揃える。
- **出力**: 差異一覧、対象件数、更新結果、未移行／不整合の理由。過去日照合は当時残高表示に限定し、現在残高を過去値へ戻さない。
- **受入条件**: 再実行結果不変、期首と過去付与の二重計算なし、取消・返品・調整・利用を反映。集計途中失敗で顧客単位の残高と派生値が分離しない。同時会計分の取りこぼしなし。
- **判断 J11**: 期首基準日、残高正典、会員情報同期、負残高、失効、遡及訂正、購入回数の定義。推奨は残高照合から導入し、移行承認後に再集計を有効化。
- **参照**: `CvBase/BaseDbKokyaku.cs`、`BaseDb1Master.cs`、`CvDomainLogic/ConvertDb.cs`。付与台帳を未整備のまま全会員残高を上書きしない。

### C08 RFMクロス分析表

- **目的・操作者**: 顧客管理／販促担当が最終購入からの日数・購入頻度・購入額で顧客分布を分析する。
- **入力・画面**: 基準日、分析期間、購入店舗／顧客所属店舗、R/F/M閾値、退会者を含むか。R×Fの人数・金額表、M別切替、セル選択の顧客明細を表示。
- **処理・出力案**: 顧客付き `Tran01Tenuri` を源泉に純購入を計算。R=基準日−最終の有効購入日、F=期間内の有効購入伝票回数、M=期間内の純購入額。完全取消の伝票をFから除外し、返品だけの日を来店とみなさない。返品の元伝票特定ができないデータは数量・額と回数の扱いを分けて明示する。
- **受入条件**: 購入なしは別群。未来売上・顧客なし売上・返品・取消・複数店舗・同日複数伝票、閾値の一致値を確認。全セル人数と対象顧客数が一致し、同基準日の再出力で不変。
- **判断 J13**: 推奨は固定閾値・過去12か月・Fは伝票回数。日別来店回数／分位点方式／任意期間、税込／税抜、退会者・返品の扱い、PDF／CSVの必要性は承認で決める。閾値の数値は業務データ分布を見て利用者が決定。
- **参照**: `CvBase/BaseDb2Trans.cs`、C01・C07。累計 `SummaryPoint.SalesCount/SalesKingaku` だけでは任意期間を分析できない。
