# HHTデータ更新（TranVulcanHht → Tran系）詳細設計

作成日: 2026-08-24 / 対象: `CvWpfclient.Views._30HHT.HhtDataUpdateView`、`HhtErrorDataInputView`
状態: **実装完了**（決定事項は 12章、実装結果は 11.1、実データ確認結果は 14章）
更新: 2026-08-24 実データ(server-user163.db)確認、A-K すべての決定を反映（未決なし）

## 1. 目的とスコープ

- `HhtManualDataReceiveView` が取り込んだ `TranVulcanHht`（VULCANデータレイアウトの一次取込テーブル）を、業務トランザクション（`Tran00Uriage` ほか）へ展開する。
- 更新ボタンで変換を実行し、
  - 成功: `TranVulcanHht.VdCnvDate` / `TargetTableName` / `TargetId` を更新（`ErrorMsg` はクリア）
  - 失敗: Tran系を作らず `TranVulcanHht.ErrorMsg` をセット（`VdCnvDate` は 0 のまま）
- 失敗データは `HhtErrorDataInputView` で内容確認・修正し、再度「HHTデータ更新」で変換できる。

スコープ外: HHT未更新データ印刷／一括削除、物流連携、再送・重複排除の運用設計。

## 3. 全体方式

```text
HhtDataUpdateView (WPF)
  └ HhtDataUpdateViewModel
       └ QueryMsgStreamAsync(Msg058_HhtDataUpdate, HhtUpdateParameter)   ← 進捗ストリーム
            └ CoreService の Msg050 系と同じ分岐
                 └ CvDomainLogic/HhtProcessUpdate.cs : HhtProcess.UpdateVulcan2TranAsyncStream()
                      ├ 対象抽出（VdCnvDate=0）
                      ├ 伝票単位にグルーピング
                      ├ 1伝票ずつ 検証 → Tran系 Insert → 在庫集計反映 → TranVulcanHht 更新
                      └ 掛集計（売掛/買掛）は対象年月をまとめて再計算
```

- 変換ロジックは**サーバ側（CvDomainLogic）**に置く。1行ずつ gRPC を往復させず、`StocktakeDb` と同じくバッチで完結させるため。
- `HhtProcess` は既に `partial` なので、`CvDomainLogic/HhtProcessUpdate.cs` を追加して `partial` で実装する（`HhtProcess.cs` / `HhtProcessTransfer.cs` は変更しない）。
- 既存の `TransferValcan2Hhtdata()`（→`TranHhtData`）は**残すが使わない**。冒頭コメントに「旧CVnet互換の中間テーブル向け。CV10の正規経路は `UpdateVulcan2Tran()`」と追記する（決定 12-A）。

## 4. `TranVulcanHht` の状態遷移

| 状態 | `VdCnvDate` | `ErrorMsg` | `TargetTableName`/`TargetId` | 意味 |
| --- | --- | --- | --- | --- |
| 未変換 | 0 | 空 | 空/0 | 受信直後。更新対象 |
| 変換エラー | 0 | エラー内容 | 空/0 | `HhtErrorDataInputView` の対象。修正後に再更新対象 |
| 処理中 | -1 | - | - | 同一トランザクション内の一時状態（正常終了時に必ず解消） |
| 変換済 | `Common.GetVdate()` | 空 | 生成した伝票 | 更新完了。`HhtUnupdatedData*` の対象外 |

- 更新対象の抽出条件は `VdCnvDate = 0`（エラー行も含む＝再試行になる）。
- 再変換時は `ErrorMsg` を必ず一度クリアしてから判定する（前回エラーの残留を防ぐ）。
- 変換済みデータの取り消し（`TargetId` の伝票削除と `VdCnvDate` 戻し）は本設計のスコープ外とする（決定 12-E）。

## 5. 変換仕様

### 5.1 伝票のグルーピング

VULCAN は 1行 = 1明細（1 JAN）であり、Tran系はヘッダ＋明細（`Jmeisai`）構造である。

- 並び順: `BackupFileName, HhtNo, Serial, LineNo`
- **ヘッダキー**: `BackupFileName, Type0, DenDay, Shop, HhtNo, Tanto, HanKubun, DenNo, ToriSaki`
  - `BackupFileName` を含めるのは、別ファイルの行が1伝票へ混ざらないようにするため（実装時に追加）。
- **連続ラン方式**: 上記順に走査し、ヘッダキーが変わったところで伝票を区切る。非連続で同キーが再出現した場合は**別伝票**とする。
  - 理由: 売上/返品は `DenNo` が顧客CDであり伝票番号ではないため、キーだけで束ねると同一顧客の別会計が1伝票に融合する。HHT のスキャン順（`Serial`）は 1会計＝連続ラン になる。
- 例外: `Type0=7`（棚卸）と `Type0=12`（客数）は 5.2 の各項を参照。
- 棚卸（`Type0=7`）は `DenNo`＝棚番であり、上記ヘッダキーに `DenNo` が含まれるため**倉庫＋棚番単位で1伝票**になる。既存 `Tran60Tana` も 1日1倉庫で複数伝票が存在し（実データ確認: 2019-09-02 は 15倉庫で 1,244伝票）、`StocktakeDb.StoreActualQty` が倉庫×SKUでSUM集計するため、伝票が分かれても集計結果は変わらない。

### 5.2 `Type0` → 生成テーブル対応

`Type0` は VULCAN では 1桁の 1-9,A-C。取込時に `Hex2Digit` で 1-12 の数値へ変換済み。

| Type0 | VULCAN区分 | 生成テーブル | Kubun | CalcFlag | 備考 |
| --- | --- | --- | --- | --- | --- |
| 1 | 売上 | `Tran01Tenuri` | 10(P) / 11(S) | +1 | `Shop`=店舗(=倉庫)、`DenNo`=顧客CD |
| 2 | 返品 | `Tran01Tenuri` | 20(P) / 21(S) | -1 | 数量は負で格納 |
| 3 | 入庫 | `Tran11IdoIn` | - | - | 積送入庫（移動受）。`ToriSaki`=移動元 |
| 4 | 出庫 | `Tran10IdoOut` | - | - | 積送出庫。`ToriSaki`=移動先 |
| 5 | 仕入 | `Tran03Shiire` | 10 | +1 | `KakeRitsu`列=発注番号8桁 → `RelateNo1` |
| 6 | 仕入返品 | `Tran03Shiire` | 20 | -1 | |
| 7 | 棚卸 | `Tran60Tana` | - | - | `DenNo` 先頭8桁=棚番 → `TanaNo` |
| 8 | 発注 | `Tran13Hachu` | 10 | +1 | `KakeRitsu`列=納品日8桁 → `NouhinDay` |
| 9 | 卸売 | `Tran00Uriage` | 10(P) / 11(S) | +1 | `ToriSaki`=得意先 |
| 10 | 卸返品 | `Tran00Uriage` | 20(P) / 21(S) | -1 | |
| 11 | 移動 | `Tran05Ido` | - | - | 即時移動。`ToriSaki`=移動先 |
| 12 | 客数 | 対象外（決定 12-B） | - | - | `DenNo` 先頭8桁=客数 |

`CalcFlag` は `Kubun` のセッタで自動算出される（`Kubun` 20-39 → -1）。移動系・棚卸は `Kubun` を持たない。

### 5.3 販売区分（`HanKubun`）

| 値 | 売上/返品(1,2,9,10) | 入庫/出庫(3,4) | その他 |
| --- | --- | --- | --- |
| 0 | プロパー → Kubun 10 / 20 | 買取 | 無視 |
| 1 | セール → Kubun 11 / 21 | 委託 | 無視 |
| 2 | 社販 | - | 決定 12-C: E015 |
| 9 | 未使用 → プロパー扱い | 未使用 | 無視 |

- 入庫/出庫の買取/委託は CV10 の移動伝票に対応列がないため、`Memo` に「委託」と記録するのみとする（決定 12-D）。

### 5.5 マスタ解決

**ロード方針**（実データの規模に合わせて分ける。14章参照）

| 対象 | 件数（実DB） | 方針 |
| --- | --- | --- |
| `MasterTokui` | 2,647 | 全件メモリへロードし `Dictionary` |
| `MasterShiire` | 501 | 同上 |
| `MasterShain` | 1,823 | 同上 |
| `DerivedShohinColSiz` | 166,162 | **バッチ内の distinct JAN を集めて `IN (...)` で分割検索**（1,000件単位）。全件ロードはしない |
| `MasterEndCustomer` | **1,555,181** | 全件ロード不可。distinct `DenNo` を集めて `IN (...)` で分割検索 |

| 対象 | 解決先 | キー |
| --- | --- | --- |
| `Shop` | `MasterTokui`（`TenType in (0,6)`） | `Code`（前0除去して比較） |
| `Tanto` | `MasterShain` | `Code`（前0除去） |
| `ToriSaki`（5,6,8） | `MasterShiire` | `Code`（前0除去） |
| `ToriSaki`（9,10） | `MasterTokui`（`TenType in (1,3)`） | `Code`（前0除去） |
| `ToriSaki`（3,4,11） | `MasterTokui`（`TenType in (0,6)`） | `Code`（前0除去） |
| `Jan1`/`Jan2` | `DerivedShohinColSiz` | 5.6 参照 |

- `Code` の前0除去は「両辺 `TrimStart('0')` して比較」で行う。VULCAN側は前0埋め（`Shop`=8桁、`Tanto`=6桁）、マスタ側は桁数が不定（実データ: `MasterTokui` は 2/3/6桁が混在、`MasterShiire` は3桁、`MasterShain` は6桁）。
- **前0除去により複数一致し得る**（実データ: `MasterTokui` に `"16"`（TenType=0/IsZaiko=0）と `"000016"`（TenType=6/IsZaiko=1）が同名で併存）。優先順位を次のとおり固定する。
  1. `Code` が完全一致（前0込み）
  2. `IsZaiko = 1`
  3. `TenType = 6`（直営店）
  4. それでも複数残るなら **E014** でエラー
- 取引先の解決先マスタが `Type0` の期待と違う場合（例: 卸売なのに倉庫コード）は **E013**。

### 5.6 JANコードの照合（決定事項）

- **上段のみ**（`Jan2` が空）: `DerivedShohinColSiz` の `Jan1` **or** `Jan2` **or** `Jan3` のいずれかに一致。
- **上段と下段の両方**（`Jan2` が非空）: `Jan1`（上段）= `DerivedShohinColSiz.Jan1` **かつ** `Jan2`（下段）= `DerivedShohinColSiz.Jan2` の**AND条件**で一致。
- **桁数フィルタ（必須）**: 照合対象は**8桁以上**の値のみとする。実データ確認で `DerivedShohinColSiz.Jan1` に `"24"` `"25"` `"23"` `"26"` `"27"` `"13"` `"22"` という2桁の値（サイズCDの誤登録）が計 1,285行あり、これを JAN として扱うと E104（複数一致）が誤発火する。8桁未満は「JAN未登録」として照合対象から除外する。
- 上段が8桁未満: **E105**（JANコードの桁数不足）。
- 一致が複数SKU: **E104**。

### 5.7 重複受信の判定（決定 12-K）

実データに同一ファイルの4重受信が存在した（14.2）。変換前に重複を検知し **E016 でエラー通知**する。

- **重複キー**: `Type0` + `DenDay` + `Shop` + `HhtNo` + `Serial`
  - `Serial` は HT単位の通し番号なので、同一HT・同一日で `Serial` が重複することは正常運用では起こらない。`BackupFileName` はファイル名なので重複キーには含めない。
- **判定対象**
  1. **既変換との重複**: 同一キーの行が既に `VdCnvDate > 0` で存在する → E016（先に変換済みの `TargetTableName`/`TargetId` をメッセージに含める）
  2. **同一バッチ内の重複**: 対象行の中に同一キーが複数ある → `BackupFileName` の昇順で最初の1件だけを変換し、残りを E016 にする
- **重複判定はグルーピングより先に行い、重複行をグルーピング対象から除く**（実装時に確定）。再受信された行はヘッダキーが元の行と完全に一致するため、残したままだと同じ伝票ランへ吸収され、1件目まで巻き込んでエラーになってしまう。
- エラーメッセージ例: `"E016 重複受信: 20260402124512_001.txt 行4009 と同一 (先行=Tran60Tana#123)"`
- 画面側は完了メッセージに「重複 {n}件」を別掲し、`HhtErrorDataInputView` で削除できるようにする。

## 6. エラー設計

### 6.1 判定単位

- **明細行1件でもエラーがあれば、その伝票（ラン）全体を生成しない。**
- エラー時は、そのランに属する**全行**の `ErrorMsg` に記録する。原因行には具体的な内容を書く。
  - 原因行: `"E103 商品未登録: JAN=4901234567890"`
  - 同一伝票の他行: `"E900 同一伝票内にエラー行あり (行=1234)"`

### 6.2 エラーコード

| コード | 内容 |
| --- | --- |
| E001 | 区分（`Type0`）が対象外（1-12以外） |
| E002 | 日付（`DenDay`）が不正 |
| E010 | 店舗/倉庫が未登録（`Shop`） |
| E011 | 担当者が未登録（`Tanto`） |
| E012 | 取引先が未登録（`ToriSaki`） |
| E013 | 取引先の店種区分が区分と不一致（例: 卸売に倉庫コード） |
| E014 | コードが複数マスタ行に一致し一意に決められない（5.5 の優先順位で解決できない） |
| E015 | 販売区分=2（社販）は未対応（決定 12-C） |
| E016 | 重複受信データ（5.7、決定 12-K） |
| E020 | 移動元と移動先が同一 |
| E100 | JANコードが空 |
| E103 | 商品未登録（JAN解決失敗） |
| E104 | JANコードが複数商品に一致 |
| E105 | JANコードの桁数不足（8桁未満） |
| E110 | 数量が 0 |
| E120 | 発注番号/納品日が不正（`KakeRitsu`） |
| E130 | 棚番が不正 |
| E900 | 同一伝票内にエラー行あり（連鎖） |
| E999 | 想定外の例外（例外メッセージを付記） |

`ErrorMsg` は 1000 文字。書式は `"{コード} {内容}"`、複数は `" / "` 連結、超過分は切り捨てる。

## 7. トランザクションと集計副作用

```text
BeginTransaction(Serializable)
  UPDATE TranVulcanHht SET VdCnvDate=-1, ErrorMsg='' WHERE <対象条件> AND VdCnvDate=0
  foreach (伝票ラン) {
      検証 → NG: 該当行に ErrorMsg、VdCnvDate=0 へ戻す / continue
      _db.Insert(伝票)
      ITranSoko なら SummaryDb.CalcTran2SummaryStock(表名, "Id_Soko", Id, false)
      ITranIdo なら  SummaryDb.CalcTran2SummaryStock(表名, "Id_Ido",  Id, false)
      該当行を VdCnvDate=GetVdate(), TargetTableName, TargetId で更新
  }
  UPDATE TranVulcanHht SET VdCnvDate=0 WHERE VdCnvDate=-1   -- 取りこぼし防止
CompleteTransaction
```

- 在庫集計は `WriteEffectRunner` を使わず `SummaryDb` を直接呼ぶ（`WriteEffectRunner` は CvServer 層のため CvDomainLogic から参照できない。`StocktakeDb` と同じ判断）。
- 売掛/買掛（`Tran00Uriage` / `Tran03Shiire` 生成時）は月次一括再計算なので、変換対象に含まれる `yyyyMM` の範囲で最後に 1回だけ `CalcSummaryUriKake` / `CalcSummaryKaiKake` を呼ぶ。
- 発注残の完了判定（`CompletionDb`）は `RelateNo1` を設定する `Tran03Shiire` のみ対象。伝票生成後にまとめて `CalcHachuEndFlag(ids)` を呼ぶ。
- 引当（`ITranReserve`）は生成対象に含まれないため不要。

## 8. `HhtDataUpdateView` 画面設計

`StockKakeUpdateView` と同じ「条件 → 実行 → 進捗」型。`Width/Height` は `StandardWindowWidth/Height`。

**入力**

| 項目 | 既定 | 備考 |
| --- | --- | --- |
| 対象日付 From / To | 当月1日 / 当日 | `DenDay` の範囲。空欄可（=全件） |
| 区分 | 全て | 全て / 売上返品 / 仕入発注 / 移動 / 棚卸 |
| エラーデータを再試行 | ON | OFF なら `ErrorMsg` が空の行のみ対象 |

**表示**

- 上段: 対象件数プレビュー（未変換件数 / うちエラー件数）。画面 `Init` と条件変更で再取得。

### 12.2 `Rate` の扱いに関する補足（決定 F の背景と、本設計外の影響）

**現状の実装は `Rate` を消費税率として使っている**（決定 F はこれを「掛率へ戻す」方向）。

- `Tran00Uriage.Rate` / `Tran01Tenuri.Rate` / `Tran03Shiire.Rate` / `Tran12Jyuchu.Rate` は列コメントが「掛率」だが、入力画面は税率として使っている。
  - `ShukkaUriageInputViewModel.LoadTaxRateAsync()`: `CurrentEdit.Rate = await AppGlobal.LogicGetTax(1, DenDay)`
  - `UpdateHeaderTotals()`: `Tax = round(abs(KingakuTotal) * CurrentEdit.Rate / 100)`
  - 店舗売上・仕入・受注も同じ。
- `Tran13Hachu`（発注）だけは `Rate` を税率に使わず、ローカル変数 `taxRatePercent` に分離している（ソースコメント「仕入先掛率(Rate)から分離した消費税率のキャッシュ」）。**今後この方式に統一する**（2026-08-24 ご方針）。
- 移動系（`Tran05Ido` / `Tran10IdoOut` / `Tran11IdoIn`）は `TranAllHeader` を継承するだけで **`Rate` 列を持たない**。掛率が来る区分 3/4/11 では `Rate` へ入れられないため、`Memo` に `掛率=999.9` を記録し、明細 `Gedai` の算出に使う。
- 旧CVnetの列名「掛率1」も実体は税率だった（`ConvertDbTran.cs:548` のコメント「掛率1（税率%。旧システムでは掛率という名称だが CV10側では消費税率として使う）」）。

**本設計のスコープ外の課題** → `Doc/spec/2026-08-24_Rate列_掛率と税率の分離課題.md` に分離した。

要点だけ再掲する。既存 `Tran00Uriage.Rate` は **10 が 50,311件**（＝税率）あり、`Rate` を掛率へ戻す改修では
この既存値の移行方針（クリアするか、税率列を新設して移すか）を別途決める必要がある。
掛率の単位は `MasterTokui.RateProper`（実データは 100 / 60）と同じパーセント整数であり、決定 F はこれに合わせた。

HHT変換で新規作成する伝票は最初から掛率で入るため、本設計側の追加対応は不要。ただし
**入力画面側の分離が済むまでは、HHT生成伝票を既存の入力画面で開くと `Tax` が誤って上書きされる**
（`UpdateHeaderTotals()` が `Rate` を税率として計算するため）。実装時に運用面を確認する。
