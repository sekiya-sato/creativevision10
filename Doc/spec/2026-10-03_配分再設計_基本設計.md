# 配分再設計 基本設計（現状整理・理想概念・段階計画）

- 作成日: 2026-10-03
- 状態: **v1.0 承認済（2026-10-03）**。D1〜D7 は推奨案どおり（D5 / D6 は取置の指示で上書き）、D8 は「確定で即伝票作成」。
  - 細目 D9〜D11 も 2026-10-03 に決定（10章）。
- 対象: CvWpfclient 大メニュー「■ 配分・出荷」、`TranHaibun`、`CvDomainLogic/ShippingDb.cs`、発注メニューの「発注配分入力」
- 作業規模: C（高リスク）。在庫引当・出荷売上・移動伝票・店舗売上の生成経路を変えるため、実装時は `AGETS-HANDOFF.md` に従い独立した Reviewer / Tester を置く。

---

## 1. 目的

配分を次の 4 種類に整理し、**「配分 = 指示データ」「配分の確定 = 実伝票（出荷売上・移動・店舗売上）を作る唯一の入口」** という一貫したモデルに作り直す。

| 英名 | 和名 | 一言でいうと |
|---|---|---|
| PurchaseReceiptAllocation | 仕入配分 | 入荷（予定・実績）を店舗・得意先へ振り分ける |
| InventoryAllocation | 在庫配分 | 倉庫の有効在庫を店舗・得意先へ振り分ける |
| SalesOrderAllocation | 受注配分 | 受注残に倉庫の有効在庫を割り当てる |
| CustomerReservationAllocation | 取置配分 | 店舗で一般顧客向けに在庫を確保しておく |

参考として示された「Allocation Engine」案は**考え方だけを取り入れる**。仕組みは CV10 の規模と「排他・状態は単純に保つ」方針に合わせて小さくする（3.2 / 5章）。

### 2.2 データモデル（`CvBase/BaseDbHaibun.cs`）

- `TranHaibun` は **1 行 = 1 SKU の明細だけ**で、ヘッダの実テーブルはない。
- 伝票の括りは仮想ヘッダ `HaibunHeaderKey` で決まる（決定 I5）。
  - キーは `DenDay + NouhinDay + Id_Soko + Id_Tenpo + Kubun + RelateNo1` の 6 列。

| 列 | 意味 |
|---|---|
| `Su` | 指示数 |
| `JitsuSu` / `ShortSu` | 実数量 / 欠品数。`Su = JitsuSu + ShortSu` が成り立つ |
| `KakuteiDay` | 出荷指示の確定日。空なら未確定 |
| `EndFlag` | 完了フラグ。立つと引当が解除される |
| `RelateNo1` | 元伝票Id（受注 / 発注） |
| `RelateNo2` | 生成した伝票Id |
| `SendFlg` | 物流連携の状態 |

- 区分 `EnumHaibun` は 0〜7 の 8 種。「どの画面で作ったか」を表していて、業務の概念と 1 対 1 に対応していない。
- 引当数（`SummaryRealStock` / `SummaryStock.ReserveQty`）は `TranHaibun` だけから集計する。
  - 対象行: `EndFlag = 0 AND Kubun <> 0`
  - 集計する数量: 未確定なら `Su`、確定済みなら `JitsuSu`
  - 集計はキー単位で引き直す（`SummaryDb.CalcHaibun2Reserve`）。保存時は `WriteEffectRunner` が自動で呼ぶ。

### 2.3 処理フロー（現行。Step 1 で変わる）

```
配分入力 ──(洗い替え: DeleteBulk → InsertBulk の2往復)──► TranHaibun（未確定・引当中※）
   │                                                  ※初回配分(Kubun=0)は引当しない
   ▼
出荷指示確定 ── ConfirmShipping: 有効在庫割れが1SKUでもあれば全件拒否 ──► KakuteiDay を立てる

   ▼
出荷処理入力 ── ProcessShipping: Vdu 楽観排他 → JitsuSu/ShortSu → CreateShippingSlips
   │            出荷先 TenType 1(卸先)/3(売仕店) → Tran00Uriage（RelateNo1=受注Id を引き継ぐ）
   │            出荷先 TenType 0(倉庫)/6(直営店) → Tran10IdoOut（積送出庫）
   ▼
EndFlag=1, RelateNo2=伝票Id（引当解除）。全量欠品は伝票を作らず完了だけ立てる
```

## 3. 理想の概念モデル

### 3.1 用語

| 用語 | 意味 | CV10 での実体 |
|---|---|---|
| Supply（供給） | 割り当てる元 | 倉庫・店舗の有効在庫（`SummaryRealStock` の Su − ReserveQty）、発注残、仕入実績 |
| Demand（需要） | 割り当て先が必要とする数 | 店舗への配分数、受注残、顧客の取置依頼 |
| 配分指示（Allocation） | Supply を Demand に割り当てた結果。**指示データ** | `TranHaibun` の未確定行 |
| 制約（Constraint） | 破ってはいけない条件。確定時に必ず検査し直す | 有効在庫 ≧ 0、入荷済み数量の範囲、修正できる状態であること |
| 配分方針（Policy） | 割り当て方の好み | 均等 / 比率（ランク）/ 前回の複写 / 優先順位 / 手入力 |
| 確定（Commit） | 実数量を受けて実伝票を作り、引当を解除する | `ShippingDb` の新しい確定処理（Step 1） |

### 3.2 参考アイデアの取捨

| 参考アイデア | 採否 | CV10 での形 |
|---|---|---|
| 計算は純粋関数で、計算中は在庫・受注・出荷を更新しない | **採用** | 按分計算を DB に依存しないクラスとして `CvDomainLogic` に置く |
| 配分結果を保存し、確定後に下流（伝票）へ変換する | **採用** | 保存 = 指示、確定 = 伝票作成 |
| 制約と配分方針を分ける | **採用** | 制約の検査を `AllocationRules` に集める。保存時は警告、確定時はエラーとして使う |
| 確定時に最新の Supply を検査し直し、変わっていれば拒否する | **採用（簡略化）** | 有効在庫の再検査と、行単位の `Vdu` 楽観排他で行う |
| 計算条件の Snapshot を保持する | **見送り** | フラット構造を維持する（D3）ため、計算条件は持たない |
| Plan Revision（再計算のたびに新版を作り、過去版は不変） | **不採用** | 確定前は洗い替えで足りる。確定後は修正できないので不変になる |
| 汎用 Engine フレームワーク | **不採用** | 共通化は保存・制約検査・確定の 3 点に限る |
| Approval（承認）を別段階にする | **不採用** | 確定操作がそのまま承認になる |

### 3.3 状態遷移（D8 反映後。4 配分で共通）

```
             保存(洗い替え)                     確定（確定数入力）
  (なし) ───────────► 未確定 ──────────────────────────► 完了
                      │ 削除（洗い替え）          ├ 確定数>0: 伝票作成, RelateNo2=伝票Id
                      ▼                          └ 確定数=0: 全量欠品（伝票なし）
                    (なし)
                                取置のみ: 取消 / 期限切れ ──► 完了（伝票なし）
```

| 状態 | 判定式 | 引当 | 修正 |
|---|---|---|---|
| 未確定 | `EndFlag=0` | 区分による（4.2） | `SendFlg=0` のときだけ可 |
| 完了 | `EndFlag=1` | 解除 | 不可 |

- 「確定済み・未出荷」という中間状態はなくなる。
- `KakuteiDay` は確定日（= 伝票日）の記録として残す。
- 確定後の訂正は、作られた伝票側（返品・赤伝など、通常の伝票の訂正手順）で行う（D9）。

## 4. 4 配分の定義

### 4.1 一覧

| 項目 | 仕入配分 | 在庫配分 | 受注配分 | 取置配分 |
|---|---|---|---|---|
| Supply | 発注の入荷予定 → 入荷実績 | 倉庫の有効在庫 | 倉庫の有効在庫 | **店舗**の有効在庫 |
| Demand | 店舗・得意先ごとの配分数 | 店舗・得意先ごとの配分数（店舗出荷依頼もここで受ける） | 受注明細の受注残 | 一般顧客の取置依頼 |
| 起点の伝票 | 発注（`RelateNo1`=発注Id） | なし（0） | 受注（`RelateNo1`=受注Id） | なし（0） |
| 出庫元 `Id_Soko` | 入荷倉庫 | 倉庫 | 受注の倉庫 | 取置する店舗 |
| 配分先 `Id_Tenpo` | 店舗・得意先 | 店舗・得意先 | 受注の得意先 | 同じ店舗（`Id_Soko` と同じ値） |
| 区分 Kubun | 0 | 1 | 2 | 6 |
| 引当 | 入荷前はしない。入荷後に対象にする（D1） | する | する | する |
| 確定時の制約 | 入荷済み数量の範囲内 ＋ 有効在庫 | 有効在庫 | 有効在庫（受注残を超える分は保存時に警告） | 有効在庫 |
| 確定で作る伝票 | TenType 0/6 → `Tran10IdoOut`<br>TenType 1/3 → `Tran00Uriage` | 同左 | `Tran00Uriage`（受注残を消化）。店舗向けは `Tran10IdoOut` | **`Tran01Tenuri`（店舗売上）** |
| 伝票なしで終わる場合 | 確定数 0（全量欠品） | 同左 | 同左 | 取消、期限切れ（自動） |
| 現行の画面 | 発注配分入力、店舗配分入力（初回） | 店舗配分入力（在庫） | 受注配分入力 | なし |

### 4.2 区分の整理（D2 承認）

| 値 | 現名 | 再設計後 |
|---|---|---|
| 0 | 初回配分 | **仕入配分**（名称の変更のみ） |
| 1 | 在庫配分 | **在庫配分** |
| 2 | 受注配分 | **受注配分** |
| 3 | 得意先別配分 | 廃止。受注配分の「得意先軸表示」へ統合 |
| 4 | 店舗出荷依頼 | 廃止。在庫配分の入力モード「店舗依頼」へ統合 |
| 5 | 在庫品配分 | 廃止。在庫配分へ統合（滞留在庫は抽出条件で扱う） |
| 6 | 取置 | **取置配分** |
| 7 | 移動指示 | 廃止。在庫配分へ統合（出荷先が倉庫・直営店なら移動伝票になる） |

- 廃止する区分の enum 値は消さずに `[Obsolete]` を付ける。旧CVnet 変換と過去の帳票表示のために残す。
- 引当の判定式 `Kubun <> 0` は変えない。

### 4.3 仕入配分（D1 承認: 発注起点で、入荷したら引当に切り替える）

- 入荷前は現行の初回配分と同じ扱い（引当しない）。
- 仕入（`Tran03Shiire`、`RelateNo1`=発注Id）を計上したら、その発注の未確定の仕入配分を、入荷した数量の範囲で引当対象・確定可能にする。
- 部分入荷の場合は、入荷した数量の範囲で、店舗の優先順位の順に確定できる。
- 判定方法（入荷済み数量を計算で求めるか、列を持つか）は Step 4 の詳細設計で決める。

### 4.4 取置配分（D5 / D6 承認）

- 対象は、**店舗で一般顧客（`MasterEndCustomer`）向けに行う取置**。
- 取置を登録（保存）した時点で、店舗の在庫に引当がかかる。
- 終わり方は 3 つ。

| 終わり方 | 処理 | 伝票 |
|---|---|---|
| 店舗売上へ変換（= 確定） | `Tran01Tenuri` を作る。`Id_Customer` を引き継ぐ | 店舗売上 |
| 取消 | 利用者の操作で完了にする | なし |
| 期限切れ | 期限日を過ぎた取置を、スケジューラの日次タスクで自動的に取消にする | なし |

- `TranHaibun` に列を追加する（Step 5、migration が必要）。
  - `Id_Customer`: 顧客Id
  - `LimitDay`: 取置の期限日 yyyyMMdd
  - 取消の理由（取消 / 期限切れ）を判別する列
- 売上変換の経路（CV10 の画面で作るか、POS の会計で消化するか）は D10 で決める。

## 5. 共通の仕組み（アーキテクチャ方針）

依存方向（層0 → 層1 → `CvDomainLogic` → `CvServer`）は守る。

1. **`AllocationRules`（CvDomainLogic）**: 制約の検査と配分可能数の算式を 1 か所にまとめる。
   - 確定時の在庫検査は「実在庫 − 確定対象以外の引当 − 今回の確定数 ≧ 0」に統一する。これで P6 も解消する。
   - 配分可能数は「実在庫 − 引当 ＋ 編集中の自分の分」（受注配分の式）に揃える。画面ごとの切り替えは各 Step で行う。
2. **`AllocationCalculator`（CvDomainLogic、純粋関数）**: 配分方針に従って按分を計算する。Step 3 で導入する。
3. **保存 API の原子化**: `HaibunSaveParam` 1 回の呼び出しで、修正可能な行の削除・登録・引当の引き直しを 1 トランザクションで行う。修正できる状態かどうかはサーバ側で強制する。
4. **確定 API の一本化**: 従来の `ShippingConfirmParam` / `ShippingCancelParam` / `ShippingCreateParam` を、1 つの確定パラメータ `HaibunCommitParam` に置き換える（Step 1）。

```
      配分問合わせ / 引当問合わせ / 有効在庫問合わせ
  ▲ 補充（1.1以降） ----
      配分関連メンテナンス / 自動発注・補充対象除外品設定 / 在庫基準自動補充メンテナンス
```

- 業務の流れは「配分入力 → ピッキングリスト印刷 → ピッキング → 配分確定（確定数を入力して伝票作成）」になる。
- 発注メニューの「発注配分入力」は、移行期間だけ仕入配分入力へのショートカットとして残す。
- 新しく作る画面のクラス名は英名にする（D7）。
  - `PurchaseReceiptAllocationInput*` / `InventoryAllocationInput*` / `CustomerReservationAllocationInput*` / `HaibunCommit*`
  - 既存の `JuchuHaibunInput*` は名前を変えない。

## 9. リスクと検証方針

- **引当数の整合**: キー単位の引き直し（`CalcHaibun2Reserve`）と、全件の作り直し（`CalcReserveQtyAll`）の結果が一致することをテストで確かめる。
- **伝票生成**: 区分ごとの伝票種別と、`RelateNo1` の引き継ぎ（受注残の消化）を回帰テストで確かめる。
- **確定の原子性**: 在庫割れ・`Vdu` 競合・状態不一致が 1 件でもあれば、何も書き込まないこと。伝票作成・在庫計上・引当解除が 1 トランザクションで行われること。
- **SQL 方言**: SQLite 方言で書き、`ExecuteDialect` / `FetchDialect` を通す。
- **データ移行**:
  - 区分 3 / 4 / 5 / 7 の既存件数を確認する。
  - 旧状態「確定済み・未出荷」（`KakuteiDay<>'' AND EndFlag=0`）の行は、新しい確定処理で未確定と同じに扱えるようにする（Step 1）。
