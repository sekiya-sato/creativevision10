### 1.2 現行の原価利用箇所

- 商品・在庫・売上分析の多くは現在値 `MasterShohin.TankaGenka` を参照する。
- 売上、受注、仕入、移動、棚卸等の伝票作成時は、現在原価を `Tran99Meisai.Gedai` へコピーする。
- 保存済み伝票の `Gedai` は伝票時点の監査値であり、原価更新時に遡及更新しない。
- 原価更新後に作る伝票だけが新しい `MasterShohin.TankaGenka` を使用する。

### 1.3 旧CV.netから維持する仕様

- 最終仕入原価は、対象期間内で最後の通常仕入を原価にする。
- 総平均原価は、前月在庫金額と当月仕入金額を数量で割る。
- 諸掛は、生地付属仕入と商品仕入の `ManualNo` を対応キーとして配賦する。
- 消化仕入は、対象商品の売上から掛計上用の商品仕入を作る。
- 各処理は再実行可能とし、同一条件の再実行で結果が増殖しない。
- 更新前に対象・エラーを確認できるようにする。

### 1.4 CV10で変更する仕様

| 旧仕様 | CV10仕様 | 理由 |
|---|---|---|
| 暦月の1日～末日 | `MasterSysman.ShimeBi` による自社締日基準の計上月 | 在庫・掛集計の既存規則と統一 |
| 諸掛更新から商品原価を任意更新 | 諸掛更新は配賦まで。原価更新は選択中の原価方式で行う | 実行順による原価上書きを防止 |
| 最終仕入原価と総平均原価を任意実行 | `MasterSysman.CostMethod` でどちらか一方を選択 | 同月・同商品の原価正典を一意にする |
| `TQ` を加算できる | 常に0、列・入力項目も作らない | D-06で不使用を決定済み |
| 商品原価変更マスタ | `TranGenka` を年月・計算根拠付きで新設 | 再計算、監査、過去年月参照を可能にする |
| 売上明細の処理済フラグ | 生成仕入と売上明細を専用リンクテーブルで関連付ける | JSON内フラグだけでは削除・再生成を追跡できない |

## 2. 共通設計仕様（承認対象）

### 2.1 計上月と対象期間

画面入力は `TargetMonth`（yyyyMM）とする。対象期間は共通部品で解決する。

```text
period = ClosingMonthCalculator.GetPeriod(TargetMonth, MasterSysman.ShimeBi)
DayFrom = period.DayFrom
DayTo   = period.DayTo
```

例: 自社締日20日、`TargetMonth=202609` の対象期間は 2026/08/21～2026/09/20。

SQL内で `substr(DenDay,1,6)` を使用して暦月化しない。

### 2.2 原価単位

- 原価は商品単位とする。色・サイズ・倉庫別原価は持たない。
- DB保存値は現行互換の円単位整数とする。
- 中間計算は `decimal` または `long` を使い、`int` への変換は保存境界だけで行う。
- 0円原価は初期値として存在し得るが、計算後原価0円はエラーとする。
- `MasterShohin.IsZaiko=0` の商品は最終仕入原価・総平均原価の対象外とする。

### 2.3 原価方式

`MasterSysman` に `CostMethod` を追加する。

| 値 | 名称 | 原価更新画面 |
|---:|---|---|
| 0 | 固定原価 | どちらも実行不可。商品マスタの現行値を継続使用 |
| 1 | 最終仕入原価 | 最終仕入原価更新のみ実行可 |
| 2 | 総平均原価 | 総平均原価更新のみ実行可 |

方式変更時は、変更適用月から最新計上月までの原価再計算を必須とする。
方式変更だけで既存原価を即時変更しない。

### 2.4 プレビューと更新

各画面は「確認」と「更新」を分ける。

1. 確認時に対象行、計算根拠、エラー行を取得する。
2. エラーが1件でもあれば更新できない。
3. 更新時はサーバーで同じ計算を再実行する。
4. 確認後に対象伝票の `Vdu`、対象マスタ、締日または原価方式が変わっていた場合は中断し、再確認を要求する。
5. 1回の更新は1トランザクションとし、部分成功を許可しない。
6. 成否にかかわらず処理名、対象月、件数、開始・終了時刻、結果を実行履歴に記録する。

プレビュー後の行選択による部分更新は採用しない。月次原価を商品ごとに任意除外すると、
同一月の在庫評価基準が混在するためである。

#### 2.5.2 共通定義

- 追加4テーブルは `BaseDbClass` を継承し、`Id`、`Vdc`、`Vdu` を共通列として持つ。
- `Id` は `long`、自動採番主キー。`Vdc`、`Vdu` は `long` のUTC Ticksで、既存共通処理に従う。
- 本項の列はすべて `NOT NULL` とし、文字列・JSONには空値、数値には0を設定して既存モデルの初期値規則に合わせる。
- `string(n)` は `[ColumnSizeDml(n)]`、JSONは `[SerializedColumn]` を使用する。物理型は既存DDL生成器によりDBごとに決定する。
- 日付は `yyyyMMdd`、計上月は `yyyyMM`、実行IDはGUIDのD形式（36文字）とする。
- `V*` 列は `CodeNameView` のJSONとする。伝票系テーブルでは実行時点の監査値であり、マスタ改名を伝播しない。
- 本設計の関連IDは論理外部キーとする。履歴保持と `0=該当なし` を許容するため、物理的な削除連鎖は設定しない。
- **`Id_Shohin`、`Id_Shain`、`Id_Shiire`、`Id_ConsignmentShiire` など `Id_*` 形式の論理FK列には、
  既存規約どおり `[ForeignKey(nameof(対象クラス))]`（`CvBase/Share/AttributeClass.cs:140`、
  メタデータのみで物理制約なし）を付与する。** 区分値列にも既存例（`Tran03Shiire.TaxRounding` の
  `[ForeignKey(nameof(EnumRounding))]`）に倣い、対応するenumを指定する。
- `SourceMaterialId`、`TargetShiireId`、`GeneratedShiireId` は `Id_*` 命名から外れるが、
  同一テーブル内に「元」「先」の2つの伝票参照が並ぶため、役割が読める名前を優先する。
  この逸脱は意図的なものとして §13 U-11 で承認する。
- `TargetLineNo`、`SourceLineNo`、`GeneratedLineNo` は `Jmeisai` JSON配列内の `No` 値であり、
  DB上の行を指さない。`[ForeignKey]` は付けられず、整合はアプリケーション側で保証する。
- 金額は円単位。単価は `int`、数量・金額・件数はオーバーフロー防止のため `long` とする。

## 3. 諸掛更新

### 3.1 目的

`Tran02Material` に入力された運賃、関税、付随費用等を、同じ `ManualNo` を持つ
`Tran03Shiire` の商品仕入明細へ配賦する。買掛金額・税額は変更せず、在庫原価計算にだけ加算する。

### 3.2 入力

| 項目 | 内容 |
|---|---|
| 対象計上月 | 必須。対象の商品仕入日は自社締日基準期間で解決 |
| 按分方法 | 1=数量平均、2=数量比率、3=金額比率 |

旧画面の「原価更新する/しない」は廃止する。諸掛反映後の原価更新は§5または§6で行う。

### 3.3 対応キー

- `Tran02Material.ManualNo == Tran03Shiire.ManualNo` の完全一致とする。
- 空文字、空白だけ、前後空白を含む値はエラーとする。
- 大文字小文字、全角半角、内部空白を自動補正しない。
- 同じ `ManualNo` の生地付属仕入が複数存在する場合は重複エラーとし、自動合算しない。
- 商品仕入側は同一 `ManualNo` の複数伝票・複数明細をまとめて配賦対象にできる。
- 対象商品仕入は `DenDay BETWEEN DayFrom AND DayTo`、`Kubun=10`、`IsStock=1` とする。
- 生地付属仕入は日付範囲を限定せず、対応する `ManualNo` の1伝票を取得する。
  旧仕様の「生地付属仕入は全データが参照対象」を維持する。
- 生地付属仕入の `Kubun=10` を正の諸掛、`Kubun=20` を負の諸掛として扱う。
  `Kubun=30`（値引）と99（その他・消費税）は対象外とする。
  `Tran02Material` の `Kubun=99` は仕入ではなく消費税へ全額計上する特殊挙動を持つ
  （`CvBase/BaseDb2Trans.cs:1390`）ため、諸掛原資に混ぜてはならない。
- 諸掛原資は税抜の `KingakuTotal * CalcFlag`。`Tax1/2/3` と `Total` は含めない。
- **1件の生地付属仕入は、生涯で1回だけ配賦する。** 既に他の計上月で配賦済みの
  `Tran02Material.Id` は、当月の配賦対象から除外する（§3.5 の重複配賦防止を参照）。

### 3.4 配賦式

対象明細を `i`、諸掛総額を `C`、数量を `Qi`、税抜仕入金額を `Ai` とする。
数量・金額は通常仕入の正値を使う。

#### 方法1 数量平均

```text
unit = floor(C / ΣQi)
allocation[i] = unit × Qi
```

#### 方法2 数量比率

```text
allocation[i] = floor(C × Qi / ΣQi)
```

#### 方法3 金額比率

```text
allocation[i] = floor(C × Ai / ΣAi)
```

方法1と方法2は、差額調整後は多くの場合同じ結果になる（`unit × Qi` と `C × Qi / ΣQi` は
切り捨て位置が違うだけ）。旧CV.netが両方を持っていたため互換のために両方残すが、
実データ確認（§11.4）で方法1の利用実績が無ければ方法2へ一本化する。

各行を切り捨てた後の差額 `C - Σallocation[i]` は、次の優先順の1行へ加算して総額を一致させる。

1. 方法1・2は数量最大、方法3は金額最大
2. 商品仕入ID最小
3. 明細No最小

この優先順は同点行が複数あっても一意に決まるが、実装は**安定ソート**を用い、
`Jmeisai` JSON配列の格納順に依存しないことを保証する。既存の
`TaxCalculator.Apportion`（`CvBase/TaxCalculator.cs:151`）も絶対値最大の1行へ寄せる同種の方式だが、
そちらは1伝票内の税区分1〜3が対象で、諸掛配賦は対象明細数が任意である点が異なる。

負の諸掛も同じ式で符号付き配賦し、配賦合計を原資と一致させる。
`floor` は負値に対して0から遠ざかる方向へ丸めるため、負の諸掛では
`Σallocation[i]` が原資を下回る。差額調整は符号にかかわらず同じ規則で行い、
最終的に `Σallocation[i] == C` を必ず満たすことを単体テストで確認する（§11.1 C-02）。

### 3.5 保存

商品仕入JSONを直接書き換えず、`TranSundryChargeAllocation` を新設する。
列、キー、索引は §2.5.4 を正典とする。

再実行時は対象月の既存配賦を削除して再作成する。処理全体を1トランザクションにするため、失敗時は旧配賦が残る。

#### 重複配賦の防止

生地付属仕入は §3.3 のとおり日付範囲を限定しない。一方、配賦先の商品仕入は計上月で限定する。
このため一意キーを `(SumMonth, SourceMaterialId, TargetShiireId, TargetLineNo)` だけにすると、
同一 `ManualNo` の商品仕入が複数の計上月にまたがる場合に、**同じ生地付属仕入の原資 `C` が
月ごとに満額配賦され、配賦総額が原資の整数倍になる**。

これを防ぐため次を規定する。

- `SourceMaterialId` に対する部分一意制約を設ける。すなわち1件の `Tran02Material` は
  ただ1つの `SumMonth` にしか配賦行を持てない。
- 配賦対象の抽出時、`TranSundryChargeAllocation` に当該 `SourceMaterialId` の行が
  他の `SumMonth` で既に存在する場合は、当月の対象から除外し、確認一覧に
  「他月で配賦済み（配賦月・配賦額）」として表示する。
- 配賦月をやり直す場合は、先に該当月の諸掛更新を再実行して既存配賦を消す。

- 商品仕入明細が空、不正JSON、商品ID=0

- 諸掛配賦後の明細原価金額が負になる
- 計算結果が `long` の範囲を超える
- 対象の生地付属仕入が他の計上月で配賦済み（§3.5）

   （仕入先＋伝票日付、発注No 等）で行っていた。→ §3.3 の対応キーを設計し直す。
3. `ManualNo` は今後の運用で入力する前提の新規キーである。→ 運用手順と
   仕入入力画面の必須化・重複チェックを本書の範囲に追加する。

§11.4 の実データ確認は、この判定を Step 1 の最優先項目として扱う。

## 4. 消化仕入更新

### 4.1 目的

消化仕入対象商品の売上を基に `Tran03Shiire` を生成し、仕入先への買掛を計上する。
生成仕入は売上に対応する仕入債務であり、商品の物理在庫を増減させない。

### 4.2 商品マスタ追加項目

列定義は §2.5.8 を正典とする。本項では保存時検査と旧データ変換だけを定める。

保存時検査:

- `PurchaseType=3` なら `Id_ConsignmentShiire` 必須。
- 計算区分0なら `TankaShiire` と `TankaGenka` の少なくとも一方が正値。
- 計算区分1なら掛率は `1..10000`、丸め単位は `1/10/100/1000`。
- `PurchaseType!=3` の場合も設定値は保持するが処理では使用しない。

旧データ変換では、旧商品マスタの「仕入区分」「消化計算区分」「消化掛率」「消化桁切指定」
「消化端数区分」を上記へ対応付ける。旧仕様で仕入先に使っていたメーカーCDは
`MasterShiire.Code` へ照合し、未一致・複数一致は変換エラーとする。

### 4.3 対象売上

- `Tran00Uriage` と `Tran01Tenuri` の `DenDay BETWEEN DayFrom AND DayTo`。
- 明細商品の `MasterShohin.PurchaseType=3`。
- 正負の判定は範囲比較を新設せず、既存の `CalcFlag` 規約に従う。
  既存実装は `CalcFlag = (Kubun >= 20 && Kubun <= 39) ? -1 : 1`（各 `OnKubunChanged`、
  例 `CvBase/BaseDb2Trans.cs:858`）であり、`Kubun=30`（値引）も負側に含まれる。
  実際に定義されている離散値は `Tran00Uriage.EnumUri00` が 10/11/20/21/30/99、
  `Tran01Tenuri.EnumUri01` が 10/11/20/21/99（30なし）である。
  したがって「`10..19` は仕入、`20..29` は仕入返品」という範囲表現は使わず、
  対象は `Kubun` 10・11（仕入生成）と 20・21（仕入返品生成）と明示列挙する。
- 値引・その他だけの明細、商品ID=0、不正JSONは対象外ではなくエラーにする。
- 数量は正値で保持し、生成仕入ヘッダの `CalcFlag` で正負を表現する。

### 4.4 仕入単価

#### 計算区分0 仕入単価/原価

```text
MasterShohin.TankaShiire > 0 ? TankaShiire : ResolveCostAsOf(売上計上日)
```

`ResolveCostAsOf` は `TranGenka.EffectiveDay <= 売上計上日` の最新原価を返し、履歴が無ければ
`MasterShohin.TankaGenka` を使用する。

消化仕入商品は `IsStock=0` の生成仕入しか持たないため、§5.1・§6.1 の原価更新対象から外れ、
`TranGenka` に行が作られない。したがって計算区分0の商品では通常
`MasterShohin.TankaGenka` へのフォールバックだけが効く。`TranGenka` を参照するのは、
過去に通常仕入商品だった商品を後から消化仕入へ変更した場合に限られる。

また §7 の推奨順では消化仕入更新が原価更新より先に実行されるため、`ResolveCostAsOf` が
返すのは常に前月以前の確定原価である。当月の原価更新結果は当月の消化仕入単価に反映しない。
これは処理順を循環させないための意図的な仕様とする。

#### 計算区分1 売価×掛率

```text
raw = 売上明細.Tanka × ConsumptionRateBasisPoints / 10000
unitCost = raw を ConsumptionRoundingUnit 単位で ConsumptionRounding
```

生成明細は `Tanka=Gedai=unitCost`、`Kingaku=Su×unitCost` とする。
上代と商品・色・サイズ・税区分は売上明細のスナップショットを引き継ぐ。

### 4.5 生成単位と対応表

生成仕入は次のキーで分割する。

```text
売上テーブル種別 + 売上ヘッダID + 仕入先ID + 倉庫ID + 正負区分
```

`Tran03Shiire` への追加列 `IsStock` / `GeneratedKind` の定義は §2.5.9 を正典とする。

消化仕入は `IsPay=1`、`IsStock=0`、`GeneratedKind=1` とする。
`IsPay` は新設ではなく既存の掛計上フラグ（旧名「掛計上FLG」）であり、
売掛・買掛集計の共通ガード `t.IsPay = 1`（`CvDomainLogic/SummaryDb.cs:781`）で既に使われている。
既存の通常仕入で `IsPay=0` のものが買掛集計対象外になる現行仕様は変更しない。

通常の商品仕入は既定値 `IsStock=1` のため既存動作を維持する。

在庫集計は `CreateSummaryStockSql`（`CvDomainLogic/SummaryDb.cs:472`）の WHERE 句に
`IsStock=1` を1条件追加する。`CalcTran2SummaryStock` も同関数を経由するため、
1箇所の修正で両経路をカバーできる。
買掛集計（`SummaryDb.cs:1449` 以降）は `IsStock` を条件にせず、消化仕入を通常仕入と同じく集計する。

売上明細と生成仕入の対応は `TranConsumptionPurchaseLink` に保存する。
列、キー、索引は §2.5.5 を正典とする。

ヘッダ単位の対応だけであれば、既存の「`RelateNo1` = 元伝票のId」規約
（`CvBase/BaseDbHaibun.cs:141`、受注→売上・発注→仕入で運用中）で表現できる。
本設計がリンクテーブルを別に設ける理由は、売上明細1行と生成仕入明細1行の
**明細単位**の対応と、再生成判定用の `SourceVdu` を保持する必要があるためである。
`Tran03Shiire.RelateNo1` は通常仕入では発注 `Tran13Hachu.Id` に使用済みであり、
`GeneratedKind` による意味の二重化を避ける狙いもある。この判断は §13 U-10 で承認する。

### 4.6 再実行

対象期間内の既存リンクと `GeneratedKind=1` の生成仕入を削除し、現在の売上から再生成する。
削除と再生成は1トランザクションとする。

売上が削除済みでもリンクに `SourceDay` が残るため、対象期間の古い生成仕入を除去できる。
生成仕入は通常の仕入入力画面では読み取り専用とし、修正・削除は消化仕入更新からだけ行う。

生成後、影響する買掛月次を既存の `SummaryDb` 経路で再計算する。

対象期間が支払計算済みの場合は、生成仕入の削除・再生成が確定済みの支払額を変えるため、
**結果画面への表示だけでなく更新自体を中断する**。支払計算を取り消してから再実行する運用とする。
既存の締日整合チェック `SummaryRebuildClosingCheck.FindMismatches`（`CvBase/SummaryRebuildClosingCheck.cs`）が
`SummaryKaiShi.DayTo` と自社締日を突合する方式を採っているため、同じ方式で
「対象期間が `SummaryKaiShi` の支払計算済み範囲に含まれるか」を判定する。

### 4.7 税

- 商品の保存済み `Id_Tax` / `TaxRate` を生成明細へ引き継ぐ。
- `TaxCalcUnit` / `TaxRounding` を伝票へスナップショットする。これらは仕入先マスタ固有ではなく
  取引先共通基底 `MasterTorihiki`（`CvBase/BaseDb1MasterTorihiki.cs:194`）に定義され、
  `MasterTokui` / `MasterShiire` の双方が継承する。消化仕入では `MasterShiire` 側の値を使う。
- 税額は共通 `TaxCalculator.Apply`（`CvBase/TaxCalculator.cs:100`）を使用し、独自の丸め式を実装しない。
  シグネチャは
  `Apply(IEnumerable<ITaxMeisaiLine> meisai, Func<long,int> rateOf, EnumTaxCalcUnit calcUnit, EnumRounding rounding) : TaxTotals`。
- **`Apply` は「1伝票の全明細をまとめて税区分別に1回だけ丸める」前提の設計**
  （`CvBase/TaxCalculator.cs:82` のコメント）である。生成仕入では明細を1行ずつ生成するたびに
  呼ぶのではなく、§4.5 の生成単位でヘッダ1件分の明細を確定させてから1回だけ呼ぶ。
  既存の伝票入力ViewModel（`ShiireInputViewModel` 等）の呼び出しパターンを踏襲する。
- 仕入返品も税区分別課税対象額と税額を保持し、符号はヘッダ `CalcFlag` で扱う。

### 4.8 エラー

- 消化仕入先、計算条件、税区分が未設定または不正
- 仕入先が無効
- 売上明細数量が0以下
- 計算単価が0以下または上限超過
- 同一売上明細に複数の既存リンクがある
- 生成仕入が通常画面で変更され、リンク内容と一致しない

## 5. 最終仕入原価更新

### 5.1 対象

- `MasterSysman.CostMethod=1` のときだけ実行できる。
- 対象期間内の `Tran03Shiire`。
- `IsStock=1`、`Kubun=10`、明細数量>0、商品ID>0。
- `MasterShohin.IsZaiko=1`（§2.2 の共通条件を本項でも明示する）。
- 仕入返品（`Kubun=20`）、値引（30）、その他（99）、消化仕入は対象外。

### 5.2 最終行の決定

商品ごとに次の降順で1明細を決定する。

```text
Tran03Shiire.DenDay, Tran03Shiire.Id, Tran99Meisai.No
```

同日複数仕入でも結果が一意になる。旧仕様で未定義だった同日競合を補う。

### 5.3 原価

```text
lineAmount = 明細.Kingaku + ΣTranSundryChargeAllocation.Amount
AfterCost = round_away_from_zero(lineAmount / 明細.Su)
```

諸掛がなければ明細単価と一致する。原価が0以下になる場合はエラーとする。

**丸め方向を最終仕入だけ `round_away_from_zero` にする理由**: 最終仕入原価は1明細の
`金額 ÷ 数量` を単価へ戻す割り戻しであり、`floor` にすると諸掛が無い場合でも
明細単価より1円低い原価になりうる（例 `Kingaku=11,490 / Su=30 = 383.0` は一致するが、
`Kingaku=11,489 / Su=30 = 382.97` は382になる）。「対象期間内で最後の通常仕入を原価にする」
という §1.3 の維持仕様を満たすため、最も近い整数へ丸める。
諸掛配賦（§3.4）と総平均（§6.4）が `floor` なのは、配分・平均の総額が原資を超えないことを
優先するためである。3処理で丸め方向が異なるのは意図的であり、単体テストで固定する。

`EffectiveDay` は選択した最終仕入の `DenDay`。`BeforeCost` はその直前の有効な `TranGenka.AfterCost`、
履歴がなければ初回基準行の原価とする。

### 5.4 再実行

- 同月・同商品の `CostMethod=1` 履歴を置換する。
- 後続月の最終仕入原価は前月原価へ依存しないため自動再計算しない。
- 現在原価は§2.7の最新有効履歴から再解決する。
- 対象期間に通常仕入がない商品は更新しない。

## 6. 総平均原価更新

### 6.1 対象

- `MasterSysman.CostMethod=2` のときだけ実行できる。
- `MasterShohin.IsZaiko=1`。
- 対象期間に `IsStock=1`、`IsPay=1` かつ `Kubun` が 10（仕入）または 20（仕入返品）の商品仕入がある商品。
  `Tran03Shiire.EnumShiire`（`CvBase/BaseDb2Trans.cs:1374`）に定義された値は 10/20/30/99 の4つだけであり、
  「`10..29`」という範囲表現は使わず実在値を列挙する。
- `Kubun=30`（値引）と99（その他）は旧仕様どおり除外する。
- 消化仕入は `IsStock=0` のため対象外。

### 6.2 前月在庫

`SummaryStock.CumulativeSu` は最新化保証がないため使用しない。
これを更新する `CalcSummaryStockCumulative`（`CvDomainLogic/SummaryDb.cs:656`）は
本番の `SummaryAllAsyncStream` から呼ばれておらずテストからのみ実行される。
この既知の問題は `CvDomainLogic/StocktakeDb.cs:550` のコメントにも記録済みである。

```text
OpeningQty = Σ SummaryStock.Su
             WHERE SumMonth < TargetMonth
               AND Id_Shohin = 対象商品
```

全倉庫・全色・全サイズを商品単位に合算する。
`SummaryStock.SumMonth` は暦月ではなく締日基準の計上月
（`CvDomainLogic/SummaryDb.cs:334` の `ClosingMonthCalculator.CalculateKakeMonth`）であり、
§2.1 の `TargetMonth` と同じ基準のため単純比較で正しい。

`BeforeCost` は対象期間 `DayFrom` より前の最新 `TranGenka.AfterCost`。
履歴がなければ初回基準行の `MasterShohin.TankaGenka` を使用する。

```text
OpeningAmount = OpeningQty × BeforeCost
```

### 6.3 当月仕入

```text
PurchaseQty = Σ(明細.Su × ヘッダ.CalcFlag)
PurchaseAmount = Σ((明細.Kingaku + 諸掛配賦額) × ヘッダ.CalcFlag)
```

仕入は正、仕入返品は負になる。諸掛配賦額は§3の保存値を使用する。

### 6.4 計算式

```text
Denominator = OpeningQty + PurchaseQty
Numerator   = OpeningAmount + PurchaseAmount
AfterCost   = floor(Numerator / Denominator)
```

`TQ` は加算しない（チェックリスト D-06。旧CV.netでは調整金額の意味だったがCV10では扱わない）。

除算はDBに委ねず、C# の `decimal` で行ってから `floor` する（§11.2）。
`floor` は旧CV.net仕様の踏襲であり、四捨五入・切上の選択肢は設けない。

### 6.5 境界値

| 条件 | 判定 |
|---|---|
| `OpeningQty < 0` | エラー。負在庫を総平均の母数にしない |
| `OpeningQty = 0`、`PurchaseQty > 0` | 当月仕入だけで計算 |
| `OpeningQty > 0`、`BeforeCost <= 0` | エラー。前月在庫金額を0評価しない |
| `Denominator <= 0` | エラー |
| `Numerator <= 0` | エラー |
| `AfterCost <= 0` | エラー |
| 当月仕入なし | 対象外。前原価を維持 |
| 当月仕入額はあるが数量0 | エラー |

負在庫は別途在庫訂正後に再実行する。自動的に0へ丸めたり、前原価を維持して成功扱いにしない。

**運用上の注意（要検討）**: 上表のエラーは §2.4-2（エラー1件で更新不可）と §10.2（全件ロールバック）と
組み合わさるため、**1商品でも条件を満たさなければ当月の総平均原価更新が一切実行できない**。
`MasterShohin` 78,932件のうち原価0円の商品が残っている状態で、その商品に当月仕入があると
`BeforeCost <= 0` で全体が止まる。これは在庫評価基準を混在させないための意図的な設計だが、
初回稼働時に大量のエラーで詰まる可能性が高い。

対策として次を Step 7 で用意する。

- 確認一覧はエラー行だけを絞り込んで表示・CSV出力できるようにし、是正対象を一覧化できること。
- §2.6 の初回基準行生成マイグレーションで、原価0円商品を事前に洗い出して件数を報告すること。
- 「原価0円の商品を総平均の対象から恒久除外する」運用が必要かを実データ件数を見て判断すること
  （`IsZaiko=0` へ落とす、または除外設定を設ける）。§13 U-15 で承認する。

### 6.6 過去年月の再実行

総平均原価は前月原価に依存する。過去年月Mを再実行し、Mより後の `CostMethod=2` 履歴が存在する場合は、
後続する履歴月を古い順に同一トランザクションで再計算する。

プレビューには対象月だけでなく再計算される後続月と変更前後差額を表示する。
途中月の伝票・在庫が不足またはエラーなら全更新を中断する。

`EffectiveDay` は各計上月の `DayFrom` とする。

## 7. 月次状態と処理順

月次状態は `SysCostMonthState`（`(SumMonth, ProcessKind)` の縦持ち）で保持する。
列、キー、状態値は§2.5.6を正典とする。同項の「テーブルを設けず都度検査する案2」を採用する場合、
本節の状態表は画面表示ロジックの仕様としてそのまま残る。

処理順の制約として、消化仕入更新（§4.4 計算区分0）は `ResolveCostAsOf` で `TranGenka` を読むため
原価更新に依存するように見えるが、参照するのは前月以前の確定原価だけであり循環しない。
当月の原価更新結果を当月の消化仕入単価へ反映しないことは §4.4 に明記した。

推奨順:

1. 対象月の売上・仕入入力を確認する。
2. 消化仕入更新を実行する。
3. 諸掛更新を実行する。
4. 在庫Rebuildを実行し、前月在庫を確定する。
5. 選択中の原価方式を実行する。
6. 買掛Rebuild、必要なら支払計算を再実行する。
7. 原価チェックリストと粗利帳票を確認する。

後続処理完了後に先行処理を再実行した場合は次の状態へ戻す。

| 再実行 | 無効化する状態 |
|---|---|
| 消化仕入 | 諸掛、原価、買掛確認 |
| 諸掛 | 原価 |
| 在庫Rebuild | 総平均原価 |
| 過去伝票修正 | 対象月以降の総平均原価 |

実際のデータ変更は、状態表示にかかわらず各画面のサーバー側再検査を通す。

## 10. 排他・失敗・回復

### 10.1 排他

- 同一DBで原価4処理は同時実行不可。
- 更新処理は `Serializable` トランザクションで実行する。これは新規の作法ではなく、
  `_db.BeginTransaction(System.Data.IsolationLevel.Serializable)` として本体コードで
  41箇所（`CvDomainLogic/SummaryDb.cs:189` 他）に定着している既存パターンをそのまま踏襲する。
- 対象月の売上、仕入、商品マスタが確認後に変わった場合は更新を中断する。
- Schedulerからの在庫・掛Rebuildと競合した場合は後から開始した処理を中断し、再実行を案内する。

**プロセス間排他は新規実装**: 既存コードには「他画面・他バッチの実行中を検知して片方を中断する」
機構が存在しない。既存の `Serializable` は単一メソッド内の一連のSQLを1トランザクションに
まとめる用途であり、SQLiteのファイルロックによる事実上の直列化はあっても、
「どちらが先に開始したか」を判定して中断する仕組みは未実装である。
上記2点（4処理間の同時実行禁止、Scheduler競合時の中断）は本設計で新設する必要がある。
実装方式（DB上の実行中ロック行、`CvFlag` 単位の排他、アプリケーションロックのいずれか）を
Step 8 で決める。

### 10.2 失敗

- 1件でも計算不能なら全件ロールバックする。
- 処理名、対象月、失敗段階、例外概要を実行履歴に記録する。記録先は §2.4 の U-14 の決定に従う。
  `SysHistAutoexec` を使う場合、同テーブルには対象月の専用列がなく
  （`CvBase/BaseDb0Config.cs:86`）、`TaskName` または `Memo` に埋め込む前提になる。
- 生成仕入、リンク、配賦、原価履歴、商品マスタの一部だけが残る状態を許可しない。

### 10.3 回復

- 同一対象月を再確認し、同じ画面から再実行する。
- 消化仕入と諸掛は対象月を洗い替えるため、成功済み結果へ戻せる。
- 原価履歴は同月・商品・方式単位で置換し、現在原価を最新履歴から再構築する。
- DB復元が必要な場合は、更新前バックアップへ戻して対象月から再実行する。

| `SysCostMonthState` | **削減候補**。既存の月次再計算は状態を永続化せず都度検査する流儀。表示専用キャッシュに過ぎないため、廃止して都度算出する案を推奨（U-13） |
| 既存テーブルへの列追加 | `MasterShohin` / `MasterSysman` / `Tran03Shiire` を実読した限り、原価方式・消化仕入・`IsStock` 相当の既存列はなく、重複追加はない |

当初案は追加4テーブル。U-13を採用すれば追加3テーブルになる。
