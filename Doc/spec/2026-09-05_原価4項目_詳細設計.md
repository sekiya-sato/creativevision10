### 1.2 現行の原価利用箇所

- 商品・在庫・売上分析の多くは現在値 `MasterShohin.TankaGenka` を参照する。
- 売上、受注、仕入、移動、棚卸等の伝票作成時は、現在原価を `Tran99Meisai.Gedai` へコピーする。
- 保存済み伝票の `Gedai` は伝票時点の監査値であり、原価更新時に遡及更新しない。

### 1.3 旧CV.netから維持する仕様

- 最終仕入原価は、対象期間内で最後の通常仕入を原価にする。
- 総平均原価は、前月在庫金額と当月仕入金額を数量で割る。
- 諸掛は、生地付属仕入の明細に入力された商品へ、入力された金額のまま算入する（§3.1）。
- 消化仕入は、対象商品の売上から掛計上用の商品仕入を作る。
- 各処理は再実行可能とし、同一条件の再実行で結果が増殖しない。
- 更新前に対象・エラーを確認できるようにする。

## 2. 共通設計仕様（承認対象）

### 2.1 計上月と対象期間

画面入力は `TargetMonth`（yyyyMM）とする。対象期間は共通部品で解決する。

```text
period = ClosingMonthCalculator.GetPeriod(TargetMonth, MasterSysman.ShimeBi)
DayFrom = period.DayFrom
DayTo   = period.DayTo
```

例: 自社締日20日、`TargetMonth=202609` の対象期間は 2026/08/21～2026/09/20。

SQL内で `substr(DenDay,1,6)` を使用して暦月化しない。

### 2.2 原価単位

- 原価は商品単位とする。色・サイズ・倉庫別原価は持たない。
- DB保存値は現行互換の円単位整数とする。
- 中間計算は `decimal` または `long` を使い、`int` への変換は保存境界だけで行う。
- 0円原価は初期値として存在し得るが、計算後原価0円はエラーとする。
- `MasterShohin.IsZaiko=0` の商品は最終仕入原価・総平均原価の対象外とする。

### 2.3 原価方式

`MasterSysman` に `CostMethod` を追加する。

| 値 | 名称 | 原価更新画面 |
|---:|---|---|
| 0 | 固定原価 | どちらも実行不可。商品マスタの現行値を継続使用 |
| 1 | 最終仕入原価 | 最終仕入原価更新のみ実行可 |
| 2 | 総平均原価 | 総平均原価更新のみ実行可 |

方式変更時は、変更適用月から最新計上月までの原価再計算を必須とする。
方式変更だけで既存原価を即時変更しない。

### 2.4 プレビューと更新

各画面は「確認」と「更新」を分ける。

1. 確認時に対象行、計算根拠、エラー行を取得する。
2. エラーが1件でもあれば更新できない。
3. 更新時はサーバーで同じ計算を再実行する。
4. 確認後に対象伝票の `Vdu`、対象マスタ、締日または原価方式が変わっていた場合は中断し、再確認を要求する。
5. 1回の更新は1トランザクションとし、部分成功を許可しない。
6. 成否にかかわらず処理名、対象月、件数、開始・終了時刻、結果を実行履歴に記録する。

プレビュー後の行選択による部分更新は採用しない。月次原価を商品ごとに任意除外すると、
同一月の在庫評価基準が混在するためである。

#### 2.5.2 共通定義

- 追加3テーブルは `BaseDbClass` を継承し、`Id`、`Vdc`、`Vdu` を共通列として持つ。
- `Id` は `long`、自動採番主キー。`Vdc`、`Vdu` は `long` のUTC Ticksで、既存共通処理に従う。
- 本項の列はすべて `NOT NULL` とし、文字列・JSONには空値、数値には0を設定して既存モデルの初期値規則に合わせる。
- `string(n)` は `[ColumnSizeDml(n)]`、JSONは `[SerializedColumn]` を使用する。物理型は既存DDL生成器によりDBごとに決定する。
- 日付は `yyyyMMdd`、計上月は `yyyyMM`、実行IDはGUIDのD形式（36文字）とする。
- `V*` 列は `CodeNameView` のJSONとする。伝票系テーブルでは実行時点の監査値であり、マスタ改名を伝播しない。
- 本設計の関連IDは論理外部キーとする。履歴保持と `0=該当なし` を許容するため、物理的な削除連鎖は設定しない。
- **`Id_Shohin`、`Id_Shain`、`Id_Shiire`、`Id_ConsignmentShiire` など `Id_*` 形式の論理FK列には、
  既存規約どおり `[ForeignKey(nameof(対象クラス))]`（`CvBase/Share/AttributeClass.cs:140`、
  メタデータのみで物理制約なし）を付与する。** 区分値列にも既存例（`Tran03Shiire.TaxRounding` の
  `[ForeignKey(nameof(EnumRounding))]`）に倣い、対応するenumを指定する。
- `SourceMaterialId`、`TargetShiireId`、`GeneratedShiireId` は `Id_*` 命名から外れるが、
  同一テーブル内に「元」「先」の2つの伝票参照が並ぶため、役割が読める名前を優先する。
  この逸脱は意図的なものとして §13 U-11 で承認する。
- `TargetLineNo`、`SourceLineNo`、`GeneratedLineNo` は `Jmeisai` JSON配列内の `No` 値であり、
  DB上の行を指さない。`[ForeignKey]` は付けられず、整合はアプリケーション側で保証する。
- 金額は円単位。単価は `int`、数量・金額・件数はオーバーフロー防止のため `long` とする。

#### 2.5.3 追加: `TranGenka`

**名前の衝突（要判断）**: `TranGenka` はコメントアウトされた空スタブとして既に予約されている
（`CvBase/BaseDb2Trans.cs:2585`、`CvBase/DefineDataTable.cs:93`）。その構想は

> 伝票No、日付(年月+末)、セールCD、評価区分(0:通常, 1:評価替え)、OFF率、[商品CD] 上代・掛率・元原価・新原価

という**手入力の原価変更伝票（評価替え登録）**であり、本書の「月次バッチが商品×計上月×原価方式で
1行を作る履歴テーブル」とは別機能である。同じ名前を本書の用途に使うと、旧構想の
原価変更登録（評価替え・セール連動OFF率）を暗黙に取り下げることになる。

**2026-09-05 追記による解決**: §16 で評価替えを10.1の対象に加えたため、この衝突は
「どちらの機能を取るか」の問題ではなくなった。次のとおり整理する。

- `TranGenka` は本書の**原価履歴**として確定する。月次原価計算と評価替えの双方が書き込む。
- どちらが書いたかは `ChangeKind`（0=月次原価計算、1=評価替え）で区別する。
- 評価替えの実行条件・指定値は `TranGenkaReval`（§2.5.11）にヘッダとして持つ。
- 旧スタブの「伝票No・セールCD・掛率を持つ手入力の原価変更伝票」形式は採らない。

#### 2.5.6 廃止: `SysCostMonthState`（月次状態は都度算出）

**2026-09-06 決定（U-13 = 案2）。状態テーブルは新設しない。**
当初案は `(SumMonth, ProcessKind)` を主キーとする縦持ちの状態テーブルを設け、
最終成功時刻・実行ID・入力データ指紋（最大 `Vdu` と件数）を保持する構成だった。これを廃止し、
画面表示時に成果テーブルと入力データを都度突合して状態を算出する。追加テーブルは4つから3つになる。

**廃止の根拠**

CV10の既存の月次再計算（在庫・売掛・買掛Rebuild）は完了状態を永続化しない。
`SummaryRebuildClosingCheck.FindMismatches`（`CvBase/SummaryRebuildClosingCheck.cs`）が示すとおり、
保存済みの `SummaryUriSei.DayTo` / `SummaryKaiShi.DayTo` と現在のマスタ締日を都度突合する
「毎回検査」方式であり、状態テーブルは既存流儀に無い。

本書も §7 末尾で「状態値だけを信用せず再検査する」と定めており、実際の正しさは毎回の再検査が担保する。
状態テーブルの役割は画面表示用キャッシュに限られ、その一方で「状態テーブルと実データがずれる」
不整合の余地を新たに作る。`Tran00Uriage` 50,311件・`Tran03Shiire` 8,608件という現行規模では
都度集計のコストは問題にならない。

**指紋と実行実績の保存先**

状態判定に必要な「最終成功時刻」「実行ID」「入力データ指紋」は、専用列を設けなくても
各工程の**成果テーブル自身**が保持している。新たな保存先は要らない。

| 工程 | 成果テーブル | 最終成功時刻 | 実行ID | 入力データ指紋 |
|---|---|---|---|---|
| 1=消化仕入 | `TranConsumptionPurchaseLink`（§2.5.5） | `MAX(Vdc)` | `BatchId` | 行ごとの `SourceVdu` と行数 |
| 3=原価更新 | `TranGenka`（§2.5.3、`ChangeKind=0`） | `MAX(Vdu)` | `BatchId` | 対象月の入力データの最大 `Vdu` と件数 |

`ProcessKind` は `EnumCostProcessKind` として `1=消化仕入`、`3=原価更新` の2値のみ定義する
（`2=諸掛` は §3.8 で更新処理そのものを廃止したため欠番）。値は状態テーブル廃止後も
画面表示ロジックの区分として使う。原価更新の最終成功時の原価方式は `TranGenka.CostMethod` から読む。

**状態値**

状態値の定義は当初案から変更しない。算出のみが変わる。

| 値 | 名称 | 定義 |
|---:|---|---|
| 0 | 未実行 | 対象月に成果行が1件も無い |
| 1 | 完了 | 入力データが最終成功時から変化していない |
| 2 | 再実行要 | 先行処理または入力データが最終成功後に変更された |
| 3 | エラー | 最終実行が失敗。詳細は §2.4 の実行履歴を参照 |

状態3（エラー）は永続化しない。更新処理が失敗した場合はその実行のトランザクションが
巻き戻り成果行が残らないため、次回表示時は状態0または2として現れる。
失敗の事実は §2.4 の実行履歴と既存ログが担う。画面は実行直後のセッション内でのみ状態3を表示する。

**算出方法**

対象計上月の期間（締日基準の `DayFrom`〜`DayTo`。§2.1）を決めたうえで、次を評価する。

*消化仕入（`ProcessKind=1`）*

1. `TranConsumptionPurchaseLink` を `SourceDay BETWEEN DayFrom AND DayTo` で引く。0件なら状態0。
2. 同期間の消化仕入対象売上明細（§4.3）を引き、`(SourceType, SourceId, SourceLineNo)` で突合する。
3. 次のいずれかがあれば状態2、無ければ状態1とする。
   - 対応行の無い売上明細がある（追加）
   - 元売上が消えた対応行がある（削除）
   - `Link.SourceVdu <> 現在の売上ヘッダまたは明細の最大 Vdu` の行がある（更新）
4. 前回実行日時は `MAX(Vdc)`、実行IDは最新行の `BatchId` を表示する。

*原価更新（`ProcessKind=3`）*

1. `TranGenka` を `SumMonth = 対象月 AND ChangeKind = 0` で引く。0件なら状態0。
2. 最終成功時刻 `T = MAX(Vdu)`、原価方式 `M = CostMethod`（最新行）を得る。
3. 次のいずれかがあれば状態2、無ければ状態1とする。
   - 現在の `MasterSysman.CostMethod <> M`（方式変更）
   - 対象期間の在庫加算仕入・売上・諸掛明細（`Tran02Material`）に `Vdu > T` の行がある
   - 対象期間の同入力データの件数が、`TranGenka` の保存済み根拠と一致しない
   - 消化仕入が状態2である（先行処理の無効化。§7 の表）
   - 対象月の `SummaryStock` に `Vdu > T` の行がある（在庫Rebuild後）
4. 前回実行日時は `T`、実行IDは最新行の `BatchId`、原価方式は `M` を表示する。

件数の比較は指紋の一部として最大 `Vdu` と併用する。削除だけが起きた場合は最大 `Vdu` が
前進しないため、件数を見ないと検出できない。

### 2.7 現在原価の反映

```text
ORDER BY EffectiveDay DESC, SumMonth DESC, ChangeKind DESC, Vdu DESC, Id DESC
```

`ChangeKind DESC` を `Vdu` より前に置くため、同一計上月に月次原価計算行と評価替え行が並ぶ場合は
常に評価替え行が選ばれる。評価替え後に同月の月次原価更新を再実行しても、評価替えの結果は
上書きされない（§16.8、§13 U-19）。

評価替えの対象抽出時に呼ぶ `ResolveCostAsOf` だけは、同一 `SumMonth` かつ `ChangeKind=1` の行を
除外して解決する。これがないと再実行のたびに原価が下がり続ける（§16.5）。

選択中の方式に履歴がなければ `CostMethod=0` の基準行を使用する。
基準行も含めて履歴が1行も無い商品は、`MasterShohin.TankaGenka` を変更しない。
基準行は初回更新の対象商品にだけ作られるため、未更新商品を0円へ落とさないための明示規定とする。
過去に選択していた別方式の履歴は監査用に残すが、現在原価の解決対象にはしない。

過去年月を再実行しても、それより新しい履歴があれば商品マスタ現在値を過去原価へ戻さない。

保存済み `Tran99Meisai.Gedai`、`GedaiTotal` は更新しない。

## 3. 諸掛

**本節は2026-09-05に全面改訂した。** 改訂前は「伝票ヘッダの `ManualNo` で生地付属仕入と商品仕入を
突き合わせ、数量平均・数量比率・金額比率のいずれかでシステムが自動配賦する」設計だったが、
運用前提が確認できたため取り下げた。旧設計の記述は本書に残さない。

### 3.1 運用前提（確定）

- 諸掛（運賃、関税、付随費用等）は生地付属仕入 `Tran02Material` の**明細単位**に入力する。
- 明細には費用の内容（費目）と、**その費用を負担する商品を1つ**入力する。
- 1件の費用が複数商品にまたがる場合は、**入力者が按分して明細を分ける**。
  **常に「1明細 = 1商品」**として運用する。
- この諸掛は**総平均原価**の計算に使う。

したがって**システムは按分を行わない**。対応キーも按分方式も不要になる。

この前提により §15.1 の未解決事項 #1（`ManualNo` が実データで成立しない）と
#2（同一原資の月次多重配賦）はいずれも解消する。#2 は自動配賦を前提とした問題であり、
按分をシステムが行わない以上発生しない。

### 3.2 旧CV.net実データによる裏付け

2026-09-05に旧Oracle（スキーマ `^CV[0-9]{2,3}$`、77スキーマ）を実測した。

| 明細 `HC$TRAN_TORI1.関連商品CD` に値を持つスキーマ | **18/77** |

### 3.4 諸掛明細の判定

対象期間は自社締日基準で解決する（§2.1）。

| 条件 | 内容 |

| 明細 | `Id_Shohin > 0` の行だけを諸掛とする |
| 金額 | 税抜 `Kingaku × CalcFlag`。`Tax1/2/3` と `Total` は含めない |

`Id_Shohin = 0` の明細は、在庫を持たない資材購入（通常の生地付属仕入）として原価計算の対象外とする。
同一伝票に諸掛明細と非諸掛明細が混在してよい。

### 3.5 集計

```text
SundryAmount[Id_Shohin] = Σ (明細.Kingaku × ヘッダ.CalcFlag)

対象: 対象計上月の Tran02Material
      Kubun IN (10, 20)
      明細.Id_Shohin = 当該商品
```

按分、端数処理、差額調整はいずれも行わない。入力された金額をそのまま合計する。
「1明細 = 1商品」の運用前提が守られている限り、商品別合計の総和は入力総額と必ず一致する。

集計は純関数であり、同じ入力に対して常に同じ結果になる。再実行で値が増えることはない。

### 3.6 原価計算での使用

| 原価方式 | 諸掛の扱い |
|---|---|
| 総平均原価（§6） | **当月仕入金額へ加算する。**§6.3・§6.4 の分子に含める |
| 最終仕入原価（§5） | **加算しない** |
| 固定原価 | 対象外 |

```text
総平均   PurchaseAmount += SundryAmount[商品]
最終仕入 AfterCost = round_away(明細.Kingaku / 明細.Su)     // 諸掛を含まない
```

最終仕入原価で加算しないのは、同方式が「対象期間で最後の1明細の単価」を採る方式であり、
月次で発生した諸掛を特定の1明細へ乗せる根拠がないためである。§13 U-24 で決定済。

**運用上の含意**: `MasterSysman.CostMethod=1`（最終仕入原価）で運用する事業所では、
生地付属仕入に入力した諸掛が商品原価へ反映されない。諸掛を原価に乗せたい場合は
総平均原価方式（`CostMethod=2`）を選択する必要がある。§3.8 の確認画面には、
現在の原価方式が1のとき「入力された諸掛は原価に反映されない」旨を表示する。

買掛金額、税額、在庫数量はいずれも変更しない。諸掛は在庫原価にだけ効く。

算入実績は `TranGenka.SundryAmount`（§2.5.3）に商品・計上月単位で残る。これが監査記録になる。

### 3.7 配賦テーブルを設けない

改訂前は `TranSundryChargeAllocation`（配賦元伝票と配賦先仕入明細のN:M対応表）を
新設する設計だった。**本改訂で廃止する。**

- 按分をシステムが行わないため、対応関係がN:Mにならない。明細1行が商品1つを直接指す。
- 対象月の集計は `Tran02Material` の走査だけで足り、実体化する必要がない。
- 「どの商品にいくら算入したか」の監査は `TranGenka.SundryAmount` が担う。
- 冪等性は集計が純関数であることから自動的に満たされ、重複配賦防止の仕組みも要らない。

これに伴い §2.5.4 は廃止、追加テーブルは5個から4個になる。§13 U-25 で承認する。

諸掛は独立した更新処理ではなくなる。総平均原価更新が実行時に §3.5 を直接集計する。
画面は保存を伴わない**入力内容の確認画面**とする。

確認画面が検出するもの。いずれも総平均原価更新の前に是正する。

**2026-09-06 追記: 「諸掛費目の明細」の判定**

CV10のデータ構造には「その明細が諸掛費目かどうか」を示すフラグが無い。§3.4 は `Id_Shohin > 0` の行だけを
諸掛と定め、`Id_Shohin = 0` は通常の生地付属仕入として対象外としている。したがって
`Id_Shohin=0` を無条件に警告すると、諸掛と無関係な通常の資材購入まで全件が警告になり
（`Tran02Material` 1,956件の大半が該当）、本当の入力漏れが埋もれる。

**「同一伝票に `Id_Shohin > 0` の明細が1行でもある」ことを諸掛伝票の判定に使い、
その伝票の中の `Id_Shohin=0` 行だけを入力漏れの疑いとして警告する。**
諸掛を1行も含まない伝票の `Id_Shohin=0` 行は警告にしない。

これは §4.3 の消化仕入で「消化仕入商品の明細を1行でも含む売上ヘッダだけを検査対象にする」のと
同じ考え方である。Step 6 で実装した（`CostUpdateDbSundry.cs`）。

一覧列は §8.2 に記す。

`EnumCostProcessKind` は `1=消化仕入`、`3=原価更新` の2値とし、`2`（諸掛）は欠番とする。
区分は画面表示ロジックでのみ使う（§2.5.6）。

## 4. 消化仕入更新

### 4.1 目的

消化仕入対象商品の売上を基に `Tran03Shiire` を生成し、仕入先への買掛を計上する。
生成仕入は売上に対応する仕入債務であり、商品の物理在庫を増減させない。

### 4.2 商品マスタ追加項目

列定義は §2.5.8 を正典とする。本項では保存時検査と旧データ変換だけを定める。

保存時検査:

- `PurchaseType=3` なら `Id_ConsignmentShiire` 必須。
- 計算区分0なら `TankaShiire` と `TankaGenka` の少なくとも一方が正値。
- 計算区分1なら掛率は `1..10000`、丸め単位は `1/10/100/1000`。
- `PurchaseType!=3` の場合も設定値は保持するが処理では使用しない。

旧データ変換では、旧商品マスタの「仕入区分」「消化計算区分」「消化掛率」「消化桁切指定」
「消化端数区分」を上記へ対応付ける。旧仕様で仕入先に使っていたメーカーCDは
`MasterShiire.Code` へ照合し、未一致・複数一致は変換エラーとする。

### 4.3 対象売上

- `Tran00Uriage` と `Tran01Tenuri` の `DenDay BETWEEN DayFrom AND DayTo`。
- 明細商品の `MasterShohin.PurchaseType=3`。
- 正負の判定は範囲比較を新設せず、既存の `CalcFlag` 規約に従う。
  既存実装は `CalcFlag = (Kubun >= 20 && Kubun <= 39) ? -1 : 1`（各 `OnKubunChanged`、
  例 `CvBase/BaseDb2Trans.cs:858`）であり、`Kubun=30`（値引）も負側に含まれる。
  実際に定義されている離散値は `Tran00Uriage.EnumUri00` が 10/11/20/21/30/99、
  `Tran01Tenuri.EnumUri01` が 10/11/20/21/99（30なし）である。
  したがって「`10..19` は仕入、`20..29` は仕入返品」という範囲表現は使わず、
  対象は `Kubun` 10・11（仕入生成）と 20・21（仕入返品生成）と明示列挙する。
- 値引・その他だけの明細、商品ID=0、不正JSONは対象外ではなくエラーにする。
- 数量は正値で保持し、生成仕入ヘッダの `CalcFlag` で正負を表現する。

### 4.4 仕入単価

#### 計算区分0 仕入単価/原価

```text
MasterShohin.TankaShiire > 0 ? TankaShiire : ResolveCostAsOf(売上計上日)
```

`ResolveCostAsOf` は `TranGenka.EffectiveDay <= 売上計上日` の最新原価を返し、履歴が無ければ
`MasterShohin.TankaGenka` を使用する。

消化仕入商品は `IsStock=0` の生成仕入しか持たないため、§5.1・§6.1 の原価更新対象から外れ、
`TranGenka` に行が作られない。したがって計算区分0の商品では通常
`MasterShohin.TankaGenka` へのフォールバックだけが効く。`TranGenka` を参照するのは、
過去に通常仕入商品だった商品を後から消化仕入へ変更した場合に限られる。

また §7 の推奨順では消化仕入更新が原価更新より先に実行されるため、`ResolveCostAsOf` が
返すのは常に前月以前の確定原価である。当月の原価更新結果は当月の消化仕入単価に反映しない。
これは処理順を循環させないための意図的な仕様とする。

#### 計算区分1 売価×掛率

```text
raw = 売上明細.Tanka × ConsumptionRateBasisPoints / 10000
unitCost = raw を ConsumptionRoundingUnit 単位で ConsumptionRounding
```

生成明細は `Tanka=Gedai=unitCost`、`Kingaku=Su×unitCost` とする。
上代と商品・色・サイズ・税区分は売上明細のスナップショットを引き継ぐ。

### 4.5 生成単位と対応表

生成仕入は次のキーで分割する。

```text
売上テーブル種別 + 売上ヘッダID + 仕入先ID + 倉庫ID + 正負区分
```

`Tran03Shiire` への追加列 `IsStock` / `GeneratedKind` の定義は §2.5.9 を正典とする。

消化仕入は `IsPay=1`、`IsStock=0`、`GeneratedKind=1` とする。
`IsPay` は新設ではなく既存の掛計上フラグ（旧名「掛計上FLG」）であり、
売掛・買掛集計の共通ガード `t.IsPay = 1`（`CvDomainLogic/SummaryDb.cs:781`）で既に使われている。
既存の通常仕入で `IsPay=0` のものが買掛集計対象外になる現行仕様は変更しない。

通常の商品仕入は既定値 `IsStock=1` のため既存動作を維持する。

在庫集計は `CreateSummaryStockSql`（年月在庫）と `CreateRealStockSql`（現在庫）の WHERE 句に
`IsStock=1` を1条件追加する。`CalcTran2SummaryStock` も両関数を経由するため、
2関数の修正で全経路をカバーできる。

**2026-09-06 追記**: 当初は `CreateSummaryStockSql` だけを挙げていたが、`CreateRealStockSql`
（`SummaryRealStock`）にも同じ条件が要る。U-04「消化仕入は在庫・総平均原価から除外」は
現在庫にも当然効くべきであり、年月在庫だけ除外すると現在庫と乖離するためである。Step 5 で両方へ入れた。

両関数は `tableName` を引数に取り、`Tran00Uriage` / `Tran01Tenuri` / `Tran05Ido` / `Tran61Chosei` など
`IsStock` 列を持たないテーブルからも呼ばれる。したがって条件は無条件に足さず、
`tableName == nameof(Tran03Shiire)` のときだけ付ける（`SummaryDb.CreateIsStockWhereClause`）。

買掛集計（`SummaryDb.cs:1449` 以降）は `IsStock` を条件にせず、消化仕入を通常仕入と同じく集計する。

売上明細と生成仕入の対応は `TranConsumptionPurchaseLink` に保存する。
列、キー、索引は §2.5.5 を正典とする。

ヘッダ単位の対応だけであれば、既存の「`RelateNo1` = 元伝票のId」規約

**明細単位**の対応と、再生成判定用の `SourceVdu` を保持する必要があるためである。
`Tran03Shiire.RelateNo1` は通常仕入では発注 `Tran13Hachu.Id` に使用済みであり、
`GeneratedKind` による意味の二重化を避ける狙いもある。この判断は §13 U-10 で承認する。

### 4.6 再実行

対象期間内の既存リンクと `GeneratedKind=1` の生成仕入を削除し、現在の売上から再生成する。
削除と再生成は1トランザクションとする。

売上が削除済みでもリンクに `SourceDay` が残るため、対象期間の古い生成仕入を除去できる。
生成仕入は通常の仕入入力画面では読み取り専用とし、修正・削除は消化仕入更新からだけ行う。

生成後、影響する買掛月次を既存の `SummaryDb` 経路で再計算する。

対象期間が支払計算済みの場合は、生成仕入の削除・再生成が確定済みの支払額を変えるため、
**結果画面への表示だけでなく更新自体を中断する**。支払計算を取り消してから再実行する運用とする。
既存の締日整合チェック `SummaryRebuildClosingCheck.FindMismatches`（`CvBase/SummaryRebuildClosingCheck.cs`）が
`SummaryKaiShi.DayTo` と自社締日を突合する方式を採っているため、同じ方式で
「対象期間が `SummaryKaiShi` の支払計算済み範囲に含まれるか」を判定する。

### 4.7 税

- 商品の保存済み `Id_Tax` / `TaxRate` を生成明細へ引き継ぐ。
- `TaxCalcUnit` / `TaxRounding` を伝票へスナップショットする。これらは仕入先マスタ固有ではなく
  取引先共通基底 `MasterTorihiki`（`CvBase/BaseDb1MasterTorihiki.cs:194`）に定義され、
  `MasterTokui` / `MasterShiire` の双方が継承する。消化仕入では `MasterShiire` 側の値を使う。
- 税額は共通 `TaxCalculator.Apply`（`CvBase/TaxCalculator.cs:100`）を使用し、独自の丸め式を実装しない。
  シグネチャは
  `Apply(IEnumerable<ITaxMeisaiLine> meisai, Func<long,int> rateOf, EnumTaxCalcUnit calcUnit, EnumRounding rounding) : TaxTotals`。
- **`Apply` は「1伝票の全明細をまとめて税区分別に1回だけ丸める」前提の設計**
  （`CvBase/TaxCalculator.cs:82` のコメント）である。生成仕入では明細を1行ずつ生成するたびに
  呼ぶのではなく、§4.5 の生成単位でヘッダ1件分の明細を確定させてから1回だけ呼ぶ。
  既存の伝票入力ViewModel（`ShiireInputViewModel` 等）の呼び出しパターンを踏襲する。
- 仕入返品も税区分別課税対象額と税額を保持し、符号はヘッダ `CalcFlag` で扱う。

### 4.8 エラー

- 消化仕入先、計算条件、税区分が未設定または不正
- 仕入先が無効
- 売上明細数量が0以下
- 計算単価が0以下または上限超過
- 同一売上明細に複数の既存リンクがある
- 生成仕入が通常画面で変更され、リンク内容と一致しない

## 5. 最終仕入原価更新

### 5.1 対象

- `MasterSysman.CostMethod=1` のときだけ実行できる。
- 対象期間内の `Tran03Shiire`。
- `IsStock=1`、`Kubun=10`、明細数量>0、商品ID>0。
- `MasterShohin.IsZaiko=1`（§2.2 の共通条件を本項でも明示する）。
- 仕入返品（`Kubun=20`）、値引（30）、その他（99）、消化仕入は対象外。

### 5.2 最終行の決定

商品ごとに次の降順で1明細を決定する。

```text
Tran03Shiire.DenDay, Tran03Shiire.Id, Tran99Meisai.No
```

同日複数仕入でも結果が一意になる。旧仕様で未定義だった同日競合を補う。

### 5.3 原価

```text
AfterCost = round_away_from_zero(明細.Kingaku / 明細.Su)
```

**諸掛は加算しない**（§3.6、§13 U-24 で決定済）。最終仕入原価は「対象期間で最後の1明細の単価」を
採る方式であり、月次で発生した諸掛を特定の1明細へ乗せる根拠がないためである。
諸掛は総平均原価方式でのみ原価に反映される。

結果は明細単価と一致する。原価が0以下になる場合はエラーとする。

**丸め方向を最終仕入だけ `round_away_from_zero` にする理由**: 最終仕入原価は1明細の
`金額 ÷ 数量` を単価へ戻す割り戻しであり、`floor` にすると諸掛が無い場合でも
明細単価より1円低い原価になりうる（例 `Kingaku=11,490 / Su=30 = 383.0` は一致するが、
`Kingaku=11,489 / Su=30 = 382.97` は382になる）。「対象期間内で最後の通常仕入を原価にする」
という §1.3 の維持仕様を満たすため、最も近い整数へ丸める。
総平均（§6.4）が `floor` なのは、平均の総額が原資を超えないことを優先するためである。
2処理で丸め方向が異なるのは意図的であり、単体テストで固定する。
諸掛（§3）は按分も丸めも行わず、総平均原価の分子へ金額のまま加算するだけである。

`EffectiveDay` は選択した最終仕入の `DenDay`。`BeforeCost` はその直前の有効な `TranGenka.AfterCost`、
履歴がなければ初回基準行の原価とする。

`OpeningQty` / `OpeningAmount` / `PurchaseAmount` / `SundryAmount` は最終仕入原価方式では
使わないため、`TranGenka` へは0で保存する（§2.5.3）。計算根拠として意味を持つのは
`SourceTranId` / `SourceLineNo` である。

### 5.4 再実行

- 同月・同商品の `CostMethod=1` 履歴を置換する。
- 後続月の最終仕入原価は前月原価へ依存しないため自動再計算しない。
- 現在原価は§2.7の最新有効履歴から再解決する。
- 対象期間に通常仕入がない商品は更新しない。

## 6. 総平均原価更新

### 6.1 対象

- `MasterSysman.CostMethod=2` のときだけ実行できる。
- `MasterShohin.IsZaiko=1`。
- 対象期間に `IsStock=1`、`IsPay=1` かつ `Kubun` が 10（仕入）または 20（仕入返品）の商品仕入がある商品。
  `Tran03Shiire.EnumShiire`（`CvBase/BaseDb2Trans.cs:1374`）に定義された値は 10/20/30/99 の4つだけであり、
  「`10..29`」という範囲表現は使わず実在値を列挙する。
- `Kubun=30`（値引）と99（その他）は旧仕様どおり除外する。
- 消化仕入は `IsStock=0` のため対象外。

### 6.2 前月在庫

`SummaryStock.CumulativeSu` は最新化保証がないため使用しない。
これを更新する `CalcSummaryStockCumulative`（`CvDomainLogic/SummaryDb.cs:656`）は
本番の `SummaryAllAsyncStream` から呼ばれておらずテストからのみ実行される。
この既知の問題は `CvDomainLogic/StocktakeDb.cs:550` のコメントにも記録済みである。

```text
OpeningQty = Σ SummaryStock.Su
             WHERE SumMonth < TargetMonth
               AND Id_Shohin = 対象商品
```

全倉庫・全色・全サイズを商品単位に合算する。
`SummaryStock.SumMonth` は暦月ではなく締日基準の計上月
（`CvDomainLogic/SummaryDb.cs:334` の `ClosingMonthCalculator.CalculateKakeMonth`）であり、
§2.1 の `TargetMonth` と同じ基準のため単純比較で正しい。

`BeforeCost` は対象期間 `DayFrom` より前の最新 `TranGenka.AfterCost`。
履歴がなければ初回基準行の `MasterShohin.TankaGenka` を使用する。

```text
OpeningAmount = OpeningQty × BeforeCost
```

### 6.3 当月仕入

```text
PurchaseQty    = Σ(Tran03Shiire 明細.Su × ヘッダ.CalcFlag)
PurchaseAmount = Σ(Tran03Shiire 明細.Kingaku × ヘッダ.CalcFlag)
               + SundryAmount[商品]
```

仕入は正、仕入返品は負になる。

`SundryAmount[商品]` は §3.5 の集計値で、対象計上月の `Tran02Material` 明細のうち
当該商品を指す行の税抜金額合計である。総平均原価更新の実行時にその場で集計する。
中間テーブルは持たない（§3.7）。集計値は `TranGenka.SundryAmount` へ計算根拠として保存する。

諸掛は金額にのみ効き、`PurchaseQty`（数量）には影響しない。
諸掛だけがあって当月仕入が無い商品は、`PurchaseQty=0` のまま `PurchaseAmount` だけが増える。
この場合の扱いは §6.5 に定める。

### 6.4 計算式

```text
Denominator = OpeningQty + PurchaseQty
Numerator   = OpeningAmount + PurchaseAmount
AfterCost   = floor(Numerator / Denominator)
```

`TQ` は加算しない（チェックリスト D-06。旧CV.netでは調整金額の意味だったがCV10では扱わない）。

除算はDBに委ねず、C# の `decimal` で行ってから `floor` する（§11.2）。
`floor` は旧CV.net仕様の踏襲であり、四捨五入・切上の選択肢は設けない。

### 6.5 境界値

| 条件 | 判定 |
|---|---|
| `OpeningQty < 0` | エラー。負在庫を総平均の母数にしない |
| `OpeningQty = 0`、`PurchaseQty > 0` | 当月仕入だけで計算 |
| `OpeningQty > 0`、`BeforeCost <= 0` | エラー。前月在庫金額を0評価しない |
| `Denominator <= 0` | エラー |
| `Numerator <= 0` | エラー |
| `AfterCost <= 0` | エラー |
| 当月仕入なし | 対象外。前原価を維持 |
| 当月仕入額はあるが数量0 | エラー |
| 当月仕入が無く諸掛だけがある | エラー。負担すべき仕入が無い商品へ諸掛が入力されている（§3.8で是正） |
| 諸掛の対象商品に当月仕入も前月在庫も無い | エラー。同上 |
| 諸掛の合計が負で `Numerator <= 0` | エラー。返品諸掛が過大 |

諸掛は `PurchaseQty` を増やさないため、諸掛だけが計上された商品は分母が0のまま分子だけが
増える。これを黙って前月在庫へ載せると在庫評価が歪むため、エラーとして是正させる。
是正は §3.8 の確認画面で行い、総平均原価更新の前に検出できる。

負在庫は別途在庫訂正後に再実行する。自動的に0へ丸めたり、前原価を維持して成功扱いにしない。

**運用上の注意（要検討）**: 上表のエラーは §2.4-2（エラー1件で更新不可）と §10.2（全件ロールバック）と
組み合わさるため、**1商品でも条件を満たさなければ当月の総平均原価更新が一切実行できない**。
`MasterShohin` 78,932件のうち原価0円の商品が残っている状態で、その商品に当月仕入があると
`BeforeCost <= 0` で全体が止まる。これは在庫評価基準を混在させないための意図的な設計だが、
初回稼働時に大量のエラーで詰まる可能性が高い。

対策として次を Step 7 で用意する。

- 確認一覧はエラー行だけを絞り込んで表示・CSV出力できるようにし、是正対象を一覧化できること。
- §2.6 の初回基準行生成マイグレーションで、原価0円商品を事前に洗い出して件数を報告すること。
- 「原価0円の商品を総平均の対象から恒久除外する」運用が必要かを実データ件数を見て判断すること
  （`IsZaiko=0` へ落とす、または除外設定を設ける）。§13 U-15 で承認する。

### 6.6 過去年月の再実行

総平均原価は前月原価に依存する。過去年月Mを再実行し、Mより後の `CostMethod=2` 履歴が存在する場合は、
後続する履歴月を古い順に同一トランザクションで再計算する。

プレビューには対象月だけでなく再計算される後続月と変更前後差額を表示する。
途中月の伝票・在庫が不足またはエラーなら全更新を中断する。

`EffectiveDay` は各計上月の `DayFrom` とする。

## 7. 月次状態と処理順

月次状態はテーブルに保持せず、画面表示時に成果テーブルと入力データから都度算出する
（§2.5.6、U-13）。状態値の定義と算出方法は§2.5.6を正典とし、本節は工程の依存関係と
再実行時の無効化範囲を定める。

処理順の制約として、消化仕入更新（§4.4 計算区分0）は `ResolveCostAsOf` で `TranGenka` を読むため
原価更新に依存するように見えるが、参照するのは前月以前の確定原価だけであり循環しない。
当月の原価更新結果を当月の消化仕入単価へ反映しないことは §4.4 に明記した。

推奨順:

1. 対象月の売上・仕入入力を確認する。
2. 消化仕入更新を実行する。
3. 諸掛の入力内容を確認する（§3.8）。更新処理ではないため、エラーが無ければ何もしない。
4. 在庫Rebuildを実行し、前月在庫を確定する。
5. 選択中の原価方式を実行する。
6. 必要なら評価替えを実行する（§16）。月末または期末の在庫評価減。任意。
7. 買掛Rebuild、必要なら支払計算を再実行する。
8. 原価チェックリストと粗利帳票を確認する。

後続処理完了後に先行処理を再実行した場合は次の状態へ戻す。

| 再実行 | 無効化する状態 |
|---|---|
| 消化仕入 | 原価、買掛確認 |
| 生地付属仕入の入力・修正（諸掛） | 対象月の総平均原価（最終仕入原価は諸掛を使わないため影響なし） |
| 在庫Rebuild | 総平均原価、評価替え |
| 過去伝票修正 | 対象月以降の総平均原価、対象月以降の評価替え |
| 評価替え | 対象月以降の総平均原価（前月在庫金額が変わるため） |

評価替えは月次原価計算を無効化しない。`ChangeKind` で行が分かれ、§2.7 の解決順で
評価替えが優先されるため、原価更新を再実行しても評価替えの結果は残る（§16.8）。
ただし原価更新画面の一覧には、同月に評価替え済みの商品がある旨を警告表示する。

実際のデータ変更は、状態表示にかかわらず各画面のサーバー側再検査を通す。

## 10. 排他・失敗・回復

### 10.1 排他

- 同一DBで原価4処理は同時実行不可。
- 更新処理は `Serializable` トランザクションで実行する。これは新規の作法ではなく、
  `_db.BeginTransaction(System.Data.IsolationLevel.Serializable)` として本体コードで
  41箇所（`CvDomainLogic/SummaryDb.cs:189` 他）に定着している既存パターンをそのまま踏襲する。
- 対象月の売上、仕入、商品マスタが確認後に変わった場合は更新を中断する。
- Schedulerからの在庫・掛Rebuildと競合した場合は後から開始した処理を中断し、再実行を案内する。

**プロセス間排他は新規実装**: 既存コードには「他画面・他バッチの実行中を検知して片方を中断する」
機構が存在しない。既存の `Serializable` は単一メソッド内の一連のSQLを1トランザクションに
まとめる用途であり、SQLiteのファイルロックによる事実上の直列化はあっても、
「どちらが先に開始したか」を判定して中断する仕組みは未実装である。
上記2点（4処理間の同時実行禁止、Scheduler競合時の中断）は本設計で新設する必要がある。
排他の対象には評価替え（§16.10）も含める。
実装方式（DB上の実行中ロック行、`CvFlag` 単位の排他、アプリケーションロックのいずれか）を
**Step 9**（gRPCストリーム・排他・履歴）で決める。§16 の追加に伴い、旧Step 8から繰り下げた。

### 10.2 失敗

- 1件でも計算不能なら全件ロールバックする。
- 処理名、対象月、失敗段階、例外概要を実行履歴に記録する。記録先は §2.4 の U-14 の決定に従う。
  `SysHistAutoexec` を使う場合、同テーブルには対象月の専用列がなく
  （`CvBase/BaseDb0Config.cs:86`）、`TaskName` または `Memo` に埋め込む前提になる。
- 生成仕入、リンク、原価履歴、商品マスタの一部だけが残る状態を許可しない。

### 10.3 回復

- 同一対象月を再確認し、同じ画面から再実行する。
- 消化仕入と諸掛は対象月を洗い替えるため、成功済み結果へ戻せる。
- 原価履歴は同月・商品・方式単位で置換し、現在原価を最新履歴から再構築する。
- DB復元が必要な場合は、更新前バックアップへ戻して対象月から再実行する。

## 16. 評価替え（2026-09-05 追加）

### 16.1 目的

条件で抽出した在庫商品の原価を、率または金額の一括指定で**引き下げ**、指定した計上月の
原価履歴として確定する。月末または期末の在庫評価減に使う。

- 引き上げは行わない。**計算後原価が現在の原価を下回る商品だけ**が処理対象になる。
- 原価を持たない商品、在庫を持たない商品は対象外とする。
- 実行結果は §2.5.3 `TranGenka` の履歴行（`ChangeKind=1`）と §2.5.11 `TranGenkaReval` の実行ヘッダに残す。
- 保存済み `Tran99Meisai.Gedai` / `GedaiTotal` は §2.7 と同じく遡及更新しない。

§1 の月次フローに対する位置づけは次のとおり。原価更新（最終仕入原価または総平均原価）が
確定したあとに実行する。

```text
消化仕入更新 → 諸掛確認 → 最終仕入原価更新 または 総平均原価更新
                                        ↓
                                  評価替え（任意・月末または期末）
                                        ↓
                                在庫評価額・粗利・棚卸資産の確認
```

### 16.2 根拠とした旧CV.net実装

旧CV.netの該当画面は `refer/cvnet_pkg/cvnetcrs/user125/SubDlg_01_GenkaHenkou.crs`
（ダイアログタイトル「評価替え更新」、更新ストアド `gen_ksn_125`）である。本節はこの実ソースを
一次資料とする。読み取れた仕様は次のとおり。

| 項目 | 旧実装 |

| セールCD連動のOFF率（`TranGenka` 空スタブの構想） | 対象外 | セール価格の適用範囲は上代一括変更の `Scope`（`Doc/spec/2026-09-05_上代一括変更_詳細設計.md` §2.1）が担う。原価側に別系統の適用範囲を作らない |

`Doc/spec/2026-09-05_CV10機能完成度チェックリスト.md` D-18 は評価替えを10.2以降としていた。
本節の追加により10.1へ前倒しする。同チェックリストのD-18と、§13 U-12 を併せて改訂する。

### 16.4 入力

| 項目 | 必須 | 内容 |
|---|:--:|---|
| 変更日（適用計上月） | ○ | `yyyyMM`。画面表示は `yyyy/MM`。`YearMonthInputBehavior` を使用。初期値は前月 |
| 適用時点 | ○ | 0=月末（既定）、1=期末 |
| 抽出条件 | | 項目選択式のFrom～To条件行。0行なら全在庫商品が対象 |
| 集計単位 | ○ | ブランド／アイテム／シーズン／メーカー／展示会。既定はブランド |
| 指定方式 | ○ | 1=率一括指定、2=金額一括指定。排他選択 |
| 率 | 方式1で○ | `RatePercent`。整数パーセント。1～100 |
| 金額 | 方式2で○ | `FixedCost`。1円以上の整数 |
| 端数単位 | ○ | 1円／10円／100円。既定1円。画面で毎回指定する（§13 U-22 で決定） |
| 端数処理 | ○ | `EnumRounding`: 0=四捨五入、1=切上、2=切捨。既定0 |

#### 抽出条件の項目

`MasterJouDaiBulkChangeViewModel` の `JodaiCondRow`（`FieldOptionsStatic`）と同じ方式で、
項目・From・To を1行として複数指定する。選択できる項目は次とする。

`商品CD` / `メーカー品番` / `ブランド` / `アイテム` / `メーカー` / `シーズン` / `展示会` / `素材` / `原産国`

`MasterMeisho` 由来の項目は `MasterShohin` のJSON列（`VBrand`、`VItem`、`VSeason` 等）の
`Code` に対する範囲比較とする。既存の `AddCodeRange` + `JsonCd()`
（`CvWpfclient/ViewModels/07Haibun/ShopHaibunInputViewModel.cs`）と同じSQL構築を使う。

**年度は選択項目に含めない**（§13 U-17 で決定済）。CV10の `MasterShohin` に年度に相当する列が
存在しないためでもある（`CvBase/BaseDb1Master.cs:373` 以降を実読して確認）。
`MasterShohin` への年度列追加とデータ移行は行わない。

#### 適用日の解決

```text
period       = ClosingMonthCalculator.GetPeriod(SumMonth, MasterSysman.ShimeBi)
EffectiveDay = period.DayTo
```

- 適用時点=0（月末）: 入力した計上月の締日基準期間末日。
- 適用時点=1（期末）: `MasterSysman.FiscalStartDate`（`yyyyMMdd`、`CvBase/BaseDb0System.cs`）の
  月を期首月とし、入力した計上月が属する会計年度の決算期末月（期首月の前月）を求める。
  `SumMonth` をその月へ読み替えたうえで、同じ規則で `EffectiveDay` を求める。

  ```text
  期首月     = substr(FiscalStartDate, 5, 2)
  決算期末月 = 期首月 の1か月前
  SumMonth   = 入力計上月が属する会計年度の決算期末月（yyyyMM）
  ```

  期首月が4月なら決算期末月は3月。入力が `202608` なら `SumMonth=202703`、
  入力が `202702` なら `SumMonth=202703` になる。
  読み替えの結果が未来月になる場合は入力エラーとする（§16.9）。

`substr(DenDay,1,6)` による暦月化は行わない（§2.1）。

### 16.5 対象抽出と計算

対象商品は次をすべて満たすものとする。

1. `MasterShohin.IsZaiko = 1`
2. §16.4 の抽出条件に一致する
3. 対象計上月末の在庫数 `Qty > 0`
4. `BeforeCost > 0`
5. `AfterCost < BeforeCost`
6. `MasterShohin.PurchaseType = 0`（通常仕入）。消化仕入商品（`PurchaseType=3`）は対象外

条件6は旧CV.netの `仕入仕方区分 NOT IN (4,5)` に対応する（§16.2）。
消化仕入は在庫に積まないため（§2.5.9 `IsStock=0`、U-04）条件3でも大半が落ちるが、
過去に通常仕入だった商品が消化仕入へ切り替わった場合に在庫が残り得るため、明示的に除外する。
消化仕入商品の原価は売上時に売価×掛率等で都度決まり（§4.4）、評価替えの対象にならない。

`Qty` は `SummaryStock.Su` を対象計上月以前で合計した月末在庫とする（§1.1）。
`SummaryStock.CumulativeSu` は本番経路で最新化されないため使用しない。

`BeforeCost` は商品マスタの現在値ではなく、**対象計上月時点の解決原価**とする。

```text
BeforeCost = ResolveCostAsOf(Id_Shohin, SumMonth)   // §2.7 の解決順
```

ただし再実行時の増分適用を防ぐため、`ResolveCostAsOf` は
**同一 `SumMonth` かつ `ChangeKind=1` の行を除外**して解決する。
これにより、同じ条件・同じ指定値での再実行は必ず同じ `AfterCost` になる（冪等）。

#### 計算式（品番単位）

```text
方式1（率一括指定）  raw = BeforeCost * RatePercent / 100
方式2（金額一括指定）raw = FixedCost
AfterCost = Round(raw, RoundingUnit, Rounding)
```

- 率は**掛率**を入力させる（§13 U-18 で決定済）。`RatePercent=70` は「元原価の70%にする」であり、
  30%引きではない。旧ツールチップ「評価減後金額＝在庫金額×画面で指定した率」と同じ意味になる。
  画面ラベルは「率」ではなく**「掛率」**とし、入力欄の直後に計算式
  `新原価 = 元原価 × 掛率%`（四捨五入等は指定した端数処理）を表示して誤入力を防ぐ。
- `raw` の中間計算は `decimal` で行い、`int` への変換は `Round` の出力でのみ行う（§2.2）。
- 方式2は**単価そのもの**の指定である。画面例の「金額一括指定 1,000」は、対象2,918点に対する
  評価減後金額 2,918,000円（= 1,000 × 2,918）に一致する。
- `AfterCost <= 0` はエラーとする（§2.2）。
- `AfterCost >= BeforeCost` は対象外とする。エラーではない。方式2で指定金額が元原価以上の商品は、
  この規則により自動的に除外される。旧実装の率入力は `Format="990%"` / `MaxLength=3` で
  100を超える値も入力できたが、100以上を指定すると全商品がこの規則で除外され結果は0件になる。
  CV10では入力段階で1～100に制限する。

#### 旧実装との丸め位置の差

旧実装は**集計行の在庫金額**に率を掛けて四捨五入していた（`Round(在庫金額 × 率 × 0.01)`）。
一方、更新自体は「一品単位」で行われるため、集計表示と実際の更新結果は本来一致しない。

CV10は**品番ごとに原価を丸め、集計行はその結果を合計する**。集計行の評価減後金額は
`Σ (AfterCost × Qty)` であり、更新後の在庫評価額と必ず一致する。

この変更により、率指定時の集計値が旧実装と数円～数十円ずれることがある。
実データ突合時はこの差を不一致として扱わない。

### 16.7 更新

「更新」は1トランザクション（`Serializable`）で次を行う。部分成功は許可しない（§2.4）。

1. §2.4-4 の再検査。確認時点から対象商品の `Vdu`、締日、原価方式が変わっていれば中断する。
2. `TranGenkaReval` ヘッダを1行作成する（`BatchId`、条件、指定値、集計値）。
3. 対象商品ごとに `TranGenka` を upsert する。

   | 列 | 値 |
   |---|---|
   | `BatchId` | 実行ID |
   | `SumMonth` | 対象計上月（適用時点=1 なら決算期末月） |
   | `EffectiveDay` | §16.4 で解決した適用日 |
   | `CostMethod` | 実行時点の `MasterSysman.CostMethod` |
   | `ChangeKind` | 1 |
   | `SourceRevalId` | 手順2で作成したヘッダの `Id` |
   | `BeforeCost` / `AfterCost` | §16.5 の値 |
   | `OpeningQty` | 対象計上月末の在庫数 `Qty` |
   | `OpeningAmount` | `BeforeCost * Qty` |
   | 上記以外の計算根拠列 | 0 |

4. `RefreshCurrentProductCost`（§2.7）で `MasterShohin.TankaGenka` へ反映する。
5. 対象計上月以降に総平均原価の履歴があれば、当該月以降の原価更新工程を「再実行要」にする。
   評価替えは在庫評価額を変えるため、翌月以降の前月在庫金額（§6.2）が変わる。

対象月の全対象商品を一括更新する。一覧の行選択による部分更新は採用しない（§2.4、U-08）。

#### 再実行と取消

- 同一 `(SumMonth, Id_Shohin, CostMethod, ChangeKind=1)` の行は置換する。
- `BeforeCost` の解決から同月の評価替え行を除外するため（§16.5）、
  同条件・同指定値の再実行は結果を変えない。指定値だけを変えて再実行すれば上書きされる。
- ヘッダ単位の取消を用意する（§13 U-23 で決定済）。`TranGenkaReval.Status=1`（取消）とし、
  当該 `SourceRevalId` の `TranGenka` 行を削除したうえで `RefreshCurrentProductCost` を再実行する。
  取消は、当該ヘッダより新しい評価替えが対象商品に1件も無い場合のみ許可する。

### 16.8 原価方式との関係

- 評価替えは `MasterSysman.CostMethod` の値にかかわらず実行できる。
  `CostMethod=0`（固定原価）でも実行可とする（§13 U-20 で決定済）。§2.3 の「どちらも実行不可」は
  最終仕入原価更新・総平均原価更新の2画面に対する規定であり、評価替えには適用しない。
  固定原価運用でも期末評価減は行われるためである。
- 同一計上月に月次原価計算行（`ChangeKind=0`）と評価替え行（`ChangeKind=1`）が並ぶ場合、
  **実行順にかかわらず「原価計算のあとに評価替えが行われた」ものとみなし、評価替えを有効**とする
  （§13 U-19 で決定済）。§2.7 の解決順が `ChangeKind DESC` を `Vdu DESC` より前に置くのはこのためで、
  月次原価更新をあとから再実行しても評価替えの結果は上書きされない。
- 評価替え後に同月の最終仕入原価更新・総平均原価更新を再実行しても、評価替え行は残り優先される。
  この状態は原価更新画面の一覧に警告として表示する。
- 原価方式を変更した場合（§2.3）、評価替え行は変更後の方式へ引き継がれない。
  `TranGenka` の一意キーに `CostMethod` を含むためである。方式変更後は評価替えを再実行する。

### 16.9 エラー

| 条件 | 扱い |
|---|---|
| 対象計上月が未入力・6桁でない | 入力エラー。確認不可 |
| 適用時点=期末で、読み替えた決算期末月が未来月 | 入力エラー（§16.4） |
| 指定方式1で率が1～100の外 | 入力エラー |
| 指定方式2で金額が0以下 | 入力エラー |
| 端数単位が1／10／100以外 | 入力エラー |
| 条件一致0件 | 更新不可。「データが存在しません」 |
| 条件一致はあるが対象0件 | 更新不可。「更新対象がありませんでした」＋対象外件数と理由を表示 |
| `AfterCost <= 0` | **エラー行**。1件でもあれば更新不可（§2.4-2） |
| 対象計上月が支払計算済み | 更新中断（§4.6 と同じ扱い） |

`BeforeCost=0` の商品は §16.5-4 により対象外であり、エラーにはしない。
§6.5 の総平均原価更新とは異なり、原価0円商品が評価替え全体を止めることはない。
