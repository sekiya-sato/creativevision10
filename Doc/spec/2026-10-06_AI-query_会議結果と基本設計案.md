## 1 結論と確定前提

**チャットで自然言語要求を受け、AIが実SQLiteスキーマと業務知識を確認し、数回の質問で集計項目・条件を確定する。確定後にSQLite SQLを生成し、既存server I/Fへ渡してCSVを作成し、SQLとCSVをダウンロード可能にする。**

今回の中心はSQL生成と対話である。認証は現行を利用し、ユーザーごとの権限差は設けず、全員が同じ照会・保存・共有機能を利用できる。以前の案にあった許可データセット、公開担当権限、認証改修、既存匿名経路の改修を本番開放条件とする方針は撤回する。

| 項目 | 確定した前提 |
|---|---|
| 利用者 | 一般担当も自然言語で作成し、内容を確認して実行する |
| 認証・権限 | 現行認証を維持。ユーザーレベルで分けず、全員同じ範囲の照会を実行可能 |
| AI接続 | ローカルLLM／クラウドAIを想定。初回は社内用ローカルLLM |
| 操作 | チャットで数往復し、集計項目・条件を確定してからSQLとCSVを生成 |
| CSV | 既存server I/Fを利用。CSV生成基盤の刷新は今回の主題としない |
| 再利用 | サーバ共有保存とPC個人保存を継承。保存SQLの再実行ではAIを呼ばない |
| 保存項目 | 日付、会話から自動生成されたタイトル、SQL文、SQLパラメータ、ユーザId、会話から推測したSQL内容の説明の6項目 |

「全て実行可能」は集計・実績取得という照会機能の範囲と解釈する。AIによる更新・削除・DDL生成は対象外。SQL手入力も同じ照会機能として扱い、利用者別の制限は追加しない。

## 4 チャットの利用フロー

1. ユーザー: 「先月の店舗別売上を商品分類ごとにCSVで欲しい」。
2. AI: 関係するテーブル候補を検索し、実SQLiteの列・型・キーと業務辞書を確認する。
3. AI: 「伝票日／計上日のどちらで集計しますか」「税込／税抜」「返品を含むか」等、要求だけでは決まらない点を質問する。
4. ユーザーの回答を反映し、必要なら関連スキーマを追加取得して質問を続ける。回答済み項目を繰り返し質問しない。
5. AI: 集計項目、集計単位、期間、抽出条件、出力列、並び順を日本語でまとめる。
6. ユーザー: 「この内容でSQL・CSVを作成」を実行する。
7. サーバ: 確定条件からSQL生成→スキーマ・構文確認→既存CSV I/Fを呼び出す。
8. チャットにSQLとCSVの結果カードを表示し、「SQL保存」「CSVダウンロード」「共有保存」「個人保存」を提供する。

「やっぱり商品別で」などの変更は同じ会話で受け付ける。変更後は以前の確定状態・生成SQL・CSVを現行結果として扱わず、条件確認へ戻す。旧結果を履歴として表示する場合は版と取得時刻を区別する。

明確な要求なら質問を省略して確認要約を提示できる。数回は目安であり、必ず同じ回数を強制しない。CSV生成に失敗しても、確定条件と生成済みSQLは保持する。

## 5 SQL生成の設計

### 5.1 スキーマ確認ツール

AIが必要な情報を都度要求し、アプリ側が実接続先SQLiteから取得する。最初にテーブル概要を提示し、関連候補の詳細だけを追加する。全スキーマを毎回プロンプトへ投入しない。

| ツール案 | 返却内容 |
|---|---|
| ListTables | 実在するテーブル・ビュー名、CV10側の日本語説明。件数集計は不要 |
| DescribeTables | 列名、SQLite型、NULL/既定値、主キー、外部キー、DDL |
| GetBusinessDefinitions | JOIN候補、JSON項目、コード区分、日付・金額・返品・粒度の規約 |
| ValidateQuery | 確定条件から生成した照会SQLの構文・存在する表/列、バインド整合の確認 |

Schema確認は`sqlite_schema`・表情報等のメタデータ取得で実装する。今回使ったcv-sqlite MCPは調査用で、製品がこのMCPに依存する設計ではない。

DDLに外部キーがない場合は推測でJOINを作らず、C#属性・既存照会SQL・業務辞書の検証済み関係を使う。JSON列の存在だけでは内部項目を分からないため、`Tran99Meisai`等の定義と既存SQLの対応を辞書へ登録する。

スキーマ確認ツールに任意SQL実行は不要。CSVや明細行をAIへ標準送信しない。絞り込み値のコード解決が必要なら既存マスタ検索を使用する案を詳細設計で確定する。

### 5.2 業務辞書

最初の3～5要求で使う範囲から作り、全業務の巨大な意味モデルを先行構築しない。

- 伝票日／計上日、税込／税抜、返品・取消・未確定、数量・金額の意味。
- ヘッダー／明細の集計粒度とJOIN時の重複回避。
- `Tran*`のV*は伝票時点値、Master等のV*は現行名称。
- `Jmeisai`のJSON展開、不正JSON防御、内部の項目・型。
- `CalcFlag`の適用規則。既に符号付きの数量・金額へ二重適用しない。
- 在庫を扱う場合は倉庫×商品×色×サイズのキー。

### 5.3 対話から確定するQuerySpec

SQL文字列とは別に、対象、指標、集計単位、期間・日付基準、抽出条件、税・返品等の扱い、出力列順、並び順、未解決事項を構造化する。AIは各応答でQuerySpecの更新と質問／確認要約を返す。

- 未解決事項がある間はCSVを実行しない。
- 「先月」等は会話開始時の基準日・業務タイムゾーンから具体的な開始／終了日に確定し、要約に表示する。
- 保存時は固定期間と実行時入力の期間を区別する。動的期間を使う場合は実行ごとに具体値を表示する。
- 列・条件・粒度の変更ごとにRevisionを進め、古いAI応答・SQL・CSVを新しい条件へ適用しない。
- スキーマ識別と業務辞書版は会話セッション内で保持する。保存データには追加せず、保存SQLの再利用時は現行スキーマとの整合を確認する。

初期から任意SQLの完全な構造化コンパイラを新設しない。QuerySpecを生成入力・確認要約・検証の基準として用い、SQLはLLMが生成する。

### 5.4 生成と確認

1. 確定QuerySpec、関連実スキーマ、業務辞書からSQLite照会SQLを生成する。
2. SQL、条件パラメータ、出力列、会話から自動生成したタイトル、会話から推測したSQL内容の説明、簡潔な生成理由を構造化応答で受け取る。説明文からSQLを正規表現で抜き取る方式を避ける。
3. 単一のSELECT／WITH...SELECTであることと、実表・列・パラメータの対応を確認する。
4. SQLite側のprepare／EXPLAIN等を使い、結果行を取得せず構文・名前解決を確認する方式を検証する。
5. エラーは必要な構文・列情報だけをLLMへ返し、最大2回を候補に修正する。意味条件を変える必要がある場合は質問へ戻す。
6. 検査成功後、確定RevisionのSQLと条件を既存CSV I/Fへ渡す。

SQL生成の正しさ確認であり、利用者別認可・許可データセット・専用SQL実行器の導入ではない。SQLite正典と既存方言経路を維持する。初回のSQL生成検証対象はSQLiteとし、他DBへの提供は別に実行結果を確認する。

`QueryListSqlParam.Parameters`は`string[]`なので、数値等のQuerySpecをそのまま文字列化して正しい結果になると仮定しない。CSV接続先が型付き値を受けるならそれを使用し、既存I/Fが文字列のみなら、型を保つCAST等のSQLと変換規則を限定して検証する。日付・文字列はバインドし、表・列名は実スキーマから解決する。

## 6 AI接続と会話状態

### 6.1 ローカルLLM先行とクラウド対応

- CvServerに小さなAI接続部を置き、接続種別、URL、モデル名、必要な資格情報、タイムアウトを設定する。
- 初回は選定した1つのローカルLLM接続を実装し、社内で会話・構造化応答・SQL精度・応答時間を確認する。
- 画面・QuerySpec・スキーマツールに特定モデルのAPI形式を混ぜず、将来クラウド接続を追加できる1つの接続境界を設ける。
- クラウド接続は将来の対応対象。初回から多数のベンダーSDKやAIフレームワークを追加しない。
- ツール呼出し／構造化応答の対応可否は選定モデルで確認する。対応しない場合はサーバがスキーマ取得→JSON形式の質問応答を段階実行する。
- ローカルLLMからクラウドへの自動フォールバックはしない。将来のクラウド利用では要求文・スキーマ・業務辞書の送信範囲を確認する。

LLMはDB接続情報やCSV生成権限を直接持たず、ツール要求をサーバが実行する。これは新しいユーザー権限分割ではなく、対話・生成処理と製品操作の責務分離である。

### 6.2 会話状態と失敗

状態は `要求受付 → スキーマ確認 → 質問中 → 条件確認待ち → SQL生成・検査 → CSV生成 → 取得可能` とする。条件変更は質問中／条件確認待ちへ戻り、AI・CSV失敗は直前の確定状態を保持する。

会話ID、Revision、QuerySpec、取得済みスキーマ、メッセージ、SQL、結果情報を1つの画面セッションとして保持する。初期は永続会話DBを追加せず、クライアント保持の会話コンテキストをサーバへ送る案を基本とする。トークン上限には古い対話の要約と関係スキーマの選択で対応する。

送信・生成中の重複操作を防ぎ、取消・画面閉鎖で要求を中断する。応答の会話ID／Revisionが一致しなければ破棄する。条件変更後に到着したCSVのダウンロード先を現行結果へ差し替えない。

## 7 画面と保存

WPFチャット画面は、会話履歴、入力欄、送信・取消、確定条件の要約、生成SQL、CSV結果カードで構成する。結果カードに「SQL保存」「CSVダウンロード」「共有保存」「個人保存」を置く。必須プレビュー画面や公開承認画面は新設しない。

`cv10-wpf`／`wpf-project-guide`に従い、BaseWindow、CommunityToolkit MVVM、既存App.xamlリソースとgRPCアクセス方法を踏襲する。標準／最小サイズで会話スクロール、入力欄、下端操作、長いSQLの表示を確認する。

| 保存先 | 内容・扱い |
|---|---|
| サーバ共有 | 指定の6項目を保存。全員利用・更新可能 |
| PC個人 | 同じ6項目をローカルJSON保存。自動共有しない。エクスポート／インポートで端末移行 |
| SQLダウンロード | 実行SQLと必要なパラメータ定義／条件を一緒に確認できる形を提供。単独SQLにプレースホルダーだけを残さない |
| CSVダウンロード | 既存I/Fの完了結果から取得。生成時刻、条件Revision、失敗状態を表示 |

### 7.1 保存データ

| 項目 | 内容 |
|---|---|
| 日付 | 保存時の日付。集計対象期間はSQLパラメータで扱う |
| タイトル | 会話で確定した対象・集計項目・条件からAIが自動生成する短いタイトル |
| SQL文 | 確定・検査済みのSQLite照会SQL |
| SQLパラメータ | SQLに対応する条件値。名前／順序・型・値を再実行できる形式で保持する |
| ユーザId | 保存操作を行った現行ログインユーザーのId。利用権限の制限には使わない |
| SQL内容の説明 | 会話から推測・確定した集計対象、項目、条件、集計単位等を日本語で説明する。生成SQLとの対応を確認する |

共有・個人とも保存データはこの6項目とする。QuerySpec、会話履歴、スキーマ版、辞書版、更新版、CSV結果は保存項目へ追加しない。会話ID・Revision等は実行中のセッション状態として扱う。

タイトルとSQL内容の説明はSQL生成の応答で同時に作成し、保存時に表示する。説明の不明点は会話で確認し、推測しただけの条件を確定済みとして扱わない。SQLや条件を会話で修正した場合は、新しい確定内容からタイトルと説明も生成し直す。保存SQLの通常再実行ではタイトル・説明の生成を含めてAIを呼ばない。

共有の承認階層は設けない。共有更新で個人コピーを自動上書きしない。保存SQLの再実行にはAIを使わず、保存されたSQLとパラメータを既存server I/Fへ渡す。保存SQLを対話で修正するときは、SQL・パラメータを新しい会話の入力として扱う。

会話全文・結果CSVを保存定義へ標準保存しない。画面履歴と再利用するSQL定義を区別する。CSVの文字コード・ヘッダー・0件・保存失敗は既存I/Fの動作を接続確認し、未対応だけを明示する。

| CvServer内のAiQuery AI接続部・設定 | ローカルLLM実装、モデル・接続先設定。クラウド用境界を維持 |
| CvDomainLogic/AiQueryの定義・検査 | 必要最小限の業務辞書、QuerySpec検証。外部AIへの依存を置かない |
| CvBaseのスキーマ取得補助 | 既存部品に不足する列・キー等の読取り。通常SQL実行経路は変更しない |
| CvWpfclientのAiQueryView／ViewModel、MenuData | チャット、確定操作、SQL／CSV取得、保存導線 |
| 共有保存定義・登録・migration | 既存の保存先を調査し、指定6項目の保存形式を定義。必要な場合のみ最小の定義テーブルを追加 |
| Tests/TestServer、Doc/test/UatVm | 対話状態とSQL生成・既存CSV接続の代表検証 |

新しい検索DSL、全文スキーマRAG基盤、ベクトルDB、任意SQLの完全コンパイラ、CSV実行エンジンの作り直しは初回対象外。

## 9 Step別実装計画

| Step | 作業 | 成果物・完了条件 |
|---|---|---|
| 0 接続と実例 | 既存CSV I/F・保存先の対応付け、ローカルLLM接続方式、代表3～5要求を確定 | 呼出し形式・条件型・結果取得形式が明確。自然言語と期待する項目・条件・結果の組を用意 |
| 1 詳細設計 | QuerySpec、対話状態、質問規則、スキーマツール、AI接続境界、CSV接続を定義 | DTO・状態遷移・代表会話・対象ファイルをレビュー。権限改修やCSV基盤刷新を含めない |
| 2 スキーマと辞書 | 実SQLiteの一覧・列取得、JSON明細・JOIN・指標説明を実装 | 存在しない表・列を根拠にしない。代表要求の必要情報を取得できる |
| 3 対話とSQL生成 | ローカルLLM、構造化応答、質問、確定要約、SQLite生成・検査、タイトル・SQL内容説明の自動生成を実装 | 不足情報は質問し、確定RevisionからSQL・タイトル・内容説明を作る。意味変更を黙って行わない |
| 4 チャットとCSV接続 | WPF画面、確定操作、既存CSV I/F、SQL／CSVダウンロードを接続 | 数往復→条件確定→生成→両ファイル取得が1画面で成立。修正・取消・失敗を扱う |
| 5 保存と再利用 | 指定6項目のサーバ共有／PC個人保存、SQLパラメータによる再実行を実装 | 会話からタイトル・SQL内容の説明を自動生成し、保存データを往復して同じSQL・条件で実行できる。AI停止中も再実行可能 |
| 6 統合確認 | 専用DB複製とサーバで代表要求、異常・境界、画面、buildを確認 | 期待値とCSVが一致。初回社内ローカルLLM運用手順・未確認事項を整理 |

Step 0でCSV接続に不足があれば、既存部品を使う最小差分を確定してからStep 4へ進む。Step 1完了後に詳細設計の確認を受けて実装へ移る。本書の更新・計画作成はコード実装の承認ではない。

## 10 検証と残る決定

- 対話: 明確な要求、不足条件、回答済み項目、条件変更、存在しない項目、古い応答、AI失敗を確認する。
- 生成SQL: テーブル・列・JSON項目、JOIN重複、期間境界、返品・取消、税込／税抜、0件を固定データの独立期待値で照合する。
- AIのSQL文字列そのものを固定期待値にせず、確定条件・出力列・実行結果で評価する。通常テストは固定AI応答、ローカルLLMの実接続は別の統合確認とする。
- CSV接続: 数値等のパラメータ型、生成失敗、取得失敗、SQL・CSVのRevision、保存SQL再実行を確認する。
- 保存: 指定6項目だけを保存し、会話に沿うタイトルとSQL内容の説明、日付・ユーザId、パラメータの型・0・false・NULL・順序の往復とAIなし再実行を確認する。
- WPF: XAML/XML・binding・対象project build、実View/ViewModel操作、標準／最小サイズを確認する。DB追加があれば新規DBと旧DB複製のmigrationも確認する。
- 文書・差分: CRLF、参照リンク、git diff --check。Doc/aicoding_log.mdは更新しない。

未決は、**ローカルLLMのモデル・API・配置、既存CSV I/Fの所在と返却形式、代表集計実例、共有保存の既存先**。クラウド接続の具体ベンダーと送信範囲は後続の導入時に確定する。認証・ユーザー権限の追加検討は不要とする。
