## 1 結論と前提

旧「なんでもCSV」の価値である、欲しいデータをSQLとして保存し、条件を変えて繰り返しCSV取得する仕組みを継承する。AI-queryは、**自然言語でクエリを作成・修正し、業務条件を確認して実行できる保存照会機能**とする。確定後の再実行ではSQLを生成し直さない。

### 1.1 ユーザーが示した事実・要件

| 区分 | 内容 |
|---|---|
| 旧機能 | SQLを記述・保存し、集計・実績データをCSVとして取得する |
| 共有保存 | サーバにSQLを保存し、共通参照できる |
| 個人保存 | PCにSQLを個別保存し、担当者単位で利用する |
| 初期利用者 | 一般担当も自然言語で作成し、内容確認後に実行する |
| AI接続 | 社内・ローカルAIを前提に検討する |

旧SQL、保存形式、画面、対象DB、CSV仕様は未確認。完全互換は現段階で約束しない。社内・ローカルAIという条件だけでは、モデル、動作端末、GPU、推論サーバ、運用者は確定しない。

### 1.2 推奨する初回提供範囲

- 一般担当: 許可データセットへの自然言語照会、条件確認、プレビュー、実行、CSV、PC個人保存、共有版の利用。
- 作成・公開担当: 同じ検査を通したSQL手入力・修正、個人定義の共有候補提出、確認済み版の公開。
- システム担当用の全体参照SQL: 別権限として必要性を判断する拡張候補。初回の一般担当機能をこれに置き換えない。
- AI停止時: 保存済み定義・型付き条件による実行、CSV取得を継続する。新規自然言語作成は利用不可と表示する。

## 4 利用フローと画面設計

### 4.1 新規作成

1. 利用者が「先月の店舗別売上を商品分類ごとにCSVで欲しい」などと入力する。
2. 許可データセットを解決し、AIが日付基準、金額、返品・取消、対象店舗、集計粒度など未確定条件を質問する。曖昧な条件を隠して実行しない。
3. 対象・期間・指標・粒度・除外・並び・列説明を「意味カード」に表示し、SQL候補を生成する。SQL欄は詳細表示とする。
4. サーバでSQLと条件を検査し、意味カードとの対応を確定する。解釈できない構文は一般担当向け実行に使用しない。
5. 利用者が意味カードを確認してプレビューを要求する。AIによるDB実行は行わない。
6. 上限・取得時刻付きのプレビューを確認し、CSV出力またはPC個人保存を行う。

初期の自然言語作成は、意味カードへ対応付けられる構文・指標に限定する。SQLは成果物として保存するが、対象・JOIN・条件・集計・列を表す検査済み構造も保存し、AIの説明と独立して照合する。任意SQLを完全に日本語化できるとは扱わない。

初期の対象業務は店舗別売上集計を候補とし、利用者の実例から確定する。税込／税抜、返品、売上日／計上日、取消・未確定、商品外明細は指標定義ごとに決める。在庫分析を加える場合は倉庫×商品×色×サイズの粒度を維持する。

### 4.2 再利用・編集・公開

- 再利用: 共有／個人一覧から選択→型付き条件入力→検査→プレビュー／CSV。AI呼出しは不要。
- 修正: 「商品別にも分けたい」などの指示で新草案を作る。SQLまたは意味定義が変わったら確認状態と旧プレビューを解除する。
- 条件変更: 期間・店舗等の実行値だけ変更する場合も旧結果を無効化し、実行時に型・範囲・認可を再検査する。
- 共有化: 個人定義を候補として明示送信→公開担当が業務意味・代表結果を確認→公開版を作成する。個人保存時に自動アップロードしない。
- 共有編集: 新版を草案として作成し、現行公開版を直ちに上書きしない。公開切替は競合検査を伴う。
- 共有廃止: 論理廃止を基本とし、新規実行不可。個人へ複製済みのSQLも最新の実行権限とスキーマ検査を通す。

共有版の「業務確認済み」は確認者・確認対象の版を伴う。個人の「内容確認済み」は本人の操作状態であり、組織の業務承認やサーバの認可を意味しない。

画面は「共有／個人一覧」「自然言語作成・修正」「意味カードと条件」「結果とCSV」を基本領域とする。SQL詳細、AI生成表示、出力上限、結果取得時刻、共有版番号を表示し、SQLを読める利用者には手入力も提供する。

要求文には機密・個人情報が含まれ得るため、対話全文は標準で永続化しない。用途説明と確定した業務条件を保存する。パラメータ実値や結果CSVは保存定義に含めないことを基本とし、条件の既定値を保存する場合は機密値を除く。

### 5.2 保存場所

- 共有: サーバDBに定義と公開版を保存。テーブル名・列型は詳細設計で確定する。版の公開切替と監査は同一トランザクションで行う。
- 個人: `%LocalAppData%\CreativeVision10\AiQuery`配下のUTF-8 JSONを候補とし、接続環境とログイン単位で分離する。PC保存はアクセス認可には使用しない。
- 個人ファイルは一時保存→置換とし、破損時は旧版へ戻せるようにする。明示的な定義のエクスポート／インポートを提供する。
- 環境識別には接続文字列や資格情報を保存しない。別環境へ取り込んだ定義はスキーマ・データセットを再検査する。
- サーバ共有をPC個人へ複製した時点で独立定義とする。共有更新を自動伝播させず、複製元との差異を表示する。PC間の自動同期は初回対象外。

共有実行は定義ID・公開版・条件を送信し、サーバでSQLを読み出す。個人実行は定義本文を送り毎回検査する。返却は順序付き列メタデータと行配列を使用し、0件でも列を返す。NULL・decimal・Int64・日時を型付きで扱い、JSON既定値省略で0・falseが別値にならない契約にする。

共有定義の汎用Insert/Update/削除経路から公開検査や競合検査を迂回できないよう、保存保護を設ける。DB追加は定義、`DefineDataTable`、`UpdateDb`、新規/旧DB移行の確認を一組とする。

## 6 実行境界とAI境界

### 6.1 許可データセット

許可データセットは、照会可能な行・列、結合キー、指標、日付、金額・返品等の規則をサーバで定義する。単なるテーブル名一覧やAIプロンプト上の禁止事項ではない。

一般担当に全社データを許可するのか、店舗・倉庫・原価等を制限するのかは未決。行制限が必要な場合、サーバ管理の実行者別の取得境界を設け、UNION・CTE・サブクエリ・別名・JOINでも範囲外へ出られないことを保証する。SQL末尾へのWHERE追加や画面の店舗選択だけでは認可としない。

初期構文を制限し、検査済み構造からサーバがSQLを確定する案を推奨する。構造と任意のSQL本文が一致しない場合は拒否する。自由SQL全般への意味解析・行認可を最初から実装しない。データセット内部でも不要な原価・個人情報は列単位で除外する。

既存のRole/Scopeは業務メニュー用であり、データ取得範囲への割当規則は別途承認する。新APIだけの保護をもってCV10全体のデータ認可が完成したとは扱わない。

### 6.2 サーバの検査順序

1. 検証済みJWT→SysLogin→利用者を解決し、失効・無効化・機能利用を検査する。利用者IDをクライアント申告から採用しない。
2. 共有版または個人本文を確定し、データセット／スキーマ版、条件型、権限を検査する。
3. 単一読取り文の構造を解析し、全ての参照先・関数・JOIN・条件を許可範囲と照合する。未知・解析不能な構文は拒否する。
4. 意味カードと検査済み構造を照合し、SQLite正典SQLを確定する。AI／手入力で検査を分岐させない。
5. 既存のSQL方言変換入口を使用し、変換後の実行SQLも制約を逸脱しないことを確認する。
6. 更新接続と分離した照会専用接続で実行し、件数・バイト数・時間・同時実行制限と中断を強制する。

書込み、DDL、複数文、他DB参照、ATTACH、PRAGMA、拡張ロード、未許可関数は一般照会対象外。文字列の先頭がSELECTかどうかだけでは判定しない。SQLiteの読取専用接続だけで全禁止操作が防げるとは扱わず、ドライバの制御と構造検査を組み合わせる実現性を確認する。

新規・変更SQLはSQLite正典とし、サーバは`ExecuteDialect` / `FetchDialect`等の共通入口を使う。ストリーム読取に不足する場合は同じ変換規則を通すDB層の入口を詳細設計する。初期検証はSQLiteから始め、MariaDB/PostgreSQLは対応構文と同値結果を実行検証してから提供する。DDL生成確認を実行・移行確認の代替にしない。

### 6.3 社内・ローカルAI

初期接続はサーバが管理する社内推論サービスを第一候補とし、単一PC環境ではローカル接続を選択できる構成を検討する。具体モデル、API、GPU、推論ランタイム、端末ごとのモデル配置は未決。

AI入力は利用者の要求と、利用者に許可したスキーマ・用語・結合規則・指標定義に限定する。全DBのスキーマ、結果行、CSV、接続文字列、資格情報、未処理の例外全文は標準入力に含めない。生成要求文も機密情報として扱い、社内推論サービスのログ保持・送信先・テレメトリを確認する。外部AIへの自動フォールバックは行わない。

AI出力はSQL候補、条件案、意味定義、不明点とする。SQL実行・共有公開の権限やDB資格情報をAIへ与えない。修正ループは有限回とし、候補値は詳細設計で定める。AIが示す確信度を実行可否・正しさの根拠にしない。

業務辞書は版管理し、TranのV*は伝票時点値、Master等のV*は現行名称、JSONは不正値防御、返品は元の符号規約を明記する。モデル変更だけでは保存SQLを変更しない。データセット・指標・スキーマ変更時は依存定義を再検証する。

## 7 実行結果とCSV契約

| 項目 | 初期案 |
|---|---|
| 列 | 列順と表示名を定義。同名列は利用者向けに一意化を要求。0件でもヘッダーを生成 |
| 文字コード | 通常はUTF-8 BOM付き、改行CRLF。cp932等の旧互換プロファイルは実例に基づき判断 |
| 書式 | 数値はカルチャ非依存、日付は定義された形式。時点・タイムゾーンを明記。NULLは空欄を候補とし、空文字との区別が必要な利用を確認 |
| 特殊文字 | カンマ・引用符・CR/LFをエスケープ。コードの先頭0は文字列として扱うが、Excelの自動型推定への対応は別に決める |
| 式対策 | Excel利用向けと外部取込向けを区別し、文字列の式評価対策を仕様化。負数等の数値を一律加工しない |
| プレビュー | 200行・10秒を仮の上限とし、全件結果ではないことを表示 |
| CSV | 10万行・100MB・60秒、利用者ごと同時1件を仮候補とする。実測と用途で確定 |
| 上限超過 | 正常完了とせず、期間短縮等を促す。プレビューの行打切りとCSVの未完了を区別 |
| 保存 | PC側一時ファイルへ逐次保存し、サーバの正常完了とローカル書込完了後に最終名へ変更 |
| 失敗・中断 | 完成CSVを残さない。DB側処理停止と接続解放を確認し、Error行をデータとして返さない |

プレビューとCSVは同じSQL版・同じ条件・同じ認可を使用する。ただし別実行のため、その間の業務更新により結果は変わり得る。画面に各取得時刻を表示し、プレビューとの完全一致を保証しない。CSVの1実行内はDBごとの一貫した読取り時点を確認する。厳密に同一結果を要求する場合の結果保持は別要件として判断する。

LIMITだけで集計負荷を制御できるとは扱わない。失敗後の自動再実行は初回対象外とし、手動再実行は新しい取得時点になることを表示する。ストリーム再開・サーバへの結果ファイル長期保存は初回対象外。

実行監査は利用者、定義ID／版／本文ハッシュ、データセット版、実行時刻、成否、件数・サイズ・時間を中心とする。結果行・CSV・機密条件値・対話全文は標準ログに記録しない。個人SQL本文をサーバへ常時保存しないため、再現調査には本人による定義の提供が必要になる。

## 8 Failure Scenarioと受入条件

| Failure Mode | 影響・検知 | 回避・復旧・受入条件 |
|---|---|---|
| JOINの重複、税・返品・日付誤り | 正常終了した誤集計 | 固定データと独立した期待値で件数・数量・金額照合。既存帳票比較だけに依存しない |
| AI説明とSQLが不一致 | 利用者が違う内容を確認 | 検査済み構造との照合。不一致・解析不能は実行不可、草案へ戻す |
| PC定義改竄・他利用者の共有版 | 取得範囲越え | 保存先・作者の権限を継承せず実行者を毎回認可。クライアントの確認済みフラグを信用しない |
| 匿名汎用Query/Streamによる迂回 | 新APIの制約が無効になる | 既存経路も含むアクセス境界を承認・実証するまで一般本番開放しない |
| SELECT内関数・CTE等で逸脱 | 書込み・別DB参照・過剰取得 | 構造検査、許可対象、照会専用接続で重ねて防御。異常入力の実行試験を行う |
| 重い集計、取消後もDB処理継続 | 業務DBが圧迫される | 実処理停止、接続・一時資源解放、同時実行制限を試験。タイムアウト応答だけでは合格にしない |
| CSV途中通信断・ディスク満杯 | 不完全CSVが後続取込される | 完了応答前に最終名へ変更しない。途中ファイルを除去し明示的再実行 |
| 共有公開の競合・改版 | 意図しない版の利用 | 版固定・Vdu等による競合検査。旧版へ公開を戻せる運用を用意 |
| 0件・長整数・NULL・日本語・式文字列 | CSV破損・値変化 | 型と列契約、ヘッダー、エスケープ、出力プロファイルを固定して確認 |
| AI停止・モデル変更・辞書陳腐化 | 作成不可・誤生成 | 保存SQLは継続。モデル更新を固定要求で評価し、スキーマ変更時は依存定義の再検証 |

## 9 段階導入とAction Items

| Step | 作業 | 完了条件 |
|---|---|---|
| 0 業務実例 | 旧SQL・CSVと自然言語要求を収集。初期データセット・指標を選ぶ | 列、粒度、日付、税・返品、件数・合計の期待値がある |
| 1 方針・技術検証 | 利用者別取得範囲、公開担当、社内AI配置を決め、構造検査・読取専用・中断を試作 | 専用DBと専用サーバで正常・境界・異常を確認。SQL解析手段と対応構文を選定 |
| 2 保存照会・CSV | 共有版管理、PC保存、型付き条件、任意列、ストリーム、監査を実装 | AIなしで同じ定義を再実行。新規/旧DB migration、競合、0件、失敗・中断が成立 |
| 3 AI作成・意味確認 | 社内AIと業務辞書、確認画面、自然言語修正を接続 | 一般担当がSQL読解なしで作成・確認・実行。許可外要求と曖昧条件を処理 |
| 4 限定UAT | 一般担当を含む限定利用者、専用環境で実例を照合 | 固定期待値、表示・操作、共有/個人、AI停止、CSV後続利用を確認 |
| 5 本番開放 | 既存汎用経路を含むアクセス境界、バックアップ・復旧、運用を確認 | 迂回不可を実証し、公開責任者・問い合わせ経路を決める |

Step 1～3は開発順序であり、一般担当向け初回提供からAI作成を除く段階リリースを意味しない。認可方針や既存サービスの意味変更は別承認とし、この設計作成を実装承認とは扱わない。

### 未確認事項と担当判断

1. ユーザー／業務担当: 最初に実現する3～5本の要求・旧SQL・CSVと後続用途。初期業務を売上から始めるか。
2. システム担当: 全社参照／店舗等の制限、原価・個人情報、SQL手入力、共有公開者。既存匿名経路の変更・環境分離をどこまで行うか。
3. AI運用担当: 社内推論サーバまたは単一PC配置、モデル・GPU・ライセンス、ネットワーク、ログ保持、利用量・同時利用。
4. 開発担当: 構造解析の手段、対応SQL、DBごとの読取専用・中断・一貫性、保存形式と契約。ライブラリ追加は選定根拠を提示して判断する。
5. 業務確認者: 共有版の確認責任、修正版の再確認範囲、CSV互換性と式対策、上限値と監査保持期間。

### ADR案

- 状態: 提案。
- 判断: AI-queryは共有／PC個人の保存照会＋CSVに、社内・ローカルAIの作成支援を追加する。一般担当も初期から自然言語で作成する。
- 実行: 意味確認済みの定義を、実行者に許可されたデータセット内でサーバが検査・実行する。再実行時はAI生成しない。
- 代替案: 非AIのみは作成支援要件を満たさない。AIの無確認自動実行・自動公開は誤集計と取得範囲の問題から初期不採用。
- 帰結: 旧自由SQLの完全互換を優先しない。安全な構文・指標から対応を広げる。既存匿名汎用経路の迂回対策は一般本番開放の前提。
- ロールバック: AI作成の無効化でも保存照会は継続。共有版は前版へ公開を戻す。実行保護が満たせない場合は新機能を閉じ、保護を緩めて運用しない。
- 再検討条件: 一般担当の必要分析が許可データセットで表現できない、旧SQL互換が必須、社内AIの資源不足、複数DBの同値性や中断が成立しない場合。
