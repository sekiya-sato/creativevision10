# 納品書印刷 R2 適格返還請求書 詳細設計

## 1. 目的と範囲

`CvWpfclient.Views._06Uriage.NouhinBookPrintView` を、`Tran00Uriage` を対象とする納品書・適格返還請求書の印刷画面へ再設計する。

- 取引区分を「全部 / 売上 / 返品 / 値引」から選べるようにする。
- 伝票タイプを選べるようにする。cv10 では選択値・旧データの種別にかかわらず、`1 自社伝票` として出力する。
- 印刷実行開始時に対象伝票の `IsPrint` を更新する。
- 返品・値引の税率別返還対価と消費税額を、確定済みの R2 QFM レイアウトへ出力する。

対象外は、`Tran00Uriage` 以外の伝票、帳票の印刷サーバー基盤、取引先・自社マスタの更新、旧システムへの変更である。

## 2. 前提と調査結果

- 旧 `_p_nohin01` の `item1` ～ `item66` を基礎にする。R2 用の追加値は、既存帳票で未使用だった `item41` ～ `item62` へ再配置済みである。
- `refer/printwrk/NouhinBookPrintView-sample/CVPNH_01_01_R2.qfm` は、人手で確認済み・確定済みのレイアウトである。実装時はこれを `printform/NouhinBookPrint.qfm` へ cp932 のままコピーし、内容を変更しない。
- SQLite 実データでは対象取引区分の 50,321 件すべてに、明細 `Jmeisai` 内の正の `TaxRate` が存在する。税計算単位は請求単位 50,312 件、伝票単位 8 件、返品 36 件、値引 1 件である。
- 請求単位の `Tax1` ～ `Tax3` は仕様上 0 となる。そのままでは返還税額を印字できない。

## 4. 画面詳細

既存の日付範囲、得意先範囲、伝票番号範囲、未発行のみ条件は残す。その下に次を追加する。

| 項目 | バインド | 初期値 | 動作 |
| --- | --- | --- | --- |
| 取引区分 | `SelectedTransactionCategory` | 全部 | `Kubun` の絞り込みに使う |
| 伝票タイプ | `SelectedSlipFormType` | `1 自社伝票` | 表示・パラメータとしてのみ保持し、SQL と QFM は常に自社伝票を使う |
| 印刷実行 | `PrintCommand` | - | 対象を確定して `IsPrint=1` を更新後、PDF 出力を開始する |

取引区分と `Kubun` の対応は以下とする。

| 選択値 | 範囲 |
| --- | --- |
| 全部 | 10 ～ 39 |
| 売上 | 10 ～ 19 |
| 返品 | 20 ～ 29 |
| 値引 | 30 ～ 39 |

`Kubun=99 (その他)` は選択肢に対応しないため印刷対象外とする。

F6 と画面の印刷ボタンは、ともに `PrintCommand` を実行する。現在の「発行済みにする」手動ボタンおよび「印刷では更新しない」の説明は削除する。

## 5. 印刷実行と `IsPrint` 更新

`BaseReportViewModel.DoOutputPdfCommand` は PDF 出力結果を返さないため、そのままでは更新順を制御できない。標準 VM に独自の `PrintCommand` を設け、次の順序を固定する。

1. 画面条件を検証する。
2. ヘッダー検索 SQL で対象の `Id` と `Vdu` を取得する。ここでは日付・得意先・伝票番号・取引区分・未発行のみの全条件を適用する。
3. 0 件ならメッセージを出し、更新・PDF 出力を行わない。
4. 取得した全行を 1 回の `PartialUpdateParam` にまとめ、`IsPrint` 列だけを `1` に更新する。各行の `Vdu` を `ExpectedVdu` に渡す。
5. 更新成功後、取得済み `Id` の集合だけを条件に 66 列の帳票 SQL を組み、PDF 出力を開始する。

この順序により、未発行のみを指定しても更新後の `IsPrint=1` によって印刷データが消えることはない。更新競合・更新失敗時は PDF を出力しない。PDF 作成開始後の失敗は `IsPrint=1` を戻さない。これは「印刷実行された時点で更新してよい」という要件に従う。

更新には、伝票保存と同じ副作用を持つ全列更新ではなく、`PartialUpdateParam(typeof(Tran00Uriage), [nameof(Tran00Uriage.IsPrint)], ...)` を使う。これにより在庫・金額・税額の再計算を起こさない。

## 6. 帳票 SQL と item 対応

帳票 SQL は `Tran00Uriage h` と `json_each(h.Jmeisai) d` から明細行を作る。得意先・担当・倉庫の名称は、伝票時点の監査値である `VTokui`、`VShain`、`VSoko` を JSON 展開して使う。自社名・登録番号は `MasterSysman` の単一行を読む。

| item | 内容 |
| --- | --- |
| 1～19 | 得意先、伝票、日付、担当、数量・金額・税額・メモ。旧 `_p_nohin01` の列順を維持 |
| 20～31 | `Jmeisai` の商品・色・サイズ・数量・単価・金額・上代・行番号 |
| 32～40 | 旧帳票の予備印字・自社情報 |
| 41 | 帳票題名。売上は「納品伝票」、返品・値引は「適格返還請求書」 |
| 42 | `MasterSysman.TaxRegistrationNumber` |
| 43, 44, 46 | 標準税率の表示名、返還対価（税抜）、消費税額 |
| 47, 48, 52 | 軽減税率の表示名、返還対価（税抜）、消費税額 |
| 58, 61 | 非課税等の表示名、金額 |
| 62 | 適格返還請求書用注記 |
| 63～66 | 旧帳票の税率、上代、行番号、原価フラグ |

`item41` ～ `item62` の再配置は、確定済み `data_columns.md` の `item67 → item41` などの対応をそのまま使う。SQL の SELECT 列数、QFM の `datarecord` 66 項目、確認 CSV 66 列を常に一致させる。

## 7. R2 税率別集計

税率は印刷時の現在マスタではなく、明細 `Jmeisai.TaxRate` のスナップショットを正典にする。税抜対価は `TaxableAmount1` ～ `TaxableAmount3` を、明細税率ごとに合算して表示する。

| 税計算単位 | 税額の出力値 |
| --- | --- |
| 伝票単位 | ヘッダーの `Tax1` ～ `Tax3` を、対応する明細税率へ配分して出力 |
| 請求単位 | 税率別税抜対価に伝票の `TaxRounding` を適用して、印刷専用に再計算する |

請求単位の再計算は DB 値を更新しない。整数端数処理は `EnumRounding` に合わせ、税抜対価 `A`、税率 `R` に対し次を使う。

- 切捨て: `CAST(A * R / 100 AS INTEGER)`
- 四捨五入: `CAST((A * R + 50) / 100 AS INTEGER)`
- 切上げ: `CAST((A * R + 99) / 100 AS INTEGER)`

これにより請求単位で保存税額が 0 でも、R2 帳票上の返還対価と税額を表示できる。税率スナップショットがない課税明細、または 10%・8% 以外の課税率が含まれる場合は、対象を発行済みにせずエラーとして印刷を中止する。

## 8. 実装時の検証

1. 取引区分ごとの SQL 条件と `Kubun=99` 除外を単体確認する。
2. 伝票タイプが常に `1 自社伝票` の QFM/SQL に到達することを確認する。
3. 未発行のみで対象取得後に `IsPrint=1` へ更新しても、取得済み Id で PDF データが出ることを確認する。
4. `Vdu` 不一致時は更新・PDF 出力とも行われないことを確認する。
5. 返品・値引の 10% / 8% / 非課税の item 値、請求単位の再計算税額を確認する。
6. QFM が cp932、CRLF、XML 妥当、66 item、66 列 CSV であることと、PDF レンダリング結果を確認する。
7. XAML のバインディング・レイアウトを確認し、`CvWpfclient` をビルドする。
8. `git diff --check` を実行し、利用者の既存差分を変更していないことを確認する。

## 9. 実装開始前の承認事項

1. 「全部」は `Kubun=10～39` とし、`99 その他` を含めない。
2. 請求単位伝票の R2 税額は、保存値を変えず印刷時に伝票単位で再計算する。
3. 現在の確定 QFM にある固定見出し「返還対価（税抜）」は売上を含む「全部 / 売上」でもそのまま用いる。売上用に中立な「税抜金額」へ変更する必要があれば、人手による QFM 修正後にその確定版を使用する。

上記 3 点を承認後、ここに記載したファイルだけを実装・検証する。
