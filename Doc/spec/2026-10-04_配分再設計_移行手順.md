# 配分再設計 移行手順（Step 1〜6 を本番 DB へ適用する）

- 作成日: 2026-10-04
- 対象: SQLite（PostgreSQL / MariaDB は対象外。10.2 で扱う）
- 前提: 配分再設計 Step 1〜6（`95ce99d1`〜`beab0402`）を含むサーバ・クライアント
- 関連: `Doc/spec/2026-10-03_配分再設計_基本設計.md`、Step3〜5の詳細設計、`Doc/spec/2026-09-28_設計判断記録.md` 2.8〜2.12、`Doc/spec/使用ガイドライン.md` 4章

---

## 1. 適用されるもの

| 版 | 内容 | 既存データへの影響 |
|---|---|---|
| 26_10_03_01 | `TranHaibun.ArrivedSu`（入荷済み数）を追加。発注に紐付かない未完了の区分0は入荷済み扱い（ArrivedSu=Su） | 列の追加と区分0の一部更新のみ |
| 26_10_03_02 | `TranHaibun.Id_Customer` / `LimitDay` / `EndReason`（取置）を追加 | 列の追加のみ（既存行は 0 / 空文字） |

| 起動時の初期データ | 自動実行ジョブ「取置期限切れ自動取消」の設定 3 行（実行フラグ=有効、cron `50 0 * * *`、メール=無効） | `MasterConfig` に不足行を追加するだけで、既存の値は変えない |

いずれもサーバの起動時に自動で適用される（`UpdateDb.WriteVersionInfoAsync`、`MasterConfig.CreateDefaultData`）。

## 2. 適用前

1. **バックアップ**: サーバを止め、DB ファイル（`.db` と `-wal` / `-shm`）を丸ごと保存する。
2. **未完了の配分の確認**（区分別の件数を記録する）

   ```sql
   SELECT Kubun, EndFlag, count(*) FROM TranHaibun GROUP BY Kubun, EndFlag ORDER BY Kubun, EndFlag;
   ```

3. **廃止区分の未完了行**（区分 3 / 4 / 5 / 7、`EndFlag = 0`）があれば、旧バージョンのうちに配分確定するか、指示取消（確定数0）で片付ける。新しいバージョンでは廃止区分は新規作成できず、出荷帳票の絞込にも出ない（「すべて」では出る）。
4. **確定済み・未出荷の行**（`KakuteiDay <> ''` かつ `EndFlag = 0`。旧 2 段階方式の中間状態）は、新しい配分確定画面でそのまま確定できる。件数だけ記録しておく。

---

## 3. 適用

1. サーバを更新する。**runtimes 込みでフォルダを丸ごと同期する**（個別 DLL のコピーは古い RID 別アセットが残って解決が壊れる）。
2. サーバを起動する。ログに `UpdateDb` のエラーが無いことを確認する。

   ```sql
   SELECT DbVersion, Memo FROM SysUpdateDb WHERE DbVersion >= 26100301 ORDER BY DbVersion;
   ```

3. クライアントを更新する（削除した画面：店舗配分入力・配分確定(商品)/(得意先)・取置入力の雛形。旧クライアントからは開けなくなる）。

---

## 4. 適用後（必須）

1. **全件再集計**を実行する。仕入配分（区分0）の入荷済み数と、全倉庫の引当数を作り直す（`SummaryDb.CalcReserveQtyAll` が `ArrivalDb.RecalcAll` を先に呼ぶ）。実行するまで、仕入配分の引当が 0 のままで有効在庫が実際より多く見える。
   - 開発 DB（11.3GB、未完了の配分 0 件）での実測: migration 141ms、引当の全件再集計 270ms。未完了の配分が多いと延びる。
2. **確認**
   - スケジューラ（自動実行管理）に「取置期限切れ自動取消」があり、有効になっている。
   - 権限設定で、配分確定（`07Haibun.HaibunCommit`）・仕入配分入力(商品別)（`07Haibun.PurchaseReceiptAllocationInput`）の許可が旧画面と同じになっている。
   - メニュー「■ 配分・出荷」が「配分入力／確定／帳票／照会／補充(1.1以降)」の構成になっている。
   - 有効在庫問合わせで、入荷済みの仕入配分の分だけ引当が積まれている。

---

## 5. 運用上の注意

- **取置の売上は取置配分入力の［売上変換］で計上する。POS で同じ商品を会計しない**（二重計上になる。POS 連携は 1.1 以降。D10）。
- 売上変換で作る店舗売上は決済内訳を持たないので、売上金種Viewerの金種別には出ない（手入力の店舗売上と同じ）。
- 配分の確定は取り消せない（D9）。訂正は作成された出荷売上・移動伝票で行う。
- 仕入配分は入荷済み数までしか確定できない。未入荷分を欠品で確定すると、後から入荷しても割り当たらない（確認ダイアログで警告する）。
- 期限を過ぎた取置は、期限日の翌日 0:50 に自動で取り消される。

---

## 6. ロールバック

- 2 章で取ったバックアップから DB を戻し、旧バージョンのサーバ・クライアントに戻す。
- migration は列の追加と権限明細の付け替えだけなので、新しいバージョンで入力した取置・配分を残したまま旧バージョンへ戻すことは想定しない（旧バージョンは取置の列・新しい画面を扱えない）。

---

## 7. 既知の制約

- 配分確定・取置のサーバ処理に、方言変換を通らない SQL（例: `ShippingDb.CreateShippingSlips` の `ifnull`）が残っている。SQLite では問題ない。PostgreSQL / MariaDB 対応（10.2）で直す（設計判断記録 2.12）。
