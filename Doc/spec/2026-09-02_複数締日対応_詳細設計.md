# 複数締日（最大3締日）対応 詳細設計

作成日: 2026-09-02
状態: **承認待ち・実装未着手**
位置づけ: 決定 E2「第1段階＝1得意先1締日、次段階で最大3締日」の**第2段階**
（`Doc/spec/archive/2026-08-17_旧cvnet比較_仕様決定判断材料.md:606`）

## 1. 目的とスコープ

得意先・仕入先が月内に最大3回の締めを持てるようにする。

対象:

- `MasterTokui` / `MasterShiire` の `Shime1` / `Shime2` / `Shime3` を業務ロジックで有効化する
- マスタ保守での締日バリデーション（昇順・前詰め）
- 締日未設定時の自社締日（`MasterSysman.ShimeBi`）フォールバック
- 請求計算 `CalcSummaryUriSei` / 支払計算 `CalcSummaryKaiShi` の複数締日対応
- 締日を単一前提で絞っている帳票・再作成・期首残高CSV・バッチツールの追随
- 締日の許容範囲を 1〜28/99 へ統一

スコープ外:

- 締日更新（伝票ロック。決定 J1 により 1.0 では入れない）
- 親子請求の合算出力方式の拡張
- 売掛残 `SummaryUriKake` / 買掛残 `SummaryKaiKake`（**自社締日**基準の月次集計であり、取引先締日とは無関係。変更しない）
- `PayMonth` / `PayDay` を締日ごとに3組へ増やすこと（4.4 の決定により1組のまま）

### 1.1 前提条件（クリア済み）

決定 E8-g「締日が月末以外だと売掛月次(`SummaryUriKake`)と請求残(`SummaryUriSei`)で税額が一致しない」は
`Doc/spec/2026-09-01_消費税計算単位・端数処理_全体設計.md:169-173` で**仕様として許容**と決定済み。
売掛月次は自社の月次管理値、請求残は得意先へ提示する確定値であり目的が異なる。本設計はこの決定に依存する。

### 2.2 請求残・支払残テーブルは複数締日を表現できる

- `SummaryUriSei` の一意キーは `uk1 = (Id_Tokui, DenDay)`（`CvBase/BaseDbKake.cs:154-159`）。
  `SummaryKaiShi` は `(Id_Shiire, DenDay)`（同:486-491）。
- `DenDay` ＝ 締日当日（`DenDay = DayTo = 締日`、決定 E3）。月内3回の締めは `DenDay` が `20260910` /
  `20260920` / `20260930` と異なるため、**一意キーの衝突なしに3行を持てる**。
- DELETE も `WHERE DenDay = @1 AND Id_Tokui IN (...)`（`CvDomainLogic/SummaryDb.cs:1013-1020`）で
  締日当日一致のため、**他の締日の行を巻き添えにしない**。
- `Shime` 列は Summary 側に存在しない。締日は `MasterTokui`/`MasterShiire` への JOIN でしか判別できない。

### 2.3 中核の問題 — `DayFrom` が取引先ごとに変わる

現状の期間算出は「請求月＋締日」だけで決まり、全取引先で共通である。

```csharp
// CvDomainLogic/SummaryDb.cs:1141-1151
var dayTo   = GetClosingDay(billingMonth, shime);              // 請求月の締日
var dayFrom = GetClosingDay(billingMonth.AddMonths(-1), shime).AddDays(1);  // 前月の同じ締日 + 1日
```

複数締日になるとこれが破綻する。**同じ「締日20の回」でも取引先ごとに開始日が違う**。

| 取引先 | 有効締日 | 締日20の回（請求月 202609）の期間 | 理由 |
|---|---|---|---|
| A社 | 10, 20, 99 | `20260911` 〜 `20260920` | 直前の締めは**同月の10日** |
| B社 | 20 のみ | `20260821` 〜 `20260920` | 直前の締めは**前月の20日** |
| C社 | 20, 99 | `20260821` 〜 `20260920` | 直前の締めは前月の99（＝前月末）…ではなく前月20日。※ 4.3 参照 |

ユーザー指示「前回締めた日+1から今回の締日までのデータを対象として計算」は、
この**取引先ごとの直前締日**を指す。伝票側は `t.KakeDay BETWEEN dayFrom AND dayTo` で
期間内に閉じているため、期間さえ正しければ集計内容は現行ロジックのままで正しい。

## 3. 仕様（2026-09-02 確定）

### 3.1 締日集合の解決規則

取引先1件の「有効締日リスト」を次で定める。**戻り値は常に1件以上の昇順リスト。**

```
ResolveClosingDays(shime1, shime2, shime3, ownShime):
    shime1 == 0  ->  [ownShime]                       // 自社締日フォールバック
    else         ->  [shime1, shime2, shime3] から 0 を除いたもの（昇順）
```

- `ownShime` は `MasterSysman.ShimeBi`。
- `99`（末日）は数値として最大なので、昇順ソートで自然に最後になる。特別扱いしない。
- 3.2 の前詰め制約により、`shime1 == 0` のとき `shime2` / `shime3` も必ず 0 である。

### 3.2 マスタ保守のバリデーション（**前詰め必須**）

得意先マスタ・仕入先マスタの追加・修正の**保存前**に検査し、違反すればエラーを表示して保存を中止する。

| # | 規則 | エラー文（案） |
|---|---|---|
| V1 | 0以外は昇順。`Shime1 < Shime2 < Shime3` | `締日は小さい順に設定してください。（締日1 < 締日2 < 締日3）` |
| V2 | 前詰め。0の後ろに0以外を置けない | `締日は締日1から順に設定してください。締日{n}が未設定のため締日{n+1}は設定できません。` |
| V3 | 重複禁止（V1が昇順を要求するので実質包含。メッセージを分けて出す） | `同じ締日が重複しています。` |
| V4 | 値域は `0` / `1`〜`28` / `99`（3.5） | `締日は1〜28日または末日で指定してください。` |

- V2 の帰結として `Shime1 = 0` なら `Shime2 = Shime3 = 0` が必須。
  `Shime1 = 0` は「自社締日とみなす」（3.1）であり、自社締日は最大でも 99 なので、
  それより後ろに締日2・締日3 を置くことは論理的に成立しない。
- 判定は**純ロジック**（DBアクセス不要）とし、`CvBase` に置いてテストする。
- 既存の親子締日不一致警告（E7、保存**後**・非ブロック）はそのまま残す。本バリデーションは保存**前**・ブロック。

### 3.3 締請求期間の算出

請求月 `yyyyMM` と対象締日 `S`、その取引先の有効締日リスト `D`（昇順）から:

```
DayTo   = 請求月における締日 S の実日付        （99 は月末、月末を超える指定は月末へ丸める）
prev    = D の中で S の直前の要素
          S が D の最小要素なら prev = D の最大要素（＝前月の締め）
DayFrom = prev が同月内   -> 請求月における prev の実日付 + 1日
          prev が前月扱い -> 前月における prev の実日付 + 1日
```

境界例（請求月 202609）:

| 有効締日 D | 対象締日 S | prev | DayFrom | DayTo |
|---|---|---|---|---|
| `[99]` | 99 | 99（前月） | `20260901` | `20260930` |
| `[20]` | 20 | 20（前月） | `20260821` | `20260920` |
| `[10,20,99]` | 10 | 99（前月） | `20260901` | `20260910` |
| `[10,20,99]` | 20 | 10（同月） | `20260911` | `20260920` |
| `[10,20,99]` | 99 | 20（同月） | `20260921` | `20260930` |
| `[20,99]` | 20 | 99（前月） | `20260901` | `20260920` |
| `[20,99]` | 99 | 20（同月） | `20260921` | `20260930` |
| `[28]` | 28 | 28（前月）| `20260829` | `20260928` |
| `[28]` | 28（請求月 202603） | 28（前月） | `20260301` | `20260328` |※

※ 2月は28日が月末のため `20260228 + 1日 = 20260301`。うるう年は `20240229 + 1日 = 20240301`。

**単一締日のときは現行の「前月の同じ締日+1」と完全に一致する**（`D` の要素が1つなら prev = 自分自身・前月扱い）。
したがって既存データの再計算で値は変わらない。

`2.3` の C社の例（`[20,99]` の締日20の回）は上表のとおり `20260901` 〜 `20260920` となる。
直前の締めが「前月の99」＝前月末なので、開始日は当月1日である。

### 3.4 入金予定日・支払予定日（`PayDay = 0` のフォールバック）

- `PayDay = 0`（未設定）→ **`MasterSysman.ShimeBi` を予定日の日として使う**。
- `PayDay = 99` → 従来どおり月末。
- `PayMonth` は従来どおり（`0`=当月 / `1`=翌月 / … / `4`=4ヶ月後）。基準月は請求月 `yyyyMM`。
- `PayMonth` / `PayDay` は**締日ごとに分けず1組のまま**とする。
  月内3回の締めはいずれも同じ請求月・同じ `PayMonth`/`PayDay` から予定日を算出するため、
  **同一取引先の3行は同じ予定日を持つ**。これは列を増やさない範囲での帰結であり、
  締日別の入金サイトが必要になった時点で別課題として扱う（9章 残課題 M1）。
- 現行データは `ShimeBi = 99` なので、この変更で**既存の予定日は1件も変わらない**
  （`PayDay IN (0,99)` → 月末、が `PayDay=0 → ShimeBi=99 → 月末` と同値）。

### 3.5 締日の許容範囲を 1〜28/99 へ統一

- 有効値は `1`〜`28` および `99`。`0` は「未設定」を表すマーカーで、締日そのものとしては無効。
- 根拠: マスタの入力手段が `EnumShime` の ComboBox であり、**29/30/31 は入力できない**。
  検証だけが 1〜31 を通す状態は、実在しない値を通す穴でしかない。
- 統一先は `ClosingMonthCalculator.ValidateShime`（`CvBase/ClosingMonthCalculator.cs:65-69`）に既にある規則。
- 緩い側（1〜31）を持つ5箇所を差し替える。`Min(shime, 月末日)` による月末丸めは
  2月の 28日締め等で必要なので**残す**。

## 4. 設計

### 4.1 `CvBase` へ純ロジックを新設

新規 `CvBase/ClosingDaySet.cs`（DB非依存・静的クラス）。

```csharp
/// <summary>取引先の締日1/2/3から有効締日リストと締請求期間を解決する。</summary>
public static class ClosingDaySet {
    /// 3.1。戻り値は昇順・1件以上。
    public static IReadOnlyList<int> Resolve(int shime1, int shime2, int shime3, int ownShime);

    /// 3.2。違反ならエラー文、正常なら空文字。
    public static string Validate(int shime1, int shime2, int shime3);

    /// 3.3。days は Resolve の戻り値。
    public static (string DayFrom, string DayTo) GetBillingPeriod(string billingYyyymm, IReadOnlyList<int> days, int targetShime);

    /// days に targetShime が含まれるか。
    public static bool Contains(IReadOnlyList<int> days, int targetShime);
}
```

- 日付の実装は既存の `ClosingMonthCalculator.GetClosingDay` 相当（99は月末、`Min(shime, 月末日)`）へ寄せ、
  **新たな重複実装を作らない**。`ClosingMonthCalculator` に `internal` で公開するか、
  `ClosingDaySet` から呼べる形へ整理する（2.4 の4重複はこの機会に3つへ減らす。全廃は 9章 M2）。
- `CvWpfclient` は `CvDomainLogic` を参照しないため、画面とサーバの双方から使う共通ロジックは
  必ず `CvBase` に置く（`Doc/spec/2026-09-01_消費税計算単位・端数処理_全体設計.md:474-476`）。

### 4.2 請求計算 `CalcSummaryUriSei` の複数締日対応

**方針: 締日パターンでグルーピングし、期間ごとに既存SQLを実行する。**

シグネチャは変えない。`CalcSummaryUriSei(billingYyyymm, shime, codeFrom, codeTo, isReissue)` の内部を次にする。

```
1. ownShime = GetOwnClosingDay()                       // MasterSysman.ShimeBi（既存 SummaryDb.cs:32-43）
2. パターン取得:
     SELECT DISTINCT Shime1, Shime2, Shime3 FROM MasterTokui
     WHERE (@codeFrom = '' OR Code >= @codeFrom) AND (@codeTo = '' OR Code <= @codeTo)
   → 実データでは高々数件（現在は得意先2件・仕入先1件）
3. 各パターンについて:
     days = ClosingDaySet.Resolve(s1, s2, s3, ownShime)
     days に shime が含まれないパターンは対象外（スキップ）
     (dayFrom, dayTo) = ClosingDaySet.GetBillingPeriod(billingYyyymm, days, shime)
4. 同じ (dayFrom, dayTo) を持つパターンをまとめ、グループごとに
   既存の prepareSql / sql を1回ずつ実行する
5. 戻り値は各グループの挿入件数の合計
```

既存SQLへの変更は**取引先の絞り込み条件だけ**:

```sql
-- 変更前（SummaryDb.cs:1010, 1017, 1061 / KaiShi は 1184, 1254）
WHERE Shime1 = @2

-- 変更後（グループのパターン集合で絞る。@P はパターンごとのパラメータ）
WHERE (Shime1, Shime2, Shime3) が当該グループのパターン集合に含まれる
```

- SQLite / Oracle / Postgre で行値比較の方言差を踏まないよう、
  `(Shime1 = @a0 AND Shime2 = @b0 AND Shime3 = @c0) OR (Shime1 = @a1 AND ...)` の OR 連結で組み立てる。
  パターン数はマスタの実データ由来で数件のため、SQL長は問題にならない。
  **パラメータは必ずバインドし、値をSQL文字列へ埋め込まない。**
- `@0`/`@1`（dayFrom/dayTo）はグループごとに異なる値を渡す。それ以外のパラメータは現行のまま。
- 期首ガード（`SummaryDb.cs:989-991`）は**グループごとに**判定する。
  あるグループの `dayTo` が期首前なら、そのグループだけスキップする。
- 一時テーブル `TempSummaryUriSeiPrevious` はグループごとに作り直す
  （既存の `DELETE FROM {temp}` が冒頭にあるため、そのまま繰り返し実行できる）。
- トランザクションは**全グループを1つのトランザクションに包む**。
  現行の `BeginTransaction` / `CompleteTransaction` をループの外へ出す。
- `NyukinYoteiDay` の式（`SummaryDb.cs:1084-1087`）を 3.4 に合わせる:

```sql
-- 変更前
WHEN t.PayDay IN (0, 99) THEN <月末>
ELSE <... MIN(t.PayDay, 月末日) ...>

-- 変更後（@7 = ownShime を追加）
WHEN (CASE WHEN t.PayDay = 0 THEN @7 ELSE t.PayDay END) = 99 THEN <月末>
ELSE <... MIN(CASE WHEN t.PayDay = 0 THEN @7 ELSE t.PayDay END, 月末日) ...>
```

`CalcSummaryKaiShi`（`SummaryDb.cs:1166-1310`）も同じ構造で対応する。対象テーブルが
`MasterShiire` / `SummaryKaiShi` / `Tran03Shiire`+`Tran02Material` / `Tran07Shiharai` に変わるだけで、
グルーピングの考え方・期間算出は同一である。

**`GetClosingPeriod`（`SummaryDb.cs:1141-1151`）は `ClosingDaySet.GetBillingPeriod` へ置き換えて削除する。**

#### 4.2.1 なぜこの方式か

| 案 | 内容 | 判断 |
|---|---|---|
| **A. パターングルーピング（採用）** | C#で締日パターンごとに期間を確定し、期間が同じものをまとめてSQLを複数回実行 | 既存SQLの構造・集計式・テスト資産をほぼそのまま使える。期間計算は純ロジックとして単体テストできる。実行回数は実データで1〜3回 |
| B. `targets` CTE 内で取引先ごとに `DayFrom` をSQL計算 | SQL 1回で完結 | 締日集合から直前締日を求める CASE 式と、そこから日付を作る `date()` 演算をSQLで書く必要がある。SQLite/Oracle/Postgre の日付関数方言をまたぐため危険度が高い。集計CTEも `BETWEEN @0 AND @1` から `JOIN targets ... BETWEEN tg.DayFrom AND tg.DayTo` へ書き換えが必要 |
| C. 取引先1件ずつループ | 最も単純 | 取引先2,800件×締日ぶんのSQL実行。性能上あり得ない |

### 4.3 「すべての締日」実行

`BillingParameter.Shime`（`CvBase/Parameters.cs:294`）は `int`。
**`Shime = 0` を「すべての締日」の意味に割り当てる。**
`0` は `EnumShime` で「未使用」であり、単一締日として渡されることは無いため、契約の形を変えずに拡張できる。

- サーバ側 `SummaryUriSeiAsyncStream` / `SummaryKaiShiAsyncStream`（`SummaryDb.cs:735-761`）で、
  `param.Shime == 0` なら対象マスタの有効締日を昇順に列挙し、締日ごとに `CalcSummaryUriSei` を呼ぶ
  ステップ列へ展開する。進捗表示はステップ数ぶん刻まれる（`StreamStepProgressRunner` は複数ステップ対応済み）。
- 有効締日の列挙は 3.1 の解決規則を通す。`Shime1 = 0` の取引先が1件でも居れば `ownShime` をリストへ加える。

```sql
SELECT DISTINCT Shime1, Shime2, Shime3 FROM MasterTokui
WHERE (@0 = '' OR Code >= @0) AND (@1 = '' OR Code <= @1)
```
→ C#で `Resolve` を通して和集合を取り、昇順に整列する。

- 画面（`BaseBillingCalculationViewModel`）:
  - 締日リスト取得SQLを上記へ差し替え、`ShimeItems` の**先頭に「すべて」(`Value = 0`)** を追加する
  - 既定選択を「すべて」にする（現行は先頭の締日）
  - 入力検証 `SelectedShime is < 1 or > 31 && != 99`（`:80`）を
    「`0`（すべて）または 1〜28 または 99」へ変更する

protected override bool ConfirmAction(string message) {

### 4.6 期首残高CSV

`OpeningBalanceCsv` は請求残・支払残の期首行を「期首直前の1期間の実績行」として作る
（`CvBase/OpeningBalanceCsv.cs:818-848`）。期首残高は取引先ごとに**1つの繰越額**であり、
締日が増えても行を分ける意味は無い。

**決定（要承認）**: 期首行は取引先の**最終締日（有効締日集合の最大値）**で1行だけ作る。

- 締日選択チェック（`:774-781`）は「選択締日 == `Shime1`」から
  「選択締日 == その取引先の**最終締日**」へ変更する。中間の締日を選んで取り込もうとした場合はエラーとし、
  「期首残高は最終締日({表記})で取り込んでください」と案内する。
- `GetDefaultKeyDate`（`:826-848`）は最終締日を渡して現行どおり計算する
  （最終締日での「期首直前の締日」と「その1つ前の締日の翌日」）。
  1つ前の締日は 3.3 の `prev` を使う。
- 期首行の `DayFrom` が実際の締期間より広くなる場合があるが、期首行は集計の入力ではなく
  `PreviousBalance`（`DayTo <` 比較）の材料でしかないため実害は無い。
