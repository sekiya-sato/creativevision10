# 本部売上入力（ShukkaUriage）消費税セットと画面表示 詳細設計（2026-09-02）

`CvWpfclient.Views._06Uriage.ShukkaUriageInputView` / `ShukkaUriageInputViewModel` について、
明細 `Id_Tax` のセット漏れとヘッダ `Tax1/2/3` 周辺の不整合を修正し、
消費税を画面へ表示できるようにする。

前提となる仕様は `Doc/spec/2026-09-01_消費税計算単位・端数処理_全体設計.md`（3.1〜3.7）を正とする。
本書はその仕様を**本部売上入力画面へ正しく適用し直す**ための修正設計であり、税計算の仕様そのものは変更しない。

**対象は本部売上（`ShukkaUriageInputViewModel` / `ShukkaUriageInputView.xaml`）のみ。**
同じ不具合を持つ他の入力画面（店舗売上・商品仕入・生地付属仕入・受注・発注）は後続作業とする（9章）。

## 1. 調査結果（現状の不具合）

### 1.1 明細 `Id_Tax` のセット漏れ（収束しない確定バグ）

明細の `Id_Tax` は基底 `BaseTranInputViewModel` の次の2経路でしか解決されない。

| 経路 | 契機 |
|------|------|
| `RecalcAllMeisaiTaxAsync()` | 伝票を開いたとき・`DenDay` 変更時（全行） |
| `RecalcMeisaiTaxAsync(m, …)` | `OnMeisaiPropertyChanged` が `Kingaku` / `Id_Shohin` の変更を検知したとき（1行） |

`OnMeisaiPropertyChanged` は `EditMeisai` へ追加する**前**に購読を張らないと発火しないため、
「値を全部詰めてから購読 → `Add`」という順で行を作る次の2箇所は、どちらも経路に乗らない。

| # | 箇所 | 内容 |
|---|------|------|
| **A** | `ApplyBarcodeMeisai`（`ShukkaUriageInputViewModel.cs:262`） | `InputBarcodeRow.ToMeisai`（`InputBarcodeViewModel.cs:259`）が `Id_Tax` を設定しない。`Kingaku`・`Id_Shohin` は購読前に確定するため再解決も走らず、`Id_Tax = 0` のまま残る |
| **B** | `ApplyShohinColSizMeisai`（同 `:299`） | 色サイズ展開で作る新規行も `Id_Tax` 未設定。`FillMeisaiFromColSizRow` が `Su`/`Kingaku` を購読前に書くため再解決も走らない |

`TaxCalculator.Apply` は `Id_Tax` が 1-3 以外の明細を課税対象額の集計から除外する（`TaxCalculator.cs:118-126`）。
したがってバーコード入力・色サイズ展開で作られた行は
**`TaxableAmount1/2/3` にも `Tax1/2/3` にも一切計上されない。**

実運用は全件が請求単位（`TaxCalcUnit=0`）で伝票の `Tax1/2/3` は元々 0 のため
画面上は異常が見えないが、`TaxableAmount1/2/3` が欠けるので
**請求計算（`SummaryDb.CalcSummaryUriSei`）が算出する消費税が過少になる。**
これが本件で最も影響の大きい不具合である。

### 1.2 ハンドラ二重購読（B に併発）

`ApplyShohinColSizMeisai` は、先頭の展開結果を既存行 `firstTarget` へ流し込んだあと

```csharp
FillMeisaiFromColSizRow(firstTarget, firstResult);
firstTarget.PropertyChanged += OnMeisaiPropertyChanged;   // ← 既に購読済み
```

としている。`firstTarget` は `SelectedMeisai`（＝ `EditMeisai` の要素）であり、
`ApplyMeisaiFromCurrentEdit` / `AddMeisai` の時点で既に購読済みである。
ここで購読が二重になり、以後この行を触るたびに `UpdateTotals()` と
`RecalcMeisaiTaxAsync` が 2 回ずつ走る。結果は同じだが無駄であり、
色サイズ展開を繰り返すと購読が 3 重・4 重に増える。

### 1.3 ヘッダ `Tax1/2/3` と関連項目

| # | 箇所 | 内容 |
|---|------|------|
| **C** | `DoSelectTokui`（`:389`） | 得意先を選び直して `TaxCalcUnit`/`TaxRounding` を差し替えても `UpdateHeaderTotals()` を呼ばない。`OnCurrentEditPropertyChanged` の監視対象にも入っていない。→ **端数処理・計算単位を変えても税額に反映されない** |
| **D** | `OnCurrentEditPropertyChanged`（`:157`） | `Tax1/2/3` の変更を監視して `UpdateHeaderTotals()` を呼ぶが、そのメソッド自身が `Tax1/2/3` を書く。**自己再入**であり、同値で `PropertyChanged` が止まることだけに依存している。監視対象として意味がなく、危うい |
| **E** | `OnCurrentEditChangedCore`（`:148`） | `RecalcAllMeisaiTaxAsync()`（税率キャッシュの充填を含む）の完了前に `UpdateHeaderTotals()` を同期実行する。税率キャッシュが空の状態で一度 `Tax1/2/3 = 0` を書いてから正しい値へ上書きされる。最終的には収束するため**実害はない**が、意図が読めない |

`TaxCalculator.Apply` の呼び方・`TaxableAmount1/2/3` への代入・
`Total = |KingakuTotal| + TaxTotal` は `ShiireInputViewModel` と同一であり**正しい**。

## 2. 修正方針

### 2.1 `Id_Tax` セットの原則

**「`EditMeisai` へ行を足したら、必ず `RecalcAllMeisaiTaxAsync()` を await する」** を本画面の規約とする。

行ごとに `RecalcMeisaiTaxAsync` を呼ぶのではなく全行版を使う理由は、

- 商品マスタの参照結果は `shohinTaxIdCache` に載るため、全行走査してもマスタアクセスは増えない
- 税率キャッシュ（`EnsureTaxRateCacheAsync`）の充填も同時に済む
- 追加した行だけでなく「数量が加算された既存行」も同じ1回で正しくなる（`ApplyBarcodeMeisai` は既存行の `Su` を加算する枝を持つ）

`RecalcAllMeisaiTaxAsync()` は内部で `UpdateTotals()` を呼ぶため、
既存の末尾 `UpdateTotals()` は置き換えになる（二重呼び出しにしない）。

これに伴い `DoInputBarcode` / `DoInputShohinColSiz` の 2 コマンドを `async Task` 化する。
`[RelayCommand]` は `async Task` メソッドをそのまま非同期コマンドにできる。

### 2.2 二重購読の除去

`ApplyShohinColSizMeisai` の `firstTarget.PropertyChanged += OnMeisaiPropertyChanged;` を削除する。
`firstTarget` は `EditMeisai` の既存要素であり必ず購読済みである。

### 2.3 ヘッダ再計算の契機を整理する

`OnCurrentEditPropertyChanged` の監視対象を次へ改める。

| 監視するプロパティ | 動作 | 理由 |
|--------------------|------|------|
| `Kubun` | `UpdateHeaderTotals()` | 現状踏襲（明細区分の正規化ポリシーがヘッダ区分に従うため） |
| `TaxCalcUnit` / `TaxRounding` | `UpdateHeaderTotals()` | **追加。** 得意先差し替えで税額を引き直す（C の修正） |
| `DenDay` | `RecalcAllMeisaiTaxAsync()` | 現状踏襲（適用税率が変わる） |
| ~~`Tax1` / `Tax2` / `Tax3`~~ | **監視をやめる** | `UpdateHeaderTotals()` の出力であり入力ではない。自己再入を断つ（D の修正） |

あわせて `DoSelectTokui` の末尾で `UpdateHeaderTotals()` を明示的に1回呼ぶ。
プロパティ監視だけに頼ると、差し替え後の `TaxCalcUnit`/`TaxRounding` が
たまたま同値だったときに走らないため。

`DoSelectShohin` も同様に、末尾で当該行の税区分を明示的に引き直す
（同じ商品を選び直すと `Id_Shohin` が同値になり `PropertyChanged` が発火しないため）。

E（`OnCurrentEditChangedCore` の一時的な 0 書き）は、
同期メソッドから await できない構造上の制約であり、`ShiireInputViewModel` ほか
既存の入力 VM 全てと同じ挙動である。**修正せず、意図を説明するコメントのみ追加する。**

## 3. 画面表示の設計

### 3.1 表示方針（請求単位のときの見せ方）

実運用は全件が請求単位（`TaxCalcUnit=0`）であり、伝票の `Tax1/2/3` は**常に 0** である。
これは仕様どおりであって異常ではない（全体設計 10.2-2「伝票を見たら消費税が 0 だ、は正常」）。

**保存値どおり 0 を表示し、なぜ 0 なのかを注記し、根拠となる課税対象額の内訳を併記する。**
画面独自に見込み税額を計算して見せることはしない。請求計算が締請求期間で1回だけ丸めた確定値と
必ず端数で食い違い、「画面と請求書で消費税が違う」という問い合わせを生むためである。

### 3.2 伝票サマリーカード（詳細タブ右）

現状の 合計数量／合計金額／上代合計／下代合計 の下へ次を追加する。

```
  合計数量            1,234
  合計金額        1,000,000
  上代合計        1,500,000
  下代合計          800,000
 ─────────────────────────
  消費税                  0        ← TaxTotal
  請求単位のため、消費税は請求計算で確定します     ← 請求単位のときだけ表示
    10% 対象         900,000        ← 課税対象額の税区分別内訳
     8% 対象         100,000
 ─────────────────────────
  総合計          1,000,000        ← CurrentEdit.Total
```

- **消費税**: `TaxTotal`（= `Tax1+Tax2+Tax3`）。伝票単位の得意先では実額が出る
- **注記**: `TaxCalcUnit == Billing` のときだけ表示する。伝票単位のときは非表示
- **内訳**: 課税対象額が 0 でない税区分だけを行として出す。ラベルは適用税率から作る（`10% 対象`）。
  伝票単位のときは税額も併記する（`10% 対象 900,000 → 90,000`）
- **総合計**: `CurrentEdit.Total`。請求単位では税抜合計と同額になる

「下代合計」が現状は太字＝最終行の扱いだが、最終行は「総合計」へ譲り、下代合計は通常表示へ戻す。

### 3.3 明細グリッド

`下代単価` 列の後ろへ3列を追加する。

| 列 | バインド | 編集 | 書式 |
|----|----------|------|------|
| 金額 | `Kingaku` | 可（`TwoWay`, `UpdateSourceTrigger=PropertyChanged`） | `N0` 右寄せ |
| 税率 | `TaxRate` | 不可 | `{0}%` 右寄せ |
| 消費税 | `Tax` | 不可 | `N0` 右寄せ |

- 金額は仕入入力（`ShiireInputView.xaml:676`）と同じく編集可にする。
  `Su`/`Tanka` の変更で自動計算されるが、手入力での上書きも従来どおり効く
  （`OnMeisaiPropertyChanged` が `Kingaku` 変更を検知して税を引き直す）
- 税率は `Id_Tax` から解決された結果そのものなので、`Id_Tax` の欠落があれば `0%` として画面に出る。
  1.1 のような不具合を利用者・保守者が発見できるようにするのが主目的
- 明細 `Tax` は請求単位では 0 になる（仕様）。伝票単位のときに按分値が出る

税区分（`Id_Tax`）そのものは列に出さない。業務利用者には税率で足りる。

### 3.4 一覧グリッド

`合計金額` の後ろへ **消費税**（`Tax`）と **総合計**（`Total`）の2列を追加する。

一覧グリッドの行の DataContext は ViewModel ではなく `Tran00Uriage` である。
`DataGridTextColumn` は Visual Tree に載らず `RelativeSource` で ViewModel を掴めないため、
ViewModel 側に表示用プロパティを置いても届かない。またそれは `CurrentEdit` 由来の単一値であり、
一覧の全行に同じ数字が並んでしまう。したがって**モデル側に派生プロパティ `Tax` を置く**（4.3）。

あわせて `LightweightSelectColumns` へ `Total,Tax1,Tax2,Tax3,TaxableAmount1,TaxableAmount2,TaxableAmount3,TaxCalcUnit,TaxRounding` を追加する。
税列は一覧表示には使わないが、**一覧から詳細タブへ遷移したときの `CurrentEdit` の初期値**になるため、
欠けていると詳細を開いた瞬間に 0 が表示されてから正しい値へ差し替わる（ちらつき）。

### 4.3 `CvBase/BaseDb2Trans.cs`（モデルの派生プロパティ）

`Tax1/2/3` を持つ伝票クラスへ、一覧グリッド表示用の派生プロパティを追加する。

```csharp
[ResultColumn]
[JsonIgnore]

```

- **DB は変更しない。** `[ResultColumn]` により DDL 生成（`ExDatabase.GetSqlColumns`）と

  一覧グリッドは読み込み済みの行を読み取り専用で表示するだけなので問題にならない

- 変更ファイルは `ShukkaUriageInputViewModel.cs` / `ShukkaUriageInputView.xaml` / `CvBase/BaseDb2Trans.cs` の 3 件

## 6. 既存データへの影響と復旧

### 6.1 既存伝票の `TaxableAmount` 欠落

1.1 の不具合により、バーコード入力・色サイズ展開を使って作成された既存伝票は
`TaxableAmount1/2/3` が実際の課税対象額より小さい（該当行ぶんが欠けている）可能性がある。

`TranTaxRebuildDb`（「システム > その他処理 > 伝票税額再更新」）は
明細の `Id_Shohin` から `Id_Tax` を引き直してヘッダを作り直すため、
**この不具合で欠けた課税対象額もあわせて修復される。**
コード修正の適用後、期首日以降の伝票に対して一括再計算 → 請求計算のやり直しを行うこと
（全体設計 8章 手順4→5→6）。

### 6.2 影響範囲の事前確認

修正前に、影響を受けた伝票の件数を次で確認できる。
明細に `Id_Tax` が 1-3 でない行を含む `Tran00Uriage` を数える。

```sql
SELECT COUNT(*) FROM Tran00Uriage t
WHERE EXISTS (
  SELECT 1 FROM json_each(t.Jmeisai) m
  WHERE COALESCE(json_extract(m.value, '$.Id_Tax'), 0) NOT BETWEEN 1 AND 3
);
```

## 7. テスト観点

| # | 観点 | 期待 |
|---|------|------|
| 1 | バーコード入力で明細を追加する | 追加行の `税率` 列に伝票日付時点の税率が出る。`TaxableAmount1/2/3` が全行の金額合計と一致する |
| 2 | バーコード入力で既存行の数量が加算される枝 | 加算後の金額で課税対象額が再集計される |
