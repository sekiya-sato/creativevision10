# マニュアル排他制御 詳細設計（2026-09-06）

状態: **詳細設計。実装は原価4項目 Step 9 で行う。**

対象: 一連のまとまった更新処理（在庫・掛の再集計、棚卸、HHT反映、原価4処理、評価替え）の
プロセス間排他と、その監視・実行履歴。

対象Release: CV10 10.1

## 0. 背景と決定

`Doc/spec/2026-09-05_原価4項目_詳細設計.md`（以下「原価4項目設計書」）§10.1 が
次のとおり記していた。

> **プロセス間排他は新規実装**: 既存コードには「他画面・他バッチの実行中を検知して片方を中断する」
> 機構が存在しない。既存の `Serializable` は単一メソッド内の一連のSQLを1トランザクションに
> まとめる用途であり、SQLiteのファイルロックによる事実上の直列化はあっても、
> 「どちらが先に開始したか」を判定して中断する仕組みは未実装である。

**2026-09-06 決定**: `SysSequence` に列を追加した**マニュアル排他制御**を新設する。
DB的なロックは掛けず、行の存在と `Vdu` の前進で「実行中かどうか」を表現する。
併せて `SysHistAutoexec` に自動実行と手動実行の区別を持たせる（原価4項目設計書 U-14）。

対応する未決事項:

| ID | 出典 | 決定 |
|---|---|---|
| U-14 | 原価4項目設計書 §2.4、§13 | `SysHistAutoexec` に `SysHistType` を追加し、自動実行と手動実行を1つの履歴で区別する |
| D-07 | 完成度チェックリスト §5.2 | 月次処理の同時実行制御を本書の方式で行う |
| D-21 | 完成度チェックリスト §5.2 | U-14 と同じ。列追加案を採用 |

**DB的なロックを使わない理由**: 対象処理は数分〜数十分かかり、その間DBロックを保持すると
他の参照系まで待たされる。またSQLiteのファイルロックはプロセス境界を越えた
「誰が先に開始したか」を表現できない。行の存在で論理的に排他し、
`Vdu` の前進で生存を示す方式なら、ロック保持なしに監視と強制解放ができる。

## 1. DB定義

### 1.1 変更: `SysSequence`

`SysSequence`（`CvBase/BaseDb0Config.cs:54`）は現在**定義と `DefineDataTable` 登録のみで、
実際には1箇所も使われていない**（`grep` で確認済み）。したがって列追加による
既存動作への影響はない。

| 追加列 | C#型 | 初期値 | 必須 | 定義・制約 |
|---|---|---:|:---:|---|
| `SysSeqType` | `int` | `0` | ○ | `EmSysSeqType`: 0=テーブル連番、1=排他制御 |
| `ExpectedDuration` | `long` | `0` | ○ | 予想処理時間（秒）。`SysSeqType=1` のときだけ意味を持つ |

既存列の `SysSeqType=1` での用途を次のとおり定める。

| 列 | `SysSeqType=1` での意味 |
|---|---|
| `TableName` | 一連のまとまった処理名（例 `在庫・掛再集計`）。排他の単位 |
| `ColumnName` | 現在実行中の処理名（例 `買掛集計`）。1b で書き換える |
| `SeqNo` | 処理順No。1c で `99` を書いてから削除する |
| `Memo` | 補足のメモ。1b で処理時間と処理内容を追記していく |
| `Vdc` | 一連処理の開始UTC Ticks |
| `Vdu` | **最後に進捗を書いた時刻**。監視タスクはこの前進で生存を判定する |

キー・索引:

- 非一意索引: `(SysSeqType, TableName)`
- **一意キーは設けない。** `SysSeqType=0`（テーブル連番）は複数行が正常であり、
  `SysSeqType=1` のときだけ「全体で1行」という制約が要るが、
  これは列値に依存する部分ユニーク制約であり、既存の `KeyDml` 属性では表現できず
  4方言のDDL生成器にも展開できない。§2.1 の挿入後再確認で担保する。

### 1.2 変更: `SysHistAutoexec`

| 追加列 | C#型 | 初期値 | 必須 | 定義・制約 |
|---|---|---:|:---:|---|
| `SysHistType` | `int` | `0` | ○ | `EmSysHistType`: 0=自動実行、1=手動実行 |

既存行は `0`（自動実行）で補完する。既存の `SysHistAutoexec` への書き込みは
`CvServer/Services/SchedulerService.cs:1351,1372` のスケジューラ自動実行だけであり、
補完後も自動実行履歴画面（`SysAutoExecHistoryViewModel`）の意味は変わらない。

**対象月の列は追加しない。** 原価4処理の対象月は `Memo` へ含める。
対象月を持つのは原価4処理と評価替えだけであり、
自動実行タスク全体に共通する列ではないためである。

### 1.3 追加: enum

`CvBase/Share/BaseEnumClass.cs` へ既存作法（`[Comment]` をenum本体と各メンバに付ける）で追加する。

```text
EmSysSeqType  : int  0=テーブル連番(TableSeq)、1=排他制御(ManualLock)
EmSysHistType : int  0=自動実行(AutoExec)、1=手動実行(ManualExec)
```

### 1.4 migration

`CvBase/UpdateDb.cs` の `versions` 末尾へ1件追加する。既存作法（SQLiteリテラルDDL）に従う。

```text
ALTER TABLE SysSequence ADD COLUMN SysSeqType NUMBER not null default 0;
ALTER TABLE SysSequence ADD COLUMN ExpectedDuration NUMBER not null default 0;
ALTER TABLE SysHistAutoexec ADD COLUMN SysHistType NUMBER not null default 0;
```

## 2. 処理側（排他を取る側）

一連のまとまった処理の開始から終了までを次の3段階で表す。
**いずれの段階もDB的なロックを掛けず、書いたら即座に開放する。**

### 2.1 開始（1a）

1. `SysSequence` へ1行 INSERT する。`SysSeqType=1`、`TableName`=一連処理名、
   `ColumnName`=最初の処理名、`SeqNo`=1、`Memo`=補足、`ExpectedDuration`=予想処理秒数。
2. INSERT 後、`SysSeqType=1` の行を数える。
3. **2件以上あれば、`Id` が大きい方（後発）が自分の行を削除して中断する。**
   利用者にはワーニングを表示し、先行処理の `TableName` / `ColumnName` / 開始時刻を伝える。
4. 1件（自分だけ）であれば処理を続行する。

**挿入後に再確認する理由**: 「既存行を確認してから挿入する」順序では、2つの処理が
ほぼ同時に開始したときに両方が「行なし」を見て両方が挿入する（TOCTOU）。
監視タスク（§3）は `SysSeqType=1` が1行であることを前提にしているため、
ここが崩れると排他として機能しない。**先に挿入してから数え、後発が降りる**ことで、
DBロックを使わずに勝者を一意に決められる。`Id` は自動採番で単調増加するため、
どちらのプロセスから見ても同じ勝者になる。

`ExpectedDuration` は**一連処理全体の見込み秒数**であり、個々の処理ステップの見込みではない。
監視タスクの異常判定（§3.4）に使う。

### 2.2 進捗（1b）

一連の処理中は、各処理の**開始時**に `(SysSeqType=1, TableName)` で一致する行を UPDATE し、
即座に開放する。

- `ColumnName` = 現在の処理名
- `SeqNo` = 処理順No
- `Memo` = 処理時間と処理内容を追記していく
- `Vdu` = 更新時刻（**監視タスクが生存判定に使う唯一の信号**）

`Memo` は `[ColumnSizeDml(300)]` で300文字までである。追記が上限に達する場合は
古い内容から切り捨て、末尾（最新）を残す。

### 2.3 終了（1c）

1. `SysSequence` に `SeqNo=99` を書いて開放する。
2. `SysHistAutoexec` へログを追加する（`SysSequence.Memo` の内容を参照して組み立てる）。
   `SysHistType=1`（手動実行）、`TaskName`=一連処理名、`StartTime`/`EndTime`/`ElapsedTime`、
   `ReturnCode`、`Count`、`Memo`。
3. `SysSequence` の行を削除して開放する。

`SeqNo=99` を先に書くのは、履歴書き込み中にプロセスが落ちた場合に
「終了処理まで到達していた」ことを監視タスクとログから読み取れるようにするためである。

### 2.4 適用対象

| 分類 | 処理 | 一連処理名 |
|---|---|---|
| 原価4項目 | 消化仕入更新（`ApplyConsumptionPurchases`） | 消化仕入更新 |
| 原価4項目 | 最終仕入原価更新（`ApplyLastPurchaseCost`） | 最終仕入原価更新 |
| 原価4項目 | 総平均原価更新（`ApplyTotalAverageCost`） | 総平均原価更新 |
| 原価4項目 | 評価替え（`ApplyRevaluation` / `CancelRevaluation`） | 評価替え |
| 既存 | `SummaryDb.SummaryAllAsyncStream` | 在庫・掛再集計 |
| 既存 | `SummaryDb.SummaryRealAsyncStream` | 現在庫再集計 |
| 既存 | `SummaryDb.SummaryUriKakeAsyncStream` | 売掛再集計 |
| 既存 | `SummaryDb.SummaryKaiKakeAsyncStream` | 買掛再集計 |
| 既存 | `SummaryDb.SummaryUriSeiAsyncStream` | 請求計算 |
| 既存 | `SummaryDb.SummaryKaiShiAsyncStream` | 支払計算 |
| 既存 | `StocktakeDb.StartAsyncStream` | 棚卸開始処理 |
| 既存 | `StocktakeDb.FixAsyncStream` | 棚卸確定処理 |
| 既存 | `HhtProcessUpdate.UpdateVulcan2TranAsyncStream` | HHT取込反映 |

諸掛（原価4項目設計書 §3.8）は参照専用で更新を持たないため対象外。
各処理の `Preview` も対象外とする。排他が要るのは書き込みだけである。

**`ConvertDb`（旧データ移行）は対象外とする。** 全テーブルを書き換えるため他処理との
同時実行は危険だが、通常は初期構築時にしか実行されず、
運用中の月次処理と競合しない。将来対象へ加える場合も本書の仕組みをそのまま使える。

排他は **`SysSeqType=1` の行が全体で1行**という単位で効くため、
上記のどれか1つが動いていれば他のすべてが中断される。処理ごとの粒度は設けない。
月次処理は互いに前後依存があり（原価4項目設計書 §7）、
並行実行して安全な組み合わせが実質的に無いためである。

## 3. 監視タスク

自動実行に監視タスクを1つ追加する。既定cron式は `*/5 * * * *`（5分毎）。
`CvBase/BaseDb1Master.cs` の `AutoExecJobDefaults` へ8件目として登録する。

タスクは**静的変数**に前回チェック時点の `SysSequence` の内容を保持する。

### 3.1 行が無い場合（2a）

`SysSeqType=1` の行が1件も無ければ**何もしない**。静的変数は初期化する。
ログも出さない。

### 3.2 行を見つけた場合（2b）

`SysSeqType=1` の行があれば、その内容（`Id`、`TableName`、`ColumnName`、`SeqNo`、
`Vdc`、`Vdu`、`ExpectedDuration`）を静的変数へ保存する。
基本的に1件のはずである（§2.1 で担保）。
**`SysHistAutoexec` へログを出す**（§3.6）。

### 3.3 `Vdu` が前進している場合（2c）

次のチェックタイミングで、DB上の `Vdu` が静的変数の値より新しければ**処理中**とみなす。
静的変数を更新し、ログは出さない。

### 3.4 `Vdu` が前進していない場合（2d）

行はあるが `Vdu` が前進していない場合、処理中か、処理自体がエラーしている可能性がある
（履歴も出さずに落ちる場合がある）。`ExpectedDuration` を考慮して妥当な時間だけ待つ。

**異常とみなす閾値（2026-09-06 決定）**:

```text
経過時間 = 現在時刻 − Vdu
閾値     = max(ExpectedDuration × 2, 15分)
経過時間 > 閾値 なら異常（§3.5 へ）
```

`ExpectedDuration` は一連処理**全体**の見込みであり、個々の処理ステップの見込みではないため
2倍の余裕を持たせる。最低15分の下限を置くのは、`ExpectedDuration` を小さく申告した処理を
監視の1〜2周期で誤って強制解放しないためである。

### 3.5 長時間更新が無い場合（2e）

閾値を超えて `Vdu` が更新されていない場合、**エラーしているものとみなす**。
`SysSequence` の該当行を削除し、静的変数もクリアする。
**`SysHistAutoexec` へログを出す**（§3.6）。`ReturnCode` はエラーを表す非0とする。

### 3.6 行が消えた場合（2f）

静的変数に保持している行が、DB上から消えていた場合は
**処理が正常終了したもの**とみなす。静的変数をクリアする。
**`SysHistAutoexec` へログを出す**（§3.7）。

処理側は §2.3-3 で自分の行を削除するため、正常終了は必ずこの経路を通る。

### 3.7 ログ規則（2g）

監視タスクが `SysHistAutoexec` へログを出すのは **§3.2（2b）、§3.5（2e）、§3.6（2f）の3つ**だけである。
§3.1（2a）と §3.3（2c）では出さない。

**ログは必ず 2b→2f（正常終了）か 2b→2e（異常終了）の対になる。**
監視タスクの履歴を時系列に読めば、開始（2b）と終了（2f または 2e）が必ず1対1で対応する。

`SysHistType` は監視タスク自身が自動実行なので **0（自動実行）**とする。
処理側が §2.3-2 で書く履歴（`SysHistType=1`）とは別行であり、
同じ一連処理について「処理側の手動実行履歴」と「監視側の自動実行履歴」の2本が残る。

**番号について**: 本節の 2a〜2g は、決定時の原文で `2f` が2回使われていたものを
重複が無いよう振り直したものである。内容は変えていない。
