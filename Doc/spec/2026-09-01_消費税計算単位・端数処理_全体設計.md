# 消費税計算単位・端数処理 全体設計（2026-09-01）

取引先ごとの **税計算単位（`TaxCalcUnit`）** と **消費税端数処理（`TaxRounding`）** を、
伝票入力・請求計算・支払計算・集計の全経路へ通す。
先行する `Doc/spec/2026-08-25_明細別消費税計算_詳細設計.md`（明細別税額）と
`Doc/spec/2026-08-28_D05_請求書税率別内訳_詳細設計.md`（適格請求書の税率別内訳）を前提とし、
「明細ごとに丸める」固定仕様を「取引先設定に従って丸める」へ拡張する。

## 1. 決定事項

| No | 決定 | 内容 |

### 1.1 実データの前提（旧CVnet 移行元 Oracle 調査 2026-09-01）

| 対象 | 消費税計算方法 | 消費税端数 | 件数 |
|------|----------------|-----------|------|
| `HC$MASTER_TOKUI` | 0（請求単位） | 0（四捨五入） | 165 |

`2=明細単位` の実データは存在しないため、D1 の丸め込みに実害はない。

## 2. データモデル

### 2.1 マスタ（追加済み・変更なし）

| テーブル | 列 | 意味 |
|----------|-----|------|
| `MasterTorihiki`（`MasterTokui` / `MasterShiire` の基底） | `TaxCalcUnit` | 0=請求単位 / 1=伝票単位 |
| 同上 | `TaxRounding` | 0=四捨五入 / 1=切上 / 2=切捨 |

### 2.2 伝票ヘッダ（今回追加）

`TaxCalcUnit` / `TaxRounding` は直近commitで追加済み（`TaxCalcUnit` は請求・支払対象の3伝票のみ）。

| `Tran01Tenuri` (店舗売上) | 済 | **追加** | — | 済 | 現金売なので常に伝票単位。端数は店舗(`Id_Tenpo`)の`MasterTokui`→なければ`MasterSysman` |
| `Tran02Material` (生地・付属仕入) | 済 | **追加** | 済 | 済 | 仕入先から転記 |
| `Tran03Shiire` (商品仕入) | 済 | **追加** | 済 | 済 | 仕入先から転記 |

`TaxCalcUnit` / `TaxRounding` は **伝票作成時点のマスタ値のスナップショット**であり、
`TranAllHeader` の `V*` 列と同じく後からマスタが変わっても伝播しない（監査値）。
これにより、取引先設定を変更しても過去伝票の税額は再現できる。

### 2.3 Summary（今回変更）

4テーブルとも `Tax` を廃し、次の6列に置き換える。

| 列 | 意味 |
|----|------|
| `Tax1` / `Tax2` / `Tax3` | 税区分ごとの消費税額 |
| `TaxableAmount1` / `TaxableAmount2` / `TaxableAmount3` | 税区分ごとの課税対象金額（税抜） |

対象: `SummaryUriKake`（売掛月次）/ `SummaryUriSei`（請求残）/ `SummaryKaiKake`（買掛月次）/ `SummaryKaiShi`（支払残）。

既存の派生式は `Tax` を `(Tax1+Tax2+Tax3)` へ置換する。
- `SummaryUriSei.TotalSales = Uriage - Henpin - Nebiki + Sonota + (Tax1+Tax2+Tax3)`
- `SummaryKaiShi.TotalShiire = Shiire - Henpin - Nebiki + (Tax1+Tax2+Tax3)`

### 2.4 `UpdateDb.cs`

`26_09_01_03` を1行追加する（Summaryの `Tax` リネーム＋`TaxableAmount` 追加＋Tranの `TaxableAmount` 追加）。
`Tax → Tax1` の RENAME は既存データの値を保持し、`Tax2/Tax3` と課税対象額は 0 で埋まる。
課税対象額 0 は「未再計算」を意味するため、`Doc` の運用手順に
「バージョンアップ後は請求計算・支払計算をやり直す」旨を追記する。

## 3. 計算仕様

### 3.1 共通の丸め

```
Tax = Rounding( Σ(課税対象額 × 税率) / 100 )
```
丸めは `TranCalcBase.RoundTax(taxableAmount, taxRate, EnumRounding)` に集約済み。
**税額は常に正値**で保持し、返品等の符号はヘッダ `Kubun` から決まる `CalcFlag` が集計側で担う（既存方針を踏襲）。

### 3.2 明細（全ケース共通・保存時）

伝票種別によらず、明細には次を保存する。丸め方針が変わっても明細の内訳は必要になるため。

| 列 | 値 |
|----|-----|
| `Id_Tax` | `MasterShohin.Id_Tax` / `MasterMaterial.Id_Tax`（引けなければ 1） |
| `TaxRate` | 伝票日付時点の税率（`TaxRateResolver.ResolveTaxRatePercent`） |
| `Tax` | 伝票単位のときのみ按分値、請求単位のときは **0** |

明細 `Tax` は「伝票内で税区分ごとに丸めた額」を明細へ按分した参考値であり、
ヘッダ `Tax1/2/3` が正となる（合計は必ず一致させる）。

### 3.3 伝票単位（`TaxCalcUnit = 1`）

伝票入力・保存時に確定する。

```
TaxableAmountN = Σ |明細.Kingaku|   (明細.Id_Tax = N)
TaxN           = RoundTax(TaxableAmountN, 税率N, ヘッダ.TaxRounding)
Total          = |KingakuTotal| + Tax1 + Tax2 + Tax3
```

同一税区分内で税率が混在することは無い（税率は伝票日付から一意に決まる）ため、
`TaxableAmountN` に対して1回丸めれば足りる。

### 3.4 請求単位（`TaxCalcUnit = 0`）

伝票入力・保存時:

```
TaxableAmountN = Σ |明細.Kingaku|   (明細.Id_Tax = N)
TaxN           = 0
Total          = |KingakuTotal|
```

請求計算（`CalcSummaryUriSei`）／支払計算（`CalcSummaryKaiShi`）時:

```
Summary.TaxableAmountN = Σ(伝票.TaxableAmountN × 符号)      -- 締請求期間の全伝票
Summary.TaxN           = RoundTax(Σ(期間内の課税対象額 × その伝票日の税率), 取引先.TaxRounding)
```

**期中の税率改定**: `MasterSysTax` は税区分ごとに `TaxRate`（現行）と
`DateFrom` 以降の `TaxNewRate`（新）の2値しか持たない。締請求期間が `DateFrom` をまたぐ場合は、
SQL 側で `DenDay >= DateFrom` の有無で課税対象額を2分し、それぞれに税率を掛けてから合算し、
**期間全体で1回だけ**丸める。これで税率改定跨ぎでも誤差が出ない。

売掛月次（`CalcSummaryUriKake`）／買掛月次（`CalcSummaryKaiKake`）も
`KakeDay` を締日で月へ畳み込んでおり請求と同じ期間境界になるため、同一の計算式を使う。

### 3.5 伝票単位と請求単位の混在

`TaxCalcUnit` は**伝票ヘッダのスナップショット値**で判定する。
1つの締請求期間に両方の伝票が混ざり得る（期中に取引先設定を変えた場合）ため、請求計算は

```
Summary.TaxN = Σ(伝票単位の伝票の TaxN)                                  -- 既に丸め済み
             + RoundTax(Σ(請求単位の伝票の TaxableAmountN × 税率), 端数)   -- 期間で1回丸め
```

とする。伝票単位ぶんは伝票の値をそのまま信用し、二重丸めを避ける。

### 3.6 `TaxRounding` の解決順

1. 伝票ヘッダの `TaxRounding`（入力時に取引先から転記済み）
2. 伝票に無い場合（旧データ）は取引先マスタの `TaxRounding`
3. 取引先も引けない場合は `MasterSysman.TaxRounding`

`Tran01Tenuri`（店舗売上）は `Id_Tenpo` の `MasterTokui` を 2. に使う。
