# 明細別消費税計算 詳細設計

作成日: 2026-08-25
発端: [2026-08-24_Rate列_掛率と税率の分離課題.md](2026-08-24_Rate列_掛率と税率の分離課題.md) の残課題（第6章）を検討中、税計算そのものが「伝票単位・単一税率」であり、商品ごとの税区分（軽減税率等）を反映していないことが判明。
状態: **方式決定・未決事項決定済み（2026-08-25）。本書をもって実装へ進む**。

## 1. 目的とする仕様（決定事項）

1. `CvWpfclient/AppGlobalSub.cs` の `LogicGetTax(no, date_ymd)` により、税Id（`MasterSysman.Jsub`＝`MasterSysTax` 1〜3）ごとの税率を伝票日付基準で取得する（切替日対応、既存実装を流用）。
2. `MasterShohin.Id_Tax`（デフォルト1、**0＝非課税**）を商品ごとの税区分として使う。
3. 入力Tran系（`Tran00Uriage`/`Tran01Tenuri`/`Tran03Shiire`/`Tran12Jyuchu`/`Tran13Hachu`）の明細入力時、明細の`Id_Shohin`から`MasterShohin.Id_Tax`を引き、`LogicGetTax()`で税率を取得して**明細ごとの税額**を計算する。
4. 明細ごとの税額を保存し、ヘッダ税額（`Tax`）は明細税額の合計とする。
5. 締日ごとの請求・支払集計（`SummaryUriSei`/`SummaryKaiShi`）はヘッダ`Tax`の集計値を正とし、入金/支払の相殺で誤差を吸収する運用は変更しない。
6. 明細テーブルはJSON列（`Jmeisai`）のため、`ALTER TABLE`は不要。C#クラス定義の変更のみで良い。

## 3. 方式比較（明細Tax列をどこに持たせるか）

### 案A: 共有`Tran99Meisai`クラスへ列追加（採用）

`Tran99Meisai`（10伝票種共通）に `Id_Tax` / `TaxRate` / `Tax` を追加し、税額計算をする5伝票種のみ値を設定する。棚卸・調整・移動系は常に`Id_Tax=0`・`Tax=0`のまま未使用とする。

**メリット**
- 変更箇所が1クラス（`BaseDb2Trans.cs`）＋対象5画面のロジックのみ。共通基盤（`BaseTranInputViewModel`/`TranMeisaiSql`/HHT変換等、`Tran99Meisai`参照37ファイル）に型分岐を持ち込まずに済む。
- JSON列なので列追加によるマイグレーションコストはゼロ（既存行は`Tax=0`として読み込まれるだけ）。
- 将来、棚卸・移動系にも金額/税の概念を持たせる要件が出た場合に流用できる。

**デメリット**
- 金額を持たない伝票（棚卸・調整・移動）のクラスにも意味の無い列が残る（実行時コストは無視できるが、コードを読む側が「なぜ移動明細にTaxがあるのか」を誤解する可能性）。
- 新しい伝票種を`TranAllHeader`から派生させる際、税関連列の初期化漏れに注意が必要（ただし全てデフォルト値0で安全側に倒れる）。

### 案B: 対象5伝票専用の明細クラスに分割

`Tran00Meisai`/`Tran01Meisai`/`Tran03Meisai`/`Tran12Meisai`/`Tran13Meisai`を新設し、金額を持たない5伝票種は従来の`Tran99Meisai`のまま据え置く。

**メリット**
- 意味論上は最も正確（税を持つ伝票だけが税列を持つ）。

**デメリット**
- `Tran99Meisai`は`BaseTranInputViewModel`/`BaseIdoInputViewModel`/`BaseStockSheetInputViewModel`/`TranMeisaiSql`/`HhtProcessUpdateMap.cs`/`ShippingDb.cs`など**37ファイルにまたがる共通基盤**が単一クラスを前提に書かれている（グリッドバインディング、JSON直列化、HHT変換、配分入力等）。5クラスに分けると、これら共通コードをジェネリクス化するか、型ごとに分岐させる必要があり、影響範囲・実装コストが大幅に増える。
- 現状の課題（税計算の不整合）に対して不釣り合いに大きな変更になる。

### 決定

**案A（共有クラスへの列追加）を採用する。** 理由: 既存の共通基盤への影響を最小化しつつ、JSON列という性質上マイグレーションコストが発生しないため。棚卸・移動系への列混入は実害が無く、コメントで用途を明示すれば十分。

## 4. 詳細設計

### 4.1 `Tran99Meisai` への列追加

`CvBase/BaseDb2Trans.cs` の`Tran99Meisai`（`:288`以降）に追加する。

```csharp
/// <summary>

/// 0 は非課税。棚卸・在庫調整・移動系の明細では未使用（常に0）。
/// </summary>
[ObservableProperty]

public partial long Id_Tax { get; set; } = 0;

/// <summary>

/// </summary>

public partial int TaxRate { get; set; } = 0;

/// <summary>

/// </summary>
```

- 棚卸(`Tran60Tana`)・調整(`Tran61Chosei`)・移動(`Tran05Ido`/`Tran10IdoOut`/`Tran11IdoIn`)は既存コードを一切変更せず、これらの列は既定値0のまま保存される。
- **列名は`TaxRate`とする**（`MasterSysTax.TaxRate`と同名だが、いずれも「消費税率(%)」で意味が一致するため揃える）。

### 4.2 明細ごとの税額計算ロジック

対象5画面（`ShukkaUriageInputViewModel.cs`, `ShopUriageInputViewModel.cs`, `ShiireInputViewModel.cs`, `JuchuInputViewModel.cs`, `HachuInputViewModel.cs`）＋返品入力(`HenpinInputViewModel.cs`)。

1. 商品選択時（`Id_Shohin`確定時）に`MasterShohin.Id_Tax`を明細行の`Id_Tax`へコピーする。商品マスタが引けない場合は`Id_Tax = 1`（標準税率）を既定とする。
2. 明細行の数量・単価・値引が変わるたび（既存の`Kingaku`再計算タイミングに合わせて）、次を実行する:
   ```csharp
   async Task RecalcMeisaiTaxAsync(Tran99Meisai m) {
       // Id_Tax=0 は非課税。LogicGetTax(0, ...) は MasterSysTax が引けず
       // Common.CompareYmd が空 DateFrom で例外になるため、呼ぶ前に落とす
       var rate = m.Id_Tax <= 0 ? 0 : await AppGlobal.LogicGetTax((int)m.Id_Tax, CurrentEdit.DenDay);
       m.TaxRate = rate;
       m.Tax = (int)Math.Round(Math.Abs(m.Kingaku) * rate / 100.0);
   }
   ```
   - **明細税額は常に正値**とする。返品・値引での符号反転はヘッダ`Kubun`から決まる`CalcFlag`(1/-1)が集計側で担うため、明細側で符号を持たせると二重反転になる（決定事項）。
   - `LogicGetTax`は`no`に応じて`MasterSysTax`をキャッシュ済みの`sysman`から引くのみで追加DBアクセスは発生しない（既存実装のまま）。
3. 伝票日付(`DenDay`)変更時（既存の`LoadTaxRateAsync`相当のタイミング）は、明細全行について`RecalcMeisaiTaxAsync`をやり直す。

### 4.3 ヘッダ`Tax`/`Total`の再計算

`UpdateHeaderTotals()`を次のように変更する（5画面共通）。

```csharp
void UpdateHeaderTotals() {
    var absKingakuTotal = Math.Abs(CurrentEdit.KingakuTotal);
    var tax = CurrentEdit.Jmeisai?.Sum(m => m.Tax) ?? 0;   // 明細Taxは常に正値
    CurrentEdit.Tax = tax;
    CurrentEdit.Total = absKingakuTotal + tax;
}
```

- 現行の`taxRatePercent`フィールドとそれを用いた一括計算は廃止する。`LoadTaxRateAsync()`は「伝票日付変更時に全明細を再計算する」役割（4.2-3）に置き換える。
- 明細が0件（未入力）の場合は`Tax=0`のまま。

### 4.4 サーバ側 税率解決ヘルパーの共通化

`CvDomainLogic/HhtProcessUpdateMap.cs:199-212` の`ResolveTaxRatePercent()`は`Id == 1`固定・private・HHT専用のため、税Id対応の共通ヘルパーへ昇格させる（4.5の一括再更新とHHT変換の双方から使う）。

```csharp
// CvDomainLogic の共通クラス（例: TaxRateResolver）へ
/// <summary>伝票日付時点の消費税率(%)を返す。taxId=0 は非課税で 0 を返す</summary>
public static int ResolveTaxRatePercent(MasterSysman sysman, long taxId, string denDay) {
    if (taxId <= 0) return 0;                       // 非課税
    var systax = sysman.Jsub?.FirstOrDefault(x => x.Id == taxId);
    if (systax == null) return DefaultTaxRatePercent;
    var rate = systax.TaxRate;
    if (IsValidYmd(denDay) && IsValidYmd(systax.DateFrom)
        && CvAsset.Common.CompareYmd(denDay, systax.DateFrom) >= 0) {
        rate = systax.TaxNewRate;
    }
    return rate > 0 ? rate : DefaultTaxRatePercent;
}
```

- `HhtProcessUpdateMap`は既存の呼び出し（税Id=1固定）をこのヘルパー経由に置き換える。振る舞いは変えない。
- クライアント側`LogicGetTax`も同じ判定（`taxId<=0`で0、`DateFrom`の桁数チェック）へ揃えると望ましいが、既存動作を壊さないよう**呼び出し側でガードする方針**（4.2-2）を優先し、`LogicGetTax`自体の改修は行わない。

### 4.5 既存・移行済み伝票の一括再更新（管理者用処理）

既存伝票は明細`Tax`が0のままなので、`SysExecMiscView`へ**「伝票税額再更新」**を追加する。

**対象と処理内容**
- 対象テーブル: `Tran00Uriage` / `Tran01Tenuri` / `Tran03Shiire` / `Tran12Jyuchu` / `Tran13Hachu`。
- 対象行: **明細`Tax`の合計が0の伝票**（＝まだ明細別税額が入っていない伝票）。既に明細別税額が入った伝票は再更新しない（冪等性の確保。何度実行しても結果が変わらない）。
- 明細1行ずつ、`Id_Shohin`→`MasterShohin.Id_Tax`を引き、`ResolveTaxRatePercent(sysman, Id_Tax, ヘッダのDenDay)`で税率を得て、`Id_Tax`/`TaxRate`/`Tax`を再セットする。
- 商品マスタが引けない明細は`Id_Tax = 1`（標準税率）を既定とする。
- ヘッダ`Tax` = 明細`Tax`の合計、`Total` = `|KingakuTotal|` + `Tax` を再計算して更新する。

**ヘッダ`Tax`が変動する点の扱い**
移行済み伝票のヘッダ`Tax`は旧「掛率1」（実質税率）からの一括計算値なので、明細合計へ置き換えると端数処理の違いで±数円ずれうる。処理結果に**「ヘッダTaxが変化した伝票の件数と差額合計」を必ず出力**し、請求・支払計算をやり直す判断材料とする。

**実装構成**（既存の`Msg047_MasterVColumnResync`と同じ流れに揃える）
| 層 | 追加内容 |
|---|---|
| `CodeShare/ICoreService.cs` | `CvFlag` に `Msg059_TranTaxRebuild = 59` を追加（`Msg058_HhtDataUpdate`の次） |
| `CvServer/Services/QueryMsgService.cs` | `_handlers` へ `[CvFlag.Msg059_TranTaxRebuild] = (req, ctx) => HandleTranTaxRebuild(req, ctx)` を追加 |

### 4.7 締日集計（`SummaryDb`）への影響

- `CalcSummaryUriSei`/`CalcSummaryKaiShi`は引き続き**ヘッダ`Tax`列をSUM**するため、集計SQL自体の変更は不要。ヘッダ`Tax`が「明細税額の合計」に変わるだけで、既存の`Kubun BETWEEN 20 AND 29`による`CalcFlag`符号処理はそのまま機能する（明細`Tax`を正値で持つ4.2の決定と整合する）。
- 明細ごとに異なる税率が混在する伝票でも、ヘッダ`Tax`は単純合計で正しく求まるため追加対応は不要。

### 4.8 適格請求書（D-05）での税率別内訳への流用

明細に`Id_Tax`/`TaxRate`/`Tax`を持たせることで、適格請求書に必要な**税率ごとの課税標準額・消費税額の内訳**を伝票データから直接集計できるようになる。本設計はその前提を作ることまでを範囲とし、帳票側の実装はD-05決定後に別途行う。

**流用の方針（D-05設計時の入力とする）**
- 集計軸: 締日期間 × 得意先（請求先） × `TaxRate`。
- 課税標準額 = 該当税率の明細`Kingaku`の合計（`CalcFlag`で符号反転）、消費税額 = 該当税率の明細`Tax`の合計（同）。
- 現行の`SummaryUriSei`は税率別の列を持たないため、税率別内訳が必要になった時点で次のいずれかを選ぶ:
  - 案1: `SummaryUriSei`へ税率別の内訳列（または内訳JSON列）を追加する。
  - 案2: 請求書出力時に`Tran*`の明細JSONを直接集計する（保存はしない）。
- **どちらを採るかはD-05で決定する。** 本設計では明細に必要な情報（税区分・適用税率・税額）が揃っている状態を作るところまでを保証する。
- 非課税明細（`Id_Tax=0`）は税率別内訳で「非課税」区分として分離できる。

### 4.9 移行処理（`ConvertDbTran.cs`）の扱い

- 旧CVnetデータには商品ごとの税区分・明細ごとの税額が存在しないため、**移行時は現行の`CalcMigratedTaxTotal()`（ヘッダ一括計算）を維持する**（ロジック変更なし）。
- 明細行の新列（`Id_Tax`/`TaxRate`/`Tax`）は移行時`0`のまま生成される。
- 移行後、4.5の「伝票税額再更新」を実行することで明細別税額が投入される。移行→再更新の順序を移行手順書へ明記する。

### 4.10 対象外にする伝票（変更しない）

- `Tran60Tana`（棚卸）・`Tran61Chosei`（在庫調整）・`Tran05Ido`/`Tran10IdoOut`/`Tran11IdoIn`（移動）は金額・税の概念を持たないため、明細の新列は常に既定値のまま放置する。これらのViewModel（`StockInputViewModel.cs`等）には変更を加えない。

## 7. テスト観点

**明細別税額計算**
- 単一税率商品のみの伝票: 従来のヘッダ一括計算と明細合計計算で`Tax`が一致すること。
- 軽減税率商品（`Id_Tax=2`、8%）混在の伝票: 明細ごとに正しい税率が適用され、ヘッダ`Tax`が明細合計と一致すること。
- `Id_Tax=0`（非課税）商品を含む伝票: 該当明細の`TaxRate=0`/`Tax=0`、他明細は通常通り課税されること。**`LogicGetTax(0, ...)`を呼ばずガードで落ちること**（4.2の例外対策）。
- 伝票日付をまたぐ税率切替（`MasterSysTax.DateFrom`前後）での明細ごとの税率適用。
- 返品入力: 明細`Tax`が正値で保存され、集計側`CalcFlag`で正しくマイナス計上されること。
- 商品マスタが引けない明細で`Id_Tax=1`が既定適用されること。

**伝票税額再更新**
- 明細`Tax`合計が0の伝票のみが対象になり、既に税額が入った伝票が変更されないこと（**2回実行して結果が変わらない＝冪等**）。
- ヘッダ`Tax`変化件数・差額合計が結果メッセージに出力されること。
- 途中エラー時にrollbackされ、部分更新が残らないこと。
- 移行データ（明細`Tax=0`）に対して実行後、請求・支払計算の結果が想定範囲内で変化すること（差額の説明がつくこと）。

**商品マスタ保守**
- 消費税区分の選択・保存・再表示。
- Row挿入後、メーカー品番以降の項目がレイアウト崩れ無く表示されること。
- 選択肢が`MasterSysTax`の内容を反映すること（非課税＋Id 1〜3）。

**回帰**
- 棚卸・在庫調整・移動の各入力が従来どおり動作すること（明細新列が既定値0で保存される）。
- HHT変換が従来どおり税率10%で計算されること（`ResolveTaxRatePercent`共通化後の振る舞い不変）。
- `TestServer.exe` の既存テストが全件成功すること。
