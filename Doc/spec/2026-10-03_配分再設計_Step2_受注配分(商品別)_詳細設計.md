## 1. 背景と目的

基本設計 7 章（D4）では、受注配分について次の 2 点を決めた。

- 受注配分入力は現行のまま続け、「得意先軸」の表示を追加する。
- 得意先別配分入力（`TokuiHaibunInput`、雛形のみ）は廃止する。

旧CVnet の受注配分入力（`refer/cvnet-knowlege/マニュアル/CVnetマニュアル-13-配分.pdf` 12〜14 ページ）は、次のような画面だった。

- 倉庫と品番を選ぶと、**行＝得意先・店舗、列＝SKU（色×サイズ）のマトリクス**が出る。
- 「受注残読込」で、各得意先の受注残を初期値として流し込む。
- 利用者が配分数を直して「決定」する。

一方、CV10 の受注配分入力（`JuchuHaibunInputViewModel`）は**受注伝票 1 件ずつ**配分する画面である。1 つの商品を複数の得意先に振り分ける業務（展示会受注の出荷など）では、伝票を 1 件ずつ開くことになり手間がかかる。

そこで Step 2 では、**商品を軸にして、複数の得意先の受注残へまとめて配分する画面**を追加する。これが「得意先軸」の実体になる。伝票別の画面はそのまま残す。

## 3. 画面仕様

### 3.1 条件

| 項目 | 必須 | 説明 |
|---|---|---|
| 出庫倉庫 | ○ | 受注ヘッダの倉庫（`Tran12Jyuchu.Id_Soko`）と一致する受注だけを対象にする。配分の `Id_Soko` になる |
| 商品 | ○ | 品番を 1 つ指定する |
| 受注日 | | 範囲指定。既定は当月 1 日〜空欄 |
| 得意先 | | 範囲（コード From〜To） |
| 指示日 / 納品日 | ○ | 登録する配分の `DenDay` / `NouhinDay`。既定は本日 |

- 対象にする受注は、区分が受注（現行の `KubunJuchu`）で未完了のもののうち、指定した商品の受注残（受注 − 出荷売上 − 未完了の受注配分）が 1 点以上残っているものに限る。
- 受注残の算式は、伝票別画面の `JuchuSkuSql` を流用する。

### 3.2 一覧（マトリクス）

- 列は「得意先」「受注件数」「合計」と、商品の SKU 列（色×サイズ。`DerivedShohinColSiz` の並び）。
- 上部の集計行:

| 行 | 内容 |
|---|---|
| 有効在庫 | SKU ごとの「実在庫 − 引当 ＋ 画面で読み込んだ自分の配分」（基本設計 5章の算式） |
| 受注残合計 | 全得意先の受注残の SKU 別合計 |
| 配分合計 | 画面で入力した配分数の SKU 別合計 |
| 配分後在庫 | 有効在庫 − 配分合計。マイナスは赤で表示する |

- 明細行は 1 行が 1 得意先。
  - 入力セルは配分数。セルの下段に、その得意先の受注残を小さく出す。
  - 受注残を超えたセルは色を変える。
- 初期値は、その得意先の対象受注×商品に**すでにある修正可能な配分**（`Kubun=2`、`TranHaibun.EditableWhereSql`）の合計にする。
  - 確定済み・送信済みの配分は受注残の算式で差し引かれるので、初期値には含めない。

### 3.3 操作

| ボタン | 内容 |
|---|---|
| 検索 (F5) | 条件で一覧を作る |
| 受注残読込 | すべてのセルを受注残で上書きする（在庫は見ない。旧「受注残読込」と同じ） |
| 在庫内で受注日順に読込 | SKU ごとに、有効在庫の範囲で、受注日の古い得意先から順に受注残を割り当てる（3.4） |
| 0クリア | すべてのセルを 0 にする |
| 登録 (F6) | 4章の手順で保存する |

### 3.4 「在庫内で受注日順に読込」の規則

- SKU ごとに、得意先を「その得意先の対象受注のうち最も古い受注日 → 得意先コード」の順に並べる。
- その順に `min(受注残, 残りの有効在庫)` を割り当てる。
- 割り当ては純粋関数として `HaibunOrderDistributor.FillByStock` に置く（単体テストの対象）。

## 4. 登録（保存）

1. **検査**（現行の伝票別画面と同じ考え方で、警告だけ出して続けられる）
   - 配分後在庫がマイナスの SKU がある → 「有効在庫を超えています。確定時にエラーになります。」
   - 受注残を超えるセルがある → 「受注残を超える分は受注に紐付かない配分として登録されます。」
2. **受注への割り付け**（`HaibunOrderDistributor.Distribute`、純粋関数）
   - 得意先×SKU の配分数を、その得意先の対象受注へ、**受注日・受注Id の古い順**に、各受注の受注残を上限として割り当てる。
   - 割り当て切れない超過分は、`RelateNo1 = 0`（受注に紐付かない配分）の行にする。現行の受注残超過の規則と同じ。
   - 超過行は、その得意先の対象受注のうち最も新しい受注の明細単価を使う。
   - 単価・上代・下代は受注明細から引き継ぐ（現行の規則）。
3. **洗い替え保存**
   - `SaveHaibunAsync(置換対象, 新しい行)` を 1 回だけ呼ぶ（Step 1 の原子保存）。
   - 置換対象は、表示中の得意先の対象受注×商品にある修正可能な `Kubun=2` の配分と、同じ得意先×倉庫×商品の `RelateNo1=0` の受注配分（`Kubun=2`）。
4. 新しい行の値:
   - `Kubun = 2`（受注配分）
   - `Id_Soko` = 倉庫、`Id_Tenpo` = 得意先
   - `DenDay` / `NouhinDay` = 画面の指示日 / 納品日
   - `RelateNo1` = 受注Id（超過分は 0）
5. 保存したら再検索する。

> 仮想ヘッダは `DenDay + NouhinDay + Id_Soko + Id_Tenpo + Kubun + RelateNo1` のままなので、出荷売上は**受注ごと**に作られ、受注残も受注ごとに消化される（現行の伝票別画面と同じ結果になる）。

## 5. 実装方針

| 層 | ファイル | 内容 |
|---|---|---|
| CvBase | `HaibunOrderDistributor.cs`（新規） | `Distribute` と `FillByStock`。入力は「得意先×SKU の配分数」「受注×SKU の受注残と受注日」。DB に依存しない（`TaxCalculator` と同じく、クライアントとテストの両方から使えるように CvBase に置く） |
| CvWpfclient | `SalesOrderAllocationInputViewModel.cs` / `View.xaml`（新規） | 動的な SKU 列は、発注配分入力（`HachuHaibunInputViewModel` の `SkuColumns` / `Cells[i]`）と同じ作りにする。受注残の SQL は伝票別画面の `JuchuSkuSql` と同じ形（共通化はしない。伝票別画面に触らないため） |
| CvWpfclient | `MenuData.cs` | 3 章 S3 のとおり |
| CvWpfclient | `TokuiHaibunInput*` | 削除 |
| Tests | `HaibunOrderDistributorTests.cs`（新規） | 受注日順の割り付け、受注残上限、超過行、複数 SKU、0 の扱い、`FillByStock` の在庫上限と順序 |
| UatVm | `HaibunScreenScenario` / 新シナリオ | 商品別画面の表示・登録・崩れ判定。得意先 2 件・受注 3 件で、割り付けと受注残の消化を確認する |

## 6. 承認をお願いしたい点

1. 「得意先軸」を、**別画面の「受注配分入力(商品別)」**（行＝得意先、列＝SKU）として作ってよいか。既存の伝票別画面は「受注配分入力(伝票別)」という名前にして残す。
2. 得意先の配分数を受注へ割り付ける順序は、**受注日・受注Id の古い順**でよいか。超過分は受注に紐付かない配分にする。
3. 「在庫内で受注日順に読込」（有効在庫の範囲で古い受注から埋める）を Step 2 に含めてよいか。
4. 受注のない得意先への配分（旧「得意先展開」）は、この画面では扱わず、在庫配分（Step 3）に任せてよいか。
