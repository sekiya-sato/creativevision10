- 作成日: 2026-10-03

- 作業規模: **C（高リスク）**。引当の算式を変え、列を追加する（migration）。仕入の保存にも副作用が加わる。実装後に独立した Reviewer / Tester を置く。

## 1. 背景と目的

### 基本設計での決定（D1）

- 仕入配分（区分 0。旧「初回配分」）は**発注起点**のまま作る。
- 入荷前は引当しない。仕入を計上したら、**入荷した数量の範囲で引当対象・確定可能にする**。
- 部分入荷の場合は、入荷した数量の範囲で、店舗の優先順位の順に確定できる。
- 判定方法（計算で求めるか列を持つか）は Step 4 で決める。

### 現状の問題（基本設計 P2）

| 画面 | 内容 | 問題 |
|---|---|---|
| 発注配分入力（`HachuHaibunInputViewModel`） | 発注 1 件を、入庫先（`TenType IN (0,3,6)`）× SKU に振り分ける。`RelateNo1` = 発注Id | 入荷しても引当に入らない |
| 店舗配分入力(初回)（`ShopHaibunInputViewModel`） | 商品を軸に、未入荷の発注の入荷予定を店舗へ振り分ける | `RelateNo1 = 0` で、発注と紐付かない |

共通の問題:

- 区分 0 は常に引当対象外（`SummaryDb.ReserveTargetWhere` が `Kubun <> 0`）。
- そのため、入荷した在庫を在庫配分や受注配分に先取りされる。
- 確定時の在庫検査（Step 1 で区分 0 の数量も検査するよう修正済み）でしか、入荷を確かめていない。
- 仕入と発注は、仕入の `RelateNo1` = 発注Id で紐付いている（発注残の自動完了 `CompletionDb.CalcHachuEndFlag` が同じ規約を使っている）。

### 目的

1. 区分 0 の配分に「入荷済み数」を持たせ、その分だけを引当・確定の対象にする。
2. 商品を軸にした仕入配分入力を作る。発注に紐付けて保存し、店舗配分入力の初回モードを置き換える。

## 3. データと算式

### 3.1 列の追加

| 列 | 型 | 既定 | 意味 |
|---|---|---|---|
| `TranHaibun.ArrivedSu` | NUMBER not null | 0 | 区分 0 の配分のうち、入荷して引当・確定できる数（0〜`Su`）。ほかの区分では使わない（0 のまま） |

migration は `CvBase/UpdateDb.cs` に 1 件追加する。

```sql
ALTER TABLE TranHaibun ADD COLUMN ArrivedSu NUMBER not null default 0;
```

`ITranReserve` に `ArrivedSu` を加え、引当の再計算キーの判定にも使う。

### 3.2 入荷割当（`ArrivalDb.Recalc(hachuIds)`）

発注×SKU ごとに次の手順で計算する。

1. **入荷数 R**: その発注に紐付く仕入（`Tran03Shiire.RelateNo1` = 発注Id）の明細数量の合計。`CalcFlag` を掛けるので、仕入返品は差し引かれる。対象は、配分の出庫元と同じ倉庫の仕入だけ（判断 5）。
2. **消費済み C**: その発注×SKU の完了済み区分 0 配分（`EndFlag = 1`）の `JitsuSu` の合計。
3. **割当できる数**: A = max(R − C, 0)
4. **割当**: 未完了の区分 0 配分（`EndFlag = 0`）を**優先順**に並べ、`min(Su, 残り)` を割り当てる。計算は `HaibunOrderDistributor.FillByStock` を流用する。
   - 優先順は、配分先の店舗コード順、同じ店舗の中は配分行の Id 順（判断 2）。
5. `ArrivedSu` が変わった行だけを更新する（`Vdu` も更新する）。
6. 変わった行の倉庫＋SKU で、引当を引き直す（`CalcHaibun2Reserve`）。

この計算は冪等で、何度呼んでも同じ結果になる。

`RecalcAll()` は、未完了の区分 0 配分を持つすべての発注に対して `Recalc` を行う。全件再集計で使う。

### 3.3 引当の算式（`SummaryDb`）

| 項目 | 現行 | 変更後 |
|---|---|---|
| 対象行 | `h.EndFlag = 0 AND h.Kubun <> 0` | `h.EndFlag = 0` |
| 数量 | `CASE WHEN KakuteiDay='' THEN Su ELSE JitsuSu END` | `CASE WHEN h.Kubun = 0 THEN h.ArrivedSu WHEN ifnull(h.KakuteiDay,'') = '' THEN h.Su ELSE h.JitsuSu END` |

- `AllocationRules.ReservedQty` も同じ式に揃える（確定時の在庫検査で使う）。
- 区分 0 は、入荷するまで引当 0 なので、入荷前の動きは現行と同じ。

### 3.4 制約（`AllocationRules`）

| 時点 | 制約 | 違反時 |
|---|---|---|
| 保存（`ValidateNewRow`） | 区分 0 の新しい行は `RelateNo1 > 0`（発注Id）が必須 | `InvalidParameter`（「仕入配分は発注に紐付けて登録してください」） |
| 確定（`Commit`） | 区分 0 は 確定数 ≦ `ArrivedSu`。確定の直前に、対象の発注の入荷割当を再計算してから判定する | `InvalidParameter`（未入荷の行を列挙）。何も書き込まない |
| 確定の後 | 確定した発注の入荷割当を再計算する。欠品で余った入荷数を、次の優先順位の行へ回すため | — |

在庫検査（`FindShortages`）は現行のまま行う。

### 3.5 既存データの扱い（判断 3）

| データ | 扱い |
|---|---|
| 発注に紐付く区分 0（`RelateNo1 > 0`） | migration の後、全件再集計（または次の仕入・保存・確定）で `ArrivedSu` が計算される |
| 発注に紐付かない区分 0（`RelateNo1 = 0`。店舗配分入力の初回モードで作ったもの） | 発注が分からず入荷を判定できない。migration で **`ArrivedSu = Su`（入荷済み扱い）** にし、確定できる状態を保つ。<br>この行は引当に入るので、その倉庫の有効在庫がその分減る |

- 開発 DB にはこのデータがない（`TranHaibun` は受注配分 1 件のみ）。本番相当のデータで件数を確認してから適用する。
- **運用手順（実装時に追加）**: migration は列と `ArrivedSu` を変えるだけで、引当数（`SummaryRealStock` / `SummaryStock.ReserveQty`）は引き直さない。適用直後に**全件再集計**（`CalcReserveQtyAll`。先頭で `ArrivalDb.RecalcAll` を行う）を実行する。実行するまでは、該当の倉庫＋SKU で有効在庫がずれて見える（確定時は再計算するので誤確定にはならない）。

## 4. 画面

### 4.1 仕入配分入力(商品別)（新規、`PurchaseReceiptAllocationInputView` / `ViewModel`）

Step 2（受注配分の商品別）と Step 3（在庫配分）の作りを組み合わせる。

**条件**

| 項目 | 説明 |
|---|---|
| 入荷倉庫（必須） | 発注の倉庫 |
| 商品（必須） | |
| 納品予定日の範囲 | 任意 |
| 仕入先 | 任意 |

- 対象にする発注: その倉庫×商品の未完了の発注（`Tran13Hachu.EndFlag = 0`）。

**列見出し（SKU ごと）**

| 項目 | 内容 |
|---|---|
| 発注 | 対象発注の発注数の合計 |
| 入荷済 | 仕入数の合計 |
| 配分可能 | 発注数 − ほかの区分 0 配分（洗い替え対象以外。完了分を含む） |
| 配分 / 残 | 配分の合計と、配分可能 − 配分 |

**行（配分先）**

- 配分先は `TenType IN (0,1,3,6)`。入荷倉庫自身は除く。
- 初期の行は、対象発注×商品にある修正可能な区分 0 配分の配分先。
- 配分先の追加・削除、［前回の配分先を読込］は在庫配分入力と同じ。

**按分パネル**

- 在庫配分入力と同じ（同数／比率、比率の基準、端数）。
- 総数の既定は「配分可能」。

**保存**

1. 配分先×SKU の数を、その倉庫×商品の対象発注へ割り付ける。
   - **実装時に追加**: まず、その配分先×SKU が既に紐付いていた発注へ、元の数を上限に割り付ける。保存し直しで入荷済みの発注から未入荷の発注へ付け替わり、入荷済み数が失われるのを防ぐため（独立レビューの指摘）。残りを下の規則で割り付ける。
   - 割り付けには `HaibunOrderDistributor.Distribute` を使う。発注の並び順は「納品予定日 → 発注Id」で、各発注の上限は「その発注の配分可能数」。
   - 割り付け切れない超過分（発注数を超える配分）は、**登録しない**。保存前にエラーにする（区分 0 は発注Id が必須のため）。
2. `SaveHaibunAsync` で洗い替える。
   - 置換対象は、対象発注×商品の修正可能な区分 0 配分すべて。
   - 新しい行は `Kubun = 0`、`RelateNo1` = 発注Id。
3. サーバの保存処理が、対象の発注の入荷割当を再計算する。

**単価**

- 在庫配分入力と同じ（上代の種類は配分先の店種で選ぶ。卸先は上代×掛率）。

### 4.2 仕入配分入力(伝票別)（既存の発注配分入力を改名）

- クラス名は変えない（D7）。表示名を変え、メニューを移す。
- SKU 見出しに「入荷 n」（その発注の入荷数）を追加する。

### 4.3 配分確定（Step 1 の画面）

- 一覧に「入荷済」列を足す。区分 0 は `ArrivedSu`、ほかの区分は空欄。
- 区分 0 の確定数の初期値は `min(Su, ArrivedSu)`。
- 未入荷分を残して確定すると、残りは欠品として完了になる。確定の確認ダイアログで、未入荷分のある仕入配分の件数を分けて警告する（実装時に追加）。
- 仕入配分を卸先・売仕店へ確定して作る出荷売上は、`RelateNo1` を 0 にする（`RelateNo1` = 受注Id の規約のため。発注Id を入れると無関係な受注の残を消化してしまう。実装時に追加）。
  - 残りの入荷を待ちたい場合は確定しない（滞留一覧に残る）。
  - 発注をあきらめた場合は、指示取消（確定数 0）で完了にする。

## 6. 承認をお願いしたい点

1. **入荷の判定方法**: `TranHaibun` に `ArrivedSu`（入荷済み数）列を追加し、仕入・保存・確定のたびに再計算する方式でよいか。
   - もう一つの案は、引当の SQL で毎回、仕入から計算する方式。列は要らないが、引当の再計算・確定・画面の SQL がすべて複雑になり、遅くなる。
2. **部分入荷の優先順**: 配分先の店舗コード順（同じ店舗内は行の Id 順）でよいか。
   - もう一つの案は、入荷数を各店舗の配分数の比率で按分する方式（端数は店舗コード順）。
3. **発注に紐付かない既存の初回配分**（`RelateNo1 = 0`）: migration で入荷済み扱い（`ArrivedSu = Su`）にしてよいか。
   - そうすると引当に入るため、その倉庫の有効在庫がその分減る。
4. **画面**: 「仕入配分入力(商品別)」を新規に作り（店舗配分入力(初回)の置き換え）、発注配分入力を「仕入配分入力(伝票別)」として残す構成でよいか。
5. **入荷数に数える仕入**: 配分の出庫元と同じ倉庫の仕入だけでよいか。別の倉庫に入荷した分は、その配分の入荷に数えない。
6. **確定の制約**: 確定数が入荷済みを超える場合は、確定全体をエラーにする（自動で入荷済みまで切り詰めない）方式でよいか。画面の初期値は入荷済みまでにする。
