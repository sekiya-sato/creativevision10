## 1. 目的・決定事項

配分による出庫元倉庫の不足と店舗の基準在庫不足を補う。計算結果をDBの補充データとして保存し、利用者の確定操作で在庫配分指示と仕入先発注を作成する。

| 項目 | 決定 |
|---|---|
| 不足対象 | 未確定配分による倉庫不足に加え、店舗の基準在庫不足を対象とする |
| 補充ファイル | 実CSVではなくDBの補充データ（`TranHoju`）。保存と確定を分離する |
| 既存発注 | 同一入荷倉庫・SKUの発注残を控除する。仕入先が異なっても供給として扱う |
| 仕入先決定 | 商品マスタの`Id_ConsignmentShiire`（委託仕入先）を通常仕入商品でも補充発注先として使用する。専用仕入先設定表は作らない |
| 商品メンテ | 委託仕入先を仕入区分に関係なく入力可能にする。消化仕入の計算条件だけ従来どおり無効化する |
| 店舗補充 | 店舗×SKUの基準在庫・補充元倉庫を設定。倉庫の供給可能在庫から在庫配分を作る |
| 追加発注 | 在庫・既存供給で補えない残りを補充データにし、確定時に自動発注区分15を作る |

今回の具体化: 手動実行から導入し、Scheduler・売上基準の予測・ロット丸め・仕入先への外部送信・確定後欠品の再需要化は対象外。発注後の入荷・仕入配分・配分確定は既存経路を使う。

## 3. 不変条件

1. 計算・プレビュー・補充保存では実在庫、引当、発注残を更新しない。
2. 補充確定は在庫配分指示と発注を作る。実在庫を動かすのは既存配分確定・仕入処理である。
3. 未完了配分は引当に既に含まれる。引当へ配分`Su`を重ねて加算しない。
4. 完了配分の`ShortSu`・未配分受注残は今回加算しない。確定欠品を再需要化すると既存「欠品は受注残・発注残に残す」方針と重複する。
5. 仕入配分の未入荷数は既存発注が支えている。未入荷分を新規発注需要へ加算しない。
6. 色・サイズを省略した集約・検索・一意キーを作らない。
7. SQLはSQLiteを正典とし、方言実行APIを使う。JSON参照は不正JSONを防御する。
8. `Tran*`の名称・単価・税条件は保存時点の監査値。確定済み発注を現行マスタ変更で書き換えない。

## 4. 設定と対象

### 4.1 店舗基準在庫

新設`MasterAutoReplenishStock`。一意キーは`Id_Tenpo + Id_Shohin + Id_Col + Id_Siz`。

| 列 | 意味 |
|---|---|
| `Id_Tenpo` | 補充対象の直営店（店種6）。売仕店3は配分確定が売上出荷となり店舗在庫が増えないため対象外 |
| `Id_Soko` | 補充元倉庫（店種0）。店舗自身は不可 |
| `Id_Shohin / Id_Col / Id_Siz` | SKU。実在庫0でも設定SKUを起点に抽出する |
| `TargetSu` | 維持する基準在庫。0以上 |
| `Priority` | 小さい値から補充。0以上。同値は店舗コード、店舗Id順 |
| `Enabled` | 1で対象。0は除外 |

店舗の曜日設定も適用する。`AutoHoju & (1 << DayOfWeek) != 0`を満たす店舗だけ対象。曜日未設定・0は対象外として理由を表示し、全日扱いにしない。

### 4.2 発注先・除外

発注先は`MasterShohin.Id_ConsignmentShiire`を使う。通常仕入でも同じ列を使用し、メーカー・直近発注・名称から推測しない。現行名称は既存`VConsignmentShiire`の伝播に従い、発注時は仕入先マスタを読み直して監査値を作る。通常仕入の一般商品まで仕入先入力を必須にせず、追加発注が必要な商品のみ存在確認する。

SKU別除外は新設`MasterAutoReplenishExclude`で管理する。一意キーは`Id_Soko + Id_Shohin + Id_Col + Id_Siz`、`Excluded=1`で店舗補充・自動発注とも除外する。店舗ごとの対象外は基準在庫設定の`Enabled=0`で管理する。除外と仕入先不足は区別し、仕入先不足は理由を表示して保存・確定を止める。

既存在庫基準補充画面で店舗設定、既存対象除外品画面でSKU除外を管理する。発注先は商品マスタメンテで入力する。配分関連メンテナンスは重複実装せず、別途範囲を決める。

消化仕入商品（`PurchaseType=3`）の追加発注は初期実装で停止し理由を表示する（利用者承認済）。既存物流の発注入荷は通常仕入として買掛を計上するため、委託入荷・消化仕入更新との整合は後続設計とする。在庫で賄える店舗配分は商品区分にかかわらず可能。

## 5. 数量計算

実行は補充元倉庫1件単位、基準日は当日。現在庫で計算し、過去日残高の再現は行わない。数量の中間計算はlong・checked、保存列の範囲外は全体エラー。

### 5.1 店舗需要

SKUごとに次を計算する。倉庫・店舗の在庫行がなければ実在庫・引当0。

```text
店舗有効在庫 E_store = 実在庫 - 引当
店舗入荷待ち A_store = 他拠点から当該店舗への未完了配分の供給予定数
店舗積送中 T_store = max(0, SummaryStock.TransitQtyの全期間合計)
店舗必要数 D_store = max(0, TargetSu - (E_store + A_store + T_store))
```

`A_store`は区分0・1・2の未完了行。未確定は`Su`、旧確定・未完了行は`JitsuSu`。仕入配分の未入荷部分は関連発注が存在・未完了の場合のみ供給に数え、同発注・倉庫・SKUの残数量を上限に店舗コード→配分行Id順で割り当てる。入荷済み`ArrivedSu`は別に加算し、無効な発注の未入荷分を控除しない。店舗自身を出庫元とする取置は入荷待ちに含めない。未完了なのに生成伝票Idがある不整合は、予定配分と積送の二重加算を避けるためエラーで停止する。将来納品分も予定供給として数える初期方式であり、即納保証はしない。

### 5.2 倉庫供給と不足

```text
倉庫有効在庫 E_source = 実在庫 - 引当
倉庫既存不足 D_source = max(0, -E_source)
今回店舗配分可能数 F = max(0, E_source)
```

`F`を店舗のPriority・店舗コード・店舗Id順に配る。`TransferSu = min(店舗必要数, 残配分可能数)`。実在庫で供給できる分だけ在庫配分にする。入荷予定だけを根拠に在庫配分を作らない。

### 5.3 既存予定供給

```text
発注SKU残 O = max(0, 同一発注のSKU発注数合計 - 関連仕入SKU数合計)
仕入配分未入荷枠 B = 未完了区分0の max(0, Su - ArrivedSu) 合計
未拘束発注残 P = 発注ごとの max(0, O - B) の合計
倉庫積送中 T = max(0, SummaryStock.TransitQtyの全期間合計)
既存予定供給 C = P + T
```

発注は同一倉庫、区分10～19、`EndFlag=0`、発注日が当日以前の全仕入先・全納期を対象。仕入実績は返品の符号を含む。発注の同一SKU複数明細は先に合計し、仕入数を明細ごとに重ねて引かない。完了発注は返品後でも供給に戻さない。物流送信済み発注も有効な供給であり、既存物流出力の送信済み除外条件は流用しない。

仕入配分に拘束された発注残は当該店舗の`A_store`に含まれるため、他需要へ回さない。未完了在庫配分はすでに`ReserveQty`に含まれるので、倉庫側でさらに控除しない。

### 5.4 追加発注

まず倉庫既存不足、次に店舗残需要へ既存予定供給`C`を順に割り当てる。供給枠はSKUごとに一度だけ消費する。

```text
店舗残需要 = D_store - TransferSu
CoveredSu = 既存予定供給で覆える数量
追加発注 Su = 需要 - TransferSu - CoveredSu
```

倉庫不足行は店舗Id=0、`TransferSu=0`。店舗Id>0の行は店舗必要数を保持する。行の関係は`DemandSu = TransferSu + CoveredSu + Su`。全列0以上。

例: 倉庫実在庫20・引当25、店舗必要数8、未拘束発注残6なら、倉庫不足5を先に控除、店舗に残り1を割当、追加発注7。引当25や店舗必要数8に既存配分数を重ねて加算しない。

発注した店舗向け不足は直ちに在庫配分へ変換しない。入荷後の次回実行で有効在庫から店舗配分するか、既存仕入配分入力で割り当てる。発注残が消化されるまでは次回計算の予定供給となり、重複発注を防ぐ。

## 6. 補充データと状態

`TranHoju`の1行1SKU構造を維持し、店舗別需要・供給の内訳を持つ。実行単位の識別・再試行・再検査に必要な`TranAutoReplenishBatch`を補助テーブルとして新設する。汎用の伝票ヘッダ＋JSON明細へ置換しない。

| 実体 | 新設・追加列 |
|---|---|
| バッチ | 倉庫Id、基準日、実行キー（GUID・一意）、状態（未確定/確定/取消）、入力Fingerprint、実行中キー（一意）、入力社員Id、確定日、保存時点の内訳JSON（`PreviewJson`） |
| `TranHoju`追加 | `Id_Batch`、`Id_Tenpo`、`DemandSu`、`TransferSu`、`CoveredSu`、`GeneratedHachuId`（long）、`GeneratedHaibunId`（long） |
| `TranHoju`既存 | `Su`は新規発注予定数、`JitsuSu`は確定発注数、`KakuteiDay`は確定日。仕入先・納期・単価等を保持 |

`RelateNo1/2`はintであり、生成発注Idを無検査で代入しない。新しいlongリンクを使う。旧行`Id_Batch=0`は一覧参照の対象にできるが、新確定APIの対象外。

```text
読取プレビュー → 補充保存（未確定） → 確定（発注・在庫配分を一括生成）
                          └→ 取消（実伝票なし）
```

同一倉庫の未確定バッチは1件。未確定中の再計算は取消後に新しく保存する。履歴を削除・洗い替えせず、確定・取消後は編集禁止。予定供給だけで覆われる数量は内訳として残し、発注数0の行から発注は作らない。需要0のバッチは保存しない。

## 7. 確定・発注生成

1. サーバーでバッチ存在、状態、`ExpectedVdu`、実行キー、行所属を検査する。確定済みの同一バッチ再試行は既存結果を返す。
2. 単一Serializableトランザクション内で現在庫・引当・配分・発注残・積送・設定・価格・仕入先税条件を再取得する。
3. プレビュー保存時の対象入力Fingerprintと比較する。追加行・削除行も検出し、不一致なら書込なしで再計算を要求する。保存済み数量をクライアント値で上書きしない。
4. `TransferSu>0`から`TranHaibun`区分1（在庫配分）を作成する。未確定状態、`RelateNo1=0`。元の配分指示を変更しない。
5. `Su>0`を倉庫＋仕入先＋納品予定日でまとめて`Tran13Hachu`区分15にする。同一SKUは明細1件へ合算する。
6. 発注挿入、配分挿入、既存`WriteEffectRunner`経由の副作用・引当更新、補充行の生成Id記録、バッチ確定を同じトランザクションで完了する。

単価・下代は現行手動発注と同じ商品`TankaGenka`、上代は当日適用上代。納品日は発注日＋仕入先`LeadTimeDays`。仕入先`RateProper/TaxRounding`、商品税区分、自社税率と既存`TaxCalculator`を使い、名称もスナップショットする。掛率を理由に仕入単価へ新しい計算式を加えない。

金額はchecked longで計算し、既存`TranHoju`のint金額へ保存できない場合は停止する。税・合計・明細番号をサーバーで組み立てる。異常時は全体ロールバックし、発注だけ、配分だけ、確定だけが残る状態を許さない。

生成後の発注訂正・削除は既存発注入力の操作に従う。補充確定を巻き戻したり、同じバッチで再生成したりしない。削除後の新しい不足は新バッチの再計算で判断する。

## 8. 画面・API構成

- 実行画面: 倉庫選択、当日基準日、プレビュー、補充保存、未確定読込、確定、取消、履歴。店舗・SKU、実在庫、引当、基準在庫、入荷待ち、積送中、必要数、店舗配分数、既存発注充当数、追加発注数、仕入先、除外・エラーを表示する。
- 数量は初期実装で直接編集しない。設定変更または取消→再計算で見直す。確定前に配分件数・発注件数・数量・金額を表示する。
- 店舗基準画面: SKU/店舗/倉庫選択、基準数・優先順位・有効フラグの保存、既存行一覧・選択。無効化で除外し、物理削除は初期実装に含めない。
- 除外品画面: 倉庫/SKU選択、除外フラグの保存、既存行一覧・選択。既存「対象除外品設定」導線を使う。
- WPFは既存`BaseWindow`、CommunityToolkitコマンド、`App.xaml`共有スタイルを使う。計算・伝票生成はViewModelに置かない。
- 通信は既存`ICoreService.QueryMsg`の型付きパラメータ方式で、Preview/Save/Load/Commit/Cancelを追加する。gRPCサービスを別途増やさない。
- 設定保存はFK・SKU・非負数・一意キーをサーバーで検証し、`ExpectedVdu`で競合を拒否する。汎用保存の無検査利用は避ける。

主な受入条件:

- 未設定SKU・在庫行なし・色サイズ違い・曜日0・対象曜日外・無効設定・仕入先欠落を正しく判定する。
- 複数SKU明細・同一SKU複数明細・部分入荷・返品・完了発注・積送の正負を確認する。
- プレビューだけでDB変更なし。保存で実在庫・引当・発注変更なし。確定で実在庫変更なし、配分分だけ引当増加。
- 保存後の在庫・配分追加・設定・発注入荷・価格変更を検出し、確定前に停止する。
- 同一実行キー保存再試行、同一バッチ確定再試行、並行実行でも発注・配分は1組だけ生成する。
- 生成途中の例外で発注・配分・引当・補充状態をすべて戻す。

検証DBは一時SQLiteを使い、参照用MCP DB・本番DBを更新しない。CvBase/CvDomainLogic/CvServer/CvWpfclientの対象build、関連テスト、XAML/XML・binding・UTF-8/CRLF、`git diff --check`を確認する。

## 10. 移行・運用制約

- 新規店舗設定の初期値は無効。除外設定の未登録は非除外。既存商品・店舗・発注は自動変更しない。
- migrationは既存`UpdateDb`の方式に従い、新表と`TranHoju`追加列・一意索引を追加する。既存未コミットmigrationと競合しない番号を確認する。
- migration番号は`26_10_05_02`。既存HHT用`26_10_05_01`を保持する。旧`TranHoju`では索引作成を列追加後に遅延し、新DBでも同じ最終索引を作る。
- ロールバックは新機能の実行停止・設定無効化を優先する。生成済み発注・配分は通常の伝票訂正で扱い、テーブル削除で巻き戻さない。
- 全納期の既存供給を控除する初期方式では、納期の遅い発注があると即時不足が残る。納期別補充・ロット・安全在庫予測は後続仕様とする。
- 在庫集計の整合が前提。プレビュー時に全件再集計は実行しない。大量在庫表を全件取得せず対象倉庫・対象SKUで絞り、発注・仕入・設定のN+1取得を避ける。
- 実装・検証結果は`Doc/aicoding_log.md`へ記録する。Step 0は文書のみのためログ追記不要。
