# 月次請求書の適格請求書対応 詳細設計（2026-09-02）

## 1. 目的・範囲

`CvWpfclient.Views._06Uriage.SeikyuBalanceDetailView`（請求書印刷、伝票単位/明細単位の2様式）を、
適格請求書等保存方式（インボイス制度）の記載要件へ近づける。

1. 発行事業者の**登録番号**（`MasterSysman.TaxRegistrationNumber`）を印字する。
2. **軽減税率対象**（`Id_Tax = 2`）の明細に `*` 印を付け、税率を正しく表示する。
3. 上記の実装過程で判明した **CSV列マッピングの全面的な不整合を修正**する（3章）。

`Doc/spec/2026-09-01_消費税計算単位・端数処理_全体設計.md` 9章 残課題 R1・R3 の一部を、
`Doc/spec/2026-09-01_請求書印刷_旧cvnet帳票移植_詳細設計.md` で実装済みの
`SeikyuBalanceDetailViewModel` / `SeikyuBalanceDetailDenpyo.qfm` / `SeikyuBalanceDetailMeisai.qfm` に対して行う。

**対象外**（既存の残課題のまま）: 適格返還請求書（R2）、POS/HHTの消費税（R4）、消費税再計算メニュー（R5）。

## 2. 決定事項

| No | 決定 | 内容 |
|----|------|------|
| D1 | 登録番号の印字位置 | 現行レイアウトで自社FAXを出していた `item33` に `TaxRegistrationNumber` を入れる。qfm側の固定ラベル `"FAX:"` → `"登録番号:"` の変更は**人間側で実施済み**（2026-09-02） |
| D2 | `*` の付与先 | 明細単位=商品名（`item57`）、伝票単位=取引区分名（`item17`） |
| D3 | 軽減税率の判定 | **`Id_Tax = 2`**。明細単位は明細JSON(`Jmeisai`)の行ごとの `Id_Tax` スナップショットで判定する。伝票単位は1行=1伝票のため伝票の `TaxableAmount2 != 0`（伝票内に軽減税率明細を1件でも含む）で判定する |
| D4 | 脚注 | 「※は軽減税率対象商品」は**両qfmに元から静的テキストとして存在**していたため追加不要（レンダリングで確認済み） |
| D5 | 税率表示（`item39`） | 明細単位は行ごとの `Id_Tax` から解決した税率。伝票単位は伝票の税区分別課税対象額から**実際に使われている税率を全て併記**する（混在伝票は `10%/8%`）。旧実装は `taxable1→2→3` の優先順で1つだけ表示しており、軽減税率明細を含む伝票が `10%` とだけ表示される誤りがあった |
| D6 | CSV列数 | 旧CRSの61列制約は**撤廃**し、66列を出力する。明細単位qfmの税率別内訳が `item62`〜`65`、スタンプ画像が `item66` にバインドされているため（3.2） |

## 3. CSV列マッピングの修正（本改修の中核）

### 3.1 判明した問題

`Doc/spec/2026-09-01_請求書印刷_旧cvnet帳票移植_詳細設計.md` の実装は、旧CRSのSQL列名一覧
（`refer/printwrk/seikyu-sho-*/d_sql.txt`）を根拠に `itemN` を割り当てていた。しかし
**qfm が実際にバインドしている用途は d_sql.txt の列名と一致していなかった**。
その結果、商品名・住所・繰越金額などが別の欄へ流れ込み、明細単位では商品CD（例 `20822270006`）が
金額欄へ数値として解釈されて `822,270,006` のような値が印字されていた。

判定は qfm の `<text><data datasrc="itemN"/></text>` 静的バインドを機械抽出して行った。
qfm 内 JavaScript の `fdXxx.value = dtitemN` はコメントアウトされた「操作例(2)」であり実行されない。
実際の転送は `page.AssignData()`（＝静的バインド）である。

### 3.2 確定した用途（両qfmを機械抽出して確認）

items 1〜55 は両様式で共通。**56〜66 は様式ごとに用途が異なる**。

| item | 用途（伝票単位） | 用途（明細単位） |
|---|---|---|
| 33 | 自社FAX欄 → **登録番号** | 同左 |
| 39 | 明細行の「税率」欄 | 同左（行ごとの税率） |
| 40 / 41 | 税率別内訳のラベル（`消費税{n}%`） | 同左 |
| 42 | お支払予定日 | 同左 |
| 43 / 44 | 今回繰越金額 / 今回御請求額 | 同左 |
| 45〜49 | 得意先名・郵便番号・住所1〜3 | 同左 |
| 51 | 担当者（名称取得未実装のため空） | 同左 |
| 52 / 53 | 当月御買上額(税抜) / 当月御買上合計(税込) | 同左 |
| 55 | 「請求書NO」欄 | 同左 |
| 56 | （未使用） | 商品CD |
| 57 | 消費税額(8%) | 商品名（`*` 付き） |
| 58 | 消費税額(10%) | 明細金額 |
| 59 | 課税対象額(8%) | 伝票番号 |
| 60 | 課税対象額(10%) | 明細数量 |
| 61 | スタンプ画像 | （未使用） |
| 62〜65 | （未使用） | 消費税額(8%) / 消費税額(10%) / 課税対象額(8%) / 課税対象額(10%) |
| 66 | （未使用） | スタンプ画像 |

税率別内訳の集計式は `ValidateTaxBreakdownAsync` と同じ `SumForRate`（税区分の解決税率が
10%/8% のものだけを連結）を `"h."` エイリアス付きで使い、`headers` CTE へ
`Tax1/2/3`・`TaxableAmount1/2/3` を追加して参照する。

### 3.3 qfm 由来の既存の癖（変更しない）

- 「請求書NO」欄の decode 型が伝票単位=number / 明細単位=string のため、
  文字列の `SeikyuNo`（例 `321-20220430-01`）は伝票単位では `321` に切り詰められる。
- 明細行の「明細消費税」欄が `item18`（数量と同じ）にバインドされている。
- これらはベンダー製 qfm 側の定義であり、qfm を変更しない方針のため対象外とする
  （`Doc/spec/2026-09-01_請求書印刷_旧cvnet帳票移植_詳細設計.md` 4.4 の方針を踏襲）。

## 6. 残課題

| # | 内容 |
|---|------|
| A | 伝票単位の税率欄は幅が狭く（約11mm）、`10%/8%` は表示幅がぎりぎり。3税率が混在すると溢れる。実運用で問題になる場合は qfm 側の欄幅調整が必要 |
| B | 「担当者」欄（`item51`）は `MasterShain` への結合が無く空欄。名称を出す場合は `headers` CTE に結合を追加する |
| C | 明細単位の「総計」は明細行ベースで集計されるため、伝票単位の総計と数量・金額が一致しない（qfm の集計定義による） |
