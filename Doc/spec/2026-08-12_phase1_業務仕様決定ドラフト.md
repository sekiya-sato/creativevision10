### 2.1 消込の定義

消込とは、売上又は仕入伝票を伝票単位で決済済みの目印をつける処理を指す。元帳などを印字した際に伝票行に`*`をつけて表示する。
入金又は支払との個別対応、充当金額、未充当金額は保持しない。

| 区分 | 対象伝票 | 処理 | 残高への効果 |
| --- | --- | --- | --- |
| 入金消込 | `Tran00Uriage` | `EndFlag = 1` | 得意先元帳の印字時に`*`をつける |
| 支払消込 | `Tran03Shiire` | `EndFlag = 1` | 仕入先元帳の印字時に`*`をつける |

  他端末の更新または削除と判断し、**トランザクション全体をrollback**して `HandleUpdate()` と同じ

#### 2.1.2 消込で追加決定が必要な事項（2026-08-14 追記）

1. **請求先Idの実体** — `MasterTokui.Id_Paysaki` / `MasterShiire.Id_Paysaki`（請求/支払先）を使う。請求先が自社の場合に自分自身のIdが入る運用が既存データにあり（`MasterCascadeDb` の自己参照ケース）、`0`（未設定）も存在しうる。対象を `Id_Paysaki = X` だけに限るか、`Id_Paysaki = X OR (Id = X AND Id_Paysaki IN (0, X))` とするかを決める。
   **推奨: 後者**。`Id_Paysaki` 未設定の得意先が、その得意先自身を請求先として選んだときに漏れるため。
2. **「支払日」の実体** — `Tran06Nyukin` / `Tran07Shiharai` に入金日・支払日の専用列は無く、日付列は `DenDay`（計上日）だけである。画面の「支払日from-to」は `DenDay` を指すものとする。列を増やすかどうかを決める。**推奨: 増やさない**。
3. **入金・支払内訳の集計キー** — 明細 `TranKinMeisai` は `Jmeisai`（`SerializedColumn`, 4000桁のJSON）に格納されており、SQLで直接 `GROUP BY` できない。集計キーは `Code_Kin`（コピーされた文字列）ではなく `Id_Kin`（`MasterMeisho` の `KIN` 区分への外部キー）とし、表示名は `Mei_Kin` を使う。展開方法を SQLite の `json_each` とサーバー側C#展開のどちらにするかを決める。
   **推奨: サーバー側C#展開**。`List<TranKinMeisai>` の型が既にあり、JSON関数への依存を増やさずに済む。
   → 展開方式は 2026-08-14 に**クライアント側C#展開**で実装済み（本書末尾の追記を参照）。移行データの `Id_Kin` が全件 `0` だった問題は 2.1.4 で決定・修正した。
4. **消込済み伝票の再表示と取消** — 一覧取得時に `EndFlag = 1` の伝票を含めるか除外するかを決める。
   **推奨: 含めて表示し、CheckBoxを初期ONにする**。消込の取消は同じ画面でCheckBoxを外して`消込実行`する操作とし、メッセージを `{n}件消込、{m}件解除しました` とする。
5. **消込の監査列** — 消込社員・消込日時を保持するか。`EndFlag` だけでは誰がいつ消したかを追えない。
   **推奨: 1.0では保持しない**（`Vdu` の更新で足りる）。保持する場合は `Tran00Uriage` / `Tran03Shiire` に2列追加となる。
6. **元帳の `*` 表示** — `TokuiLedger` / `ShiireLedger` はTran直読みで、現在 `EndFlag` を読む条件が無い。両画面に `*` 列を追加する。列位置と、`*` 列を印字対象に含めるかを決める。
7. **入金側の対象範囲** — `Tran06Nyukin.Id_Torisaki` が請求先配下の得意先であることを条件とし、請求先配下でない入金は集計へ含めない。店舗売上 `Tran01Tenuri` は消込対象外（2.1 の確定どおり）。

#### 2.1.4 入金・支払内訳の旧コード対応（2026-08-16 ユーザー決定・実装済み）

2.1.2-3 で集計キーを `Id_Kin` と決めたが、**移行済みデータでは機能していなかった**。実DBで確認した事実。

| 事実 | 内容 |
| --- | --- |
| `Id_Kin` が全て `0` | `Tran06Nyukin` 2,302件の `Jmeisai` は `Id_Kin = 0` / `Mei_Kin = ""`。手入力の4件だけ正しい |
| `Code_Kin` は旧コード | `80` / `82` / `85` / `88` / `89` が入っており、`KIN` 区分の `01`〜`05` と体系が違う |
| 原因 | `CvDomainLogic/ConvertDbTran.cs` の `BuildKinMeisaiList()` が `getMeisho("PAY", code)` を引いていた。`MasterMeisho` に `Kubun = 'PAY'` は**存在しない**ため常に `null` となり、旧コードをそのまま `Code_Kin` へ落としていた |

この状態では消込画面の区分別集計が「名称空欄の1グループ」に全額集約されるため、次のとおり決定した。

| 旧コード | 旧システムでの意味 | `MasterMeisho` `KIN` の割り当て |
| --- | --- | --- |
| `80` | 現金 | `01` 現金入金 |
| `82` | 振込 | `01` 現金入金 |
| `85` | 振込手数料 | `02` 振込手数料 |
| `88` | 相殺 | `04` 相殺入金 |
| `89` | その他 | `05` その他入金 |

- 旧82（振込）は入金手段として旧80（現金）と同じ扱いにし、`01` 現金入金へ寄せる。
- `KIN` の `03` 手形入金へ対応する旧コードは実データに存在しない。
- 対応表に無い旧コードは変換せず `Id_Kin = 0` のままとし、`Code_Kin` へ旧コードを残す（消込画面では未分類として1本に集約される）。
- 変換ロジックは `ConvertDbTran.KinKubunCodeMap` / `getKinMeisho()` として実装した。入金・支払の両方が同じ `BuildKinMeisaiList()` を通るため1箇所の修正で両方に効く。
- 既に移行済みのDBは再変換せず、`Jmeisai` を `json_set` で書き換える一括SQLで是正する（SQL全文は `Doc/aicoding_log.md` の 2026-08-16 の記録）。

支払側も `KIN` 区分（名称は「現金入金」など入金表記）を共用する。名称の使い分けは1.0では行わない。

### 2.6 SummaryUriKake / SummaryKaiKake の更新ロジック（2026-08-14 追記）

### 2.7 請求計算・支払計算（`SummaryUriSei` / `SummaryKaiShi`）（2026-08-14 追記）

`SummaryUriSei` / `SummaryKaiShi` はスキーマだけが存在し、生成処理が `CvDomainLogic` に無い（実DBで0件）。列構成は `SummaryUriKake` に
`DenDay`（請求日）／`DayFrom`／`DayTo` を加えたもので、ユニークキーは `Id_Tokui + DenDay` である。

決定が必要な事項。

1. **集計キー** — 請求は相手先締日に合わせるため、`Id_Tokui` ではなく請求先（`Id_Paysaki`）で束ねるのが自然だが、スキーマのユニークキーは `Id_Tokui + DenDay` である。列名を維持したまま請求先Idを格納するか、キーを変更するかを決める。
2. **締日の取得元** — `MasterTokui.Shime1..Shime3` / `PayMonth` / `PayDay`（`EnumShime`）を使う。3つの締日をどう使い分けるか、`MasterSysKanri` 側に自社締日があるかを確認して確定する。
3. **請求日・期間の決定規則** — `DayFrom` / `DayTo` を締日から算出する規則、`DenDay`（請求日）を締日当日とするか翌日とするか。
4. **消込との関係** — 請求計算は伝票単位の `EndFlag` を参照しない（残高は伝票金額ベース）。この点を明記する。
5. **再計算の単位** — 夜間ジョブへ組み込む場合、`SummaryUriKake` と同様に「対象期間DELETE → 再作成」でよいか、請求済みデータを不変とするか。
6. **Rebuild対応** — 現状 Rebuild 対象は在庫・売掛・買掛の3つのみ。請求・支払を追加する際は `通常更新値 = Rebuild値` の検証対象に含める。

### 2.8 引当数の保持方式（2.2 の未決部分の具体化）（2026-08-14 追記）

`SummaryRealStock` の列は `Id_Soko` / `Id_Shohin` / `Id_Col` / `Id_Siz` / `Su` のみで、`AdjustQty` は月次の `SummaryStock` にしかない。
2.2 と3章の確定内容を実装に落とすには、以下を決める必要がある。

1. **引当数を列で持つか都度算出するか** — 引当の源泉は `TranHaibun`（`KakuteiDay` が空＝未確定、`RelateNo2 = 0`＝伝票未生成）であり、Rebuildで再生成できる。
   **推奨: `SummaryRealStock` へ引当数列を追加し、`TranHaibun` から再生成する**（照会性能のため）。列名は `ReserveQty` を候補とする。
2. **引当対象とする `EnumHaibun`** — `Hatsukai=0` / `Zaiko=1` / `Juchu=2` / `Tokui=3` / `ShopRequest=4` / `ZaikoHin=5` / `Reservation=6` / `IdoShiji=7` のどれを引当に数えるか。
   在庫を確保する意味を持つのは `Zaiko` / `Juchu` / `Tokui` / `ZaikoHin` / `Reservation` / `IdoShiji`、入荷前の割付である `Hatsukai` は実在庫を押さえない。
3. **引当の解除条件** — `KakuteiDay` が入り `RelateNo2` に生成伝票Idが入った時点で引当を解除し、実在庫の減少へ置き換える。この二段階の間に二重計上しない順序を定義する。
4. **調整数の保持先** — 3章の調整専用伝票から再生成する `AdjustQty` は `SummaryStock`（月次）にしか列が無い。`SummaryRealStock` 側は `Su` に含める（内訳を持たない）ことを確定するか、内訳列を追加するかを決める。

#### 2.8.1 決定と実装（2026-08-15 ユーザー承認・実装済み）

1〜3 を次のとおり決定し実装した。4（調整数の保持先）は本作業の対象外で未決のままとする。

| 論点 | 決定 |
| --- | --- |
| 2.8-1 保持方式 | **列で持つ**。`SummaryRealStock.ReserveQty` に加え、月次の `SummaryStock.ReserveQty` も追加する（`SummaryStock` は `SummaryRealStock` の派生クラスなので定義は1箇所） |
| 2.8-2 引当対象の `Kubun` | **全 `EnumHaibun` を対象**とする。`Hatsukai` も含める。`Kubun` では判定せず `EndFlag` だけで判定する |
| 2.8-3 解除条件 | **`TranHaibun.EndFlag` を新設し、`EndFlag = 1`（振り分け後入庫済み）で解除**する。`KakuteiDay` / `RelateNo2` / `SendFlg` は引当の判定に使わない |

集計の定義。

- `SummaryStock.ReserveQty` = `substr(DenDay,1,6)` + 倉庫 + SKU 単位の、`EndFlag = 0` の `TranHaibun.Su` 合計。
- `SummaryRealStock.ReserveQty` = 倉庫 + SKU 単位の、**全月**の `EndFlag = 0` の `TranHaibun.Su` 合計。
  `SummaryStock` の月次合計ではなく `TranHaibun` から直接引く。`SummaryRealStock` の再作成は
  「`SumMonth <= 対象年月`」で打ち切るため、未来日付の配分指示が引当から漏れるのを避けるため。

更新方式は**差分の加減算ではなく対象キーの引き直し**とする。`ITranSoko` 系の在庫計算（旧値の反転→新値の加算）と異なり、
影響キーについて `TranHaibun` から `ReserveQty` を再集計する。累積値ではなく「現時点の引当残」なので引き直しが常に正解になり、
通常更新値とRebuild値が原理的に一致する（2.8-3 が求める「二重計上しない順序」は、順序に依存しないことで満たす）。
修正時は修正前と修正後の両方のキーを渡す。

### 2.2 引当数・有効在庫

`SummaryRealStock` と `SummaryStock` に引当数列を追加する。**2026-08-15 に `ReserveQty` として実装済み**（詳細と決定内容は 2.8.1）。

### 2.3 掛更新の実行契約

売掛・買掛は伝票保存時には更新しない。月次再集計バッチで更新する。

- 夜間の月次再集計で在庫更新と併せて売掛・買掛更新を実行し、リアルタイム性は求めないが翌日には整合する状態を受入条件とする。
- 現行 `SchedulerService.ExecuteMonthlyResummaryCoreAsync()` は、在庫・売掛・買掛を前月、当月の順に既に実行している。この構造を維持する。
- 請求・支払集計を追加した場合は、消込結果を含めた後続区分として同じ夜間ジョブへ組み込み、失敗時は対象区分・対象年月を自動実行履歴とログに残す。

### 2.4 発注・受注残の強制完了

`Tran13Hachu`（発注）及び `Tran12Jyuchu`（受注）へ `EndFlag` を追加する。

- `EndFlag = 0` を未完了、`EndFlag = 1` を強制完了とする。
- 発注残・受注残の照会と完了設定画面は、強制完了の行を残計算・未完了一覧から除外する。
- 完了の取消可否、操作社員・操作日時の監査列の要否は詳細設計で決める。

### 2.5 納品予定日

納品予定日は、確定した配分日とは別の、発注・受注に対する目安のリードタイムとして扱う。

- `TranHaibun.NouhinDay` を発注・受注の納品予定日に流用しない。
- 予定日を保存する列を発注／受注のヘッダ又は明細のどちらへ置くか、リードタイムの基準（仕入先、商品、又は個別伝票）と併せて詳細設計で決める。
- 既存の発注残管理表・仕入未受リストは、予定日未導入中の代替照会として維持する。

## 3. 在庫調整の決定

在庫調整は棚卸の実在庫とは別の業務として扱う。`SummaryRealStock` 又は `SummaryStock` を更新する設計を採用する場合、既存の通常更新・範囲Rebuild・全件Rebuildも必ず同時に変更し、調整値を失わないことを必須とする。

調整専用伝票（例: `Tran61Chosei`）を新設する案を採用する。

- 調整伝票から `Su` と `AdjustQty` を再生成する。`SummaryRealStock` を直接更新する処理は持たない。
- 棚卸の `StocktakeDdate`／`ActualQty` と調整数を混同しない。範囲Rebuild・全件Rebuildは、調整伝票由来の調整数を再計算する。
- 調整伝票の追加・修正・削除は、既存の在庫伝票と同様に、旧値の反転と新値の加算で `SummaryStock`／`SummaryRealStock` に反映する。
- 調整伝票には、調整日、倉庫、SKU、増減数量、調整理由、操作社員を保持する。取消は伝票の削除又は訂正として履歴を残す方式を詳細設計で確定する。
