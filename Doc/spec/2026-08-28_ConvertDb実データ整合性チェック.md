# ConvertDb.cs / ConvertDbTran.cs 実データ整合性チェック（2026-08-28）

## 目的・方法

`CvDomainLogic/ConvertDb.cs`・`CvDomainLogic/ConvertDbTran.cs` の変換ロジックが、cv-oracle 経由で参照できる実データ（スキーマ `CV163`、現在接続中）と整合しているかを確認した。区分値の分布など変換元にほぼ現れない値については、比較用に `cv52` スキーマも参照した。

- 接続先: cv-oracle（読み取り専用）
  - 既定スキーマ = `CV163`（本番相当の実データ。生地資材・区分2の10/20実績なし等、他社と分布が異なる）
  - `cv52` スキーマ = 比較用の別テナントデータ

## 重大な問題

### 1. 消費税額の算出が実データと矛盾している（CalcMigratedTaxTotal）

`ConvertDbTran.cs` の `CnvTran00HonUri` / `CnvTran01TenUri` / `CnvTran03Shiire` / `CnvTran12Jyuchu` / `CnvTran13Hachu` は、いずれも「旧『掛率1』は実質すべて消費税率(%)が入っている」という前提で `CalcMigratedTaxTotal(kingakuTotal, 掛率1)` を使い、税額・合計を算出している。

しかし実データでは:

- `HC$tran_tori0.掛率1` の値は伝票処理区分ごとに **`0` / `60` / `100`** のような値しか取らず、消費税率らしい値（8, 10 等）は一切現れない（例: 伝票処理区分=1（店舗売上）は `0` または `100` の2値のみ、347万件）。
- 一方 `HC$tran_tori0` には **独立した `消費税率` 列**が存在し、こちらは `0 / 8 / 10` という正しい消費税率が入っている（伝票処理区分=1で 8%:465,408件, 10%:2,961,077件など）。
- さらに伝票処理区分=1では `外税消費税` 列にも実額が入っており、`外税消費税 / 明細金額合計` を計算すると **常に約8%または10%**（実測サンプルで9.78〜10.00%）と、まさに正しい消費税額になっている。にもかかわらず対応する行の `掛率1` は常に `100` である。

つまり `掛率1` は消費税率ではなく（内容は不明だが、値の出方から見て「課税/非課税」に近いフラグ、もしくは掛率とは別系統の値）、`CalcMigratedTaxTotal` は **実際の消費税額列（`内税消費税`/`外税消費税`）や、正しい税率を持つ `消費税率` 列を一切参照せず、無関係な `掛率1` を100%として税額計算している**。この結果、店舗売上（区分1）では移行後の `Tax`/`Total` が実際の約10倍（`掛率1=100` → 税率100%扱い）になっている可能性が高い。

比較として `CnvTran02Material`（伝票処理区分=2）は同じ問題を認識してか `内税消費税 + 外税消費税` を直接使っており、そちらは実データと整合する設計になっている。00/01/03/12/13 系だけこの矛盾したロジックが残っている。

**確認用SQL**
```sql
-- 掛率1 の値の分布（消費税率らしくない値のみ）
select 伝票処理区分, 掛率1, count(*) from HC$tran_tori0
 where 伝票処理区分 in (0,1,3,10,11,12,13) group by 伝票処理区分, 掛率1;

-- 独立した消費税率列（0/8/10が正しく入っている）
select 伝票処理区分, 消費税率, count(*) from HC$tran_tori0 group by 伝票処理区分, 消費税率;

-- 実際の外税消費税から逆算した税率（掛率1とは無関係に約8-10%になる）
select 掛率1, 明細金額合計, 外税消費税,
       round(外税消費税/nullif(明細金額合計,0)*100,2) taxpct
  from HC$tran_tori0 where 伝票処理区分=1 and 外税消費税<>0 and rownum<=20;
```

**推奨対応**: `消費税率`列・`内税消費税`/`外税消費税`列が入っている伝票種別についてはそちらを正として採用し、`掛率1`ベースの `CalcMigratedTaxTotal` は使わない（または `掛率1` の本当の用途を業務担当に確認してから設計し直す）。すでに一括更新済みとされている `IsPay` 固定運用（後述）と同様、影響範囲（過去移行済み件数）を洗い出した上で再移行が必要になる可能性が高い。

### 2. カラム名の不一致による無言のデータ消失

`getString(rec, key)` は該当キーが辞書に無くても例外を出さず空文字を返す実装のため、ソース側カラム名の誤りに気付きにくい。実データで下記の不一致を複数確認した（いずれも該当フィールドが常に空になる）。

| 変換先 | コード上の参照キー | 実際のカラム名 | 影響 |
|---|---|---|---|
| `MasterSysman.BankAccount1/2/3`（`CnvMasterSys`） | `"振込先1"` `"振込先2"` `"振込先3"` | `振込金1` `振込金2` `振込金3`（`HC$MASTER_SYSKANRI`） | 自社振込先情報が常に空 |
| `MasterTokui.Jdetail.BankAccount1/2/3`（`CnvMasterTokui`） | `"振込先1"` `"振込先2"` `"振込先3"` | `振込金1` `振込金2` `振込金3`（`HC$MASTER_TOKUI`） | 得意先の振込先情報が常に空 |
| `MasterEndCustomer.Tel`（`CnvMasterEndCustomer`） | `"TEL"` → 空なら `"TEL2"` | `TEL1` `TEL2`（`HC$MASTER_KOKYAKU`。`"TEL"`列は存在しない） | `TEL1`（メインの電話番号）が常に失われ、`TEL2`のみ採用される |
| `MasterShain.Kana`（`CnvMasterShain`） | `"フリカナ"`（清音カ） | `フリガナ`（濁音ガ、`HC$MASTER_SHAIN`） | 社員のフリガナが常に空 |

※ 対照として `MasterShiire`（`CnvMasterShiire`）の振込先は `振込銀行`/`振込支店`/`振込種別`/`振込口座` を個別に組み立てており、こちらは実カラム名と一致していて問題なし。

**確認用SQL**
```sql
select column_name from user_tab_columns where table_name='HC$MASTER_SYSKANRI' and column_name like '%振込%';
select column_name from user_tab_columns where table_name='HC$MASTER_TOKUI'    and column_name like '%振込%';
select column_name from user_tab_columns where table_name='HC$MASTER_KOKYAKU'  and column_name like '%TEL%';
select column_name from user_tab_columns where table_name='HC$MASTER_SHAIN'    and column_name like '%フリ%';
```

**推奨対応**: 上記4項目のキー名をそれぞれ実カラム名に修正する。また `getString` が「キー不在」と「値が実際に空」を区別できない現状の実装は、今回のような単純な命名ミスを検知不能にしている。変換対象カラムをホワイトリスト化した際にキー不在を警告ログに出す、あるいは変換前に必須カラムの存在チェックを行う仕組みの追加を検討したい。

## 確認したが問題なし（気になったが実データと整合していた点）

- **伝票処理区分=2（生地・付属仕入）の取引区分**: 本番データ（`CV163`）では実績が **30(値引)・99(その他)のみ**（10/20の実績なし）。`cv52` スキーマでは 10(仕入)・99 が存在する。`CnvTran02Material`/`BuildMaterialMeisaiList` は10/20/30/99の全区分に対応済みであり、テナントごとの分布差異があっても問題ない。また `HC$MASTER_SHKIJI`（生地資材マスタ）自体が0件のテナントであり、区分30/99のプレースホルダのみで実際の資材コード参照が発生しない点も整合している。
- **T18（調整理由）⇔ CHR のコード対応**（`CnvTran61Chosei`）: `HC$MASTER_MEISHO`（名称区分='T18'）のコードは `10,20,21,22,23,29` の6件。実データの伝票処理区分=18のヘッダ`取引区分`・明細`明細取引区分`は共に `10,20,22,23,29`（21は未使用）で、ヘッダとの一致率は検証した範囲で **7,045/7,045件= 100%一致**。ヘッダ単位で `Id_Riyu` を決めている設計で問題ない。
- **KINコード対応表**（`KinKubunCodeMap`、入金・支払明細）: 実データの `明細取引区分` は `80,82,85,88,89` の5種のみで、対応表がすべてカバーしている。
- **店舗売上の「顧客TEL」列が実は顧客CDを格納している仕様**（`CnvTran01TenUri`）: `HC$tran_tori0.顧客TEL` を `HC$MASTER_KOKYAKU.顧客CD` に結合すると **2,417,832/2,417,868件（99.9985%）が一致**。設計通りで、未一致はマスタ削除等による自然なノイズと判断できる範囲。
- **`掛率`・`セール掛率`等の小数点以下**: `HC$MASTER_TOKUI.掛率` は `NUMBER(6,3)` だが実データは `60` `100` の整数値のみで、`getDataInt` による切り捨てでも実害はない。

## ドキュメントと実データの乖離（要確認）

`CnvTran03Shiire` のコメントには「Tran03Shiireの移行済み25件も同様に1へ一括更新済み」とあるが、実データでは伝票処理区分=3（仕入）が **8,602件**存在する（うち `掛計上FLG=1` は全8,602件で、たまたま `IsPay=1` 固定と結果的に一致している）。コメントの「25件」は現在の実データ規模と大きく異なっており、コメント作成時点より後に本番データが積み増しされた、または別環境を指している可能性がある。実害は無い（現状の実データでは`掛計上FLG`が既に全件1のため固定値と一致）が、今後 `掛計上FLG=0` の仕入データが混入した場合に無条件で `IsPay=1` に上書きされる点は認識しておく必要がある。

## まとめ・優先度

1. **最優先**: 消費税額算出ロジック（`CalcMigratedTaxTotal`と`掛率1`の扱い）の見直し。実データでは店舗売上を中心に税額が実態と大きく乖離する可能性が高い。
2. **優先**: カラム名不一致4件（振込先/振込金 ×2、TEL/TEL1、フリカナ/フリガナ）の修正。
3. 参考: `getString`のキー不在検知の仕組み化、`CnvTran03Shiire`コメントの実データ件数更新。
