# CvWpfpos 強化計画

調査日: 2026-11-05
調査対象: CV10 `1425b764`、CVPOS32 `28fc40e`
位置付け: 現行ソースの限定比較に基づく提案。実装・業務仕様の承認を意味しない。

## 1. 目的と前提

CVPOS32 の店舗運用を参考に、CvWpfpos の会計継続性、操作性、店舗業務への対応を段階的に強化する。CVPOS32 には顧客別・設定別の分岐があるため、画面や処理を一律に移植せず、対象店舗の要件を決める。調査は代表的な画面・処理に限定しており、機能の完全な棚卸しや実機確認は未実施。

既存のサーバ確定方式を維持する。売上・返品の単価、税、合計と精算値はサーバで確定し、保存済み伝票をレシートに使用する。返品明細は正値で保持し、集計には `CalcFlag` を使う。POS の標準 CRUD 経路と既存の再送・取消・精算の判断は [設計判断記録 §2.18](2026-09-28_設計判断記録.md) を基準とする。

## 2. 現状比較と改善候補

| 領域 | CVPOS32 の参考箇所 | CvWpfpos の現状 | 提案・優先度 |
| --- | --- | --- | --- |
| 会計の復旧 | `SalesPosViewModel` の売上・入金処理 | `PosUriageInputViewModel` は会計開始時に取引IDを作成。同一IDの再送はサーバ側で既存伝票を返すが、応答不明時の表示は一般的なエラー・中止表示で、会計を開き直すと新IDになる。 | **P0** 応答不明を独立状態にし、同じ取引IDによる結果照会・復旧を設計する。再送前に送信内容の一致も確認する。 |
| 保留 | `SalesPosViewModel.SaveHoryuData/GetHoryuData`、`HoryuListViewModel` | 売上画面の `HoldList` に保持。復元時に現在の明細をクリアし、選択した保留を一覧から取り除いていない。 | **P0** 現在明細の上書き防止、復元後の保留の扱い、返品状態の保持を決定する。**P1** 再起動後の復旧が必要なら保存方式を設計する。CVPOS32 の保留もここでは永続性未確認。 |
| 取消・印字 | `JournalSearchViewModel`、`JournalCancelViewModel`、`PrintReceiptViewModel` | 伝票一覧から POS 売上の取消、レシート・領収書の再印字が可能。会計後の印字失敗も確定済みと表示する。 | **P1** 応答不明・印字失敗から対象伝票の検索／再印字までを店舗操作としてつなぐ。取消時の再送・権限・監査を確認する。 |
| 精算・現金管理 | `SeisanViewModel`、`MoneyInoutViewModel` | レジ別の売上集計、金種入力、精算確定がある。同日・同レジの精算重複はサーバで拒否。 | **P1** 精算応答不明時に登録済み精算を確認する導線を検討。入出金や準備金の運用は要件確認後に追加を判断。 |
| 商品・値引 | `SalesPosViewModel` の商品入力、明細・小計値引 | JAN／SKU検索、数量変更、明細担当・区分指定がある。調査した売上画面には値引入力が見当たらない。 | **P2** 明細・小計値引の必要性と権限、按分・端数・返品・税・在庫・帳票への影響を確定してから設計する。 |
| 決済 | `SalesPosViewModel`、`CafisArchViewModel`、`PaymentAlipayViewModel` | 現金・カード・その他の金額入力と複合支払がある。調査範囲では外部決済端末との連携は確認できていない。 | **P2** 実際に使う金種と端末を選定し、決済成功後の売上失敗・取消・照合の責任分界を先に決める。 |
| 顧客・ポイント・取置 | `CustomerSearchViewModel`、`PointModifyViewModel`、`ToriokiListViewModel` | 調査した POS 画面に専用導線は見当たらない。CV10 側の関連基盤の適用範囲は未調査。 | **P2** 必要店舗・顧客識別・残高・失効・返品時の戻し・取置期限を棚卸しする。 |
| 免税 | `InboundInputViewModel`、`MenzeiScanView` | 調査した POS 画面に免税入力・外部送信の導線は見当たらない。 | **P2** 適用する制度、Pie 等との契約・送信／取消・障害回復・個人情報管理を別途確認する。旧実装を現行制度の根拠にしない。 |
| 周辺機器・画面 | `ClassPrint` と各入力画面 | Epson プリンタ・客用表示機、レシート印字、画面リソースがある。 | **P1** 対象機器・用紙・画面解像度・タッチ／キーボード操作を実機で確認し、切断・再接続・印字失敗の復旧を改善する。 |

P0 は取引喪失・重複を防ぐ基盤、P1 は店舗運用の成立確認、P2 は採用範囲を判断する機能拡張。優先度は提案であり、必須機能は店舗ごとに確定する。

## 3. 段階別計画と受入条件

### Step 0: 店舗要件と基準の確定

- 対象店舗、端末台数、金種、機器、ネットワーク、営業時間、必須帳票と CVPOS32 の顧客別設定を確認し、機能一覧を「必須・任意・対象外」に分類する。
- CVPOS32 の実際の利用設定・操作手順と CV10 の関連サーバ／データ契約を確認する。現行運用との差異と移行対象を記録する。
- 受入条件: 対象店舗と必須業務、既存データの扱い、未決事項と判断者が明確になっている。

### Step 1: 会計・保留の安全な復旧

- 会計の送信前・送信中・確定・応答不明を区別する。取引IDと送信内容を復旧可能に保ち、結果確認・同一ID再送・再起動時の復旧方法を設計する。取消操作や画面再入場で新IDが発行される場合の二重計上を防ぐ。
- 保留復元時の既存明細の扱い、復元済み保留の削除・再保留、返品モードと明細区分を整合させる。永続化の範囲・保存先・障害時の復旧は業務判断後に決める。
- 受入条件: サーバ確定前後の通信切断、応答欠落、キャンセル、再起動、同一ID再送、二重操作でも伝票・在庫が二重計上されず、保留と入力中明細が意図せず消失・重複しない。画面で未確定と確定済みを判別できる。

### Step 2: 精算・印字・操作の実運用

- 精算応答不明時は店舗・営業日・レジで登録済み結果を確認できるようにし、既存の二重精算拒否を維持する。確定後の売上・取消の扱いは現行サーバの制約と店舗運用を確認して決める。
- レシート再印字、領収書、返品・取消、機器切断／再接続、営業日切替、担当者交代を含む一連の操作を確認する。
- 受入条件: 現金・カード・その他の複合支払、釣銭、返品、取消を含め、レジ別集計と保存値・印字値が一致。精算済みか不明な場合も重複確定せず復旧できる。対象機器で印字と再印字を確認する。

### Step 3: 採用する業務機能を個別設計

- Step 0 で採用した値引・金種・決済端末・顧客／ポイント・取置・免税を個別に設計し、店舗ごとに段階導入する。
- 各機能で UI → gRPC → サーバ検証 → 保存・副作用 → 帳票・精算を追跡する。外部連携は実行キー、状態遷移、重複・応答不明・取消・照合を定義する。
- 受入条件: 仕様・権限・保存契約・移行・取消・競合・途中失敗・再実行・運用手順が承認され、専用 DB と対象外部環境で正常系／境界値／異常系を検証する。

## 4. 検証・導入方針

- `Doc/test/UatPos` を基点に専用 DB・専用サーバで確認する。既存 README は売上・再送・返品・取消・レジ別精算・在庫照合を対象としているが、今回の調査では再実行していない。画面の目視、認証を有効にした接続、実機・印字は別途実施する。
- 切断の発生位置をサーバ保存前／保存後・応答前／印字中に分け、取引数・伝票・在庫を独立に照合する。精算は営業日×店舗×レジで照合する。
- 新旧 POS で同一の固定データ・操作を実施し、合計、税、釣銭、返品、取消、精算、帳票を比較する。差異は仕様差か不具合かを判断する。
- 試験店舗・限定端末で導入し、未確定取引・保留・外部決済・免税送信の復旧手順と旧端末への切戻し条件を準備する。DB 変更が必要な機能は新規 DB と旧 DB 複製の移行・復元を検証する。

## 5. 実装前に決めること

1. 対象店舗と CVPOS32 の必須機能・顧客別設定、優先順位。
2. 応答不明の会計を誰が照会・再送・取消できるか、端末障害時にどこまで復旧するか。
3. 保留の永続期間・共有範囲・復元後の削除、返品保留、価格変更時の扱い。
4. 値引・返品・精算後の取消、金種・入出金、税・端数・権限の業務ルール。
5. 外部決済・免税の契約、送信／取消の責任分界、個人情報の保存期間と障害時の運用。
