## 2. 確定仕様

### 2.1 基準日の解決

```
TanaDay = Tran60TanaDate.TanaDay          （店舗別 yyyyMMdd）
          未設定(19010101) の場合は フォールバック計上月の DayTo
shime   = MasterSysman.ShimeBi            （自社締日 1-28 / 99=末日、全社共通）
M       = ClosingMonthCalculator.CalculateKakeMonth(TanaDay, shime)   … 計上月 yyyyMM
DayTo   = ClosingMonthCalculator.GetPeriod(M, shime).DayTo            … 計上月の最終日
```

- **月境界は暦月ではなく自社締日基準の計上月**。締日20日なら `TanaDay=2026/08/25` の計上月は `202609` になる。
  これは仕様として正とする（8月下旬の棚卸が9月計上になる）。**誤解を避けるため、開始・確定画面に計上月を列として表示する。**
- 未設定店舗は月末フォールバックにより、既存の月末一括運用がそのまま動く。
  `ClosingDaySet` の「`Shime1=0` なら自社締日へフォールバック」と同型のパターンを踏襲する。

### 2.2 帳簿在庫（日次）— 逆算方式

```
BookQty(店舗, SKU)
  = Σ SummaryStock.Su   WHERE SumMonth <= M                        … 計上月末時点の累計（既存SQL流用）
  − Σ 伝票の在庫増減     WHERE DenDay > TanaDay AND DenDay <= DayTo  … 基準日より後の分を戻す
```

`SummaryStock` が計上月末時点の在庫を持っているので、そこから基準日より後の伝票を差し引いて基準日時点へ戻す。

**採用理由**

- 既存の月次累計SQL（`StocktakeDb.cs:76-83`）をそのまま流用でき、Rebuild との整合も崩れない。
- 走査対象が「当該計上月かつ基準日より後」に限定される。棚卸日は月末寄りが通常なので、
  月初から積み上げる方式より対象行が少ない。
- **`SummaryStock.CumulativeSu` は使わない。** 書き手 `CalcSummaryStockCumulative`（`SummaryDb.cs:656-690`）は
  本番経路から呼ばれておらずテストからのみで、メソッド上のコメントも「不要と思われる」（`:652-653`）。
  実運用で最新化されている保証がないため土台にできない。

**逆算対象の伝票と符号**

在庫に効くのは7クラス（`SummaryDb.cs:218-226`）。符号は `TranCalcBase.GetCalcSoko` / `GetCalcIdosaki` /
`GetCalcAdjust`（`CvBase/BaseDb2Trans.cs:82-167`）が返す値をそのまま使う。**符号表を再定義せず既存メソッドを呼ぶ。**

| 伝票 | `Id_Soko` 軸 Su | `Id_Ido` 軸 Su | 備考 |
|---|---|---|---|
| `Tran00Uriage` | −1 | — | 出庫 |
| `Tran01Tenuri` | −1 | — | 出庫 |
| `Tran03Shiire` | +1 | — | 入庫 |
| `Tran05Ido` | −1 | +1 | 移動（即時） |
| `Tran10IdoOut` | −1 | 0（Transitのみ +1） | 移動出庫 |
| `Tran11IdoIn` | 0 | +1（Transit −1） | 移動入庫 |
| `Tran61Chosei` | +1 | — | `AdjustQty` へ積む |

- ヘッダ単位の符号反転 `t.CalcFlag`（返品等）を必ず掛ける。
- `MasterTokui.IsZaiko=0` / `MasterShohin.IsZaiko=0` は集計除外（`CreateSummaryStockSql` と同条件）。

**実データによる検証（2026-09-05）**

`CvServer/server-user163.db`（自社締日=末日）で、倉庫113/253/284 × 3ヶ月の計 **61,196 SKU** について
逆算と順算（前月末累計＋月初からの積み上げ）を突き合わせた。この一致は
`SummaryStock.Su(当月) == Σ伝票(当月)` と同値であり、上表の伝票集合と符号が
`SummaryStock` を作った側と一致していることの検証になる。

| 条件 | 結果 |
|---|---|
| `IsZaiko` 除外条件なし | 不一致 **0件** |
| `IsZaiko` 除外条件あり | `MasterShohin.IsZaiko=0` の商品のみ不一致（倉庫113/202204で10件、倉庫253/202203で1件） |

不一致の原因は、`IsZaiko=0` の商品の `SummaryStock` 行が **14,066件** 残っていること。
これは過去の更新ロジックで作られた行であり、現行仕様では `IsZaiko` を見るのが正しい。
Rebuild を通せば当該行は落ちて整合する。**つまり不一致は保存済みデータの陳腐化であって
逆算ロジックの誤りではない**ため、除外条件は `CreateSummaryStockSql` と同一に保つ。

**実装上の落とし穴**: CTE(`WITH`)で書くと NPoco の `Fetch<T>(sql, args)` が
「SQLが `SELECT` で始まらなければ `SELECT ... FROM <テーブル名>` を前置する」挙動により
SQLを壊す（`near "Cum": syntax error`）。派生表で書いて `SELECT` 始まりにする。

**移動中(`TransitQty`)の扱い**

`TransitQty` は `Su` の外側の内訳列であり、帳簿在庫の加減算には使わない。**移動中の現物は実地棚卸で数えられない**ため、
これは業務的にも正しい：移動出庫の時点で発側の `Su` は既に減り、着側は入庫確定まで増えない。つまり移動中在庫は
どちらの倉庫の実棚にも現れず、帳簿在庫にも含まれないので**差異を生まない**。`TransitQty` は棚卸処理では読み書きしない。

**引当(`ReserveQty`)の扱い**

`TranHaibun` のみを源泉とし在庫計算とは独立（`BaseDb3Summary.cs:51-58`）。帳簿在庫（`Su`）とは無関係なので棚卸処理では扱わない。

### 2.3 実棚数

```
ActualQty(店舗, SKU) = Σ Tran60Tana WHERE Id_Soko = 店舗 AND DenDay = TanaDay
```

- `TanaDay` との**厳密一致**。棚番違いの複数伝票は合計する。
- 棚卸伝票が無いSKUは「実棚0」ではなく「数えていない」なので `ActualQty = BookQty` とし差異0にする（現行踏襲）。
- 基準日以外の日付で入力された棚卸伝票は集計されない。**運用ミスを検知できるよう、差異問合せ・チェックリストで
  「基準日以外の棚卸入力あり」を確認できるようにする**（Step 8）。

### 2.4 調整伝票と記録

```
Tran61Chosei { DenDay = TanaDay, TanaMonth = M, EnKubun = Tanaoroshi,
               Su(明細) = ActualQty − BookQty }     … 店舗ごとに1伝票、差0のSKUは明細に含めない
SummaryStock.StocktakeDdate = TanaDay        （8桁、B-1 の是正）
Tran60TanaDate.FixDay       = 確定処理の実行日 （新規に書き込む）
```

調整伝票の計上月は `DenDay=TanaDay` から既存の自社締日ロジック（`CreateKakeMonthSql`）が自動決定するため、
`SummaryStock.SumMonth = M` と一致する。在庫恒等式 `Su = InQty + OutQty + AdjustQty` は維持される。

### 2.5 再確定要否の判定（F0''）

```
再確定要 = ∃ 伝票 ( Id_Soko = 店舗 AND DenDay <= TanaDay AND Vdu > FixDay )
```

`FixDay` に確定実行日が入ることで初めて成立する判定。基準日以前の伝票が確定後に修正されたら当該店舗を
「再確定要」として一覧に表示する。旧CV.netの「確定処理後に過去の伝票を訂正した場合は再度確定の表示がでます」に対応する。

### 2.6 対象店舗

- `MasterTokui` の `TenType in (0,3,6)`（倉庫/売仕店/直営店）かつ `IsZaiko=1`。
  棚卸日一括メンテナンス（`StockDateBulkMenteViewModel.cs:274`）と同条件に統一する。
- HHT変換の `ResolveSoko`（`HhtProcessUpdateMap.cs:590`）は `(0,6)` のみで売仕店(3)を落としており不整合。`(0,3,6)` へ是正する。

### 2.7 スキーマ変更

**なし。**`Tran60TanaDate` の一意キーが `Id_Shop` 単体＝同時に有効な `TanaDay` は店舗あたり1つなので、
既存の `SummaryStock`(SumMonth, Id_Soko, SKU) 行がそのまま各店舗のスナップショット置き場になる。
過去分の棚卸日履歴は `SummaryStock.StocktakeDdate` 列に残る。

## 4. 判断済み事項

### 決定: 欠落行の補完は INSERT + UPDATE の2文で行う（UPSERTを使わない）

B-3 の是正として、棚卸開始処理で `SummaryStock` に行が無いSKUを補う。補うべき対象は2種類ある。

- (a) 計上月Mまでの累計在庫が非0だが、当月Mに動きが無く行が存在しないSKU
- (b) 基準日の棚卸伝票にあるが `SummaryStock` に行が無いSKU

`ON CONFLICT ... DO UPDATE` によるUPSERTではなく、**欠落行を作る `INSERT ... SELECT ... WHERE NOT EXISTS` と、
値を入れる `UPDATE` の2文**に分ける。

- どちらも集合演算1文であり行ごとの往復が無いため、UPSERTとの性能差は文が1本増える分に留まる。
- 欠落行の抽出は anti-join になるが、`unq1(SumMonth, Id_Soko, Id_Shohin, Id_Col, Id_Siz)`（`BaseDb3Summary.cs:67`）の
  一意インデックスで解決される。
- **`ON CONFLICT` は SQLite 固有構文で方言変換に依存する**のに対し、`INSERT ... SELECT WHERE NOT EXISTS` と `UPDATE` は
  4方言すべてで素の構文のまま通る。B-2（方言未対応）の是正と方向が一致する。

### 決定: 補完した行と Rebuild の関係 — 案A（Rebuild後に棚卸開始を再実行する運用）

行補完により **Rebuild との衝突**が生じる。`CalcSummaryStockRange`（`SummaryDb.cs:181-273`）は対象期間の
`SummaryStock` を DELETE して7伝票から作り直すため、(a)(b) で作った「伝票の裏付けが無い行」は Rebuild で消える。
また非Tran列の復元対象は `CumulativeSu` / `StocktakeDdate` / `ActualQty` のみで **`BookQty` は復元されない**（`:228`）。
つまり現行実装でも「Rebuild すると `BookQty` は失われる」状態であり、行補完でこの範囲が広がる。

**採用: 案A。** Rebuild後は棚卸開始処理を再実行する運用手順とする。`SummaryStock` の構造には手を入れない。
棚卸開始処理は冪等で何度でも再実行できる設計（`StocktakeDb.cs:63-65` のコメント）なので運用上成立する。

**ただし運用者が黙って踏まないよう、関連画面に注意を明示する**（Step 7 / Step 8 の実装対象）:

| 画面 | 表示する注意 |
|---|---|
| 棚卸開始処理 | 「在庫再集計(Rebuild)を実行した後は、本処理を再実行してください。帳簿在庫のスナップショットは再集計で失われます」 |
| 棚卸確定処理 | 同旨。加えて開始処理が未実行/失効の可能性がある店舗を一覧で判別できるようにする（`StocktakeDdate` が基準日と不一致なら「開始未実行」） |
| 在庫再集計（Rebuild）系画面 | 「棚卸中の店舗がある場合、再集計後に棚卸開始処理の再実行が必要です」 |

確定処理側の「開始未実行」判定は `SummaryStock.StocktakeDdate <> TanaDay` で機械的に出せるため、
案Aの弱点（帳簿在庫が黙って消える）は画面表示で埋められる。

### 決定: 基準日以外に入力された棚卸伝票 — 警告＋日付補正の確認

`DenDay = TanaDay` 厳密一致とした結果、基準日以外の日付で入力された棚卸伝票は集計対象から漏れる。
確定処理に実行前チェックを設け、検知したら日付補正まで案内する。

**検知範囲**: 当該店舗の `Tran60Tana` のうち `DenDay` が**計上月の範囲内**（`DayFrom <= DenDay <= DayTo`）かつ
`DenDay <> TanaDay` のもの。計上月の外にある棚卸入力は別の月の棚卸なので対象にしない。

**フロー**:

1. 確定処理を実行すると、サーバが上記の伝票を検出し、件数と日付内訳を返して**確定処理を中断**する
2. クライアントが「基準日以外の棚卸入力が N 件あります。基準日(`TanaDay`)に補正しますか？」を Yes/No で確認する
3. **Yes** → 対象伝票の `DenDay` を `TanaDay` へ更新してから、確定処理を続行する
4. **No** → 補正せず確定処理を続行する（当該伝票は集計されない。警告した事実はログに残す）

**`DenDay` 補正の安全性**: `Tran60Tana` は `ITranSoko` を実装せず在庫を動かさない伝票（`BaseDb2Trans.cs:106`,
`HhtProcessUpdate.cs:325-328`）なので、`DenDay` の更新に在庫側の副作用は無い。影響は棚卸明細表・
チェックリスト（`DenDay` の範囲で検索する帳票）の見え方だけであり、補正後は基準日に揃うため整合が良くなる。

**実装上の注意**: 補正は伝票の書き換えであり、`Vdu`（更新日時）を更新する。§2.5 の再確定要否判定は
`DenDay <= TanaDay AND Vdu > FixDay` なので、補正した伝票が直後に「再確定要」として現れないよう、
補正 → 確定 → `FixDay` 書き込み の順序を1トランザクション内で守る。

### 実装上の作法

- json_each や `ON CONFLICT ... DO UPDATE` を含むSQLは必ず `_db.ExecuteDialect` / `_db.FetchDialect` を通す
  （`SummaryDb.ExecuteAndCounts` と同じ経路）。SQLは SQLite 方言のまま書き、変換は `CvBase/Sql/Rules/` に委ねる。
  既存 `StocktakeDb` の直書きは踏襲せず是正する。
- 符号表をコード内に再定義しない。`TranCalcBase` のメソッドを呼ぶ。
- 店舗ごとに `TanaDay` が異なるため、単一SQLで全店舗を捌かず**店舗ループ**にする。店舗数は数十〜数百規模であり、
  既存のストリーミング進捗（`StartAsyncStream` / `FixAsyncStream`）に載せて件数を報告する。
  トランザクション境界は現行どおり `RunFixInTransaction` の `Serializable` を維持する。
