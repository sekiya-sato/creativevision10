# 請求書印刷：旧cvnet帳票移植 詳細設計

> **注記（2026-09-02）: 本書 4章のCSV列設計は
> `Doc/spec/2026-09-02_月次請求書_適格請求書対応_詳細設計.md` により全面的に置換された。**
> 本書は旧CRSの列名一覧（`refer/printwrk/seikyu-sho-*/d_sql.txt`）を根拠に `itemN` を割り当てていたが、
> qfm が実際にバインドしている用途は d_sql.txt の列名と一致していなかった。
> そのため商品名・住所・繰越金額などが別の欄へ流れ込み、明細単位では商品CDが金額欄へ
> 数値として解釈される不具合が出ていた。正しい対応は上記設計書 3.2 の表を参照すること。
> あわせて「CSVは常に61列」という制約（4.4・2.2）も撤廃し、66列を出力する。
> 本書のそれ以外の記述（画面・様式選択・データ取得の考え方）は有効である。

## 1. 目的・範囲

`CvWpfclient.Views._06Uriage.SeikyuBalanceDetailView` の請求書印刷を、旧cvnet の次の2様式で出力できるようにする。

| 出力単位 | 旧資材 | 新しいフォーム名 |
|---|---|---|
| 伝票単位 | `refer/printwrk/seikyu-sho-denpyo/CVPSK003f.qfm` | `printform/SeikyuBalanceDetailDenpyo.qfm` |
| 明細単位 | `refer/printwrk/seikyu-sho-meisai/CVPSK003_hinf.qfm` | `printform/SeikyuBalanceDetailMeisai.qfm` |

- 上記2つのqfmは**内容を変更せず**、cp932（Shift_JIS）のまま `printform/` へコピーする。変更するのはファイル名だけである。
- 対象は既存の「請求書印刷」画面だけとし、メニュー、請求計算、`SummaryUriSei` のスキーマ、税計算・集計ロジックは変更しない。
- 既存の請求日、得意先範囲、出力対象、入金明細を含める指定を維持する。

## 2. 調査結果と設計上の前提

### 2.1 現行実装

- ViewModel は `SeikyuBalanceDetailViewModel`、現行フォームは `SeikyuBalanceDetail.qfm` である。
- `SummaryUriSei` を請求ヘッダ、`Tran00Uriage` と `Tran06Nyukin` を請求期間内の明細として読む。
- 前回残高は `PreviousBalance`（`SummaryUriSei` を対象期間の開始 `DayFrom` より前で
  `SUM(TotalSales - TotalIn)` した表示専用値）で復元する。
  `Doc/spec/2026-09-02_Summary残高_期間集計化とPreviousBalance_詳細設計.md` により
  `Balance` が繰越を含まない当期間ネットへ変更されたため、旧来の `Balance + TotalSales - TotalIn`
  という逆算式は成立しなくなり、`PreviousBalance` ベースへ置き換えた。
- 税率別内訳の事前検査、10%/8%/非課税の計算、区分99の既存の扱いは維持する。

### 2.2 旧帳票

- `refer/printwrk/seikyu-sho-denpyo/seikyu-insatu_program_crs.txt` は、伝票単位と商品CD単位（本設計でいう明細単位）の**両方**を扱う旧画面プログラムである。実行時にSQLをCSVへ出力し、選択値に応じてqfmを選び、PrintStreamでPDFプレビューを開く。
- CRSの「出力単位」は、伝票単位なら `CVPSK003f.qfm`、商品CD単位なら `CVPSK003_hinf.qfm` を選択する。この対応をCV10の様式選択とフォーム名にそのまま引き継ぐ。
- CRSには別軸の「出力タイプ（親のみ／子明細）」もある。ただし子明細では `CVPSK003_31f.qfm` / `CVPSK003_hin_31f.qfm` を使い、今回指定された参照資材には含まれない。したがって本設計の対象は旧CRSの**親のみ**相当で固定し、「子明細」選択は追加しない。
- 両qfmは `item1` ～ `item69` を持ち、グループキーとJavaScriptに依存する。現行フォームの20列CSVとは互換でない。
- 伝票単位qfmは、`item11` の得意先単位で改ページし、`item53` の請求ヘッダ単位で明細合計を印字する。スクリプトは `item14=6` を入金、`item16=99` を消費税行として扱う。
- 明細単位qfmは、`item53` の請求ヘッダ単位で改ページし、`item57` を伝票内グループとして商品明細を印字する。伝票番号は `item59`、商品欄は `item56`～`item60` を使用する。
- qfmは69項目を定義するが、旧CRSが実際に出力するCSVは61列である。現行の `WriteDynamicCsv` もSELECT列順をそのままCSVへ書くため、新SQLは旧CRSと同じ**61列を常に同じ順序で返す**ものとする。`item62`～`item69` はqfm定義上の未使用予約項目であり、CSV列を追加しない。

## 3. 画面・操作設計

### 3.1 追加する選択肢

既存の「印字明細」行に次のラジオボタンを追加する。

| 表示 | ViewModel値 | 初期値 | フォーム |
|---|---|---:|---|
| 伝票単位 | `IsMeisaiUnit=false` | 選択 | `SeikyuBalanceDetailDenpyo.qfm` |
| 明細単位（旧CRSの「商品CD単位」） | `IsMeisaiUnit=true` | 非選択 | `SeikyuBalanceDetailMeisai.qfm` |

- 「入金明細も印字」は両様式に適用する。未選択なら `Tran06Nyukin` 行をCSVへ含めない。旧CRSは入金を明細行として扱い、qfmスクリプトの `item14=6` で金額欄へ振り分けるため、この制御値を維持する。
- 印刷実行（F6）と既存の入力検証は変更しない。
- `FormFileName` は `IsMeisaiUnit` に応じて上表のフォーム名を返すようにする。基底クラス・code-behindは変更しない。

## 4. データ取得・CSV設計

### 4.1 共通ヘッダ

`SummaryUriSei s` を起点に `MasterTokui t` と自社1件の `MasterSysman c` を結合する。抽出条件は現行どおり以下とする。

```text
s.DenDay = 指定請求日
t.Code = 指定得意先範囲
IsActiveOnly=true の場合: s.TotalSales != 0 OR s.Balance != 0
```

ヘッダには次を設定する。

| 意味 | 値 |
|---|---|
| 前回御請求額 | `PreviousBalance`（`SUM(TotalSales - TotalIn) WHERE DayTo < DayFrom` のCTE。旧 `s.Balance + s.TotalSales - s.TotalIn` は `Balance` の符号・意味変更により廃止） |
| 御入金額 | `s.TotalIn` |
| 今回相殺額 | `s.Offset` |
| 当月御買上額 | `s.TotalSales - (s.Tax1+s.Tax2+s.Tax3)` |
| 消費税計 | `s.Tax1+s.Tax2+s.Tax3` |
| 当月御買上合計 | `s.TotalSales` |
| 今回御請求額 | `PreviousBalance + s.Balance`（当期間ネットの `s.Balance` に前回残高を足した繰越込みの値。旧仕様の `s.Balance` 単独出力は廃止） |
| 支払日 | `s.NyukinYoteiDay` |
| 得意先・自社・振込先 | `MasterTokui` / `MasterSysman` のコード、名称、住所、電話、振込先 |

`SummaryUriSei` は請求計算の確定結果であるため、ヘッダ金額を伝票から再集計しない。税率別内訳の列と事前検査は現行実装をそのまま実行するが、コピーqfmに表示欄がない列はCSVの予約列へ出さない。

### 4.2 伝票単位行

`Tran00Uriage` は `Id_Tokui` と `KakeDay BETWEEN DayFrom AND DayTo` で結合し、1伝票につき1行とする。

| qfm用の意味 | 売上行 | 入金行 |
|---|---|---|
| 種別 (`item14`) | `0` | `6` |
| 区分 (`item16` / `item17`) | `u.Kubun` / 既存の区分名 | `0` / `入金` |
| 日付・伝票番号 | `u.KakeDay` / `u.Id` | `n.KakeDay` / `n.Id` |
| 数量・金額・税 (`item18`～`item20`) | `u.SuTotal` / 伝票本体金額 / `u.Tax1+u.Tax2+u.Tax3` | `0` / `0` / `0` |
| 入金額 (`item24`) | `0` | `n.KingakuTotal` |
| メモ (`item22`) | `u.Memo` | `n.Memo` |

伝票本体金額は現行と同じ `CASE WHEN u.Total != 0 THEN u.Total ELSE u.KingakuTotal + u.Tax1 + u.Tax2 + u.Tax3 END` を使う。`item16=99` の行は旧スクリプトの仕様どおり税額欄を使う。

旧CRSの「親のみ」SQLは売上を伝票ヘッダの先頭行へ畳み、入金は入金明細ごとに出している。CV10では売上ヘッダがすでに1レコードであるため前者は `Tran00Uriage` の1行、後者は `Tran06Nyukin` の1行でそれぞれ再現する。

### 4.3 明細単位行

売上は `Tran00Uriage.Jmeisai` を明細ごとに展開する。

- 明細JSONは `json_valid(u.Jmeisai)` を確認してから `json_each` する。
- 商品コード単位に集約してから出力する。これは旧CRSが `ヘッダNO, 明細取引区分, 商品CD` で `SUM(金額), SUM(数量)` する仕様に合わせるためである。色・サイズまで分ける仕様にはしない。
- 商品コード・名称・数量・金額は既存の `TranMeisaiSql.Str/Num` を使う。色・サイズ名はqfmへ渡さず、商品名のみを既存商品名称欄へ渡す。
- 伝票内グループキー（`item57`）には `u.Id` を設定し、同一伝票の複数商品が一まとまりになるようにする。
- `item59` には `u.Id`、商品名・数量・金額は `item56`、`item58`、`item60` に設定する。
- 明細を持たない売上、または不正JSONの売上も伝票ヘッダを欠落させない。商品欄を空欄とした1行を補い、印刷を継続する。
- 入金は商品欄を空欄にした1行を追加し、伝票単位と同じ `item14=6` の旧スクリプト分岐で印字する。

### 4.4 CSV列契約

> **2026-09-02 に置換**: 下表の割り当ては qfm の実バインドと一致していなかった。
> 現行の割り当てと66列への拡張は
> `Doc/spec/2026-09-02_月次請求書_適格請求書対応_詳細設計.md` 3.2 を参照すること。

両SQLのSELECTは旧CRSと同じ61列（`item1`～`item61`）を順序固定で返す。未使用の列も `''` または `0` を明示して省略しない。

| 範囲 | 内容 |
|---|---|
| `item1`～`item12` | 帳票・請求ヘッダのグループキー、請求日、金額、得意先コード、締日 |
| `item13`～`item26` | 売上／入金の伝票制御、日付、区分、数量、金額、税、メモ、行番号 |
| `item27`～`item51` | 自社・得意先の住所、連絡先、振込先、相殺・請求額、担当者 |
| `item52`～`item61` | 当月金額、商品明細または伝票番号、商品数量・金額、税率表示、入金予定日 |

qfmを変更しないため、既存qfmスクリプトの誤字・旧表示仕様も修正対象外とする。

### 4.5 並び順

- 伝票単位: 得意先コード、請求ヘッダキー、掛計上日、売上→入金、伝票番号。
- 明細単位: 得意先コード、請求ヘッダキー、掛計上日、売上→入金、伝票番号、明細行No。
- 同一請求書の全行でqfmグループキーとヘッダ値を同じ値にする。

## 6. 実装前の互換性確認

コピーqfmには旧JavaScriptと複数グループが含まれるため、実装前に次を先行確認する。

1. 旧qfmと添付 `data.txt` を `tools/qfmprint` で描画し、添付 `data.pdf` のページ数、請求ヘッダ、伝票／商品明細、合計と一致することを確認する。
2. 現行 `PrintPdfService` の `WriteDynamicCsv` が、SELECTの61列順を旧CRSと同じCSVとして渡すことを、固定61列の検証CSVで確認する。
3. 一致しない場合はqfmを編集せず、`QueryListSqlParam` ではなく `PrintByCsvParam` で明示的にCSVを作る案へ切り替える。その切替は本詳細設計の変更として再承認を受ける。

## 7. 検証計画

1. qfmコピーのSHA-256とcp932読み込みを確認し、XML宣言・`item1`～`item69`・JavaScript・グループ定義が元ファイルと同一であることを確認する。
2. 単位テストで、前回残高、当月売上・入金・相殺・請求額、区分99、入金あり/なし、複数商品、空明細、不正JSONを確認する。
3. 実行時に両様式でPDFを出力し、旧参考PDFと比較して、得意先ごとの改ページ、伝票小計、明細の親子表示、金額・税・請求額、空欄行を確認する。
4. `CvWpfclient` と対象テストプロジェクトをビルドし、`git diff --check` を実行する。

## 8. 承認確認事項

- 画面初期値を「伝票単位」とし、利用者が「明細単位」を選択して切り替える仕様でよいか。
- 旧qfmのJavaScript・レイアウト・表示上の既存不備も含め、内容を一切変えずコピーする方針でよいか。
- `item61`～`item69` の画像・未使用予約列は空欄とし、自社ロゴ等を新設しない方針でよいか。
- qfmランタイム互換性確認でSELECT 69列方式が成立しない場合、`PrintByCsvParam` へ切り替える設計変更を別途承認とする。
- 旧CRSの「子明細」様式（親子請求先をROLLUPで集約する仕様）は今回の対象外とする。これを追加する場合は、別qfm資材・請求先集約規則・画面の出力タイプ選択を含む別詳細設計とする。
