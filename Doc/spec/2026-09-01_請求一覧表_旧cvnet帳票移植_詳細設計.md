# 請求一覧表 旧cvnet帳票移植 詳細設計

## 1. 目的

`CvWpfclient.Views._06Uriage.SeikyuListReportView` の請求一覧表を、旧cvnetの
`refer/printwrk/seikyu-ichiran` にある親のみ／子含む帳票、CSV列定義、出力PDFおよびCRSの動作に合わせる。

対象は既存画面の XAML と ViewModel、および帳票qfmの追加だけとする。請求計算、`SummaryUriSei`、サーバーのPDF生成経路、メニュー、code-behindは変更しない。

## 2. 調査結果と移植範囲

| 根拠 | 確認結果 | 設計への反映 |
| --- | --- | --- |
| `seikyu-ichiran_program_crs.txt` | 締日・対象月・請求先範囲・出力基準（請求集計月／入金予定月）・親のみ／子含む・並び順を指定する。 | 本画面は締日、対象月、請求先範囲、出力基準、並び順を持つ。 |
| 同CRS | `親のみ` 時は `cvnet03prn03f.qfm`、`子含む` 時は `cvnet03prn03_ko_f.qfm` を選択する。子含むは親CD・親名および親別のウィンドウ集計を出力する。 | XAMLに親のみ／子含むの選択を追加し、選択に応じてqfmとSQL列数を切り替える。 |
| `d_sql.txt` / `data.txt` | CSVは23列で、ヘッダ無しの1データ行を確認した。 | SQLの先頭23列を旧CSV順に固定する。 |
| `cvnet03prn03f.qfm` | `item1`～`item23`を定義する親のみ用qfm。 | 親単位へ集約したSQLは23列を一意な `item1`～`item23` 別名で返す。 |
| `cvnet03prn03_ko_f.qfm` | `item1`～`item42`を定義する子含む用qfm。`item24`～`item42`は親グループ・親集計の表示に使う。 | 子行SQLは42列を一意な `item1`～`item42` 別名で返す。 |
| `data.pdf` | A4横。請求日・締日、請求先の子行、親単位の集計行、全体合計を印字する。 | qfmは変更せずそのまま使用する。 |
| 現行ViewModel | `SummaryUriSei`を得意先単位で直接出力する11列帳票で、締日・入金予定月・親子・並び順を扱わない。 | SQLと入力項目を旧仕様へ置き換える。 |

旧CRSのCSV保存機能は旧クライアント固有である。現行 `BaseReportViewModel` のPDF出力経路を変更せず、今回はPDF用CSV（`PrintPdfService`内部生成）の列順を合わせるだけで、利用者向けCSV保存機能は追加しない。

## 3. 画面詳細設計

### 3.1 入力状態

`SeikyuListReportViewModel` は次の状態へ変更する。

| プロパティ | XAML表示 | 初期値 | 用途 |
| --- | --- | --- | --- |
| `TargetMonth` | 対象月 | 当月（`yyyy/MM`） | 月初～月末の範囲を作る。 |
| `ShimeDay` | 締日 | `99` | `1`～`28`または`99`（末日）。`MasterTokui.Shime1`と一致する請求集計だけを対象にする。 |
| `IsNyukinYoteiBasis` | 出力基準 | `false` | `false`=請求集計月、`true`=入金予定月。 |
| `PaysakiCodeFrom` / `PaysakiCodeTo` | 請求先 | 空欄 | 親（請求先）のコード範囲。既存の得意先選択ダイアログを利用する。 |
| `IsIncludeChildren` | 印刷区分 | `false` | `false`=親のみ、`true`=子含む。qfmとSQLを切り替える。 |
| `IsPaysakiCodeOrder` | 並び順 | `true` | `false`=出力基準日／相手日／請求先CD、`true`=請求先CD／出力基準日／相手日。 |

- 既存の `SeikyuDayFrom`、`SeikyuDayTo`、`TokuiCodeFrom`、`TokuiCodeTo`、`IsActiveOnly` は削除する。
- 旧CRSと同じく、残高・入金・売上増減のすべてがゼロの行は出力しない。画面に「全て」選択は置かない。
- 印刷区分は旧CRSと同じ「親のみ」「子含む」のラジオボタンとする。初期値は旧CRSと同じ親のみとする。
- PDF出力（F6）とEsc、既存の画面構造・共通スタイルは維持する。code-behindは変更しない。

### 3.2 入力検証

1. `TargetMonth` は `yyyy/MM`、`yyyy/M`、`yyyyMM`、`yyyy-MM` を受け付け、月初・月末を `yyyyMMdd` へ正規化する。形式不正なら既存の警告ダイアログを出してPDF生成を開始しない。
2. `ShimeDay` は `1`～`28`または`99`のみ受け付ける。
3. 請求先コード範囲は既存 `BuildCodeRangeWhere` を用い、From/To逆転時は既存ヘルパーの検証結果に従う。

## 4. SQL詳細設計

### 4.1 データ元と親子判定

主表は請求計算が保存した `SummaryUriSei s` とする。子（得意先）は `MasterTokui c`、親（請求先）は `MasterTokui p` とする。

```sql
LEFT JOIN MasterTokui p ON p.Id = c.Id_Paysaki
```

親IDが未設定（`0`）または不正参照の場合は、`COALESCE(p.Id, c.Id)`、`COALESCE(p.Code, c.Code)`、`COALESCE(p.Name, c.Name)` で子自身を親として扱う。これにより、`Id_Paysaki=0`、自分自身、他得意先を請求先にする既存データを漏らさない。

対象条件は次のとおりとする。

```sql
c.IsPay = 1
AND c.Shime1 = @shimeDay
AND <出力基準日> BETWEEN @monthFrom AND @monthTo
AND <親コード範囲>
AND (
    s.Balance <> 0 OR s.TotalIn <> 0 OR s.TotalSales <> 0
)
```

`<出力基準日>` は `IsNyukinYoteiBasis=false` なら `s.DenDay`、`true` なら `s.NyukinYoteiDay` とする。入金予定日が空欄の行は入金予定月基準では対象外とする。

### 4.2 金額算式

`SummaryUriSei`は請求計算の確定値であるため、伝票・明細JSONを再集計しない。

| 表示項目 | SQL式 |
| --- | --- |
| 前月残 | `s.Balance + s.TotalSales - s.TotalIn` |
| 当月残 | `s.Balance` |
| 現金／振込手数料／手形／相殺／その他 | `s.Cash` / `s.Fee` / `s.Densai` / `s.Offset` / `s.Other` |
| 入金合計 | `s.TotalIn` |
| 売上／返品／値引／その他売上 | `s.Uriage` / `s.Henpin` / `s.Nebiki` / `s.Sonota` |
| 消費税 | `s.Tax1 + s.Tax2 + s.Tax3` |
| 売上合計 | `s.TotalSales`（`Uriage - Henpin - Nebiki + Sonota + Tax`） |
| 繰越金額 | `前月残 - 入金合計` |
| 純売上 | `売上合計 - 消費税` |

残高の符号・金額値は既存の`SummaryUriSei`をそのまま使用する。表示用に正負を反転しない。

### 4.3 親のみの23列CSV契約

親のみでは、4.1の子行を親ID・出力基準日・相手基準日で集約する。item3・item4は解決済み親のコード・名称とし、item5～item23は子行の金額を合計する。親単位で1行になるため、`cvnet03prn03f.qfm`へそのまま渡せる。

| item | 旧CSV列 | 値 |
| --- | --- | --- |
| 1 | 請求日または入金予定日 | 出力基準日 |
| 2 | 締日 | `c.Shime1` |
| 3-4 | 請求先CD・名称 | 解決済み親のコード・名称 |
| 5-18 | 前月残～売上合計 | 4.2の各金額を親単位で合計 |
| 19 | 相手基準日 | 出力基準と反対側の`DenDay`または`NyukinYoteiDay` |
| 20-21 | 列見出し文字列 | `請求日`/`入金予定日`を出力基準に応じて入替 |
| 22-23 | 繰越金額・純売上 | 4.2の算式を親単位で合計 |

### 4.4 子含むの42列CSV契約

`PrintPdfService`はSQL結果の列順をCSVへ書き出すため、全列へ一意な`itemN`別名を付ける。重複した無名列は作らない。

| item | 旧CSV列／qfm用途 | 値 |
| --- | --- | --- |
| 1 | 請求日または入金予定日 | 出力基準日 |
| 2 | 締日 | `c.Shime1` |
| 3-4 | 子の請求先CD・名称 | `c.Code`, `c.Name` |
| 5-18 | 前月残～売上合計 | 4.2の各金額（前月残、当月残、入金5内訳、入金合計、売上4内訳、消費税、売上合計） |
| 19 | 相手基準日 | 出力基準と反対側の`DenDay`または`NyukinYoteiDay` |
| 20-21 | 列見出し文字列 | `請求日`/`入金予定日`を出力基準に応じて入替 |
| 22-23 | 繰越金額・純売上 | 4.2の算式 |
| 24-25 | 親CD・親名 | 解決済み請求先のコード・名称 |
| 26-41 | 親の前月残～純売上 | `SUM(item5～item18, item22～item23) OVER (PARTITION BY parentId, item1)` |
| 42 | 親の相手基準日 | `MAX(item19) OVER (PARTITION BY parentId, item1)` |

SQLは、まず`rows` CTEで`item1`～`item25`相当の子行を作り、外側SELECTでウィンドウ集計の`item26`～`item42`を付与する。ウィンドウのパーティションは親と出力基準日で固定し、旧CRSの `PARTITION BY 親CD, 請求日` に相当させる。

並び順は `IsPaysakiCodeOrder=false` なら `item1, item19, item24, item3`、`true` なら `item24, item1, item19, item3` とする。値はSQL文字列へ固定選択し、利用者入力を連結しない。

## 7. 受入条件と検証

1. 両方のコピー元・先qfmのSHA-256が一致し、cp932で読め、XML rootが`printstream`、item数が親のみ23・子含む42である。
2. 旧`d_sql.txt`の23列と親のみSQLの`item1`～`item23`を列順・算式ともに照合する。
3. 親のみSQLの`AS item1`～`AS item23`、子含むSQLの`AS item1`～`AS item42`が連番・一意で、実データ実行時も各列数と一致する。
4. 単独得意先（`Id_Paysaki=0`）、自己請求先、子あり請求先で、親のみは1親1行、子含むは子行＋親グループと親合計が正しく出る。
5. 請求集計月／入金予定月、2種の並び順、締日、請求先範囲のそれぞれで対象行が変わることを確認する。
6. 旧`data.txt`で親のみqfmをローカル描画し、`data.pdf`とA4横レイアウト・見出し・金額位置を比較する。子含むqfmは、親子の固定42列検証CSVで子行・親合計の位置を確認する。
7. XAMLのXML・バインディング、`CvWpfclient/CvWpfclient.csproj`ビルド、`git diff --check`、CRLFを確認する。

## 8. 承認確認事項

上記の「親のみ／子含む切替」「旧CSV保存機能は追加しない」「対象月＋締日入力への変更」を承認後、ViewModel・XAML・2本のqfmコピーの実装へ進む。
