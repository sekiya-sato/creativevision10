## 1. 旧CV AMS連携の調査結果

### 1.1 全体構成

旧CVの AMS連携は、標準の WMS連携（`Cvnet_Cust02.cs` の `User09ExtCoopWMS*`）をベースに、EC連携の枠組み（`Cvnet_Cust121b.cs` の `User121ExtCoopEC*`）へ「サイトCD=10（AMS）」の分岐として組み込まれていた。

```
            ┌──────── CV.net ────────┐                       ┌── AMS（外部倉庫） ──┐
 マスタ出力  │ PD(商品SKU) / BSY(場所)  │ ── ExtCoop\AMS\Send ──▶ │                     │
 送信       │ ORDER(出荷指示)          │ ── (FtpAMSOut.bat) ───▶ │ 出荷・入荷・棚卸作業 │
            │ STOCK(入荷予定)          │                       │                     │
            │ ZAIKO(在庫)             │                       │                     │
 受信       │ ORDERFIX(出荷確定)       │ ◀── ExtCoop\AMS\Recv ── │                     │
            │ STOCKFIX(入荷確定)       │ ◀── (FtpAMSIn.bat) ──── │                     │
            │ LACK(欠品)              │                       │                     │
            │ INVENTORY(棚卸)          │                       │                     │
            └─────────────────────────┘                       └─────────────────────┘
```

| 機能 | 旧画面（crs） | 旧処理（自動実行番号） | 主な関数 |
|---|---|---|---|
| 連携用マスタデータ作成 | `SubDlg_71_pos1.crs`「外部連携：連携用マスタデータ作成」 | 45 AMSマスタ出力 | `User00AMSMasterout` → `User00ExtCoopAMSMST(kubun="PD"/"BSY")` |
| 連携データ手動送信 | `SubDlg_71_SendManual_EC.crs`「外部連携：連携データ手動送信」 | 12106 入荷予定 / 12108 出荷指示 / 12109 在庫 | `User121ECSendOUT`/`OUT2`/`OUT4` → `User121ExtCoopECSend` → `User00ExtCoopAMSSend{ORDER,STOCK,ZAIKO}` |
| 連携データ受信 | （自動実行が主。手動は同ロジック） | 12105 ECデータ入力 | `User121ECRecvIN` → `User121ExtCoopECRecv` → `Sub1`(ワーク取込) → `Sub2`(検査・反映) |
| WMSエラーデータ照会・再取込 | `SubDlg_71_WMSError.crs`「WMSエラーデータ照会」 | － | `User121ExtCoopECRecvErr` → `ErrRecv`/`ErrRecv2` → `Sub2` |

- 連携先の設定は名称マスタ `名称区分='ECS'`、`名称CD=サイトCD`（`カナ`=格納フォルダ名、`ランク`=FTPバッチ起動FLG）。
- 対象倉庫は **得意先マスタ `倉庫区分=8`（AMS）**（#35350 で標準WMSの対象 `2,3,4,6,7` から 8 を分離）。在庫データだけは変換マスタ `HC$MASTER_CONVERT 区分='AMS'` の `一意CD01`（倉庫CD）で対象を指定。
- 通信は FTP をバッチ（`Ftp{サイト}Out.bat`/`In.bat`）で起動するだけ。結果確認は最大60秒待ちで、失敗しても処理結果には反映されない。

| JANコード1・サイズCD・色CD | JANマスタ |

| 在庫管理区分 | 在庫管理FLG 0→1、1→0（反転） |

| 予備01〜20 | コード + 名称マスタ Y01〜Y20 の名称 |

| 配分ランク01/02・削除FLG・作成日付・作成時刻 | |

### 1.4 送信データ（旧）

**ORDER 出荷指示**（配分 `HC$TRAN_HIBN1` から）

- 対象: `送信FLG=0` かつ `確定FLG=1` かつ 納品日（未設定なら配分指示日）≦前日 かつ 倉庫が `倉庫区分=8`。
- 抽出と同じトランザクションで `送信FLG=1` にする（送達確認はない。再送は FLG を戻す運用）。
- 項目: 区分（`10`=移動／`20`=卸先出荷(店種1)／`30`=倉庫間移動(区分2が15/95で同じ倉庫区分)）、伝票NO、行NO、配分指示日、納品日、倉庫CD、得意先CD、JANCODE、商品CD、原価FLG、色CD、サイズCD、商品シリアル、予定数量、単価、上代単価、下代単価、関連伝票NO、関連伝票行NO、為替区分、ブランドCD、メモ1、業務区分、掛け率、外貨単価。

**STOCK 入荷予定**（取引 `HC$TRAN_TORI0/1` から）

- 対象: `送信FLG=0` かつ 在庫計上日≦前日 かつ 次のいずれか。
  - 伝票処理区分13（発注）で、納品倉庫が AMS倉庫 → 区分`20`（仕入入荷予定）
  - 伝票処理区分10（移動・積送出庫）で、移動先が AMS倉庫 → 区分`10`（移動入荷予定）
- 抽出と同じトランザクションで `送信FLG=1`。
- 項目: 区分、伝票NO(SEQ_NO)、行NO、在庫計上日、納品日、倉庫CD（入荷先）、取引先CD（仕入先／移動元）、SKU・数量・単価類、関連伝票NO、関連伝票NO2、為替区分、ブランドCD、メモ、掛け率、外貨単価。

**ZAIKO 在庫**（全件スナップショット）

- 対象倉庫: 変換マスタ `区分='AMS'` に登録した倉庫。
- 項目: 店種区分、倉庫CD、商品CD、色CD、サイズCD、在庫数（#35039 で**有効在庫=当月在庫−引当**に変更）、移動出中、移動中、ブランドCD。いずれかが正の SKU だけ。

### 1.5 受信データと反映（旧）

受信は「ファイル1本＝1トランザクション」。ワーク `HC$WKS_TORI1` へ全行を取り込み、検査で `エラーFLG=-1` を立て、エラー行を `HC$TRAN_ERRTORI1`（区分=`{種別}_E`）へ退避してから、残りで伝票を作る。

**処理区分（受信ファイルの1列目）と生成伝票**（伝票処理区分は `refer/cvnet-knowlege/伝票処理区分_HHT区分_ﾊﾝﾃﾞｨﾚｲｱｳﾄ3.0.xlsx` で確認）

| 種別 | 処理区分 | 意味 | 旧で生成した伝票 | 付随処理 |
|---|---|---|---|---|
| ORDERFIX | 10 | 配分の出荷（店舗へ） | 移動・積送出庫（10） | 配分 確定数加算・確定日・`完了FLG`（予定=確定+欠品） |
| ORDERFIX | 20 | 配分の出荷（卸先へ） | 出荷売上（0） | 同上 |
| ORDERFIX | 30 | 配分の倉庫間移動 | 移動・即時（5） | 同上 |
| ORDERFIX | 40 | 仕入返品の出荷 | 仕入（3）返品 | 為替換算 |
| ORDERFIX | 50 | EC受注 | 受注（12）→配分自動作成 | ECのみ |
| ORDERFIX | 60 | EC売上 | 店舗売上（1） | 受注番号で配分を消込。ECのみ |
| STOCKFIX | 10 | 移動の入荷 | 移動受（11） | 関連伝票NO＝送信した移動伝票 |
| STOCKFIX | 20 | 仕入の入荷 | 仕入（3） | 関連伝票NO＝送信した発注 |
| STOCKFIX | 30 | 倉庫間移動の入荷 | 移動・即時（5） | |
| STOCKFIX | 40 / 60 | 返品の入荷 | 出荷売上返品（0）／店舗売上返品（1） | |
| LACK | 10〜40 | 配分の欠品 | なし | 配分 欠品数・欠品日、`完了FLG`（予定=確定+欠品） |
| INVENTORY | － | 棚卸結果 | 棚卸（TANA0/1） | 棚番＝ブランドCD列、棚卸年月＝納品日列 |

**検査（ビット指定）**: ORDERFIX `111001`、STOCKFIX `110101`、LACK `101000`、INVENTORY `110010`。

| ビット | 内容 |
|---|---|
| 0 | 商品×色×サイズが JANマスタに無い |
| 1 | 倉庫CD が得意先（仕入返品系は仕入先）に無い |
| 2 | 関連伝票NO の配分が無い、または完了済み |
| 3 | 関連伝票NO の取引伝票が無い |
| 4 | 倉庫CD が得意先に無い |
| 5 | 得意先CD が得意先に無い |

- 1行でもエラーになった伝票（関連伝票NO・倉庫・得意先・処理区分・取引区分・出荷日・納品日が同じ行）は全行エラーにする。
- 伝票のまとめ単位は 処理区分・取引区分・出荷日・納品日・倉庫CD・得意先CD・関連伝票NO・関連伝票NO2（・商品シリアル）。
- 伝票作成後に 消費税・原価・在庫・売掛・買掛・投入日・在庫RK を伝票ごとに再計算。
- 重複受信の防止は、EC受注・売上（処理区分50/60/10）で「同じ関連伝票NO2＋注文番号の伝票が既にあれば除外」だけ。出荷確定・入荷確定の二重取込は防いでいない（配分の完了済み検査で一部だけ弾ける）。

**エラー再取込**: エラー照会画面で行を選び、倉庫・得意先・SKU・数量・単価類を修正して再取込すると、`ERRTORI1` から削除してワークへ戻し、同じ反映処理を通す。

### 1.6 旧仕様の問題点と cv10 での扱い

| 旧の問題・癖 | cv10 での扱い |
|---|---|
| 送信と同時に `送信FLG=1`。送達確認・再送の管理がない | 送信バッチを履歴に残し、`SendFlg` 0→1（ファイル作成）→2（配置完了）で管理。再出力は同じバッチの内容から行う（3.3） |
| 出荷確定・入荷確定の二重取込を防げない | 受信行に送信時の CV 側行ID（配分Id／元伝票Id・行No）を必須にし、適用済み行・完了済み配分は拒否（4.4） |
| 確定・欠品が別ファイルで累積加算（複数回出荷可） | cv10 の配分確定は**1回確定・残り欠品で完了**（決定 D8）。出荷確定1行で確定数を渡し、残りは欠品として完了する（4.4.1） |
| 数量×100、サイズ区分前置、`'.'` 空値 | cv10 既定形式では採用しない。連携先が要求する場合は形式定義（5.1）で変換する |
| 対象倉庫を得意先 `倉庫区分=8` と変換マスタの2か所で指定 | 連携設定の対象倉庫リスト1か所に集約（2.2） |
| エラー再取込の SQL に画面入力の文字列を連結 | 行Idのパラメータ指定のみ。修正は「訂正版の追加」で行い原文を変えない（4.5） |
| EC受注・EC売上・送料・代引き・AMS顧客CD・為替 | 対象外（EC 連携は 10.0 範囲外） |
| FTP バッチ起動 | 対象外。サーバの連携フォルダへの配置／取得までとし、転送は運用または将来の送受信アダプタ（6.3） |

## 2. cv10 仮実装の範囲と前提

### 2.1 範囲

| ID | 画面 | 種別 | cv10 で扱う | 旧の対応 |
|---|---|---|---|---|
| L01 | マスタデータ作成 | 出力 | `PD` 商品SKU、`BSY` 場所（倉庫・店舗・得意先・仕入先） | 45 AMSマスタ出力 |
| L02 | 連携データ手動送信 | 出力 | `ORDER` 出荷指示（配分）、`STOCK` 入荷予定（発注・移動出庫）、`ZAIKO` 在庫 | 12108 / 12106 / 12109 |
| L03 | 連携データ手動受信 | 取込・反映 | `ORDERFIX` 出荷確定（`LACK` 欠品を含む）、`STOCKFIX` 入荷確定（仕入・移動受）、`INVENTORY` 棚卸 | 12105 |
| L04 | 連携エラーデータ照会 | 照会・再処理 | 送信・受信バッチと行の照会、エラー行の除外・訂正版再取込、送信バッチの再出力 | WMSエラーデータ照会 |

対象外: 自動実行への登録、FTP/API 通信、EC 受注・売上（処理区分50/60）、返品入荷（STOCKFIX 30/40/60）、仕入返品出荷（ORDERFIX 40）、為替・外貨、複数連携先の同時運用（設定は連携先コード付きで持つが画面は1連携先を前提）。

### 2.2 連携設定（`MasterConfig`、カテゴリ `物流連携`）

新しいマスタ画面は作らず、既存の `MasterConfig`（`Category`/`Name`/`Val`/`Example`/`Memo`）に初期データとして追加する。サーバ側で読む。

| Name | 既定値 | 内容 |
|---|---|---|
| `LogisticsLinkCode` | `WMS` | 連携先コード。ファイル名・履歴に付く |
| `LogisticsBaseFolder` | （空） | サーバ上の連携フォルダ。空なら連携機能を使用不可として画面に表示 |
| `LogisticsTargetSoko` | （空） | 対象倉庫のコード（カンマ区切り）。旧の `倉庫区分=8` と変換マスタ `AMS` を兼ねる |
| `LogisticsEncoding` | `shift_jis` | 送受信ファイルの文字コード（`shift_jis`=cp932 / `utf-8`） |
| `LogisticsFileFormat` | `cv10-v1` | 形式定義の識別子（5.1）。連携先決定時に追加する |

- フォルダはサーバのローカル／共有パス。クライアントの PC フォルダではない（自動実行と同じ場所を使うため）。
  - 既存の HHT 連携・HHT マスタ出力は「サーバが行データを返し、クライアントがファイルを読み書き」する方式だが、物流連携は自動実行化を前提にサーバ側で読み書きする。手動受信で利用者 PC のファイルを使う場合は、クライアントが内容（バイト列＋ファイル名）をサーバへ渡し、以降はサーバ受信と同じ処理にする。
- 対象倉庫は得意先マスタの倉庫（`MasterTokui.TenType=0`）のコードで指定する。cv10 に倉庫区分（旧 `倉庫区分=8`）相当の列はないため列は追加しない。
- 連携フォルダ配下は `send`（送信待ち）、`send_bak`（控え）、`recv`（受信待ち）、`recv_bak`（取込済み原文）、`work`（作成中）。無ければ作る。

### 2.3 前提・不変条件

- 旧CVは機能ベースで再実装する。旧の SQL・区分値・ファイル形式をそのまま再現することを目的にしない。
- 配分の確定は既存 `ShippingDb.Commit` を唯一の経路とする（確定・伝票作成・引当解除が1段階、決定 D8）。物流受信のために配分確定仕様を変えない。
- 修正可能な配分は `TranHaibun.EditableWhereSql`（`SendFlg=0`・未完了・確定日なし）。送信した配分（`SendFlg>=1`）は配分修正画面で編集不可になる。この既存仕様をそのまま使う。
- 取置配分（区分6）は配分確定の対象外なので送信しない。
- 伝票生成・在庫更新は既存の保存経路と同じ後処理（在庫集計・引当・発注完了・入荷割当・売掛買掛）を通す（4.4）。
- 締済み期間への計上は、締管理（`SysPeriodClose` 仮称）が実装されたら共通検査に従う。未実装の間は HHT 取込と同等とする。

### 3.1 L01 マスタデータ作成

| 項目 | 仕様 |

| 入力 | 種別（PD / BSY、複数選択可）、全件／差分、差分基準日時（既定: 前回成功した同種別バッチの作成日時） |

| BSY 対象 | 倉庫・店舗・得意先（`MasterTokui`）と仕入先（`MasterShiire`）。差分は `Vdu` 基準 |
| 検査 | JAN 重複（同一JANが別SKU）、SKU にJANなし、コード重複。**警告として件数と一覧を表示**し、出力は可能（旧も止めていない）。JAN重複は連携先で SKU を特定できないため確認ダイアログで明示 |

### 3.2 L02 連携データ手動送信

画面で種別を選んで「対象取得 → 確認 → 送信ファイル作成」を行う。

**ORDER 出荷指示（配分）**

### 3.3 ファイル作成と状態遷移

DB 更新と外部配置を1トランザクションで完結したとみなさない（概要設計 5.1）。

```
[対象取得] → [確認] → ①トランザクション: バッチ作成(Status=作成中)・行保存・SendFlg=1
                    → ② work へ一時ファイル作成 → send / send_bak へ移動（同名上書き禁止）
                    → ③ Status=配置済み、配分 SendFlg=2
   ②で失敗 → Status=配置失敗（SendFlg=1 のまま）→ L04 から「再出力」（同じバッチ・同じ行・同じファイル名で②③をやり直す）
```

- 再出力は保存済みの送信行から作る（その時点の配分・伝票を読み直さない）。

- 連携先から受領通知がない間は「配置済み」を送達確認済みとみなす（仮実装）。

## 4. 受信の仕様（L03 / L04）

### 4.1 受信の流れ

```
① 取込: recv の *.csv/*.txt（または画面で選んだファイル）を読み、FileHash で既取込を検出
        → バッチ(Direction=受信, Status=取込済み) と 行(Status=未処理, RawText) を保存
        → 原文ファイルを recv_bak へ移動
② 検査: 行ごとに 4.3 の検査。エラーは行に ErrorCode/ErrorMsg、Status=エラー
③ 確認: 画面に 指示数・確定数・欠品数・エラーを一覧表示（ここまでは在庫・伝票を変更しない）
④ 反映: 利用者の「反映」で 4.4 を実行。伝票単位で成功/失敗を分ける
```

- ①②は1トランザクション。④は「伝票（まとめ単位）ごとに1トランザクション」とし、1件の失敗で他の伝票を巻き戻さない（旧はファイル単位全件。概要設計 L03 の推奨に合わせる）。
- 自動実行では ③ を飛ばして ①②④ を続けて呼ぶ（6章の `AutoApply`）。
- 同じファイル（FileHash 一致）の再取込は「既取込」として行を作らずに返す。

### 4.2 受信ファイルの種別判定

ファイル名に種別文字列を含むかで判定する（旧と同じ）。`ORDERFIX` / `LACK` / `STOCKFIX` / `INVENTORY`。判定できないファイルは取込せず、バッチを `取込失敗` で記録して `recv` に残す。

### 4.3 検査

| コード | 内容 | 対象種別 |
|---|---|---|
| E01 | 列数・必須項目・日付・数値の形式不正 | 全種別 |
| E02 | SKU 不明（商品・色・サイズ、または JAN で解決できない）。JAN と商品コードが両方ある場合は商品・色・サイズを優先し、JAN は不一致を警告 | 全種別 |
| E03 | 倉庫コード不明、または対象倉庫外 | 全種別 |
| E10 | CV 行ID（配分Id）が無い・SKU が配分と不一致 | ORDERFIX/LACK |
| E11 | 配分が完了済み・確定済み・取置・未送信（`SendFlg=0`）。**完了済みへの再適用はしない**（重複受信） | ORDERFIX/LACK |
| E12 | 確定数＜0、確定数＞指示数、欠品数＜0。最終実績として 確定数＋欠品数≠指示数 の場合は警告（4.4.1） | ORDERFIX/LACK |
| E13 | 同一配分Id がファイル内または未反映の他バッチに重複 | ORDERFIX/LACK |
| E20 | 元伝票Id（発注・移動出庫）が無い・送信していない | STOCKFIX |
| E21 | 移動出庫が受入済み（移動受の重複）／発注が完了済み | STOCKFIX |
| E22 | 入荷数≦0 | STOCKFIX |
| E30 | 同一 倉庫・棚卸日・SKU・棚番 がファイル内に重複 | INVENTORY |

- 旧と同じく、**1行でもエラーのあるまとめ単位（伝票）は全行反映しない**（関連行は Status=エラー、ErrorMsg に「同一伝票内にエラー行あり」）。
- エラーは行に保存し、ファイル単位で失敗にしない。

### 4.4 反映

#### 4.4.1 ORDERFIX / LACK（出荷確定・欠品）

- まとめ単位: 出荷日 × `HaibunHeaderKey`。
- 1回確定（決定 D8）: 配分行ごとに `KakuteiSu = 確定数` で `ShippingDb.Commit(rows, denDay=出荷日, idShain)` を呼ぶ。`ExpectedVdu` は送信行の `RefVdu` ではなく**現在の配分 `Vdu`**（送信後に `SendFlg=2` へ更新しているため）を使い、送信後に配分が別経路で変更されていないことは `SendFlg>=1`・未完了・確定日なしの検査（E11）で担保する。
- 指示数−確定数は欠品数として完了する（`ShippingDb` の既存動作）。ファイルの欠品数は照合にだけ使い、不一致は警告（E12）。
- LACK ファイルは確定数0・欠品数n の ORDERFIX と同じ扱い（全量欠品で完了、伝票なし）。
- 部分出荷（同じ配分を複数回に分けて確定）は受けない。2回目は E11 になる。※J-07
- `CommitOutcome` が `Shortage`（有効在庫割れ）・`NotArrived`・`Conflict` の場合は、そのまとめ単位の行をエラーにして他は続行する。在庫割れは「CV 在庫と倉庫実在庫の差」なので、L04 で原因（入荷確定の未反映など）を確認して再反映する。
- 生成伝票（出荷売上 `Tran00Uriage` ／ 移動出庫 `Tran10IdoOut`）の Id を行の `TargetTable/TargetId` へ保存。

#### 4.4.2 STOCKFIX（入荷確定）

| 処理区分 | 元伝票 | 生成伝票 | 後処理 |
|---|---|---|---|
| 20 仕入入荷 | `Tran13Hachu` | `Tran03Shiire`（`RelateNo1`=発注Id、仕入先・単価は発注明細） | 発注完了判定 `CompletionDb.CalcHachuEndFlag`、入荷割当 `ArrivalDb.Recalc`、買掛集計 |
| 10 移動入荷 | `Tran10IdoOut` | `Tran11IdoIn`（`RelateNo1`=移動出庫Id） | 在庫・積送の集計 |

- まとめ単位: 入荷日 × 元伝票。
- 伝票の組立・在庫反映は HHT 取込（`HhtProcess.UpdateVulcan2Tran` の `BuildSlip`／`ApplyStockEffect` と後処理）と同じ経路を使う。共通化が必要なら HHT 側の振る舞いを変えない範囲でヘルパへ切り出す。
- 発注残を超える入荷は警告として反映可（HHT と同じ）。※J-06

#### 4.4.3 INVENTORY（棚卸）

- `Tran60Tana`（倉庫・棚卸日・棚番ごとに1伝票、明細 SKU・数量）を作る。棚卸確定・在庫調整は既存の棚卸確定画面で行い、受信では実施しない（HHT の棚卸取込と同じ位置付け）。
- 対象倉庫の棚卸日が `Tran60TanaDate` に設定されていない場合は警告。

### 4.5 L04 エラー照会・再処理

| 操作 | 仕様 |
|---|---|
| 照会 | 連携先、期間、方向、種別、状態（未反映／エラー／配置失敗／送信後変更あり）、倉庫、商品。バッチ一覧 → 行一覧（原文・解決キー・エラー・生成伝票） |
| 再検査・再反映 | マスタ修正後などに、選んだバッチの未処理・エラー行を 4.3→4.4 で再実行 |
| 訂正版の追加 | エラー行を画面で訂正（倉庫・SKU・数量・日付）すると、原行を `Status=訂正済み` にし、`Id_LineOrg` 付きの新しい行を同じバッチへ追加して検査する。原文 `RawText` は変更しない（旧の直接書換・SQL連結を廃止） |
| 除外 | 反映しない行を `Status=除外`（理由を Memo に記録） |
| 再出力・送信取消 | 3.3 |
| 禁止 | この画面から確定数量・在庫・伝票を直接修正しない |

## 5. ファイル形式（cv10 既定形式 `cv10-v1`、仮）

連携先未定のため、旧 AMS 形式の項目構成を基に、cv10 の整数・コード体系へ合わせた既定形式を定める。連携先決定時は形式定義を追加して切り替える（5.1）。

### 5.1 共通

| 項目 | 仕様 |
|---|---|
| 形式 | CSV、カンマ区切り、全項目ダブルクォート囲み（項目内の `"` は `""`）、CRLF |
| ヘッダ行 | **あり**（項目名、1行目）。旧はなし。連携先形式でなしにできる |
| 文字コード | 設定 `LogisticsEncoding`（既定 cp932） |
| 数値 | 整数そのまま（×100 しない）。金額・単価は円 |
| 日付 | `yyyyMMdd` |
| コード | 商品・色・サイズ・倉庫・取引先は cv10 のコード（`Code`）。サイズにサイズ区分を前置しない |
| ファイル名 | `{LinkCode}_{DataKind}_{yyyyMMddHHmmss}_{BatchId}.csv` |
| 形式定義 | 種別ごとの「列名・順序・CV 項目・変換（ゼロ埋め、×100 等）」を形式識別子ごとにコードで持つ（`ILogisticsFileFormat`）。旧 AMS 互換形式が必要になったら `ams-compatible` として追加する |

**ZAIKO 在庫**: データ区分(`ZAIKO`)、基準日時、倉庫CD、商品CD、色CD、サイズCD、JAN、有効在庫、積送中

### 5.3 受信レイアウト

**ORDERFIX / LACK**: データ区分、区分（`10`/`20`）、指示ID（配分Id、必須）、出荷日、倉庫CD、出荷先CD、商品CD、色CD、サイズCD、JAN、確定数、欠品数、送り状NO、メモ

**STOCKFIX**: データ区分、区分（`10`/`20`）、元伝票ID（必須）、元伝票行No、入荷日、入荷倉庫CD、取引先CD、商品CD、色CD、サイズCD、JAN、入荷数、メモ

**INVENTORY**: データ区分、棚卸日、倉庫CD、棚番、商品CD、色CD、サイズCD、JAN、数量、メモ

- 送り状NO・メモは行に保存し、生成伝票の明細メモへ入れる（伝票ヘッダ `Memo` は「WMS受信 {BatchId}」）。

## 6. サーバ I/F（自動実行へ後から組み込める構成）

### 6.1 構成

```
CvWpfclient (L01〜L04 ViewModel)
   │  gRPC（既存 ICoreService。新しいサービス・proto は作らない）
   │    ・短い処理: QueryMsgAsync(Msg201_Op_Execute) + 新しい Param 型を HandleOpExecute で振り分け（HaibunCommit・OpeningBalanceImport と同じ）
   │    ・長い処理（反映）: QueryMsgStreamAsync + 新しい CvFlag（HHT 更新 Msg058 と同じ）
   ▼
CvServer (HandlerClass → 薄い受け口のみ)        ← 将来: SchedulerService のジョブ
   │                                                       │
   ▼                                                       ▼
CvDomainLogic/LogisticsLinkDb（処理本体。画面・gRPC に依存しない）
   ├ CreateMasterFiles(LogisticsMasterParam)
   ├ CreateSendBatch(LogisticsSendParam)        … 対象取得・確保・ファイル配置
   ├ RewriteSendBatch(batchId) / CancelSendBatch(batchId)
   ├ ImportReceiveFiles(LogisticsReceiveParam)  … 取込・検査
   ├ ApplyReceiveBatch(LogisticsApplyParam)     … 反映
   └ Preview*（件数・一覧の照会。DB を変えない）
   CvBase/LogisticsContracts.cs（Param/Result の record。クライアントと共有）
```

- 処理本体は `ExDatabase` を受け取るクラス（`ShippingDb`・`HhtProcess` と同じ形）にし、トランザクションは呼び出し側（gRPC ハンドラ／将来のジョブ）が張る。4.1 の伝票単位トランザクションは本体内部で区切るため、本体に「伝票単位のトランザクション実行デリゲート」を渡せるようにする。
- Param は画面入力をそのまま持たず、**自動実行でも作れる値だけ**にする（連携先コード、種別、基準日、対象倉庫は設定から、`ExecType`、`Id_Shain`＝自動実行時はシステム社員）。
- Result は `BatchId`、件数（対象・成功・エラー・警告）、生成伝票Id、メッセージ。画面表示と自動実行の結果メール（`AutoExecMailService`）の両方で使える形にする。
- 長時間処理は既存の `StreamStepProgress` によるストリーム進捗で画面に表示する（HHT 更新と同じ）。

### 6.2 排他・履歴

- 同時実行防止は既存のマニュアル排他（`ManualLockDb`、`SysSequence.SysSeqType=1`）を使い、キーは `Logistics{Direction}{DataKind}`。送信と同じ種別の受信反映、配分確定画面との競合は配分行の `Vdu`・`SendFlg` で検出する（排他を複雑にしない）。
- 実行履歴は `SysHistAutoexec` に `SysHistType=1`（手動）で1件記録（TaskName=「物流連携 {DataKind}」）。自動実行化したら同じ処理が `SysHistType=0` で記録する。

### 6.3 将来の自動実行への組み込み（今回は実装しない）

- `SchedulerService` にジョブ（例: 出荷指示送信、入荷予定送信、在庫送信、受信取込・反映）を追加し、`SchedulerJobConfigDb` で有効化・cron を管理する。ジョブは 6.1 の本体を `ExecType=0` で呼ぶだけにする。
- 自動受信は `ApplyReceiveBatch(AutoApply=true)` で確認を省く。エラー行は L04 に残し、結果メールで通知する。
- 転送（FTP/SFTP/API）が必要になったら `ILogisticsTransport`（Put/Get/List）を追加し、既定実装は「連携フォルダへの配置／取得」とする。本書の範囲ではフォルダ実装のみ。
