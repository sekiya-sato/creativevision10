# SQL方言3DB対応 調査結果と10.2対応計画

作成日: 2026-09-13

## 0. 本書の位置づけ

`CvBase/Sql/` の SQL方言吸収機構をレビューした結果と、残課題をまとめる。

**10.0 は SQLite 単独運用を前提としており、本書に挙げる残課題はいずれも 10.0 の動作に影響しない。**
SQLite 経路は `PassThroughSqlDialect` による恒等変換で、`Translate` は引数の同一参照を返す。
したがって本書の §3 以降は **すべて 10.2 以降（PostgreSQL / MariaDB の本格対応）で必要となる処理**である。

基礎設計は `.omo/2026-08-25_sql_dialect_translator_detail_design.md`（以下「設計書」）にある。
本書はその設計書のフェーズ計画のうち、**1.0 スコープ外として棚上げされた部分**（Phase 7 相当）と、
レビューで新たに判明した欠落を、10.2 の作業単位として整理したものである。

## 1. レビュー結論

| 層 | 判定 |
|---|---|
| 骨格（字句解析・置換・復元・SQLite恒等性） | 健全。字句列の連結復元性、右→左走査による入れ子の取り込み、`Mutated` 判定による無変換時の同一参照返却はいずれも設計どおり |
| 構文吸収（カテゴリA/B/C のルール） | ほぼ完成。実SQLコーパス 218本に対し PostgreSQL / MariaDB とも 216本（99.1%）が未対応構文ゼロ |
| 意味差（同じ構文で結果が変わる差） | **未着手**。設計書が Phase 7 として 1.0 スコープ外に置いたまま |
| 実DB検証 | **実績ゼロ**。3DB差分テスト（設計書 T7）のプロジェクトも実行環境定義も無く、`appsettings` に `Database` セクション自体が存在しない |

**構文カバー率 99.1% が保証しているのは「SQLが構文エラーにならない」ことだけであり、値が一致することは何も保証していない。**
これが 10.2 に向けた最大の論点である。

### 実行経路（確認済み）

- クライアント由来SQLの変換入口は `CvServer/Services/HandlerClass.cs` の `TranslateClientSql` 1箇所で、
  呼び出し元は `HandleQueryOne` / `HandleQueryList` / `HandleQueryListSql` の3点のみ。
  処理順は `Dialect.TranslatesSql` の判定 → `SqlOverrideCatalog.TryGet` → `Dialect.Translate`。
- サーバ層は `CvBase/ExDatabase.cs` の `ExecuteDialect` / `FetchDialect` / `TranslateDialect` が第2の経路で、
  CvDomainLogic の JSON配列再構築と UPSERT がここを通る（`ServerLayerRuleTests` で網羅）。
- `SqlDialectGuard.WarnIfUnsupported` は `CvWpfclient/Helpers/Communication/CoreServiceClient.cs` の
  `QuerySqlListAsync` から呼ばれる開発時自己検査。警告のみでSQLを変更せず、送信も止めない。
- `Dialect.Validate` は `CvServer/Program.cs` の起動処理で接続先に対して1回呼ばれる。
  `SessionSetupCommands` は MariaDB のみ `ExDatabaseMaria.Open()` から実行される。

## 2. 10.0 で実施した小穴塞ぎ（Step A）

10.0 の SQLite 経路を変えずに塞げるものだけを先行して実施した。詳細は該当コミットを参照。

| 項目 | 内容 |
|---|---|
| `group_concat` の吸収 | 目録未登録かつルール未実装だったため、Guard も Strict モードも検知できず素通りしていた。2引数形を PostgreSQL `string_agg((expr)::text, sep)` / MariaDB `GROUP_CONCAT(expr SEPARATOR sep)` へ変換する。カンマ区切りのままでは MariaDB が第2引数を別の集約対象と解釈するため必ず `SEPARATOR` 形にする |
| 既定モードのプロバイダー別化 | 設計書 §4.4 は SQLite=Auto / PostgreSQL・MariaDB=Strict と定めているが、実装は一律 `Auto` だった。設定 `Database:SqlTranslation` が明示されていればそれを優先し、未設定ならプロバイダー別の既定を適用する |
| `OFFSET` の誤引用 | `ReservedIdentifierRule` が後方のトークンだけを見ていたため、`LIMIT 10 OFFSET SomeColumn` のようにキーワードの後ろが列名/式になる形でキーワードを引用していた。直前トークン基準の判定へ変更 |
| ドキュメント不一致 | `SqlDialectBase` 冒頭が「左から右へ走査」と書いていたが実装は右から左。`ISqlDialect` 冒頭が「CvBase / CvDomainLogic 内部のSQLは変換器を通さない」と断言していたが、実際は `ExecuteDialect` 系で通している。いずれも実態に合わせて修正 |

## 3. 【10.2】意味差の封じ込め

構文としては変換できているが、**実行結果が SQLite と変わる**もの。すべて 10.2 の課題。
SQLite 側の値は実DB（`server-user163.db`）で実測した。

### 3.1 月加算の月末挙動が逆（影響大）

```
SQLite : date('2024-01-31','+1 months') -> 2024-03-02   (2月31日を繰り越して正規化)
PG     : (d::date + '1 months'::interval)::date -> 2024-02-29   (月末へクランプ)
MariaDB: DATE_ADD(d, INTERVAL 1 MONTH)          -> 2024-02-29   (月末へクランプ)

SQLite : date('2024-02-29','+1 year') -> 2025-03-01
PG/Maria: 2025-02-28
```

`B07-DateModifier` の変換は字句としては正しいが、**SQLite だけが繰り越す**ため結果が変わる。
該当は `date(X, '+' || n || ' months')` 系で 24箇所前後（`date({BaseMonth}, '+1 month', '-1 day')` のような
複数修飾子形も含む。複数修飾子自体はルールが対応済み）。

実SQLの多くは月初日（`{startDate}` が月初）を起点にしており、その場合は顕在化しない。
10.2 では **呼び出し箇所ごとに起点が月初に限定されるかを点検**し、限定されない箇所は
SQLite 側で結果が変わらない書き方（月初起点へ寄せる）に直すか、変換対象から外して未対応として弾く。

### 3.2 cast の整数丸め（MariaDB）

```
SQLite : cast(2.7 as integer) -> 2    (切り捨て)
MariaDB: CAST(2.7 AS SIGNED)  -> 3    (四捨五入寄り)
```

`A02-CastType` の `INTEGER -> SIGNED` 写像で混入する。10.2 では MariaDB 向けを
`TRUNCATE(x, 0)` 相当へ変えるか、整数化が意図されている箇所を洗い出して個別に対処する。
除算結果を整数へ丸める箇所（設計書 §8 の「MariaDBの整数除算」と同じ論点）と併せて扱う。

### 3.3 printf の負数ゼロ埋め

```
SQLite : printf('%04d',-5) -> -005
変換後 : lpad('-5'::text,4,'0') / LPAD('-5',4,'0') -> 00-5
```

`B06-Printf` は年月日など非負値での使用を前提にしている。10.2 では
負値を取り得る式を変換対象から外すか、符号を保つ書式関数へ変える。

### 3.4 json_extract の戻り値型

```
SQLite : json_extract('{"a":true}','$.a')    -> 1            (整数)
PG     : (X)::jsonb ->> 'a'                  -> 'true'       (テキスト)

SQLite : json_extract('{"a":{"b":1}}','$.a') -> {"b":1}      (部分木のテキスト)
MariaDB: JSON_VALUE(X,'$.a')                 -> NULL         (スカラーのみ返す仕様)
```

`B01-JsonExtract` は単一階層パスに限定しているが、**値の型までは保証していない**。
10.2 では対象プロパティの実データ型を洗い出し、真偽値・オブジェクト・配列を返すプロパティを
変換対象から外すか、MariaDB 側を `JSON_EXTRACT` + `JSON_UNQUOTE` の組へ変える。

### 3.5 MariaDB のタイムゾーン依存

`B05-Strftime` の `strftime('%s', X)` は MariaDB で `UNIX_TIMESTAMP(X)` になるが、
これはセッションの `time_zone` で引数を解釈するため、サーバ既定TZ次第で値がずれる。
`MariaSqlDialect.SessionSetupCommands` にタイムゾーン固定が無い。
10.2 では `SET time_zone` をセッション設定へ追加する（照合順序 `utf8mb4_bin` と同じ扱いで、
接続時に決め切る）。

### 3.6 UPSERT の衝突判定（要確認）

MariaDB の `ON DUPLICATE KEY UPDATE` は、`ON CONFLICT` で指定した列以外のユニークキー衝突でも
UPDATE が発火する。現行スキーマでは 1テーブルにつきユニーク索引が1本しか無いことを確認済みで、
かつ UPSERT 対象の INSERT が主キー `Id` を明示しなければ実害は無い見込み。
10.2 で UPSERT 対象の INSERT が `Id` を与えているかを確認し、与えているなら個別対処する。

### 3.7 設計書 §8 に既出の意味差（10.2 で継続）

設計書 §8 が挙げている以下も未着手のまま 10.2 の対象である。

- 照合順序（MariaDB は `utf8mb4_bin`、PostgreSQL は `LC_COLLATE=C` でのDB作成）— DDL/接続で決め切る
- MariaDB の整数除算
- PostgreSQL の `GROUP BY` 厳格化（非集約の裸列）
- 集約の戻り型
- 不正JSONの評価順（`WHERE json_valid(x) AND json_extract(...)` を `CASE WHEN` 形へ）
- 文字列列と数値リテラルの比較

いずれも「**SQLite で結果が変わらない書き方に寄せる**」という設計書の原則を守ること。

## 4. 【10.2】検証基盤（最優先）

**3.x の修正は、実DBで突き合わせる手段が無いと当て推量になる。** したがって 10.2 では
意味差の修正より先にこれを作る。設計書 T7 に相当する。

- `Tests/TestDialectParity` プロジェクトを新設する。環境変数で接続先が与えられたときだけ実行し、
  与えられなければスキップする（既存のテスト実行を止めない）。
- PostgreSQL 16 以降 / MariaDB 10.11 LTS 以降の実行環境定義を用意する（設計書 §11 の下限に従う）。
- 同一 fixture を3DBへ投入し、行数・並び順・NULLの位置・金額の丸め・日付境界・JSON欠落・不正JSONを比較する。
- 縦切りの最初の3本は設計書 §9 のとおり。
  1. 単純一覧（`ifnull` + `LIMIT` + `LIKE ... ESCAPE` + `ORDER BY Code/Kana`）→ 照合順序とNULL順を確定
  2. JSON明細（`TranMeisaiSql` を使う帳票1本）→ 空文字・不正JSON・欠落プロパティ・空配列
  3. 日付集計（`PeriodSql` を使う週次／月次帳票1本）→ 整数除算と集約の戻り型

`A04-NullsOrder`（PostgreSQL の `NULLS FIRST` 付与）は既定無効のままである。
設計書の決定どおり、この差分テストで必要性を確認してから有効化を判断する。

## 5. 【10.2】運用経路の整備

| 項目 | 内容 |
|---|---|
| マイグレーション | `CvBase/UpdateDb.cs` の移行定義は SQLite 方言の SQL（`NUMBER` 型・`strftime('%s','now')`・`DROP COLUMN` 等）をそのまま並べており、方言変換もプロバイダー別のゲートも通さず `ExecuteAsync` で実行される。**10.0 は SQLite 単独想定なのでこれで問題ない。** 10.2 では設計書 §7 の「プロバイダー別ベースライン版数」を導入し、PostgreSQL / MariaDB は `CreateTable` で現行スキーマから新規作成してベースライン以前の移行を適用対象外にする。SQLite の履歴は一切変更しない |
| 設定 | 現行の `appsettings*.json` に `Database` セクションが存在せず、`Database:Provider` 未設定時は SQLite になる。10.2 では PostgreSQL / MariaDB の接続文字列と `Database:Provider` / `Database:SqlTranslation` / `Database:SqlRules:A04-NullsOrder` の雛形を環境別設定へ追加する |
| 変換入口の外にあるSQL | `HandlerClass.HandlePartialUpdate` と `CvBase/OpeningBalanceCsv.cs` 系（CSV取込）は、いずれの変換経路も通さず独自にSQLを組み立てて実行する。識別子は allowlist で解決済みの値を使い、SQLite固有構文も含まないため現状は実害が無い。10.2 では「変換経路は2つだけ」という前提を崩さないよう、この2箇所に注記を置くか `ExecuteDialect` 経由へ寄せる |
| PostgreSQL のセッション設定 | `PostgreSqlDialect.SessionSetupCommands` は空で、`ExDatabasePostgre` 側にも呼び出しが無い。現状は空なので実害が無いが、3.5 のタイムゾーン対応を入れる際に PostgreSQL 側も呼び出し口を用意する |

## 6. 【10.2】検出漏れの残り（軽微）

- `SqlTokenizer.ScanNumber` はドットを何度でも数値本体に取り込む（`1.2.3` が1トークンになる）。復元性は壊れないが、数値トークンを見るルールが増えたときの誤判定の芽。
- 角括弧識別子 `[col]` の `]]` エスケープに未対応。リポジトリ内に実使用は無い。
- `SqliteConstructCatalog` の `conflict` 判定は裸の識別子も拾うため、`Conflict` という列名やエイリアスを作ると `C04-Upsert` として誤検知しうる。現状該当なし。
- `GLOB` / `rowid` / `IIF` / `RETURNING` は現時点で実使用ゼロのため目録に未登録。使い始めるなら同時に登録する。
