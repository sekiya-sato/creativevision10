## 3. 管理者の視点

### 3.1 運用の流れ

```text
① 権限プロファイル設定 … 「店舗スタッフ」「経理」などを作り、メニューごとに 許可/禁止/既定 を決める
② 社員マスタメンテ    … 社員にプロファイルを割り当てる
③ 試行               … 対象者に再ログインしてもらい、見え方を確認（既定ポリシーはAuditのまま）
④ 本運用             … 必要ならシステム管理マスタで既定ポリシーを Deny に切り替える
```

運用方式は2通りあり、既定ポリシーで選ぶ。

| 方式 | 既定ポリシー | 明細の書き方 | 向く場面 |
|---|---|---|---|
| 禁止リスト | Audit（現行値） | 見せたくないメニューだけ「禁止」 | 大半の社員が全機能を使い、一部だけ隠す |
| 許可リスト | Deny | 使ってよいメニューだけ「許可」 | 店舗スタッフなど使う機能が少ない |

### 3.2 権限プロファイル設定画面（新規1画面）

- 配置: `■ システム管理 › ▲ ログイン管理 › 権限プロファイル設定`（`Views._00System.SysPermissionProfileMenteView`、FunctionId `00System.SysPermissionProfileMente`）。
- 構成（既存メンテ画面の配置に揃える）:

```text
┌ プロファイル一覧 ─────────┐┌ メニュー権限 ─────────────────────────────┐
│ コード / 名称 / 有効        ││ [許可][禁止][既定] ← 選択中フォルダ配下へ一括    │
│ FullAccess 全機能標準権限 ○ ││ ■ マスター                                       │
│ StoreOperationStandard ...  ││   ▲ 基本設定                                     │
│ ...                         ││     システム管理マスタ   [既定▼] → 既定時: 許可   │
│ [新規][保存]                ││     ...                                          │
│ コード/名称/メモ/有効 編集欄 ││ 既定ポリシー: 監査のみ（システム管理マスタで変更） │
└─────────────────────────┘└──────────────────── [保存] ┘
```

- メニュー木は `MenuData.CreateAll()` をそのまま表示し、実行可能な項目ごとに「既定／許可／禁止」を選ぶ。右に「この設定での結果（許可/不可）」を出し、既定ポリシーの影響が分かるようにする。
- 同じFunctionIdがロール別ショートカット（■店舗業務・■倉庫業務）と標準メニューの両方にある場合、設定は1つで両方に効く（画面上も連動表示）。
- フォルダを選んで一括ボタンを押すと配下全項目へ同じ値を入れる（208項目を1つずつ設定させないため）。
- プロファイルの削除は設けず「無効」で止める（割当済み社員が宙に浮かないため）。
- `FullAccess`（Id=1）は**固定で全許可**とし、メニュー権限欄は編集不可にする（J3、ロックアウト防止）。
- 保存は1プロファイル分の明細を**1トランザクションで洗い替え**する（6.3節）。他端末が同時に保存していたら競合として全体を取り消す。

### 3.3 社員マスタメンテ

- 既存の `Id_PermissionProfile` 数値入力欄を、有効なプロファイルの選択（コード＋名称、先頭に「未割当」）に置き換える。列・保存経路は変えない。

### 3.4 反映タイミング・緊急復旧

- 設定変更は**対象者の次回ログインから**反映する（旧詳細設計 8.5節と同じ）。
- 誰も権限設定画面を開けなくなった場合は、DBで管理者の社員に `Id_PermissionProfile=1` を入れて再ログインする（手順を使用ガイドラインへ追記）。`FullAccess` は明細に関係なく全許可なので必ず戻れる。

## 4. 使用者の視点

### 4.1 メニューの見え方

- ログインすると、使えないメニューは**表示されない**。中身が全部消えたフォルダも出さない。
- 使える範囲は従来と同じ操作で開ける。既定ポリシーがAuditでプロファイル未割当なら、今と何も変わらない。
- 権限変更は再ログインで反映される。万一非表示のメニューへ到達した場合（お気に入り等）は「このメニューを使う権限がありません。管理者に確認してください。」と表示して開かない。
- ログイン前（起動直後）の表示は現行どおり。サーバ処理は認証が必要なので、ログイン前に開いても業務処理は動かない。

### 4.2 お気に入り

```text
★ お気に入り            ← 1件以上登録したときだけ最上部に出る
   店舗売上入力
   在庫問合せ
■ 店舗業務
■ マスター
...
```

- メニュー項目を右クリック →「お気に入りに追加」。お気に入り内の項目を右クリック →「お気に入りから外す」。並びは追加順。
- 表示名・説明は元のメニューと同じ。権限で使えなくなったメニューはお気に入りからも表示されない（登録は消さないので、権限が戻れば再表示）。
- 保存先は使っているPCの `%LocalAppData%\CreativeVision10\Menu\favorites_<ログインID>.json`。共用PCでもログインIDごとに分かれる。**別のPCには引き継がれない**（J5）。
- ファイルが壊れていた場合はお気に入りを出さずに通知し、ファイルは上書きしない（AI照会の個人保存と同じ扱い）。

## 5. 判定規則

`CanOpen(functionId)` を次の順で決める（旧詳細設計 8.2節のView判定）。

1. ログインユーザーの社員のプロファイルが `FullAccess`(Id=1) → 許可。
2. 固定許可リストに含まれる → 許可（J3で旧案を採る場合のみ。推奨案では空）。
3. プロファイルの明細（View）に `IsAllowed=false` → 不可。
4. 明細に `IsAllowed=true` → 許可。
5. 明細なし → 既定ポリシー: Audit=許可、Warn=許可（クライアントログへ警告）、Deny=不可。

- プロファイル未割当(0)・無効プロファイル・存在しないId は「明細なし」として5へ進む（J4）。
- FunctionIdを導出できない項目（`Views/Sub` 等）はメニューに無いので対象外。
- `Edit`(2) の明細行は読み込むが判定に使わない（既存初期データはそのまま残る）。

## 6. データ・契約・処理

### 6.1 テーブル

**追加・変更なし。** migrationも不要。

### 6.2 ログイン応答に1項目追加

```csharp
// CodeShare/ILogin.cs LoginReply
/// <summary>ログインユーザの社員に割り当てた権限プロファイル（MasterShain.Id_PermissionProfile）。0=未割当</summary>
[DataMember(Order = 6)]
public long PermissionProfileId { get; set; }
```

- `LoginService.LoginAsync` / `LoginRefreshAsync` が `SysLogin.Id_Shain` → `MasterShain.Id_PermissionProfile` を引いて設定する（クライアント申告にしない）。
- 既定値0は「未割当」で、protobuf-netの既定値省略でも意味が変わらない（AGENTS 7.1）。旧クライアントは項目を無視するだけ。
- クライアントはログイン後、既存 `Msg101_Op_Query` で該当プロファイル・明細と `MasterSysman.PermissionDefaultMode` を読み、メニューを作り直す。読込失敗時は「権限情報を取得できませんでした」と表示し、**従来どおり全メニュー**で続行する（業務を止めない。権限はセキュリティ境界ではないため）。

### 6.3 権限プロファイル保存（既存の一括保存パターン）

`HaibunSaveParam` と同じく、`Msg201_Op_Execute` の型分岐へパラメータを1つ追加する（新CvFlagなし）。

```csharp
// CvBase/Parameters.cs
public sealed record PermissionProfileSaveParam(SysPermissionProfile Profile, long ExpectedVdu, SysPermissionProfileDetail[] ViewRows);
```

- サーバは1トランザクションで、プロファイル行の追加/更新（`ExpectedVdu` 不一致は `ConcurrentUpdate` で全体取消）→ そのプロファイルの `PermissionType=1` 明細を削除 → `ViewRows` を挿入する。`Edit` 明細には触れない。
- `Id=1`(FullAccess) の明細変更は拒否する。`Code` 重複は既存の一意キー `uq1` で拒否されるので、画面へ分かる文言で返す。
- 汎用 Insert/Update/Delete 経路はこれまでどおり開いたまま（J1の扱いと同じく、業務権限はセキュリティ境界ではない）。

## 8. 既存データと導入時の挙動

- 開発DBは割当社員0人・既定Audit なので、導入直後は**全員が全メニューを使える**（現行と同じ）。
- 既存初期データの明細はすべて「許可」行で、Audit下では表示に影響しない。Deny に切り替える前に、各プロファイルの許可行を権限プロファイル設定画面で整える。
- `SysLogin.Id_Role` によるロール別メニュー切替は既に全メニュー表示で実質無効。今回は触らない。
