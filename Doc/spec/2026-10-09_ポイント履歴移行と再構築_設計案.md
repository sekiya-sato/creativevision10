## 3. 初期化範囲

| 対象 | 初期化 |
|---|---|
| TranPointEvent | 全履歴を削除。既存の試作・手動・失効履歴も再利用しない |
| SummaryPoint.Point | 全顧客を0へ戻す。行と購買回数・購買金額は保持 |
| MasterEndCustomerAccount.Point | 全会員を0へ戻す。会員行・ランク・来店情報は保持 |
| Tran01Tenuri.GrantPoint | 全売上を0へ戻す。再計算する売上だけ再設定 |

初期化は再構築専用処理だけで行い、起動migrationや通常convertの `isInit` に連動させない。通常の台帳更新・削除禁止は維持する。全再構築を再実行すると切替後の手動・失効履歴も消えるため、初回切替専用とする。

## 4. 旧履歴の保持

旧1行を `TranPointEvent` の1行へ移す。既存enumの値は変えず `LegacyHistory=7`（旧CV履歴）を追加する。純増減だけでなく元の内訳・識別情報を保持する。

| 項目 | 内容 |
|---|---|
| EventKey | `LEGACY:{移行元識別子}:POINT:{SEQ_NO}`。再送でも固定、160文字以内 |
| EventType | LegacyHistory |
| PointDelta | 付与－使用－失効。0の行も登録 |
| DenDay | 検証済み旧ポイント計上日 |
| Id_Customer/Id_Tenpo/Id_Shain | 元コードで既存マスタへ対応付け。旧数値IDを流用しない |
| Id_Tenuri | 0。旧履歴と売上に確実な共通IDがないため推測で結び付けない |
| Id_PointBase/Rank/Bonus、Id_OriginalEvent、SourceVdu | 0。旧制度を現行の制度版へ推測変換しない |
| Jcalc | SourceSystem、旧SEQ_NO、旧顧客/店舗/社員コード、ランク、日付、取引/発生区分、レジ/レシート番号、付与/使用/失効数、作成/更新値、備考を保存 |
| Memo | 旧備考。「.」等の元値はJcalcにも残す |
| Vdc/Vdu | CV10への登録時刻。元時刻はJcalcに保持 |

JcalcはJSON妥当性・4,000文字上限と、0値を含む往復一致を確認する。元行の再現とポイント種別別の照会はJcalcの内訳を使い、単純なEventType別集計へ混ぜない。画面に「旧CV履歴」と付与・使用・失効の内訳を追加し、移行行の手動取消は許可しない。

同一キー・同一内容は再取込をスキップし、同一キーの内容変更は停止して差異を報告する。追加0件でも変換完了時に全件残高を台帳から同期する。切替後の旧履歴更新を無条件に上書きする差分同期は今回対象外。

## 5. 残高と旧現在残高の扱い

正本は台帳。常に `SUM(PointDelta) = SummaryPoint.Point = MasterEndCustomerAccount.Point` を成立させる。

- 通常の付与・使用・手動・失効では、変更顧客の両残高へ台帳合計を代入する。会員ポイントの増減加算は廃止する。
- 移行後と最終段階では専用の全件残高再構築を行う。履歴のない顧客も0となる。Summaryの購買情報は更新しない。
- 顧客convertは新規会員ポイントを0で作成し、旧現在残高を直接代入しない。既存会員の再取込ではポイントを0へ上書きせず、既存顧客行を再作成してIDを振り直さない。
- `HC$POINT_REAL` は照合元とし、現在残高全額のOpeningBalanceを重ねて投入しない。
- 差異27顧客は例外として提示する。現在残高を優先する承認が得られた場合に限り、差額だけをOpeningBalanceで切替日に追記する。未承認の差額を自動補正しない。
- 台帳はlong、残高は既存int。範囲外を事前検査して停止し、切捨て・丸めをしない。

## 6. 再計算の境界

対象は `OldSeqNo=0` のCV10作成店舗売上。顧客・売上/返品区分・適用制度等の既存条件も満たすものだけ計算する。旧売上に履歴がなくても `OldSeqNo>0` は除外する。

- Recalcの抽出、イベント経由の伝票再読込、保存時SyncTenuri、共通Syncの入口で同じ除外条件を適用する。CalcExpectedを空にするだけでは旧イベントの取消が起きるため不可。
- 削除時は元伝票を使って判定する。現在のnull引数だけではOldSeqNoが分からない。更新時も保存前・後のどちらかが旧売上なら除外し、OldSeqNoの変更・部分更新で除外を解除させない。HHT・取置の直接同期経路も共通判定で保護する。
- 旧履歴はLegacyHistory、Id_Tenuri=0で保持し、通常売上の自動取消対象にしない。
- 初回再構築は対象の最古月から最新月まで年月昇順、月内はDenDay・Id順。ボーナス回数上限の適用を時系列で確定する。
- 初回購入判定には旧売上も含める。旧売上を再計算しないことと、購入実績を無視することは分ける。
- 旧ボーナスは現行版への対応が不明なため、現行ボーナスの回数上限に推測で算入しない。この境界は切替時に確認する。
- 旧売上の編集・削除でも移行ポイントは固定。必要なポイント訂正は理由付きの調整登録とする。旧売上のUsePoint変更はサーバで拒否する。
- 再構築に新たな失効処理は含めない。旧失効は移行履歴に含まれ、切替後の失効は既存処理で行う。

## 7. 再構築の順序と復旧

1. 取込元・切替日を固定。旧CV/CV10の更新を止め、月次ポイント再計算・失効ジョブも停止する。取込先DBをバックアップする。
2. コピーDBに製品migrationを適用し、入力マスタ・使用ポイント・制度設定・不整合を事前検査する。
3. §3のポイント履歴・残高・計算値を初期化する。
4. 顧客/店舗/社員のID対応を確認し、専用 `CnvTranPointHistory` で旧確定履歴をチャンク取込する。通常convertのタスク一覧にも追加するが、全初期化は専用手順だけで行う。
5. 移行件数・元行内訳・顧客別合計・旧現在残高を照合する。承認した差額処理があれば追記する。
6. 移行済み履歴を残して、CV10作成売上だけ既存計算を用いて再計算する。
7. 全顧客の残高を台帳から再構築し、三者一致・旧履歴不変・再実行結果を確認する。
8. 合格したコピーDBへ切り替え、停止したジョブを元の状態へ戻す。失効ジョブを新たに有効化しない。

各チャンクは履歴保存をトランザクション化し、通常再計算は履歴・売上計算値・残高を同一トランザクションで反映する。全工程完了前のDBは業務に公開しない。失敗時はコピーDBで再開/再作成し、切替失敗はバックアップへ戻す。稼働DBへ段階的に全削除・部分取込する運用は採らない。

## 8. 例外方針と受入条件

日付未設定、顧客未解決、店舗・社員参照未解決、金額範囲外は事前集計する。日付の架空補完、顧客の自動新設、履歴の黙示スキップはしない。元コードと旧SEQ_NOを付けた例外一覧を用意し、解決または取込方針の承認まで切替を止める。例外一覧はアクセスを限定し、個人情報を通常ログへ出さない。

| 検証 | 期待結果 |
|---|---|
| 正常・返品・複数種別・全0 | 旧1行=新1行、元項目・符号・純増減が一致 |
| 重複取込・同一キー変更 | 重複なし。追加0件でも両残高が台帳合計に一致。変更は報告して停止 |
| 旧売上の再計算/更新/削除 | 移行履歴とポイント残高に自動増減なし |
| CV10売上の付与/使用/返品/削除 | 既存条件で計算し、通常再実行で二重計上なし |
| 初回・ボーナス上限 | 旧購入実績を考慮し、時系列順で期待回数・額に一致 |
| 残高 | 全顧客の台帳・Summary・会員が一致、台帳なしは0 |
| 途中失敗・再実行 | チャンク/業務単位の部分適用なし。失敗DBを公開しない |
| 接続先SQLiteの現状 | CV10作成売上0件のため再計算追加0件 |

実装時は対象project build、SQLite複製DBのmigration/移行/UAT、SQL方言の対象DB確認、独立Reviewer/Testerで確認する。既存設定・入力値・購買情報の保持と、移行前後の明細/顧客別合計も比較する。
