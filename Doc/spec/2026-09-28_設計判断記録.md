## 1. マスタ V* 列・名称伝播（DB・SQL）

### 1.1 マスタV*列の伝播は明示マップ(CascadeVRule)を唯一の正とする

- 判断: Master系V*列の伝播はSQLのUPDATE文で対象行を書き換える方式とし(十万行規模を1行ずつFetch/ループしない)、`[ForeignKey]`属性からの自動導出は行わず、明示マップ(CascadeVRule、当時22件・現行28件)を唯一の正とする。SQLiteのjson_extractは不正JSONに例外を投げるため、伝播対象のJSON列はjson_valid()で必ずガードする。
- 理由: Id_Paysakiは宣言型ごとに参照先が異なり(MasterTokui→MasterTokui、MasterShiire→MasterShiire)基底の`[ForeignKey]`属性だけでは表現できない。過去にALTER TABLE ADD COLUMN DEFAULT ''直後の空文字1行でマスタ改名がロールバックする実害があったため、json_validガードは必須。
- 影響範囲: CvDomainLogic/MasterCascadeDb.cs、Master系全V*列(MasterMeisho/MasterTokui/MasterShain/MasterShiireが伝播元)
- 出典: aicoding_log_011.md [2026-07-27]

### 1.2 マスタ更新時のV*列伝播フックの発動条件と自己参照時のVdu整合

- 判断: 伝播要否はNeedsCascade(伝播元マスタ4型かつCode/Name変化時のみ)で判定する。CascadeFromMasterへはHandleUpdateのvdateをそのまま渡し、伝播は同一トランザクション内で実行してSQLエラーは送出する。
- 理由: 請求先が自社(MasterTokui.Id_Paysakiが自分自身)のケースで、伝播側が別途vdateを採番するとクライアントへ返すVduとDB上の値がずれ、次回保存が楽観排他で弾かれるため。マスタ更新だけが成功しV*列が古いまま残る状態を作らない。
- 影響範囲: CvServer/Services/HandlerClass.cs HandleUpdate
- 出典: aicoding_log_011.md [2026-07-27]

### 1.3 Jsub等JSONスナップショットの伝播ルールとKb/Kbnameの意味確定

- 判断: Jsubの`Kb`は`MasterMeisho.Kubun`、`Kbname`は`Kubun='IDX'`かつ`Code=Kb`の行の`Name`である。MasterMeisho.KubunNameの伝播からは`Kubun='IDX'`の行自身を除外する(初期データのKubunName値を壊さないため)。区分コード自体が変更された場合は区分名を伝播せず警告ログのみとする(区分体系変更は伝播では解決できない)。DerivedShohinColSizは個別UPDATEでなくDelete→Insertで再構築する。
- 理由: 実コードから初めて確定させた仕様であり、以後の実装・調査で誤解を避けるため明文化した。
- 影響範囲: CvDomainLogic/MasterCascadeDb.cs, MasterShohin.Jcolsiz, DerivedShohinColSiz, MasterMeisho.KubunName
- 出典: aicoding_log_011.md [2026-07-27]

### 1.4 Master系V*列は物理列でも「常に現行名称」、クライアント側の同時更新責務

- 判断: Master系のV*列は物理列であり「常に現行名称」が不変条件。サーバの伝播はマスタ改名時にしか走らないため、参照Idを変更する画面・新規登録経路ではクライアントがV*列を同時に埋める必要がある。商品マスタのVTenji/VSeason/VMaterial/VCountryも同様に、`[ForeignKey(meishoKubun:…)]`属性(TNJ/SZN/SZI/GEN)を正としてメンテ画面の選択コマンドでId_*とV*を対で更新する。
- 理由: BaseMenteViewModel.CreateUpdateParamはエンティティ全体を送るため、一覧SQLでV*列を選択しないと修正保存時に空値で上書きされる。参照Idを変更する経路ではサーバ側の伝播は改名時にしか走らないため。
- 影響範囲: MasterYosanHanbaiMenteViewModel, MasterSysKanriMenteViewModel, MasterYosanBrandMenteViewModel, ExternalCsvImportViewModel, MasterShohinMenteViewModel
- 出典: aicoding_log_011.md [2026-07-29]

### 1.5 V*列一括再同期(Msg047)は失敗時に成功扱いしない、全件再同期は走査回数削減で高速化

- 判断: 一括再同期で一部ルールだけ失敗した場合は成功扱いにせずCode<0で返す(応答のDataMsgは「更新行数=N」の文字列)。全件再同期の性能問題は原因がインデックス不足ではなく同一テーブルを列ごとに何度も全走査する構造だったため、Id_*列へのインデックス追加ではなく走査回数自体を削減する方針(22回→10回等)を採った。この結果、応答の更新行数の意味が「列ごとの合計」から「更新された行数」に変わった。
- 理由: 更新0件=既に同期済み、と更新0件=全ルール失敗、を利用者が区別できないと修復したつもりで放置される危険がある。全件再同期は本質的に全走査が必要なため、インデックスでは速くならない。
- 影響範囲: CodeShare.CvFlag.Msg047_MasterVColumnResync, HandlerClass.HandleMasterVColumnResync, CvDomainLogic/MasterCascadeDb.cs ResyncAll, Tests/TestServerの期待値
- 出典: aicoding_log_011.md [2026-07-27]

### 1.6 Tran系V*列の物理保持方式は現状維持

- 判断: 現状の物理保持(方式1)、`[ComputedColumn]`+SQL再構成(方式2)、Idのみ保持+JOIN(方式3)を比較検討した結果、Tran系V*列は伝票時点の監査値として現状維持(変更しない)と結論した。
- 理由: 方式3はCodeNameView統一パターンを崩し改修量が最大になるため非推奨。Tran系V*列は業務監査上、伝票時点の名称を保持することが本質的要件である。
- 影響範囲: TranAllHeader派生の全伝票テーブル(AGENTS.mdのV*列不変条件として明文化済み)
- 出典: aicoding_log_011.md [2026-07-26]

### 1.7 V*列は選択時にインスタンス丸ごと差し替え、コード範囲条件はId化しない

- 判断: V*列は`[ObservableProperty]`かつ選択時に必ずインスタンス丸ごと差し替え、内部プロパティへの直接代入(V*.Cd=...等)はしない。帳票/集計系の「～CodeFrom/～CodeTo」範囲条件(78ファイル)は意図的にId化していない。
- 理由: SQLの範囲条件がコード順に依存しており、Id順へ変えると抽出結果が変わる仕様変更になるため。
- 影響範囲: V*列(CodeNameView)を持つ全マスタ・伝票系ViewModel
- 出典: aicoding_log_011.md [2026-08-03]

### 1.8 検索TextBox付き項目の表示規約と帳票印字のV*列書式

- 判断: 同一行にId編集用のSearchTextBoxAssistがある項目は「コード 名称」表示(ConverterParameter=NoId)とし、一覧(DataGrid)列と選択ウィンドウのプレビューは「(Id) コード 名称」のまま維持する。帳票印字も画面用書式(CodeNameDisplay.Format)と帳票SQL用書式(CodeNameDisplay.Sql/SqlFromVColumn)を同一クラスに集約し、印刷用SQLで手書き結合(||)はしない。
- 理由: Id省略可否は「隣にId入力欄があるか」という画面構造で機械的に決まる。書式のC#版とSQL版を別ファイルに置くと必ずdriftするため。
- 影響範囲: CvWpfclient/Views全体(20ファイル・56箇所)、CodeNameViewDisplayConverter.cs、伝票入力系印刷SQL全般
- 出典: aicoding_log_011.md [2026-08-03]

## 2. 更新経路・サーバ処理（DB・SQL）

- 判断: `SchedulerTaskInfo.IsEnabled`の初期化子`=true`を削除した。protobuf-netはboolの既定値`false`をワイヤに載せないため、初期化子で`true`を持たせるとサーバが返した`false`が受信側で`true`のまま残る不具合になる。今後、protobuf-net DTOのbool初期化子には既定値falseを前提とする。

### 2.8 配分は「確定で即伝票作成」の1段階、確定取消なし（旧決定 I3 / I6 の変更）

- 判断: 配分(TranHaibun)の確定は、確定数の反映・有効在庫の再検査・出荷売上/移動伝票の作成・EndFlag=1(引当解除)を1トランザクションで行う(`HaibunCommitParam` → `ShippingDb.Commit`)。旧CV.net由来の「出荷指示確定 → 出荷処理入力」の2段階(I3)と、実数量を出荷処理入力で入れる方式(I6)は廃止し、確定数は配分確定画面で入れる。確定取消は設けず、訂正は作成された伝票側で行う(D9)。在庫検査式は「実在庫 − (引当数 − 確定対象の引当分) − 確定数 ≧ 0」とし、引当外の仕入配分(Kubun=0)の数量も必ず差し引く。配分の洗い替え保存は `HaibunSaveParam` で削除・登録・引当引き直しを1トランザクションにし、修正可能条件(`SendFlg=0 AND EndFlag=0 AND KakuteiDay=''`)をサーバで強制する。
- 理由: 利用者判断(2026-10-03、配分再設計 D8/D9)。配分を「指示データ」、確定を「実伝票を作る唯一の入口」に揃えるため。旧2段階では確定済み・未出荷の中間状態と確定取消が必要になり、状態が複雑だった。旧検査式は仕入配分の数量を見ておらず在庫不足でも確定できた。旧保存はDeleteBulk/InsertBulkの別トランザクションで途中失敗時に指示が消え、店舗配分入力は確定済み・未送信の指示も洗い替えで消し得た。
- 影響範囲: CvDomainLogic/ShippingDb.cs, CvDomainLogic/AllocationRules.cs, CvServer/Services/HandlerClass.cs, 配分確定(商品/得意先)・滞留欠品例外・出荷指示明細書・配分入力3画面。出荷処理入力画面は削除。滞留の定義は「未確定のまま指示日からN日経過または納品日超過」へ変更
- 出典: Doc/spec/archive/2026-10-03_配分再設計_基本設計.md。対応実装: CvDomainLogic/ShippingDb.cs, CvServer/Services/HandlerClass.cs
- 現行補足: 上記の「区分0は引当外」は後続の2.9で変更済み。現在の区分0の引当数量は`ArrivedSu`であり、引当・確定の判断には2.9を併せて参照する。

### 2.9 仕入配分(区分0)は入荷済み数(ArrivedSu)だけを引当・確定の対象にする（旧「区分0は引当外」の変更）

- 判断: `TranHaibun.ArrivedSu`（入荷済み数）を追加し、引当の対象を `EndFlag=0` の全区分、数量を「区分0は ArrivedSu、それ以外は未確定なら Su・確定済みなら JitsuSu」とする。ArrivedSu は発注×SKU ごとに「発注と同じ倉庫への仕入数（CalcFlag 符号付き）− 確定済み仕入配分の JitsuSu」を、未完了の仕入配分へ店舗コード→Id 順に割り当てた値で、`ArrivalDb.Recalc` が仕入の書き込み・HHT取込・配分保存・配分確定の前後・全件再集計で再計算する。区分0の新規行は発注Id(RelateNo1)必須、確定数は ArrivedSu 以下。発注に紐付かない既存の区分0は migration で ArrivedSu=Su（入荷済み扱い）。

### 2.13 TranHaibun はフラット行（1行=1SKU）＋仮想ヘッダを維持し、ヘッダ・明細構造化は採らない

- 将来の再検討条件: 配分No や計算条件の保存が必要になった時点で再検討する。その場合もキーは上記6列、明細は JSON 内包ではなく実テーブル（例 `TranHaibunMeisai`）とし、`TranHoju` も同時に扱う。製品内で唯一の2テーブル伝票となり `BaseTranInputViewModel` の再利用は失われる。

### 7.1 明細が JSON null の伝票で SummaryStock 再集計が NOT NULL 違反になった（2026-09-01）

- 症状: 締日変更後の在庫再集計（2019/05〜2026/09・全て）で `NOT NULL constraint failed: SummaryStock.InQty`。
- 原因: `CROSS JOIN json_each(t.Jmeisai)` は、`Jmeisai` が JSON 配列でなく JSON null（文字列 `"null"`）のとき、`key`・`value` が NULL の1行を返す。この行で `Id_Shohin`・`Su` 系の集計式が全て NULL になり、同一グループに実データ行が無いと `SUM` が NULL のまま `InQty` へ挿入された。該当は明細を持たない `Tran03Shiire`（Id=8609〜8614、DenDay 2026/07/06〜07/14）。
- 修正: `CreateSummaryStockSql` / `CreateRealStockSql` の WHERE に `json_type(t.Jmeisai) = 'array'` を追加した。現行の `SummaryDb` に加え `StocktakeDb`・`CostUpdateDbConsumption` の同種 SQL も同じ条件を持つ。
- 再発防止: Tran の明細 JSON を `json_each` で展開する SQL は、配列でない行を `json_type` で除外する（AGENTS.md §7.1 の JSON 防御と同趣旨）。画面で入力された明細なしの仕入伝票（`OldSeqNo=0`・`Jmeisai=null`・`KingakuTotal` に実額）は、旧DB再変換の `isInit=true`（drop table）で消えるため、再変換の前に退避する。
- 出典: commit `3e5d2fb4`、[SummaryDb](../../CvDomainLogic/SummaryDb.cs)

### 7.2 SysHistAutoexec.ElapsedTime の型変更に UpdateDb の移行が漏れていた（2026-09-03）

- 症状: 自動実行履歴画面で `Unable to cast object of type 'System.Int64' to type 'System.Double'`。
- 原因: commit `5ca83eff`（2026-08-31）で `ElapsedTime` を int→double に変えたが、既存の物理DBの列定義へ追随する `UpdateDb` の移行が無かった。SQLite の `NUMBER`（NUMERIC 親和性）列は整数値を INTEGER で保存し、NPoco が `double` へキャストできなかった。新しい行は小数のため REAL で保存され問題にならなかった。
- 修正: `UpdateDb` にバージョン `26_09_03_01` を追加し、列を `double(14,8)` へ付け替えた（`+ 0.0` で既存値を実数のまま保持）。複製DBで全行が `typeof=real` になることを確認している。
- 再発防止: 列の型・長さを変えるときは、定義属性の変更だけで済ませず `UpdateDb` の移行を同じ変更に含める（AGENTS.md §7.5）。属性変更は既存DBの物理列に反映されない。
- 出典: commit `5ca83eff`、[UpdateDb](../../CvBase/UpdateDb.cs)

### 7.3 履歴 Memo の列幅が既定（255）のまま300文字を書こうとしていた（2026-09-07）

- 内容: マニュアル排他制御の試験（Step T0〜T9）で、履歴テーブルの `Memo` が列幅未指定（既定255）なのにアプリが300文字まで書こうとする潜在不具合を見つけ、`[ColumnSizeDml(2000)]` へ拡張した。強制クリア履歴へ端末情報を追記するための拡張でもある。
- 制約: 属性の変更は既存DBの物理列を広げない。SQLite は TEXT のため影響しないが、PostgreSQL の既存DBは別途 `ALTER TABLE` が必要。`UpdateDb` に勝手に追加せず、試験計画書の宿題として記録した。
- 出典: [BaseDb0Config](../../CvBase/BaseDb0Config.cs)、[ManualLockDb](../../CvDomainLogic/ManualLockDb.cs)（`HistoryMemoMaxLength`）

### 7.5 MariaDB で列0個の CREATE TABLE が生成されていた（2026-08-25）

- 原因: 基底 `ExDatabase.GetSqlColumns` の `GetProperties(BindingFlags.Public)` は `Instance` / `Static` を指定しないと何も返さない。SQLite と PostgreSQL は override しているため影響せず、MariaDB だけがテーブルを作れない状態だった。
- 修正: `Public | Instance` を指定し、回帰テストを追加した（commit `8f4c5981`）。
- 未修正のまま許容した差: `DerivedJodai.TodaySql`（static の SQL 式プロパティ）が SQLite の DDL にだけ余剰列として現れる。稼働中の SQLite の DDL を変えないため直さず、`Tests/TestSqlDialect` の既知差一覧で許容している。
- 見積り訂正: MariaDB の整数除算は「`/` を含むファイル147」ではなく、字句解析で SQL リテラルだけを数えると13本、`strftime('%w')` の算術は1本だった。

### 7.6 AI照会の504は前段のリバースプロキシが60秒で切断していた（2026-10-19）

- 症状: クラウド環境の `Msg091_AiQueryChat` が `Unavailable / HTTP status code: 504`。
- 調査: サーバログで、要求全体が 60,010ms ちょうどで打ち切られ、`context.CancellationToken` のキャンセルで実行中の LLM 呼出（3回目）が `TaskCanceledException` になっていた。CvServer の LLM タイムアウト（`AiQuery:TimeoutSeconds=180`）とクライアントのタイムアウト（10分）には達していない。1対話で LLM を複数回呼び、1回20〜25秒かかることがある。
- 結論: nginx の `grpc_read_timeout` / `proxy_read_timeout` の既定60秒が原因と推定した。コード変更は不要で、`grpc_read_timeout` / `grpc_send_timeout` を 600s へ延ばす（ALB・Cloudflare 等を経由する場合は各アイドルタイムアウトも延ばす。Cloudflare 無料プランは100秒が上限）。
- 未確認: プロキシ設定はリポジトリに無く、実サーバの設定は確認していない。業務辞書 `AiQueryDictionary.md` が配置されていない警告は別件で、SQL生成精度に影響する。
- 出典: 2026-10-19 のセッション記録

### 7.7 Linux 配置で System.Transactions.Local.dll が見つからなかった（2026-09-11）

## 8. セッションで確定した設計判断（補足）

### 8.1 期首残高は外部CSV取込で対応し、再計算は期首以降に限る

- 判断: 期首残高の専用入力画面は作らない。外部CSV取込で Summary 系の各テーブルへ「期首の前年月」として投入し、再計算は期首以降だけを対象にして、期首前年月の残高行を再計算で潰さない。
- 理由: 期首残高は移行時の初期値で、伝票から再集計できない。
- 実装: `SummaryDb` に期首ガード（`GetFiscalStartDate()` ほか）を追加し、単体テスト3件を加えた。取込は [OpeningBalanceCsv](../../CvBase/OpeningBalanceCsv.cs) / [OpeningBalanceDb](../../CvDomainLogic/OpeningBalanceDb.cs)。
- 出典: commit `e2360f55`（2026-08-19）

### 8.2 残高は期間集計とし、前月残は表示専用の PreviousBalance で持つ

- 判断: 残高系の Summary テーブル4つへ表示専用列 `PreviousBalance` を追加し、再計算ロジックの繰越除去と `Sonota` 統一を行った。帳票10本は `PreviousBalance` を使い、期首残高CSVも符号反転と `Sonota` 展開に合わせた。既存データは `UpdateDb` の `26_09_02_02` が `Balance` の符号を反転する。
- 検証: 当時、実データ（202608）で4帳票（2,357／502／1,604／502件）の「前月残＋当月増減＝当月残」の差分が0、バッチを2回続けた実行で `SummaryUriSei` / `SummaryKaiShi` の件数・合計が一致、TestServer 264件が成功した。
- 適用時の影響: 承認事項として、支払額が区分99の分だけ増えること、前月残の値が変わる取引先があることを確認している。適用後は期首日以降の全期間で売掛残・買掛残・請求・支払を再計算する。実データへの適用は人が行う。
- 出典: commit `b792ae3`〜`f7bc2e0`（2026-09-01〜02）、[BaseDbKake](../../CvBase/BaseDbKake.cs)

### 8.3 税率は0%を10%へ読み替えない（TaxRateResolver）

- 判断: `ResolveTaxRatePercent` と `SummaryDb.LoadTaxRateDefs` の「0% → 既定10%」の読み替えを廃止し、0%は0%のままにした。`Jsub` に該当 `Id_Tax` の定義が無い（マスタ未整備）場合だけ10%に倒す。0を返すと課税漏れになるため。`DateFrom` による新旧税率の切替判定は `ResolveRateOf` に1本化した。
- 注意（既知の仕様）: `CvAsset.Common.CompareYmd(ymd1, ymd2)` は `ymd2` が初期値 `19010101` 以下なら必ず -1 を返す。旧CVnet実データの `MasterSysTax` Id=3（`TaxRate=15`・`DateFrom=19010101`・`TaxNewRate=0`）は `TaxNewRate=0` が効かず常に15%で解決される。15%は実在しない税率なので、Id=3 を商品へ割り当てない。

### 8.4 在庫管理外（IsZaiko=0）の側は在庫集計を作らない

- 判断: `CreateSummaryStockSql` / `CreateRealStockSql` は `MasterTokui`・`MasterShohin` を LEFT JOIN し、`COALESCE(IsZaiko, 1) = 1` の行だけを集計する。マスタ行が無い場合は管理対象（従来どおり）とみなす。移動元・移動先・商品はそれぞれ独立に判定するため、管理あり↔なしの移動では管理している側だけ増減が記録される。

### 8.5 諸掛は総平均原価にだけ算入し、最終仕入原価には算入しない

- 判断: 原価4項目の設計で、生地付属仕入の諸掛は総平均原価にだけ算入し、最終仕入原価（`AfterCost = round_away(明細.Kingaku / 明細.Su)`）には加算しない。`CostMethod=1`（最終仕入原価）で運用すると、入力した諸掛は商品原価へ反映されない。この旨は諸掛確認画面に表示する、と設計書に記載している。
