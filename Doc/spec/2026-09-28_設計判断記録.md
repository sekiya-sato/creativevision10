## 1. マスタ V* 列・名称伝播（DB・SQL）

### 1.1 マスタV*列の伝播は明示マップ(CascadeVRule)を唯一の正とする

- 判断: Master系V*列の伝播はSQLのUPDATEで行い（十万行規模を1行ずつ処理しない）、`[ForeignKey]` からの自動導出はせず明示マップ `MasterCascadeDb.VRules`（当時22件・現行33件）を唯一の正とする。伝播対象のJSON列は `json_valid()` で必ずガードする。
- 理由: `Id_Paysaki` は宣言型ごとに参照先が異なり属性では表せない。`ALTER TABLE ADD COLUMN DEFAULT ''` 直後の空文字1行で json_extract が例外となり、マスタ改名がロールバックした実害があった。
- 影響範囲: CvDomainLogic/MasterCascadeDb.cs（伝播元 MasterMeisho/MasterTokui/MasterShain/MasterShiire）。出典: aicoding_log_011 [2026-07-27]

### 1.2 マスタ更新時のV*列伝播フックの発動条件と自己参照時のVdu整合

- 判断: 伝播要否は `NeedsCascade`（伝播元4型かつCode/Name変化時）で判定する。`CascadeFromMaster` には HandleUpdate の vdate をそのまま渡し、同一トランザクション内で実行してSQLエラーは送出する。
- 理由: 請求先が自分自身の得意先で伝播側が別に vdate を採番すると、返却Vduとずれ次回保存が楽観排他で弾かれる。マスタだけ更新されV*が古い状態を作らない。
- 影響範囲: CvServer/Services/HandlerClass.cs HandleUpdate。出典: aicoding_log_011 [2026-07-27]

### 1.3 Jsub等JSONスナップショットの伝播ルールとKb/Kbnameの意味確定

- 判断: Jsubの `Kb` は `MasterMeisho.Kubun`、`Kbname` は `Kubun='IDX'` かつ `Code=Kb` 行の `Name`。KubunName の伝播から `Kubun='IDX'` 行自身を除外する。区分コード自体の変更は伝播せず警告ログのみ。DerivedShohinColSiz は Delete→Insert で再構築する。
- 理由: 実コードから確定させた仕様で、誤解を避けるため明文化した。区分体系の変更は伝播では解決できない。
- 影響範囲: MasterCascadeDb.cs、MasterShohin.Jcolsiz、DerivedShohinColSiz、MasterMeisho.KubunName。出典: aicoding_log_011 [2026-07-27]

### 1.4 Master系V*列は物理列でも「常に現行名称」、クライアント側の同時更新責務

- 判断: Master系V*列は「常に現行名称」が不変条件。サーバ伝播はマスタ改名時だけなので、参照Idを変える画面・新規登録経路ではクライアントがV*列を同時に埋める。商品の VTenji/VSeason/VMaterial/VCountry も `[ForeignKey(meishoKubun:…)]`（TNJ/SZN/SZI/GEN）を正として Id_* と V* を対で更新する。
- 理由: `BaseMenteViewModel.CreateUpdateParam` はエンティティ全体を送るため、一覧SQLでV*列を選ばないと修正保存で空値上書きになる。
- 影響範囲: MasterYosanHanbai/MasterSysKanri/MasterYosanBrand/MasterShohin 各メンテ、ExternalCsvImportViewModel。出典: aicoding_log_011 [2026-07-29]

### 1.5 V*列一括再同期(Msg047)は失敗時に成功扱いしない、全件再同期は走査回数削減で高速化

- 判断: 一部ルールが失敗したら Code<0 で返す（DataMsg は「更新行数=N」）。全件再同期の高速化は索引追加ではなく同一テーブルの全走査回数の削減（22回→10回等）で行い、更新行数の意味は「列ごとの合計」から「更新された行数」に変わった。
- 理由: 「0件=同期済み」と「0件=全失敗」を区別できないと修復したつもりで放置される。全件再同期は本質的に全走査なので索引では速くならない。
- 影響範囲: `CvFlag.Msg047_MasterVColumnResync`、HandleMasterVColumnResync、MasterCascadeDb.ResyncAll。出典: aicoding_log_011 [2026-07-27]

### 1.6 Tran系V*列の物理保持方式は現状維持

- 判断: 物理保持（方式1）・`[ComputedColumn]`+SQL再構成（方式2）・Idのみ+JOIN（方式3）を比較し、Tran系V*列は伝票時点の監査値として現状維持とした（AGENTS.md §7.1）。
- 理由: 伝票時点の名称保持が業務監査上の要件。方式3は CodeNameView の統一パターンを崩し改修量が最大。出典: aicoding_log_011 [2026-07-26]

### 1.7 V*列は選択時にインスタンス丸ごと差し替え、コード範囲条件はId化しない

- 判断: V*列は `[ObservableProperty]` で、選択時は必ずインスタンスを丸ごと差し替える（`V*.Cd=...` の直接代入をしない）。帳票・集計の「～CodeFrom/～CodeTo」範囲条件はId化しない。
- 理由: 範囲条件はコード順に依存しており、Id順に変えると抽出結果が変わる仕様変更になる。出典: aicoding_log_011 [2026-08-03]

### 1.8 検索TextBox付き項目の表示規約と帳票印字のV*列書式

- 判断: 同一行にId入力欄（SearchTextBoxAssist）がある項目は「コード 名称」（ConverterParameter=NoId）、一覧列と選択ウィンドウのプレビューは「(Id) コード 名称」。画面用書式（`CodeNameDisplay.Format`）と帳票SQL用書式（`CodeNameDisplay.Sql`/`SqlFromVColumn`）は同一クラスに置き、印刷SQLで `||` の手書き結合をしない。
- 理由: Id省略可否は画面構造で機械的に決まる。C#版とSQL版を分けると必ずずれる。出典: aicoding_log_011 [2026-08-03]

### 2.2 消込のPartialUpdate経路(禁止列リスト方式)と部分更新の楽観排他

- 判断: Tran00Uriage/Tran03Shiire の `EndFlag` による伝票単位の消込とし、付随処理（在庫再集計・V*伝播・Derived更新）を通さない専用経路 `PartialUpdateParam`/`HandlePartialUpdate` を設ける。対象列は禁止列リスト方式。楽観排他は `PartialUpdateRow.ExpectedVdu` の `WHERE Id=@ AND Vdu=@ExpectedVdu` で、1件でも競合すれば全体をrollbackする。FIFO自動充当・`TranKesikomi` 案は廃止。

### 2.3 月次自動再集計と上代パージの実行方式

### 2.12 サーバ SQL はすべて方言変換を通し、変換しない書き方の差は正典側で3DB共通に書く（2026-11-05）

- 判断: 配分（`ShippingDb`・`ReservationDb`）を含むサーバSQLは `FetchDialect` / `ExecuteDialect` を通す（SQLite では `Fetch` / `Execute` と同じ）。変換器で書き換えない書き方の差は、SQLite の意味を変えない3DB共通の形で正典側に書く。
  - `WITH … INSERT` は `INSERT INTO t (列…) WITH … SELECT`。派生表には必ず別名。
  - `UPDATE … SET (a, b) = (SELECT …)` は列ごとのスカラー副問合せ。
  - `date()` の可変修飾子は `'+' || n || ' months'` の連結形。整数除算は割り切れる形（`(a - a % 100) / 100`）。`ON CONFLICT … DO UPDATE` の加算列は表名で修飾する。
  - 関数の意味差は変換ルールで吸収する（MariaDB の `length` → `CHAR_LENGTH`、`printf`、`json_type` など）。
- 経緯: 配分SQLの変換対応は一時延期していたが、DB切替（§2.19）の実DB検証に合わせて解消し、3DB対応は利用者判断（2026-11-06）で完了扱い。
- 回帰検出: 変換を通らない実行・`INSERT OR`・`WITH … 更新文`・派生表の別名なし・行値の一括代入は `SqlRouteInventoryTests` が静的に検出する（`UpdateDb` の移行SQLは対象外）。
- 残る制約: `UpdateDb` の移行SQLは方言別に未定義。棚卸の MariaDB / PostgreSQL 実行と在庫の3DB比較は未確認。JSON の `Id_*` は `cast(… as integer)`（PostgreSQL int4）で、Id が 2^31 を超える運用では見直す。詳細は [SQL方言変換 実DB検証結果](../test/2026-11-04_SQL方言変換_実DB検証結果.md) §5・§5.1。出典: commit `ab5c4ef1`・`62416ed3`・`1425b764`

### 2.13 TranHaibun はフラット行（1行=1SKU）＋仮想ヘッダを維持し、ヘッダ・明細構造化は採らない

### 3.7 残高計算には必ずヘッダの CalcFlag を使い、元帳の借方・数量は伝票の正値で表示する

- 判断: 売上・仕入系伝票の返品・値引（Kubun 20〜39）は数量・金額・税を正値で保持し、符号はヘッダ `CalcFlag`（`TranCalcBase.GetKubunCalcFlag`: 20〜39 が −1）が決める。残高・繰越・合計など符号付き集計では必ず `h.CalcFlag *` を掛ける。売掛・買掛元帳（`TokuiLedgerViewModel` / `ShiireLedgerViewModel`）は次の規則とする。
  - 繰越: 期間前の伝票金額を `h.CalcFlag * 金額` で借方に集計し、入金・支払（貸方）を引く。
  - 期間内の行: 借方・数量は正値で表示し（返品は区分名で識別）、残高の増減だけ `借方 × CalcFlag − 貸方` とする。入金・支払行の係数は1。
  - 返品を貸方へ振り替える方式は採らない。
- 注意: 既に符号付きの値（在庫調整 `Tran61Chosei` の明細 Su、旧ポイント履歴の負数など）や `SummaryDb.SignExpr` 等で符号適用済みの集計値へ二重に掛けない。明細とヘッダの合計を独立集計で照合する。
- 理由: 掛けないと返品が加算され残高が返品額の2倍ずれる。表示金額と qfm はそのまま、残高だけを正す最小変更とした。

## 7. 不具合修正の履歴（AIエージェントのセッションから）

> 2026-10-28 に agentsview の実行履歴から原因調査と修正が記録された不具合を抽出し、修正が現行ソースにあることを確認した（7.6・7.7 は運用上の調査結果）。§7.8 は以後のコミットから追加。

### 7.1 明細が JSON null の伝票で SummaryStock 再集計が NOT NULL 違反になった（2026-09-01）

- 原因: `CROSS JOIN json_each(t.Jmeisai)` は `Jmeisai` が JSON null のとき `key`・`value` が NULL の1行を返し、`SUM` が NULL のまま `InQty` へ挿入された（明細なしの `Tran03Shiire` Id=8609〜8614）。
- 修正: `CreateSummaryStockSql` / `CreateRealStockSql` に `json_type(t.Jmeisai) = 'array'` を追加。`StocktakeDb`・`CostUpdateDbConsumption` の同種SQLも同じ条件（変換ルール B09 で MariaDB / PostgreSQL へ変換）。
- 再発防止: 明細JSONを `json_each` で展開するSQLは配列でない行を `json_type` で除外する（AGENTS.md §7.1）。画面入力の明細なし仕入伝票（`OldSeqNo=0`・`Jmeisai=null`）は旧DB再変換の `isInit=true` で消えるため事前に退避する。出典: commit `3e5d2fb4`

### 7.2 SysHistAutoexec.ElapsedTime の型変更に UpdateDb の移行が漏れていた（2026-09-03）

- 原因: commit `5ca83eff` で `ElapsedTime` を int→double に変えたが `UpdateDb` の移行が無く、SQLite の NUMERIC 親和性列に整数で保存された既存行を NPoco が `double` へキャストできなかった。
- 修正: `UpdateDb` `26_09_03_01` で列を `double(14,8)` へ付け替え（`+ 0.0` で実数化）、複製DBで全行 `typeof=real` を確認。
- 再発防止: 列の型・長さの変更は定義属性だけでなく `UpdateDb` の移行を同じ変更に含める（AGENTS.md §7.5）。

### 7.3 履歴 Memo の列幅が既定（255）のまま300文字を書こうとしていた（2026-09-07）

- 内容: マニュアル排他制御の試験で、履歴 `Memo` が既定255なのに300文字まで書く潜在不具合を見つけ `[ColumnSizeDml(2000)]` へ拡張した。
- 制約: 属性変更は既存DBの物理列を広げない（SQLite は TEXT で影響なし、DB切替で作った MariaDB / PostgreSQL は2000）。それ以前からの MariaDB / PostgreSQL 既存DBは別途 `ALTER TABLE` が要る（§2.12）。出典: CvBase/BaseDb0Config.cs、ManualLockDb（`HistoryMemoMaxLength`）

### 7.4 HHT取込明細に上代一括変更が反映されていなかった（2026-09-10）

- 調査・修正: 全画面を調べ、漏れは HHT取込だけだった（原価改定の元上代・商品マスタは定価が正、売上分析は伝票時点のため対象外）。`HhtProcessUpdateMap` で `JodaiDb.ResolveJodaiList` を伝票グループ単位に呼び `Jodai`・`Gedai` を入力系画面と同じ判定軸で引き直す。出典: commit `cd432133`

### 7.5 MariaDB で列0個の CREATE TABLE が生成されていた（2026-08-25）

- 原因・修正: 当時の基底 `GetSqlColumns` が `GetProperties(BindingFlags.Public)` で何も返さず、MariaDB だけ表を作れなかった。`Public | Instance` を指定し回帰テストを追加（commit `8f4c5981`）。
- 現行補足（2026-11-12）: 列定義の生成は各プロバイダーへ移り、基底は共通の列選択（`GetColumnProperties`、public インスタンスのみ）だけを持つ（§2.21）。SQLite が static の `DerivedJodai.TodaySql` を余剰列として作っていた差も新規DBでは解消した（既存DBの列は残す。commit `7349f493`）。
- 見積り訂正: MariaDB の整数除算は字句解析で SQL リテラル13本、`strftime('%w')` の算術1本だった（書き方は §2.12）。出典: commit `ce4c7f20`・`8f4c5981`

### 7.6 AI照会の504は前段のリバースプロキシが60秒で切断していた（2026-10-19）

- 調査: クラウド環境の `Msg091_AiQueryChat` が504。要求全体が 60,010ms で打ち切られ、LLM呼出（1対話で複数回、各20〜25秒）がキャンセルされていた。CvServer（180秒）・クライアント（10分）のタイムアウトには達していない。
- 結論: nginx の `grpc_read_timeout` / `proxy_read_timeout` 既定60秒が原因と推定。コード変更は不要で `grpc_read_timeout` / `grpc_send_timeout` を 600s に延ばす（ALB・Cloudflare 等も同様。Cloudflare 無料プランは100秒上限）。
- 未確認: 実サーバのプロキシ設定と `AiQueryDictionary.md` の実サーバ配置は確認していない。出典: 2026-10-19 のセッション記録

### 7.7 Linux 配置で System.Transactions.Local.dll が見つからなかった（2026-09-11）

- 対処: 個別DLLのコピーをやめ、`dotnet publish CvServer/CvServer.csproj -r linux-x64 --self-contained true` の出力を丸ごと同期する。起動は apphost（`chmod +x`）。framework-dependent のまま運用する場合は `runtimes/` を必ず含める。
- 未解明: framework-dependent 構成が動かなかった理由は未調査。出典: 2026-09-11 のセッション記録

### 7.8 強制再作成で索引が作られない・親の列構成で作り直される不具合（2026-11-12）

- 原因・修正: MariaDB は `DROP INDEX` に `ON 表名` が必須で、強制再作成（`CreateTable(isForce:true)`）が構文エラーになり索引が作られなかった（`GetSqlDropIndex` を MariaDB で上書き）。`SummaryStock` は親 `SummaryRealStock` と同名の一意索引を別の列構成で持ち、強制再作成で親の構成（年月なし）に作り直されていた（同名の索引は派生クラスの定義だけを使う）。同時に SQLite の列挙型列を `NUMBER`（TEXT では読み戻せない）、MariaDB の `ColumnSizeDml` で型なし列になる不具合を直した。
- 確認: 全テーブルの CREATE 文は `TodaySql` 列の除外以外、変更前と同一（コミット記載。本書では再実行していない）。出典: commit `7349f493`、CvBase/ExDatabase.cs

## 8. セッションで確定した設計判断（補足）

> 2026-10-28 に agentsview の実行履歴から §1〜§6 に無かった判断を補った。

### 8.1 期首残高は外部CSV取込で対応し、再計算は期首以降に限る

- 判断: 期首残高の専用画面は作らず、外部CSV取込で Summary 系各テーブルへ「期首の前年月」として投入する。再計算は期首以降だけを対象にし、期首前年月の行を潰さない。
- 理由: 期首残高は移行時の初期値で伝票から再集計できない。
- 実装: `SummaryDb` の期首ガード（`GetFiscalStartDate()` ほか）、[OpeningBalanceCsv](../../CvBase/OpeningBalanceCsv.cs) / [OpeningBalanceDb](../../CvDomainLogic/OpeningBalanceDb.cs)。出典: commit `e2360f55`（2026-08-19）

### 8.2 残高は期間集計とし、前月残は表示専用の PreviousBalance で持つ

- 判断: 残高系 Summary 4表に表示専用列 `PreviousBalance` を追加し、再計算の繰越除去と `Sonota` 統一を行った。帳票10本は `PreviousBalance` を使い、期首残高CSVも合わせた。既存データは `UpdateDb` `26_09_02_02` が `Balance` の符号を反転する。
- 検証（当時）: 実データ202608で4帳票の「前月残＋当月増減＝当月残」の差分0、バッチ2回の結果一致、TestServer 264件成功。
- 適用時の影響: 支払額が区分99の分だけ増え、前月残が変わる取引先があることを承認済み。適用後は期首日以降の全期間を再計算する。実データへの適用は人が行う。出典: commit `b792ae3`〜`f7bc2e0`

### 8.3 税率は0%を10%へ読み替えない（TaxRateResolver）

- 判断: `ResolveTaxRatePercent` と `SummaryDb.LoadTaxRateDefs` の「0%→10%」読み替えを廃止した。`Jsub` に該当 `Id_Tax` の定義が無い（マスタ未整備）場合だけ10%に倒す（0にすると課税漏れになる）。新旧税率の切替判定は `ResolveRateOf` に1本化。
- 注意（既知の仕様）: `CvAsset.Common.CompareYmd(ymd1, ymd2)` は `ymd2` が `19010101` 以下なら必ず -1 を返す。旧CVnet の `MasterSysTax` Id=3（`TaxRate=15`・`DateFrom=19010101`・`TaxNewRate=0`）は常に15%で解決されるため、Id=3 を商品へ割り当てない。出典: commit `6e8103b3`（2026-09-01）

### 8.4 在庫管理外（IsZaiko=0）の側は在庫集計を作らない

- 判断: `CreateSummaryStockSql` / `CreateRealStockSql` は `MasterTokui`・`MasterShohin` を LEFT JOIN し `COALESCE(IsZaiko, 1) = 1` だけを集計する（マスタ行なしは管理対象）。移動元・移動先・商品は独立に判定し、管理あり↔なしの移動では管理側だけ増減する。試験データの倉庫も `IsZaiko` に注意する（原価UATで倉庫 Id=1 が対象外だった）。出典: 2026-08-31 のセッション記録

### 8.5 原価4項目: 諸掛は総平均原価にだけ算入し、最終仕入原価は0円明細を採用しない

- 判断: 生地付属仕入の諸掛は総平均原価にだけ算入し、最終仕入原価（`AfterCost = round_away(明細.Kingaku / 明細.Su)`）には加えない。`CostMethod=1` では諸掛が商品原価に反映されない旨を諸掛確認画面に表示する。2026-09-05 に設計案 U-24（最終仕入原価へも算入）を巻き戻した。
- 現行補足（2026-11-06）:
  - 最終仕入原価は明細金額 > 0 の明細だけを採用し（利用者判断）、0円明細しか無い商品は更新しない。月次状態の対象商品数（`CostUpdateDb.FetchEligibleProductCount`）も同条件（commit `75711a3c`）。
  - 過去月の再計算では前原価に後続月の結果を使わない（利用者判断）。後続月再計算のプレビューは評価替え後の原価で保存値と一致させる（commit `bef8e2c6`）。
  - 受入の「旧CVnet 3か月分と突合」は、旧CV（CV52）が固定原価運用で総平均原価の記録を持たないため2022年実データでの試算・利用者確認に置き換えた（利用者判断）。[原価2022年試算](../test/2026-11-06_原価2022年試算.md)・[原価3か月UAT手順](../test/2026-11-06_原価3か月UAT手順.md)、状態は [やることリスト](archive/2026-11-05_todolist.md) P1-2。
- 出典: [原価4項目 詳細設計](archive/2026-09-05_原価4項目_詳細設計.md) §3.6・§3.8

### 8.6 手動排他制御は単純に保ち、業務チェックの中断では排他を解放する

- 判断: 手動ロックの目的は長時間タスク中の割り込み防止だけで、粒度の細分化・待ち行列・自動リトライを足さない。
- 試験結果（2026-09-07）: 自動E2E 101件成功、製品不具合0件。再起動をまたいで対にならない監視ログ「2b」を閉じるマーカー `[2h:孤立2b補完]` を追加した。
- 中断の区別（2026-11-05）: 業務チェック（支払計算済み範囲、原価方式不一致、対象なし、棚卸の日付違い等）で止めた場合は `ManualLockDb.CompleteBusinessStop` で排他行を解放し、結果コード `2`・メモ先頭 `[業務チェック中断]` の履歴を残す。想定外の例外では行を残し監視タスクか強制クリアで解放する。判定は `ManualLockDb.IsBusinessStopException`（`ArgumentNullException` は除外）。物流連携の想定外例外は再実行運用のため解放し、結果コード `-1` で区別する。
  - 理由: 業務チェック後に行が残ると、条件を直して再実行するまで最短15分待たされた。
- 出典: [ManualLockDb](../../CvDomainLogic/ManualLockDb.cs)、commit `1425b764`
