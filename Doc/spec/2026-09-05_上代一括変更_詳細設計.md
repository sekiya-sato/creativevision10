## 0. 位置づけ

先行検討文書は「上代一括変更を Price Event 方式にする」ことを推奨していたが、**cv10 は既にその方式で実装されている**（`CvBase/BaseDbJodai.cs`、2026-08-11 設計）。

本設計は方式転換ではなく、その Phase 2 に相当する機能追加である。すなわち、

- 店舗価格グループ
- 1伝票内の段階値下げ（Markdown Ladder）
- 店別 × 期間別の例外価格
- Price Matrix / Timeline
- シミュレーション（確定前プレビュー）／ 競合検出

を、既存の `TranJodai` / `DerivedJodai` を壊さずに積み増す。

### 0.1 先行文書の未決事項に対する回答

先行文書が「別途 Architecture Board で決定する」としていた3点は、いずれも現行実装で既に決着している。本設計はその決定を追認し、明文化する。

| 未決事項 | 決定 | 根拠 |
|---|---|---|
| Rate 方式の基準上代を、イベント作成時点で Snapshot するか、発効時点の通常上代から再計算するか | **作成時点の通常上代を Snapshot する** | `TranJodaiMeisai.JodaiOld` / `JodaiNew` が確定価格を保持し、`DerivedJodai.Jodai` へそのまま展開される。発効時に再計算する経路は無い |
| 終了日をその営業日に含めるか | **Inclusive（その営業日を含む）** | `DerivedJodai.ResolveSql` が `dayExpr BETWEEN dj.DayFrom AND dj.DayTo` |
| 確定後にグループ所属や商品分類が変わったとき対象範囲が動くか | **動かない。確定時に対象商品・対象店舗を Snapshot する** | `Jmeisai` / `Jshop` が確定リスト |

### 0.2 先行文書のうち cv10 で該当しない項目

先行文書の「配信・オフライン考慮」（承認済み価格を発効日前に各店舗／POS へ配信し、店舗側で将来価格を事前保持する）は cv10 では該当しない。cv10 の POS は `PointOfSaleService` 経由でサーバの適用上代を直接引くため、価格そのものの事前配信は不要である。`TranJodai.SendFlg` は**店頭の値札・棚札を差し替えたかどうかの運用管理フラグ**であり、配信 Version 管理は導入しない。

「AI 活用（自然言語から Price Event Draft を生成）」は本設計の対象外とする。

## 2. 基本設計（承認対象）

### 2.1 Scope（適用範囲）の導入

先行文書の「基本ルール＋例外ルール」と「Price Matrix」は、**同じものを別の角度から見たもの**である。本設計はこれを `Scope`（適用範囲）という単一の概念で表す。

```
Jscope（適用範囲）＝ Price Matrix の「列」 かつ 段階値下げの「段」
  範囲（全店 / 価格グループ / 個別店舗）× 期間 × 価格ルール

Jshop（確定時スナップショット）  = 実店舗 → 所属 Scope
Jmeisai（価格セル）              = 商品 × Scope → 確定価格
```

商品と店舗の全直積に価格を持たせると JSON が肥大するため（1000商品 × 100店舗 = 10万セル）、Scope を中間層に置く。JSON の規模は「商品数 × Scope 数」（1000商品 × 3 Scope = 3000セル）に収まる。

展開 SQL は `Jshop.No_Scope = Jmeisai.No_Scope` の等値結合で済み、**`DerivedJodai` の列は増えない**。したがって 1.2 の参照元は無改修である。

### 2.2 用語

| 用語 | 意味 |
|---|---|
| Scope（適用範囲） | 「どの店舗に・いつ・どういう価格ルールで」を1組にしたもの。伝票内で一意な `No` を持つ |
| 価格グループ | 店舗をまとめた分類（全国 / OUTLET / EC / 関東 など）。`MasterTokui` の専用列 3 軸で表す（2.4） |
| 段（Stage） | 同一範囲に対して期間をずらした複数の Scope。段階値下げを表す |
| 基準上代 | 価格計算の基となる価格。`MasterShohin.TankaJodai`（通常上代）を既定とする |
| 確定 | `Status=1`。`DerivedJodai` へ展開され価格が有効になる |

### 2.3 データフロー

```
1. 商品選択（Jcond → Jmeisai の商品行）
      ↓
2. 適用範囲の設定（Jscope）：範囲 × 期間 × 価格ルール
      ↓
3. 価格の確定（Price Matrix：商品 × Scope → JodaiNew）
      ↓
4. プレビュー（対象件数・平均値下率・原価割れ）
      ↓
5. 競合検出（伝票内・他伝票）
      ↓
6. 登録（Status=0。価格は未反映）
      ↓
7. 確定（Status=1）
      │  ├ Jscope を実店舗へ解決し Jshop へ Snapshot
      │  └ DerivedDb が DerivedJodai へ展開
      ↓
8. 価格解決（DerivedJodai.ResolveSql → 無ければ TankaJodai）
```

### 2.4 価格グループ

**新テーブルは作らない。`MasterTokui` に専用列を 3 軸ぶん追加する。**

当初は `MasterTokui.Jsub`（名称リスト）の区分を1つ使う案だったが採らない。`Jsub` は `[ColumnSizeDml(1000)]` の JSON 列で、1要素が `Sid`/`Cd`/`Mei`/`Kb`/`Kbname` を持つため実質 8〜10 件が上限であり、価格グループを入れると利用者向けの `C01`〜`C10` 枠を圧迫する。また「あるグループに属する店舗の一覧」を引くのに `json_extract` の全行走査が要る。

専用列にすることで、

- Scope の解決が `WHERE t.Id_PriceGroup = @g` の等値比較になる（索引も張れる）
- 利用者の `Jsub` 枠を消費しない
- 得意先マスタ保守画面に通常のマスタ項目として入力欄を置ける

#### 2.4.1 3 つの軸

1店舗が複数のグループに属せるよう、直交する 3 軸を持つ。Scope はこのうち 1 軸を指定する。

| 軸 | 列 | 区分 | 例 |
|---|---|---|---|
| 価格グループ | `Id_PriceGroup` / `VPriceGroup` | `C30` | 全国 / OUTLET / EC / FLAGSHIP |
| 地域 | `Id_PriceArea` / `VPriceArea` | `C31` | 関東 / 関西 / 中部 |
| チャネル | `Id_PriceChannel` / `VPriceChannel` | `C32` | 実店舗 / EC / 催事 |

- 区分は `C30`〜`C32`。`C01`〜`C10` は利用者が自由に使う枠として空けておく
- `MasterMeisho` に定数 `KubunPriceGroup = "C30"` / `KubunPriceArea = "C31"` / `KubunPriceChannel = "C32"` を定義し、コードから区分文字列をハードコードしない（`KubunBrand` などと同じ扱い）
- 既存の得意先データは全軸 `0`（未設定）のままとする。未設定の店舗はグループ Scope に該当せず、全店 Scope だけが適用される
- `V*` 列は Master 系なので `MasterCascadeDb.VRules` へ登録する（3.2）

これにより「全国 30% OFF、OUTLET だけ 40%、関西だけ 35%」を Scope 3 件で表せる。

先行文書が挙げていた `StorePriceGroupMember.ValidFrom/ValidTo`（所属期間）は導入しない。対象店舗は確定時に Snapshot されるため、所属期間を持つ必要が無い（0.1）。

#### 2.4.2 名称マスタの初期データ

`MasterMeisho` へ区分名の定義行を追加する（マイグレーション 3.9）。グループの実体（全国 / OUTLET など）は運用で登録するため初期データには入れない。

| Kubun | Code | Name |
|---|---|---|
| `IDX` | `C30` | 価格グループ |
| `IDX` | `C31` | 地域 |
| `IDX` | `C32` | チャネル |

### 2.5 Scope の優先順位と確定時スナップショット

先行文書が示した優先概念

```
個別 Store Override > StorePriceGroup Override > Price Event 基本条件 > 通常上代
```

を、**確定時に画面側で解決して `Jshop` へ焼き込む**。

- Scope の `RangeType` は 0:全店 / 1:価格グループ / 2:個別店舗。数値が大きいほど具体的で優先度が高い
- `IncExc`（0:対象 / 1:除外）を持つ。除外は同一 `RangeType` 内で対象より先に効く
- 1店舗が複数の Scope に該当した場合、`RangeType` の大きい方を採る。同点なら `Odr`、さらに同点なら `Jscope` の並び順で後の方を採る
- 解決結果は「実店舗 → ただ1つの Scope」の対応表となり、`Jshop` に Snapshot される
- **解決の過程で複数 Scope に該当した店舗は競合として画面に提示する**（2.8）。黙って優先順位だけで決着させない

これにより、展開後の `DerivedJodai` では 1店舗 × 1商品 × 1期間 につき常に1行となり、`uk1` の一意性が保たれる。

先行文書の記法でいえば、次の入力がそのまま Scope 3件になる。

```
対象: 全国        2026-09-10 ～ 2026-09-20   30% OFF
除外: 銀座店、新宿店
Override: OUTLET  2026-09-10 ～ 2026-09-20   40% OFF
Override: EC      2026-09-10 ～ 2026-09-30   固定 7,900円
```

「100店舗中98店舗を選択する」操作を不要にすることが狙いである。

### 2.6 段階値下げ（Markdown Ladder）

同一範囲に対して期間の異なる Scope を並べることで表す。伝票を分けない。

```
Scope#1  全国  2026-09-10 ～ 2026-09-20  30% OFF
Scope#2  全国  2026-09-21 ～ 2026-09-30  40% OFF
Scope#3  全国  2026-10-01 ～ 2026-10-10  50% OFF
```

- 同一店舗が Scope#1〜#3 のすべてに該当する（期間が異なるので競合ではない）
- したがって 2.5 の「1店舗 → 1 Scope」は **期間が重ならない Scope の集合に対して成立する**と読む。`Jshop` は「店舗 × Scope」の行を持つ
- 期間が重なる同一範囲の Scope は競合として検出する（2.8 C2）
- `DerivedJodai` は同一店舗 × 同一商品で複数期間の行を持つことになるため、`uk1` へ `DayFrom` を追加する（3.7）

画面上は Scope の一覧を「範囲 × 段」の表として編集する（5.3）。

### 2.7 価格方式と丸め

Scope ごとに指定する。先行文書が挙げた6方式を実装する。

| PriceMethod | 内容 | 使用列 | 計算 |
|---|---|---|---|
| 0 固定額 | 例 7,900円 | `FixedPrice` | `FixedPrice` |
| 1 値下率 | 例 30% OFF | `RateOff` | `基準上代 × (1 - RateOff/100)` |
| 2 値引額 | 例 −2,000円 | `Amount` | `基準上代 - Amount` |
| 3 掛率 | 例 70.00% | `RateOn` | `基準上代 × RateOn/100` |
| 4 実効上代からの値下率 | 発効日時点の実効上代を基準にした率 | `RateOff` | `実効上代 × (1 - RateOff/100)` |
| 5 価格ポイント | 算出後に価格ポイント表へ寄せる | `Id_PricePoint` | 下記 |

- 既存の `CalcType`（0:金額 / 1:率）は `PriceMethod` 0 / 1 と互換。移行は 3.10 のとおり
- **方式 4 の基準は「伝票作成時点で解決した実効上代」を Snapshot する**（0.1 と同じ扱い）。発効時の再計算はしない
- 丸めは全方式共通で、算出後に `RoundUnit`（1/10/100/1000円）× `RoundType`（切捨/四捨五入/切上）を適用する（現行と同じ）
- 価格ポイント（方式5）は丸めの代わりに価格ポイント表の最近値へ寄せる。例: 算出値 7,680円 → 7,900円。表は `MasterMeisho` の新区分（`Kubun='PPT'`）に「コード=表名、名称=価格の並び」として持つ。末尾90円・末尾900円のような規則も、価格の並びとして表現する

計算ロジックは `CvBase` の純粋クラス `JodaiPriceRule` へ切り出し、クライアント・サーバ・テストから同一コードを使う（第6章）。

### 2.8 競合検出

確定前に検出し、**一覧で提示してから利用者に判断させる**。検出しても確定を機械的に禁止はしない（除外の運用があるため）。ただし「伝票内の同一店舗 × 同一商品 × 期間重複」だけは展開が失敗するため確定を禁止する。

| # | 種別 | 判定 | 扱い |
|---|---|---|---|
| C1 | 伝票内・スコープ重複 | 同一店舗が期間の重なる複数 Scope に該当 | **エラー（確定不可）** |
| C2 | 伝票内・段階期間の重複 | 同一範囲の Scope 同士で期間が重なる | **エラー（確定不可）** |
| C3 | 伝票内・商品重複 | `Jmeisai` に同一 Scope × 同一商品が複数 | 自動解消（`Normalize`。件数を通知） |
| C4 | 他伝票との競合 | 確定済み `DerivedJodai` に 同一商品 × 同一店舗 × 期間重複 | 警告（一覧提示。既定は続行可） |
| C5 | 個別店舗とグループの衝突 | C1 のうち `RangeType` が異なるもの | 情報（採用された Scope を明示） |
| C6 | 恒久上代変更との基準不整合 | 期間内に `Kubun=Proper` の伝票が別途有効 | 警告 |
| C7 | 原価割れ | `JodaiNew < MasterShohin.TankaGenka` | 警告（件数と明細） |
| C8 | 最低販売価格違反 | `JodaiNew < MasterConfig.JodaiMinPrice`（0 なら判定しない） | 警告 |

C4 は「JK-001 / 銀座店 / 2026-09-15 に SALE-A=7,900円 と SALE-B=6,900円 が同時に有効」という状況を指す。単純に Priority で一方を採用して黙るのではなく、登録時に利用者へ提示する。

C4 の判定 SQL（自伝票を除く）:

```sql
SELECT dj.Id_Shohin, dj.Id_Tenpo, dj.DayFrom, dj.DayTo, dj.Jodai, dj.Id_Tran
  FROM DerivedJodai dj
 WHERE dj.Id_Tran <> @self
   AND dj.TaishoType = @taisho
   AND dj.Id_Shohin IN (対象商品)
   AND dj.Id_Tenpo IN (対象店舗, 0)
   AND dj.DayFrom <= @dayTo AND dj.DayTo >= @dayFrom
```

### 2.9 プレビュー（シミュレーション）

大量価格変更は誤設定の影響が大きいため、確定前プレビューを必須とする。

| 項目 | 算出 |
|---|---|
| 対象 Style 数 | `Jmeisai` の商品 Id の異なり数 |
| 対象 SKU 数 | 対象商品の `DerivedShohinColSiz` 件数 |
| 対象店舗数 | `Jshop` の店舗 Id の異なり数 |
| 適用期間 | Scope の最小 `DayFrom` ～ 最大 `DayTo` |
| 現在平均上代 | `avg(JodaiOld)` |
| 変更後平均上代 | `avg(JodaiNew)` |
| 平均値下率 | `1 - sum(JodaiNew)/sum(JodaiOld)` |
| 展開見込行数 | `Jshop` 件数 × Scope 内商品件数の合計 |

| 最低販売価格違反件数 | C8 |

展開見込行数が `MasterConfig.JodaiExpandWarnRows`（既定 200,000）を超える場合は確定前に警告する。

### 2.10 承認と配信

承認は**任意の運用記録**とし、展開のゲートにはしない。`Status` の遷移は現行のまま変えない。

- `TranJodai` に `ApproveDay` / `Id_ApproveShain` / `VApproveShain` を追加する
- 確定操作時、`MasterConfig.JodaiNeedApprove` が `1` のときだけ承認者の入力を求める。既定は `0`（不要）
- 配信は 0.2 のとおり導入しない。`SendFlg` は現行の値札差し替え運用フラグのまま

### 3.10 後方互換

`No_Scope=0` を「暗黙の単一 Scope」とみなすことで、既存伝票をそのまま扱う。

- 読み込み時、`Jscope` が空で `Jshop` / `Jmeisai` がある伝票は、`Jscope` に `No=1` の全店 Scope を1つ補い、`No_Scope` を 1 に振り直して画面へ載せる（**メモリ上の正規化のみ。保存するまで DB は変えない**）
- 展開 SQL は `No_Scope` が両側とも `0` の場合も結合が成立するよう `ifnull` で補正する（第4章）
- `CalcType`=0 → `PriceMethod`=0、`CalcType`=1 → `PriceMethod`=1 として補完する

`DefineDataTable.cs` の `TableTypes` は変更不要（`TranJodaiScope` は `[SubTableDefine]` のため物理テーブルを作らない）。

### 3.11 JSON 規模の上限

`Jmeisai` の要素数は「商品数 × Scope 数」になる。現行の抽出上限（既定 1000 件・最大 20000 件）のまま Scope を 10 本立てると 20 万要素となり、JSON 列が数十 MB に達する。1伝票の読み書きがそのまま重くなるため上限を設ける。

- `Jmeisai` の総セル数の上限を `MasterConfig.JodaiMaxCells`（既定 30,000）とする
- 抽出時（対象取得）と Scope 追加時に「商品数 × Scope 数」を判定し、超える場合は**実行前に警告して中止**する。伝票を分けるよう案内する
- 商品数の上限（現行 1000／最大 20000）は残す。両者の小さい方が効く
- `Jshop` は「店舗数 × Scope 数」で、100店舗 × 10 Scope = 1,000 要素にとどまるため上限を設けない
- 一覧 SQL では現行どおり `Jcond` / `Jshop` / `Jmeisai` / `Jscope` を SELECT 句に含めない。件数は `ShopCnt` / `MeisaiCnt` / `ScopeCnt` / `ExpandCnt` を使う

## 4. 展開 SQL

`DerivedJodai.CreateSql` を Scope 結合に変更する。**出力列は現行と同一**。

```sql
Insert into DerivedJodai
  (Vdc,Vdu,TaishoType,Id_Tenpo,Id_Shohin,DayFrom,DayTo,Kubun,Jodai,RateOff,Id_Tran,No,Priority)
SELECT
  T.Vdc, T.Vdu,
  T.TaishoType,
  ifnull(json_extract(S.value, '$.Id_Tenpo'), 0),
  ifnull(json_extract(M.value, '$.Id_Shohin'), 0),
  ifnull(nullif(json_extract(S.value, '$.DayFrom'), ''), T.DayFrom),
  ifnull(nullif(json_extract(S.value, '$.DayTo'),   ''), T.DayTo),
  T.Kubun,
  ifnull(json_extract(M.value, '$.JodaiNew'), 0),
  ifnull(json_extract(M.value, '$.RateOff'), 0),
  T.Id,
  ifnull(json_extract(M.value, '$.No'), 0),
  T.Id
FROM TranJodai T, json_each(T.Jshop) S, json_each(T.Jmeisai) M
WHERE T.Status = 1
  AND json_valid(T.Jshop) AND json_valid(T.Jmeisai)
  AND ifnull(json_extract(S.value, '$.No_Scope'), 0)
    = ifnull(json_extract(M.value, '$.No_Scope'), 0)
```

- 追加したのは末尾の `No_Scope` 等値結合のみ
- 既存伝票（`No_Scope` 欠落）は両辺 `0` となり、現行と同じ直積が得られる
- `Jscope` は展開に使わない。Scope の解決は確定時に画面側で `Jshop` へ焼き込まれている（2.5）ため、SQL 側は結合キーだけを見る

## 付録A. 先行検討文書からの引き継ぎ

先行文書「CV10 上代一括変更・店別／期間別セール上代管理 設計案」（2026-09-05）は本書へ統合して削除する。本書の各章で扱わなかった記述のうち、記録として残すものを以下に転記する。

### A.1 基本モデル

```
Product × Location Scope × Effective Period × Price Rule = Effective Selling Price
```

一般的な小売価格管理では、商品ごとの価格を店舗単位で直接大量登録するのではなく、Price Zone / Price Group / Location Group 等の単位を介して、商品・対象ロケーション・有効期間・価格を管理する方式が多い。cv10 もこの考え方に沿う。

### A.2 想定していた操作フロー

```
1. 商品選択 → 2. 店舗／店舗グループ選択 → 3. 期間・価格ルール設定 → 4. 例外設定
→ 5. Price Matrix / Timeline確認 → 6. シミュレーション → 7. Conflict Check
→ 8. 承認 → 9. 事前配信 → 10. Effective Dateから自動適用
```

本設計では 9（事前配信）を 0.2 のとおり対象外とし、8（承認）を 2.10 のとおり任意の運用記録とする。残りは 2.3 のデータフローに対応する。

### A.3 店舗価格グループの例

| グループ | 内容 |
|---|---|
| ALL | 全店舗 |
| KANTO | 関東店舗 |
| KANSAI | 関西店舗 |
| URBAN | 都市型店舗 |
| SUBURBAN | 郊外店舗 |
| OUTLET | Outlet店舗 |
| EC | ECチャネル |
| FLAGSHIP | 旗艦店 |

cv10 では 2.4 のとおり `MasterTokui` の専用列 3 軸（価格グループ / 地域 / チャネル）として持ち、値は `MasterMeisho` の `C30`〜`C32` 区分に登録する。店舗は 3 軸まで同時に所属できる。

### A.4 画面名称について

先行文書は画面名称を「上代一括変更」より「価格変更計画」または「Price Event」とすることを推奨していた。本設計では**既存の名称「上代一括変更」を維持する**。cv10 のメニュー体系・利用者の呼称・旧 cvnet からの連続性を優先する。

### A.5 7者会議の最終見解（記録）

- cvnet-developer: 旧 cvnet の操作方式は要確認。ただし旧方式を理由に直接上代書換を継承しない。
- CV10-Architect: Product × Location Scope × Effective Period × Price Rule の Price Event 方式を推奨。
- CV10-Developer: WPF では条件 Panel + DataGrid + Timeline + Preview で実装可能。大量 SKU × 店舗の全面展開は避ける。
- CV10-Reviewer: 最大リスクは期間重複、店舗 Group 重複、誤った大量変更、配信漏れ。Preview と Conflict Check を必須とする。
- CV10-User-Sales: 「この商品を全国30%OFF、Outlet だけ40%、EC だけ固定価格」という業務思考をそのまま入力できる I/F が望ましい。
- CV10-User-System: 承認済み将来価格を発効日前に配信し、オフラインでも確実に切替可能にする。
- CV10-AICreator: 初期は AI 不要。将来は自然言語から Draft を生成する用途に限定して導入価値が高い。

Decision Confidence: 96 / 100

### A.6 将来構想（Phase 3・本設計の対象外）

自然言語から Price Event の Draft を生成する用途。例:

```
「2026AWで残在庫率40%以上の商品を、関東店だけ来週から30%OFFにして」
```

役割は Draft 生成までとし、`自然言語 → 条件解釈 → Draft → Preview → 人間承認 → 確定` の流れを維持する。AI が価格を直接確定・配信する設計にはしない。
