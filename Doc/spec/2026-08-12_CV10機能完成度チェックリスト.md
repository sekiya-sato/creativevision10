## 1. 判定基準と判定方法

`2026-08暫定スケジュールと課題.md` の L0〜L5 をそのまま用いる。

| Level | 定義 | 本調査での判定根拠 |
|---|---|---|
| L0 | 未実装 | ViewModel が `BaseViewModel` を継承した空クラス、かつ View が `<Grid />` のみ（XAML 17行） |
| L1 | 画面表示可能 | View に UI があるが ViewModel にデータ取得が無い |
| L2 | CRUD可能 | 伝票/マスタの登録・修正・削除が成立する。ただし後続の在庫・掛へ波及しない |
| L3 | 業務ロジック接続済み | 集計SQL・帳票・照会が業務的に意味のある値を返す |
| L4 | 在庫・掛・集計まで整合 | 登録/修正/削除が `SummaryRealStock` / `SummaryStock` / `Summary*Kake` に反映される |
| L5 | E2Eテスト済み | 自動テストで業務シナリオが検証されている |

判定に使った実装上の事実:

- 在庫反映は汎用CRUDハンドラ側で自動実行される。`CvServer/Services/HandlerClass.cs` の
  Insert / BulkInsert / Update / Delete / DeleteById が、対象型が `ITranSoko` を実装していれば
  `SummaryDb.CalcTran2SummaryStock()` を呼ぶ。更新時は「旧値を反転して打ち消す→新値を加算」の2回呼び。
- `ITranSoko` を実装しているのは `Tran00Uriage` / `Tran01Tenuri` / `Tran03Shiire` /
  `Tran05Ido` / `Tran10IdoOut` / `Tran11IdoIn` の6テーブルのみ（`CvBase/BaseDb2Trans.cs`）。
- 取引区分ごとの在庫増減方向は `TranCalcBase.GetCalcSoko()` / `GetCalcIdosaki()` に集約済み
  （在庫・入庫・出庫・移動中の4フラグ）。
- 当初調査では「L4 かどうか」を **ViewModel が上記6テーブルのどれを保存するか** で判定した。
  `5399328` で、`CalcTran2SummaryStock()` は `idSoko == "Id_Ido"` の場合に
  `GetCalcIdosaki()` を使用するよう修正された。本P0ではさらに、`SummaryStock` の更新判定を4フラグ全体へ広げ、
  `TransitQty` だけを更新する積送出庫の移動先も反映した。Rebuildは対象範囲の削除・6伝票再生成・
  `SummaryRealStock` 再構築を単一トランザクションにし、再実行、消滅キー、前月値復帰をテスト済み。
  ただし元の L4 定義は「在庫・掛・集計まで整合」であり、掛を即時反映しない売上・仕入も含め、
  以下の L4=8 は**分類基準の確定前の暫定値**とする。

薄い ViewModel = 未実装ではない点に注意。`IdoInputSokuViewModel` は11行だが基底
`BaseIdoInputViewModel<T>`（503行）が実装本体であり、View は599行ある。逆に
`DeliveryScheduleInquiryViewModel` は39行あるがすべてコメントで、実体は空クラスである。
