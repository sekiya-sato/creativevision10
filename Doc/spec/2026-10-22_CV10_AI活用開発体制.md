# Creative Vision 10 AI活用開発体制

- 作成日：2026年10月22日／決定日：2026年10月23日／確認日：2026年11月15日
- 調査対象HEAD：`166cda67`（AGENTS.md の整理（検索順序・§8.1）と静的照合し§6を更新。開発体制の決定は変更しない）
- 状態：決定／開発責任者：SatoAdmiin／対象：CV10標準パッケージ開発・顧客別カスタマイズ

## 1. 結論

**人間が業務と受入れを決定し、Claude Codeが実装・検証を一貫して担い、必要な独立確認をCodex等が行う。**
標準パッケージを軸に変更を最小化し、検証・受入れできる速度で開発する。

## 2. 役割

| 担当 | 主な責任 |
|---|---|
| SatoAdmiin | 要件定義・要求分析・仕様設計を主導し、顧客合意、優先順位、残余リスク、受入れ・統合・公開を判断する（AIが調査・仕様案作成を補助） |
| Claude Code | 詳細仕様・コーディング・テスト・自己レビュー・文書作成を主導し、進行と報告窓口を兼ねる（人間が業務観点の確認を補助） |
| Codex（必要時） | 実装担当から独立して、承認仕様と実差分、関連コード、検証結果を確認する |
| 独立Tester（高リスク時） | 実装担当と別の担当・セッションで、受入条件と境界・失敗条件を検証する |

業務・品質・リリースの最終責任はSatoAdmiinが持つ。常設の管理AIや工程ごとの専任担当は置かない。

## 3. パッケージ主体の変更判断

対応方法は **標準機能 → 設定・マスタ・運用 → 既存の拡張方法 → 標準改善 → 顧客固有開発** の順に検討し、SatoAdmiinが共通性・互換性・保守負担を踏まえて選ぶ。対象顧客・版・適用条件を明確にし、顧客固有の挙動が標準や他顧客へ漏れないことを確認して、標準版更新時の回帰確認点を残す。

## 4. 進め方と記録

**差分を調査 → 人間が仕様・計画を承認 → AIが実装・検証・文書更新 → 人間が受入れ・公開判断** で進める。1変更を単独で受入れ・差戻しできる大きさにし、承認範囲内はAIが継続する。業務意味・適用範囲・互換性の変更は再判断を求める。

REBOKの要求管理を参考に、1変更につき変更票1枚相当のMarkdownまたは課題で管理する。工程別の重複文書や別のレビュー報告書は作らず、次の情報と既存仕様書への参照をまとめる。

- **識別・要求**：要求ID、対象顧客・版、比較元と対象HEAD、目的、業務例、対象外。未コミット差分はファイルと保存先等で識別する。
- **計画**：対応方法、影響範囲、不変条件、リスク区分、受入条件・期待値・検証方法。
- **結果**：対象差分、実装・独立確認の担当、受入条件ごとの検証証跡、指摘と対応、技術判定、未確認事項、必要な移行・復旧手順、人間の受入れ・残余リスク判断・許可操作。

## 5. 品質とレビュー

全変更をAIが確認する。人間の全行読解を一律には求めず、業務目的への適合と実装の正しさを分けて判断する。レビューは「必要性 → 適用範囲・互換性 → 正しさ・保護 → 検証の妥当性 → 保守・更新・復旧」の順に行う。

### 5.1 リスクと確認体制

区分の対象例はAGENTS.md §5のA〜Cと同じ。

| 区分 | 必須の確認 |
|---|---|
| A：通常 | 自己レビューと必要なbuild/test・表示確認。範囲を限定でき、期待結果と実際の結果を示せることが前提 |
| B：注意 | Aに加え、呼出元・保存経路・互換性・副作用と正常・境界・異常系。影響を限定できない、期待結果が曖昧、指摘が解消しない場合は独立確認へ回す |
| C：高リスク | 実装前の人間判断、影響分析、実装担当と独立したReviewer・Tester、必要な復旧手順、最終承認 |

区分は行数ではなく影響範囲・被害・不確実性・検証可能性・回復可能性で決め、計画時にAIが根拠を示してSatoAdmiinが確認する。理解不足・検証不能があれば確認を増やし、上位区分に該当すれば引き上げる。

### 5.2 独立確認と検証証拠

- 担当製品を入れ替えても実装と独立確認を分離する。Reviewer・Testerは原則read-only、修正は実装担当が行う。
- 実装者の説明だけで結論を出さず、承認仕様・実差分・関連コードを読み、指摘を否定できる条件や既存の防御も確認する。可能なら再現・実験で裏付ける。
- 期待値は承認された業務例・固定データ・独立集計に基づける。実装した計算をテストへ写すだけでは根拠にしない。
- 対象顧客と標準動作を検証し、共通部分の変更は影響する他顧客へ広げる。AIの一致、指摘なし、build成功だけを業務上の合格根拠にしない。
- 個別の検証手順はAGENTS.md §8と該当Skillsに従う。文書のみの変更では製品buildを必須にしない。
- コードの切戻しとデータ復旧を区別し、DB更新・外部送信がコードの切戻しだけで戻ると扱わない。

### 5.3 指摘と判定

| 指摘区分 | 扱い |
|---|---|
| 必須修正 | 要求違反、実害のある不具合、互換性・保護・上位規約の違反。修正と再確認まで合格にしない |
| 要確認 | 仕様・環境・再現等が不足。必要な情報と確認方法を示し、重大な不確実性が残る間は保留 |
| 任意改善 | 今回の完了を妨げず、必要なら別課題にする |
| 既存問題 | 今回導入・悪化させていない問題として分離。安全な適用を妨げる場合は要確認とする |

指摘は「区分・重大度／箇所／発生条件／期待結果と実際の問題／影響／根拠・未確認部分」を簡潔に示す。重複・反証済みの指摘を除き、好みの書式や依頼外のリファクタリングを必須修正にしない。指摘なしでも確認範囲と未実施事項を返す。

| 技術判定 | 条件 |
|---|---|
| 合格 | 受入条件・必須検証・必要な独立確認を満たし、必須修正と重大な要確認が残らない |
| 条件付き | 重大な問題はないが限定的な未確認事項があり、影響・代替証拠・残余リスク・後続対応を明示。合格や公開許可とは区別する |
| 保留 | 必須修正、重大な要確認、必須検証の失敗・不足、必要な独立確認の欠落がある。再判定に必要な対応を示す |

AI判断で必須の確認を省略しない。SatoAdmiinが業務受入れ・残余リスク・運用制限を別に判断し、commit・rebase・merge・push・公開は明示指示に従う。

### 5.4 修正後の再確認

修正箇所と影響する回帰確認を行い、旧判定を無条件で引き継がない。仕様・共通契約・適用範囲が変われば区分と検証範囲を見直す。同じ問題が解消しない場合は、試した内容と未解決点を人間へ戻し、無制限なAI間往復をしない。

## 6. MCP・Skillsと作業環境

調査は AGENTS.md §4.2 の順序（graphify で構造を絞る → agentsview で経緯を確認 → 実ファイルを読む）で行う。

| 手段 | 使い方 |
|---|---|
| graphify-out | 型・呼出関係・ファイルの絞込みに使い、生成元コミットとHEADを照合して実コードで裏付ける。`graphify update .`は実行しない |
| 実行履歴（agentsview） | 過去の判断・修正・手順が関係する場合だけ小さく検索する（`agentsview-finding-history` スキル）。現行の正は実コードと[設計判断記録](2026-09-28_設計判断記録.md)。繰り返す失敗はAGENTS.md §8.1へ反映済み（分析は設計判断記録 §5.12） |
| MCP | cv-sqlite（開発DB）・cv-oracle（旧CV.net）でスキーマ・データ・集計を必要最小限read-onlyで確認する。課題管理は利用可能な接続・権限の範囲で使う |
| Skills | `.agents/skills/`の該当SKILL.mdを読み、WPF・QFM・gRPC等の既存手順と検証を再利用する |

接続先・権限を確認し、機密値を記録しない。利用できない手段はコード・DDL等で補完して未確認部分を明記する。更新を伴う検証は専用DBまたは複製DBと専用サーバを使い、共有開発DBを更新しない。

## 7. 開発量の制御と改善

基本は1件ずつ完了させ、独立案件のみ最大2件程度から並列化する（別branch・worktree、1ファイル1 Writer、共通部分の統合順序を調整）。
週1回程度、受入れまでの実装・検証・手戻りと公開後の障害対応を合わせた総時間を評価し、不具合件数・重大度、誤指摘、人間の負担、復旧時間、AI費用も確認する。レビュー通過率や指摘数だけを成果にしない。
確認待ちや不具合が増えたら着手・公開量を下げて検証範囲を見直し、繰り返す問題はテスト・Skills・規約の改善へ戻す。人間の確認削減や自動承認の拡大は、品質を保てた実績に基づく別の方針変更とする。

## 8. 補足事項（要求工学の活用候補）

- ペルソナパターンで顧客要望を詳細化し、要求仕様・ユースケースを作る（必要ならIEEE標準形式）。利用ログに基づくデータ駆動型ペルソナも候補。
- ユースケースはペルソナを特定のアクターに割り当てて検証・具体化し、図はPlantUML形式で出力する。
- 内省・逆質問・認識確認・質問洗練の各パターンで、要求間の矛盾、要求と設計・実装の不一致、曖昧さ・不完全さを洗い出す。
