# DB初期化・Migration・初期データ 詳細設計（2026-09-12）

状態: **Step 1 詳細設計。実装は承認後の Step 2 以降で行う。**

## 1. 決定事項

- `SysUpdateDb` は、DB作成時点の基準版と以後のMigration履歴を管理する既存責務を維持する。
- 起動時、DDLより前に管理対象の実表が0件かを一度だけ判定し、`isNewDatabase` として保持する。データ行数では判定しない。
- `isNewDatabase=true` の場合だけ、初期・標準データの後にサンプルデータを独立メソッドで投入する。
- 初期データ、業務必須データ、サンプルデータは別責務とする。業務必須データの補完条件は各マスタの既存契約を維持する。
- 標準マスタは技術的には削除可能とし、業務に必要な行を削除しないことは運用で制限する。
- 初期化またはMigrationの異常時は、サーバログを出力して起動を停止する。要復旧用テーブル・列は追加しない。復旧はシステム管理者がDB状態とログを確認して決定する。
- 複数サーバの同時初期化は対象外とする。

## 2. 現行責務と設計方針

`SysUpdateDb` は新規DBに最新基準版を記録し、既存DBには基準版より後の `UpdateDb` を適用する。この方式自体は維持する。

`CreateTable` を先行して不足テーブルを作成する現行順序も維持する。MigrationにはDDLだけでなく旧データ変換や、移行に必要な標準データのDMLを含めてよい。ただし、Migrationの前提データと事後検証を対象版ごとに明示する。

今回分離するのは、次の5責務である。

| 区分 | 実行条件 | 内容 |
|---|---|---|
| テーブル準備 | 全DB | 事前調整と不足テーブル・索引の作成 |
| 初期データ | 新規DB | 管理者、ログイン、会社設定、税率などの起動基盤 |
| 業務必須データ | 各マスタの契約 | Role、権限、名称、設定、配送などの初期投入・不足補完 |
| サンプルデータ | 新規DBのみ | 商品、色・サイズ、得意先、仕入先、店舗などのデモ用データ |
| 版管理・Migration | 全DB | 新規DBの基準版記録、または既存DBへの未適用版適用 |

## 3. 状態判定

### 3.1 判定時点

`InitializeAsync` の開始直後、DDL/DMLの前に `ReadInitialDatabaseState` を実行する。DBエンジン内部表を除き、`SysUpdateDb` を含む管理対象の実表が0件なら `isNewDatabase=true` とする。

`GetTableCounts()` は `Sys%` を除外し行数を返すため、この判定には使用しない。既存表の全行が0件でも、または `Sys*` 表だけが存在していても、新規DBとは扱わない。

### 3.2 分岐

```text
DDL前の状態確認
├ 実表0件
│  → isNewDatabase=true
│  → テーブル準備
│  → 初期データ
│  → 業務必須データ
│  → サンプルデータ
│  → 内容検証
│  → SysUpdateDbへ現行基準版を記録
└ 実表あり
   → isNewDatabase=false
   → 履歴を確認
   → テーブル準備
   → Migration前提の業務必須データ
   → 基準版以後のMigration
   → 正常終了
```

実表あり・履歴なし、履歴と実スキーマが明らかに矛盾する場合、またはDBがプログラムより将来版の場合は、自動で基準版を記録・巻戻し・初期化しない。ログを出力して起動を停止し、管理者判断とする。

## 4. メソッド責務

| メソッド（仮称） | 責務 |
|---|---|
| `InitializeAsync` | 初期状態の取得、フェーズ順序制御、失敗伝播 |
| `ReadInitialDatabaseState` | DDL前の実表有無と履歴を読取し、`isNewDatabase` を確定 |
| `EnsureTables` | `PreAdjustTable` と `CreateTable` による現行テーブル準備 |
| `CreateInitialData` | 新規DBの管理者・ログイン・会社設定・税率を投入 |
| `EnsureBusinessDefaultData` | 各 `CreateDefaultData` を固有の補完契約で呼び出す |
| `CreateSampleData` | 新規DBフラグがtrueの場合だけサンプルを投入 |
| `WriteVersionInfoAsync` | 新規DBの基準版記録、既存DBの後続Migration適用 |

既存の `InitializeDatabase` は、上記の `CreateInitialData` と `CreateSampleData` へ分ける。サンプルが参照する管理者・標準名称は、戻り値または自然キーで引き継ぐ。固定IDや `?? 0` によって参照欠落を隠蔽しない。

## 5. 業務必須データとMigrationの関係

標準マスタの削除可能性は、全ての不足補完を廃止する理由にはならない。現在の契約は次のとおりであり、今回一律には変更しない。

| 対象 | 現行の投入条件 |
|---|---|
| `MasterShipping`、`MasterResponsibilityRole`、`MasterMeisho` | 対象表が0件の場合に一括投入 |
| `SysPermissionProfile` | 親表が0件の場合に親・明細を投入 |
| `MasterConfig` | キー単位で不足行だけを追加し、既存値を維持 |

Migrationが特定のRoleや名称を必要とする場合、そのMigrationの前提として投入または存在確認を明示する。例えば、2026-09-12の担当Role移行は `MasterResponsibilityRole` をJOINするため、必要Roleが存在しない場合の移行漏れを事後検証する。

`MasterMeisho` の標準名称とサンプル名称は分離する。新規DBは過去Migrationを流さないため、現行の標準セットには現行版で必須のIDXコードを含める。既存DB向けMigrationのINSERTは維持し、二重投入を生じさせない。

## 6. バージョン管理と異常契約

新規DBでは、テーブル・初期データ・業務必須データ・サンプルデータ・内容検証が全て正常に終わった後で、`SysUpdateDb` に現行基準版を1件記録する。過去Migration SQLは実行しない。

既存DBでは、記録された基準版より後のMigrationを昇順に適用する。Migrationで必要状態に到達できない異常は、後続Migrationとサーバ起動を停止する。

ただし現行には、`SysSequence` の事前再作成後に同列を追加するMigrationなど、存在済み列エラーの継続を前提とする経路がある。Step 2では対象旧版と実スキーマを確認し、「既に必要状態」と「復旧が必要な失敗」を版ごとに区別する。SQLエラーの一律無視・一律停止のいずれも採用しない。

既存履歴にはエラーを `Memo` に記録して版を進めたものがあり得るため、過去履歴の最大版を検証済み成功版とは再解釈しない。履歴の一括改変も今回の対象外とする。

## 7. ログと管理者復旧

異常時は、接続文字列・資格情報を除き、次をサーバログへ出力する。

- DB識別子（Provider、DB名またはパス）
- 起動時の `isNewDatabase`、初期化フェーズ、対象テーブル
- 対象Migration版とSQL内の処理位置
- 起動時の記録版、今回最後に完了した版
- 例外内容、後続処理・起動を停止したこと、管理者確認が必要なこと

永続的な要復旧記録は持たない。プロセス強制終了などの途中状態は、開始・完了ログの不一致とDB状態を管理者が確認し、修復・再実行・履歴調整の手順を決定する。アプリは履歴削除、破損DBの初期化、または自動再実行で復旧しない。

`AppGlobal.InitAsync` は初期化失敗またはキャンセル時に後続の起動処理を続行しない。

## 8. 受入条件

1. 実表がないDBでは、標準・初期・サンプルデータを一度だけ投入し、現行基準版を1件記録する。
2. 正常再起動では、サンプル・標準データ・基準版が重複せず、既存設定値を保持する。
3. 実表ありで全行0件、またはSys系表だけがあるDBでは、サンプルを投入しない。
4. 実表あり・履歴なしDB、および将来版DBは変更せず、ログを出して起動を停止する。
5. 対象旧版DBでは、Migration前提のRole・標準データ、権限変換、名称追加を含むMigrationが依存順に実行される。
6. `SysSequence` の存在済み列を含む既存Migration経路を停止させない。
7. 標準マスタの部分削除時、各マスタの既存補完契約を維持する。
8. DDL、データ投入、Migration、履歴記録の異常またはキャンセルでは、後続処理とサーバ起動を停止し、管理者が識別できるログを残す。
9. 今回独自のテーブル、列、索引、永続復旧マーカーを追加しない。
