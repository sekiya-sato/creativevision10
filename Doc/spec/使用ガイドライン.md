### 複製DBと専用サーバ

更新する試験は、共有開発DB `CvServer/server-user163.db` または本番DBへ直接実行しない。シード・再集計・migrationもDB更新に含む。

1. 複製元を利用するサーバ／クライアントを正規停止するか、SQLiteの整合したバックアップを取得する。WAL書込み中の `.db` 単独コピー、`-wal`／`-shm`の削除をしない。
2. 毎回、新しい専用フォルダへ整合したDBをコピーする。前回更新済みDBを再利用するなら、どのシード・設定・残置伝票があるか明示する。
3. 対象DBが必要なマスタと製品スキーマを持つことを確認する。古い複製は専用サーバで製品migrationを先に適用し、正規停止してからシードする。シーダー共通の `SeedSchema.ApplyMigrations` も各シーダーの呼出を確認する。すべてのツールが自動初期化するわけではない。
4. シード時は、その**複製DBを開くサーバを停止**しておく。外部サーバに接続する場合は、その接続先DBも同じ複製であることを確認する。
5. 専用URL／ポートを使う。以下の例は `http://127.0.0.1:5017`。ポート使用中なら既存プロセスを止めるのではなく試験用の空きポートを選ぶ。

次は、複製元を正規停止済みでWALの内容が反映されている場合の準備例。以後のコマンドは同じPowerShellで `$dbPath` と `$runDirectory` を使用する。

### 3.2 seikyushiharai_recalc

**用途**: 既存Summaryにある締日・月を列挙して請求／支払を再計算し、売掛／買掛を全期間で再計算する。

| mode | 処理 | DB更新 |
| --- | --- | --- |
| `plan`（省略時） | 請求／支払の締日×月の実行計画 | 業務再計算なし、起動時migrationあり |
| `run` | 計画に従ってCalcSummaryUriSei／KaiShi | あり |
| `kake-plan` | 売掛／買掛の期間を表示 | 業務再計算なし、起動時migrationあり |
| `kake-run` | CalcSummaryUriKake／KaiKake | あり |

```powershell
& 'C:\gitroot\UT\vscmd.bat' dotnet run --project Doc/spec/tools/seikyushiharai_recalc/seikyushiharai_recalc.csproj -- plan $dbPath
& 'C:\gitroot\UT\vscmd.bat' dotnet run --project Doc/spec/tools/seikyushiharai_recalc/seikyushiharai_recalc.csproj -- kake-plan $dbPath
```

計画の期間・締日・件数が意図したものだと確認できた場合だけ、同じ専用コピーに `run`／`kake-run` を指定する。

- DB省略時は共有開発DBを選ぶため、パスを必ず渡す。ツール自体はバックアップを取らない。
- **plan／kake-planもread-onlyではない**。mode分岐より前に `UpdateDb.WriteVersionInfoAsync` を呼ぶため、スキーマ・版管理・そのmigrationに含まれるデータ更新が起き得る。計画表示から専用コピーを使用する。
- 締日はShime1/2/3と自社締日のフォールバックを使う。締計算の月は既存 `SummaryUriSei`／`SummaryKaiShi` のDayTo等から求める。**Summary未生成の空状態から全過去期間を自動発見するツールではない**。
- 複数期間を連続処理するため、途中にNGがあれば先の期間は更新済みになり得る。全バッチを単一トランザクションで戻すという前提を置かない。失敗期間と反映済み範囲を記録し、元コピーからやり直すか判断する。
- 終了コードと出力の成功／失敗件数・期間を保存する。計画だけでは更新結果の正しさを証明しない。実行後の帳票・残高を独立に検算する。

### 3.3 summaryreconcile

**用途**: 固定の202607データを投入して締計算・掛計算・在庫再集計を検算する開発ハーネス。

| command | 処理 | 副作用 |
| --- | --- | --- |
| `seed`（省略時） | Clean→投入→4計算→表示 | 伝票削除・投入、Summary再計算 |
| `show` | 現在の対象Summary表示 | 業務表示のみ、起動時migrationあり |
| `idempotent` | 計算を再実行しスナップショットを比較 | 再計算 |
| `closingcheck` | 締日不一致の警告判定 | 取引先締日を一時変更しfinallyで99へ設定 |
| `paysakicheck` | 親子の請求先／支払先締日検査 | テストデータ・設定変更を伴う |
| `stockrebuild` | Clean→投入→在庫全件再集計→照合 | 伝票・Summaryの削除／投入／再集計 |
| `all` | seed→show→idempotent→closingcheck→paysakicheck→stockrebuild | 上記すべて |

```powershell
& 'C:\gitroot\UT\vscmd.bat' dotnet run --project Doc/spec/tools/summaryreconcile/summaryreconcile.csproj -- all $dbPath
```

**この例は専用コピーだけに実行する。** 次の削除範囲と残置を理解したうえで使う。

- **showもread-onlyではない**。command分岐より前に `UpdateDb.WriteVersionInfoAsync` が走るため、旧コピーではmigrationによるDB更新があり得る。

- `Clean()` は202607の `SummaryUriKake`／`SummaryKaiKake`、20260731の `SummaryUriSei`／`SummaryKaiShi` を **取引先で絞らず削除**する。テスト伝票と対象SKUのSummaryStock／SummaryRealStockも削除する。
- `stockrebuild`／`all`の最後は、この削除後に在庫を再計算するが、削除した請求／支払／掛Summaryを最後に再作成しない。専用DBにも削除状態が残る。
- テスト期間202607、得意先・仕入先・倉庫・KIN区分等の固定実データに依存する。「元々取引ゼロ」という当時の前提は現在の共有DBで保証されない。
- `closingcheck`の復元は保存していた元値への復元ではなく **99へ設定**する。例外時finallyもプロセス強制終了まで保証しない。設定が完全復旧するという前提で共有DBを使わない。
- **プロセス終了0だけでは合格としない**。各単独チェックのbool戻り値は終了コードに反映されず、未知commandも表示だけで正常終了し得る。`all`は最後の `ALL: idempotent=PASS closingcheck=PASS paysakicheck=PASS stockrebuild=PASS` と途中のFAIL／例外を確認する。
- 成功後もDBを共有側へ戻さない。再試験は初期バックアップから新しいコピーで始める。

## 4. Doc/test/UatVmの使用方法

### 4.1 標準の実行順

1. 2章で複製DBと出力フォルダを準備する。
2. 対象シナリオとシーダーの固定年月・対象コード・生成／削除範囲・期待値をソースで確認する。
3. `change4uat_run.ps1` で認証を解除し、サーバとUatVmをbuildする。UatVmのbuildだけではCvServerの実行dllを準備したことにならない。
4. 対象コピーを開くサーバが停止している状態で、`--sqlite`・`--url`・`--manage-server`を付けてシナリオを1本実行する。
5. 終了コード、VERDICT、JSONL、画像／帳票、DB残置を確認する。続く試験で前提を汚さないよう、必要なら初期コピーから再準備する。
6. 専用サーバを正規停止し、`change4uat_run.ps1 enable_auth` で認証を復元してCvServerを再ビルドする。試験失敗時も復元する。

```powershell
try {
    & ./Doc/spec/tools/change4uat_run.ps1
    & 'C:\gitroot\UT\vscmd.bat' dotnet build CvServer/CvServer.csproj
    if ($LASTEXITCODE -ne 0) { throw 'CvServerのbuildに失敗しました。' }
    & 'C:\gitroot\UT\vscmd.bat' dotnet build Doc/test/UatVm/UatVm.csproj
    if ($LASTEXITCODE -ne 0) { throw 'UatVmのbuildに失敗しました。' }
    & ./Doc/test/UatVm/bin/Debug/net10.0-windows10.0.19041/UatVm.exe haibunflow --sqlite $dbPath --url http://127.0.0.1:5017 --manage-server
    if ($LASTEXITCODE -ne 0) { throw 'UATに失敗しました。証跡を確認してください。' }
}
finally {
    & ./Doc/spec/tools/change4uat_run.ps1 enable_auth
    & 'C:\gitroot\UT\vscmd.bat' dotnet build CvServer/CvServer.csproj
    if ($LASTEXITCODE -ne 0) { throw '認証復元後のCvServerのbuildに失敗しました。' }
}
```

この例の `haibunflow` は配分の通し試験で、シード・在庫・引当・伝票生成を伴う。画面表示が必要な試験では `--hide-views`を付けない。`billing` は画面表示時の初期化で締日一覧を取得するため、`--no-execute` の場合も `--hide-views` を付けない（非表示では初期化待ちがタイムアウトする）。

### 4.2 引数と既定値

| 引数 | 意味・適用範囲 | 注意点 |
| --- | --- | --- |
| 最初の位置引数scenario | 下表のシナリオ名 | 省略／未登録名は使い方を表示し終了2。名前は大文字小文字を区別しない。 |

`--sqlite`の指定、`--no-seed`、`--no-execute`だけで既存サーバが安全になるわけではない。外部サーバを利用するなら、専用DB・専用URLで起動済みと確認し、シードは事前にそのサーバを停止して行う。

### 4.4 結果と証跡

- UatVmの終了 **0** はハーネスの失敗件数0、**1** はFAIL、**2** はシナリオ引数誤り。build／起動例外・接続失敗は業務FAILと区別して記録する。
- consoleの `VERDICT: PASS` とJSONLの `fail`／`result` を照合する。期待したシナリオ・check件数・接続先・DBを確認し、スキップ／未実施をPASSに含めない。
- 既定の証跡は `Doc/test/UatVm/out/<scenario>-<yyyyMMdd-HHmmss>.jsonl`。Programには一般の出力先変更CLI引数がなく、`--sqlite`のフォルダへ自動移動しない。
- `Doc/test/UatVm/out/boot.log` は起動経路の追記ログ。シナリオ終了後、該当時刻のJSONL・bootログ・画像・PDFを専用runDirectoryへコピーして、対応するREADMEに条件と所見を残す。
- 既定JSONL名は秒単位。同時・同秒再実行で上書きし得るため一般シナリオを並列実行しない。manuallockraceのみラベル・ミリ秒・PIDを付加する。
- rfmは `rfm-screens-<日時>`、pointsummaryは `point-summary-screens-<日時>` に画像を保存する。標準・最小サイズ、見切れ・重なり・スクロール最終列・フォーム下端を目視する。
- pointsummaryは再計算画面の描画試験で、ポイントDB再計算の受入を代替しない。rfmは既存2021年データを条件指定し独立SQLと比較するため、データ不足のDBで過去の件数を期待しない。

### 4.5 排他の競合・再起動と停止補助

| 補助スクリプト | パラメータ・用途 | 現行の制約 |
| --- | --- | --- |
| `Run-ManualLockRace.ps1` | Url=127.0.0.1:5002、LeadSeconds=40、ManageServer=true、SleepBeginMs=60000。2プロセスを同時発火 | **SQLiteパスの引数なし**。専用接続文字列を環境で指定し管理起動、またはManageServer=falseで専用サーバへ接続する。 |
| `Run-ManualLockRestart.ps1` | Url=127.0.0.1:5002、HideViews=true。restart1→restart2でサーバを2回起動 | **SQLiteパスの引数なし**。restart1/2も固定DB直接書込み。通常checkoutでは実行せず、リポジトリごと隔離した試験環境でのみ使う。 |
| `Stop-CvServer.ps1` | ProcessId、TimeoutSeconds=30。Ctrl+C相当の正規停止 | PID省略時はCvServerらしいプロセスの先頭を選ぶ。**必ず専用PIDを渡す**。共有サーバを停止しない。 |

これらを引数なしで実行しない。通常は `--sqlite` を使えるUatVmを優先し、競合は接続先・設定を確認して専用環境で実行する。`manuallock`／`manuallock2`／再起動は上記の固定DB問題があるためリポジトリごと隔離した環境を必要とする。

競合試験では、CvServerは1本、UatVmをA/Bの2プロセスとして同じURL・同じ発火時刻へ送る。A/B単体では勝ち・負けのどちらもPASSになり得るため、**2本を合わせて勝者1・敗者1、排他行と結果の整合**を確認する。`CV10_LOCK_SLEEP_BEGIN_MS` 等の試験スイッチは専用サーバだけに設定し、試験終了後は解除する。

再起動観測の前提は、専用DBのマニュアル排他監視ジョブを有効にしcronを `*/1 * * * *` に設定してサーバへ反映すること。試験の前後で設定を保存／復元する。restart1が作った排他行と監視の「前回状態」を観測し、正規停止後にrestart2を実行する。監視できない・スキップの場合は再起動ケースPASSとしない。

専用PIDが確認できた場合の停止形は次のとおり。`12345` は実際に記録した専用サーバPIDへ置き換える。

```powershell
& ./Doc/test/UatVm/Stop-CvServer.ps1 -ProcessId 12345 -TimeoutSeconds 30
```

強制終了やWAL削除で試験DBを片付けない。通常のmanage-serverはハーネスの正規終了へ任せ、停止に失敗したら専用PID・接続・DB状態を調べる。

& 'C:\gitroot\UT\vscmd.bat' dotnet run --project Doc/test/UAT01/UAT01Runner.csproj -- $dbPath

Get-Content -LiteralPath './Doc/test/UAT01/Verify-UAT01.sql' -Raw -Encoding utf8 | & sqlite3 -readonly $dbPath

## 7. 試験を追加するとき

1. `UatVm/Scenarios` に `public static Task RunAsync(VmSession session)` を持つシナリオを追加し、Programのscenarios辞書へ名前と実行メソッドを登録する。
2. データ投入が必要ならUatVmSeed等へシーダーを用意し、シナリオのSeederとProgramのseeders辞書へ登録する。引数のdbPathを使い共有DBパスを埋め込まない。製品migrationを投入・再集計より先に適用する。
3. 既存の実View・ViewModelと `session.OpenView`／Input／RunAsync／Check系を使う。計算結果は独立SQL・手計算・集計元と比較し、同じ実装を呼ぶだけの期待値にしない。
4. 通常・境界・エラーに加え、更新処理は再実行・競合・途中失敗・rollbackを確認する。在庫は倉庫×商品×色×サイズの同じキーで逐次更新と再集計を照合する。
5. 本書のシナリオ表・引数・副作用を更新する。登録追加だけのためにVmHost／VmSession／ViewDriverを一律変更しない。

## 8. 記録・終了・再現性

- 専用runDirectoryに、確認日・対象HEAD・用途・対象外・実行コマンド・終了コード・DBコピー元／パス・対象年月／コード・seed有無・件数／期待値・復旧方針をREADME等で記録する。
- PASS／FAIL／SKIP／未実施を分け、JSONL・画像・PDFへの対応を残す。古い報告の件数を新DBの期待値にしない。
- ファイル生成・送受信試験では送信／受信／出力先も専用フォルダにする。外部先や共有運用フォルダにテストファイルを配置しない。
- 試験後は専用サーバを正規停止し、`change4uat_run.ps1 enable_auth` とCvServerの再ビルドで認証を復元する。接続文字列・試験スイッチ・監視cron等の変更も元へ戻す。検証したDBを共有開発DBへ上書きしない。
- 証跡に秘密情報・資格情報・無関係な個人データを含めない。既存の結果・DB・outを一括削除しない。保存・削除の判断は人間が行う。
- `Doc/aicoding_log.md` は作成・追記しない。試験結果は該当する専用証跡フォルダへ記録する。
