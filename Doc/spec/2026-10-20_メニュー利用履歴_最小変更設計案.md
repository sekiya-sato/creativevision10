## 3. 記録する内容

### 3.1 記録の種類

| Kind | 名称 | 記録する時点 | 記録者 | 条件(Condition)に入るもの |
|---|---|---|---|---|
| 1 | 画面起動 | `DoMenu` でViewを開く直前 | クライアント→サーバ | 起動パラメータ（`InitParam`・`AddInfo`、汎用テーブルメンテはテーブル名） |
| 2 | 画面終了 | 起動した画面の `Closed` | クライアント→サーバ | 空（利用時間は起動行との差で求める） |
| 3 | 照会 | `Msg101_Op_Query` 受信後 | サーバ | `Where`・`Order`・`Parameters`・`ItemType`・`MaxCount` |
| 4 | 更新 | `Msg201_Op_Execute` 受信後 | サーバ | **対象型・件数・Idのみ**（レコード本体は残さない。H3） |
| 5 | 処理実行 | `QueryMsgStreamAsync`（集計・原価更新・DB変換など）終了後、および `QueryMsgAsync` の Msg101/201 以外（原価プレビュー・AI照会・POS等） | サーバ | パラメータJSON（対象月・倉庫・実行ID等） |
| 6 | 印刷 | `PrintPdfAsync` 終了後 | サーバ | 帳票パラメータJSON |

- Kind 3〜6 は**どの画面から呼ばれたか**（画面セッション）を持つので、「この人がこのメニューを開き、この条件で3回検索し、1回印刷した」を1つの流れとして追える。
- 失敗した要求も記録する（`ResultCode` に負値）。エラーで止まった操作の分析に使う。

### 3.2 記録しないもの

- 接続確認・バージョン取得など業務と無関係な要求（`Msg001`〜`Msg004`、天気、郵便番号）。
- ログイン要求（パスワードを含むため。ログインは既存 `SysHistJwt` に残る）。
- 本履歴テーブル自身への書込み（再帰防止）。
- 記録レベルで除外したもの（6.3節）。

## 4. テーブル

### 4.1 `SysHistOperation`（新規、`CvBase/BaseDb0Login.cs` に追加）

| 列 | 型 | 内容 | 値の出所 |
|---|---|---|---|
| Id | long PK AutoIncrement | | |
| Vdc / Vdu | (BaseDbClass) | | |
| OpTime | TEXT(17) | 記録時刻 `yyyyMMddHHmmssfff` | **サーバ時刻** |
| Kind | int | 3.1節の種類 | サーバ |
| Id_Login | long | `SysLogin.Id`（未ログインは0） | JWT（サーバ解決） |
| Id_Shain | long | 社員Id | JWT→SysLogin（サーバ解決） |
| ClientId | TEXT(36) | 端末インスタンスId（`X-ClientId`） | 申告 |
| ScreenSession | TEXT(36) | 画面を1回開くごとのGUID。起動〜終了と、その間の照会・実行を結ぶ | 申告 |
| FunctionId | TEXT(100) | `06Uriage.ShopUriageInput` 等 | 申告 |
| MenuPath | TEXT(200) | `■ 売上 › ▲ 店舗業務 › 店舗売上入力`（起動行のみ。旧 SUBMENU+MENUNAME 相当） | 申告 |
| Op | TEXT(60) | `Msg101_Op_Query`・`PrintPdf`・`MenuOpen` 等 | サーバ |
| DataType | TEXT(100) | `QueryListParam`・対象テーブル型名など | サーバ |
| Condition | TEXT | 条件JSON（最大 4,000 文字で切詰め、切詰め時は末尾に印） | サーバ |
| ResultCode | int | 0=成功、負=エラーコード | サーバ |
| ResultCount | int | 取得・更新件数（不明は -1） | サーバ |
| ElapsedMs | int | 処理時間 | サーバ |
| Ip | TEXT(45) | 接続元IP | サーバ（`RemoteIpAddress`） |

- 索引: `ix1 (OpTime)`、`ix2 (Id_Shain, OpTime)`、`ix3 (FunctionId, OpTime)`、`ix4 (ScreenSession)`。
- 社員名・メニュー名称は持たない（`MasterShain` と JOIN。`Sys*` の `V*` 列を増やすと `MasterCascadeDb.VRules` の伝播対象が増えるため）。旧CVの `TANTOCD` が後年空になった問題は、**サーバがJWTから社員Idを入れる**ことで起きない。
- 端末名・Windowsユーザは `Id_Login` から最新の `SysHistJwt.Jsub` を参照する（ログイン単位で同じ値のため重複保持しない）。
- `Condition` はJSON文字列。読み出し側は `json_valid(Condition)` で防御する（AGENTS 7.1）。切詰めでJSONが壊れる場合は `{"truncated":true,"head":"…"}` 形式に包んで常に有効なJSONにする。
- 0値の意味: `Kind`・`ResultCode`・`ResultCount` の既定0と初期値は同じで、protobuf/JSON往復で値が変わらない（`ResultCount` の不明は -1 を明示代入）。

### 4.2 スキーマ移行

- `DefineDataTable` に `typeof(SysHistOperation)` を登録する。起動時の `InitializeAsync` が既存DBにも表と索引4本（`SysHistOperation_nk1`〜`nk4`）を作るので、`UpdateDb` への追加は不要（新規表は既存の前例どおり `DefineDataTable` が作成。既存行なし）。
- 期間削除タスクの設定行（`MasterConfig` の自動実行管理3行）は `MasterConfig.CreateDefaultData` が既存DBにも不足分として追加する。
- PostgreSQL / MariaDB は既存の DDL 生成・方言変換に従う（新規のSQLite固有構文は使わない）。

## 5. 処理の流れ

```text
[メインメニュー]                         [サーバ]
 DoMenu
  ├ ScreenSession=新GUID を画面へ付与
  ├ Msg093_OperationLog(Kind=1) ────────▶ SysHistOperation へ1行
  └ 画面表示
     画面がアクティブになる → AppGlobal.CurrentScreen = (ScreenSession, FunctionId)
     検索ボタン → QueryMsgAsync ─(X-Cv-Screen ヘッダ)─▶ 処理 → 結果件数・時間とともに1行（Kind=3）
     印刷       → PrintPdfAsync ─(X-Cv-Screen)────────▶ 処理 → 1行（Kind=6）
  画面Closed → Msg093_OperationLog(Kind=2) ──▶ 1行
```

### 5.1 クライアント

| 変更 | 内容 |
|---|---|
| `AppGlobal` | `CurrentScreen`（ScreenSession・FunctionId）を保持し、`CreateDefaultMetadata` で `X-Cv-Screen: <ScreenSession>|<FunctionId>` を付与（ASCIIのみ）。メインメニュー表示中は `|MainMenu` |
| `MainMenuViewModel.DoMenu` | 画面生成後に ScreenSession を採番し、`Activated` で `CurrentScreen` を切替、`Closed` で終了記録と `CurrentScreen` の解除。起動記録を送る |
| 起動・終了の送信 | 既存 `QueryMsgAsync` に `CvFlag.Msg093_OperationLog`（`OperationLogParam`）を追加して送る。**送信失敗・未ログインでも画面起動は止めない**（待たずに送り、失敗はクライアントログのみ） |

- 画面内から開く子ダイアログ（条件選択Win等）は ScreenSession を持たないので、親画面の値を引き継ぐ（子の要求も親画面の操作として残る）。
- ログイン前に開いた画面（ログイン画面・接続設定）は認証が無く記録できない。ログイン操作自体は `SysHistJwt` に残る。

### 5.2 サーバ

| 変更 | 内容 |
|---|---|
| `OperationLogDb`（新、CvDomainLogic） | 記録1行の組立て（Condition の要約・切詰め・JSON化）・INSERT・期間削除。単体テスト対象 |
| `QueryMsgService.QueryMsgAsync` | ハンドラ実行の前後で時間を測り、結果コード・件数とともに記録。**記録の失敗は握りつぶして業務応答を返す**（NLogへ警告） |
| `QueryMsgStreamAsync` / `PrintPdfAsync` | 終了時（正常・例外・キャンセル）に1行記録 |
| `Msg093_OperationLog` ハンドラ | 起動・終了行を記録。利用者・時刻・IPはサーバで上書き（申告させない） |
| 汎用経路の保護 | `SysHistOperation` への汎用 Insert/Update/Delete・一括処理を拒否（`AiQueryHandler` の `SysAiQuery` 保護と同じ方式。AGENTS 7.4） |

- 記録は**業務処理のトランザクションとは別**に、業務処理の後で行う。業務が成功して記録だけ失敗しても業務結果は変えない（履歴は監査の正ではなく利用分析用。H5）。
- 記録の INSERT は `ExDatabase.ExecuteDialect` 経由の通常 INSERT のみで、DB種別分岐を書かない。

### 5.3 Condition の作り方（DataType別）

| DataType | 記録内容 |
|---|---|
| `QueryListParam` / `QueryListSimpleParam` | `{"type":"MasterShohin","where":"…","order":"…","params":[…],"max":500}` |
| `QueryListSqlParam` | SQL本文とパラメータ（汎用SQL・AI照会の実行SQL） |
| `QueryByIdParam` | 型名と Id |
| `InsertParam` / `UpdateParam` / `DeleteParam` / 一括系 | `{"type":"…","count":n,"ids":[…先頭100件]}`（本体なし） |
| AI照会 `AiQueryChatParam` | 利用者の入力文（先頭1,000文字）。LLM応答本文は残さない |
| `PrintByCsvParam`（CSV印刷） | 行数のみ（`{"csvLines":n}`。CSV本体は残さない） |
| 印刷（`PrintPdfAsync`） | `{"form":"帳票ファイル","param":…}` |
| その他（集計・原価等） | 公開プロパティの値（文字列は2,000文字・配列は100件まで、入れ子は2段まで。切詰めあり） |

## 6. 運用・設定

### 6.1 分析SQL例（旧SQLの置換え）

```sql
-- 2026年6〜12月に「AI照会」を開いた人と日時（旧CVの例と同じ観点）
select substr(h.OpTime,1,8) 日付, s.Code 社員コード, s.Name 社員名,
       h.MenuPath メニュー, h.FunctionId
  from SysHistOperation h left join MasterShain s on s.Id = h.Id_Shain
 where h.Kind = 1
   and substr(h.OpTime,1,8) between '20260601' and '20261231'
   and h.FunctionId like '23AiQuery.%'
 order by h.OpTime;

-- 1回の画面利用で何をしたか（起動〜終了、条件つき）
select h.OpTime, h.Kind, h.Op, h.DataType, h.Condition, h.ResultCount, h.ElapsedMs
  from SysHistOperation h
 where h.ScreenSession = @0
 order by h.OpTime;

-- メニュー別・月別の利用回数と利用者数
select substr(OpTime,1,6) 年月, FunctionId, count(*) 回数, count(distinct Id_Shain) 人数
  from SysHistOperation where Kind = 1
 group by substr(OpTime,1,6), FunctionId order by 1, 3 desc;
```

### 6.2 参照手段

- 当面は既存の汎用テーブルメンテ（参照）・汎用SQL・cv-sqlite 等で SQL を実行する。専用画面は作らない（H6）。

### 6.3 記録レベル（サーバ `appsettings.json` の `OperationLog`）

| 設定 | 既定 | 内容 |
|---|---|---|
| `Level` | 3 | 0=記録しない、1=画面起動・終了のみ（旧CV相当）、2=＋更新・処理実行・印刷、3=＋照会 |
| `SkipEmptyQuery` | true | `Where` も `Parameters` も空の照会（コンボ用の全件取得など）は記録しない |
| `MaxConditionLength` | 4000 | Condition の最大文字数 |

- 設定変更はサーバ再起動で反映する（既存設定と同じ）。件数が問題になれば Level を下げて即時に抑えられる。

## 7. 件数・容量の見込み

- 旧CVの最多年 約70万行/年（画面起動のみ、172端末）。CV10 で照会まで記録すると 1画面利用あたり数回〜十数回の照会が加わり、**年 300〜700万行程度**を見込む。1行 300〜600 バイトで **年 2〜4 GB**。
- `SkipEmptyQuery` でコンボ用の全件取得は除外される。それでも多い場合は Level=2 に下げる。
- 期間削除（H4）を入れない場合、DBが単調に増える。

## 8. 検証

1. `vscmd.bat dotnet build creativevision10.slnx`、`git diff --check`。
2. サーバテスト: 各Kindの記録、利用者がJWTから入ること（申告値で上書きできない）、`Msg201` で本体が残らないこと、Condition 切詰め後も `json_valid`、記録失敗時に業務応答が変わらないこと、汎用経路での更新・削除の拒否、Level 0〜3 と `SkipEmptyQuery`。
3. migration: 新規DBと開発DBの複製で起動し、テーブル・索引が作られること。PostgreSQL/MariaDB は DDL 生成の確認と実行確認を区別して報告する。
4. UatVm（開発DBの複製・専用サーバ）: メニュー起動→検索2回→印刷→終了で、同じ ScreenSession に Kind 1,3,3,6,2 が並ぶこと。子ダイアログからの照会が親画面の ScreenSession で残ること。サーバ停止中にメニューを開いても画面が開くこと。
5. 応答時間: 記録あり/なしで代表照会の応答差を測る（目安 数ms）。

## 10. 承認が必要な判断事項

| No | 論点 | 推奨 | 代替 |
|---|---|---|---|
| H1 | 条件の取り方 | **サーバ受信口で一括記録**（画面改修なし。条件はSQL条件・パラメータJSONの形） | 各画面のViewModelで条件を組み立てて送る（読みやすいが約200画面の改修） |
| H2 | 照会（Msg101）まで記録するか | **記録する**（Level=3、空条件は除外） | Level=2（更新・実行・印刷のみ。件数は大幅に減るが検索条件が残らない） |
| H3 | 更新内容（レコード本体）を残すか | **残さない**（型・件数・Idのみ。個人情報・容量のため。変更前後は各テーブルの Vdu・伝票で追う） | 本体JSONも残す（差分監査に使えるが容量と個人情報の扱いが重い） |
| H4 | 保持期間 | **13か月**。既存の自動実行に「操作履歴の期間削除」タスクを1つ追加 | 削除しない（容量増、7章）／手動SQLで削除 |
| H5 | 記録失敗時の扱い | **業務を止めない**（履歴は利用分析用で監査の正ではない） | 記録できなければ業務もエラー（確実だが記録障害で業務停止） |
| H6 | 参照手段 | **当面はSQL・汎用テーブルメンテ**、専用画面は後段 | 今回から照会画面を作る |
| H7 | 旧CV `HC$TRAN_CLICKCNT` の移行 | **移行しない**（2023年以降は担当者未設定で、FunctionIdへの対応表も無い。旧DBで参照する） | メニュー名で対応付けて取り込む |
| H8 | 照会条件に含まれる顧客名・電話番号等の検索語 | **そのまま残し**、閲覧はシステム管理者に限る運用とする | 文字列パラメータを伏せ字にする（分析できる情報が減る） |

### 13.1 設計からの差分

### 13.3 残余リスク

- 画面の切替は「アクティブになった画面」で判定する。画面がアクティブでない間に裏で動く要求（非アクティブ画面のタイマー等）は、そのとき操作中の画面に付く。
- 利用者は JWT から解決するため、UAT（認証解除）では0になる。本番相当のログイン状態での利用者記録は単体テストで確認し、実画面では未確認。
- 汎用SQL（`QueryListSqlParam`）は従来どおり任意SQLを実行できるため、その経路からの履歴改ざんは防げない（既存の全表に共通の制約）。
- 件数見込み（7章）は実測ではない。本番導入後に件数・DB容量を確認し、必要なら `Level` を下げる。
